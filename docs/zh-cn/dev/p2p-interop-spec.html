1. 关于本文档

1.1 目的与适用范围

本文档是一份规范，用于以另一种实现的形式，制作能与 ShogiBoardQ（将棋盘Q。启用了P2P对局的构建）的“P2P对局”相互对局的软件。它规定在网络上传输的字节序列、步骤、检查、时间规则，以及对局记录（凭证）的文件格式。按照本文档制作的实现之间，可以通过传递邀请字符串进行连接、对局，并留下双方都已确定的对局记录。

本文档的对象是协议版本 1（帧的 version 为 1，各值的版本为 1）。以下内容不在对象范围内，各实现可以自由决定。

  • 画面与操作、设置的保存、玩家密钥的保管方法（操作系统的密钥库、加密的文件等）
  • 负责通信的部分与负责对局和画面的部分的划分方式（ShogiBoardQ 将其分为不同的进程，并用 JSON 的 IPC 连接，但这与兼容性无关）
  • 权限的限制（沙箱）等实现内部的安全措施

1.2 用语

写法含义
必须……／……（直述句）为了兼容性和安全，一定要遵守（MUST）
不得……一定要避免（MUST NOT）
应当……如无特殊理由，就要遵从（SHOULD）
可以……由实现选择（MAY）

收到本文档中写明要“拒绝”“拒收”的输入的实现，不得把它当作正确的输入处理。如何告知（发送 REJECT、关闭流、默默丢弃）写在各节中。

1.3 整体流程

设对局者为 2 人，把发出邀请的一方称为邀请方（在协议中称为“募集方”，role = 2），把接受邀请并连接的一方称为申请方（role = 1）。

  1. 连接：双方启动 libp2p 的节点（第 4 章）。通过互联网时，还要连接用户指定的协作节点（负责中继和可达性确认的节点）。
  2. 邀请：邀请方生成邀请字符串，由用户通过其他途径（消息等）交给对方（第 5 章）。
  3. 流：申请方连接邀请字符串中的地址，打开对局流，首先发送邀请口令（INVITE_TOKEN）（第 6 章）。
  4. 开始前的协商：交换 HELLO，决定条件和先后手，双方用玩家密钥对开始协议（StartAgreement）签名（第 8 章）。
  5. 对局：每走一手，由走棋的一方提议状态（State），对方确认后予以认可。双方都用单局密钥签名（第 9 章）。
  6. 终局：对照结果（FinalResult），双方用玩家密钥签名（第 10 章）。
  7. 记录：各方把开始协议、全部着法序列、签名保存到一个文件（凭证）中。任何人都可以验证（第 13 章）。

没有对局服务器。对局的正确性不靠信任对方的应用来保证，而是由自己确认收到的值来保证。线路断开时，可以重新连接到同一局对局（第 11 章）。

1.4 无法防止的情况

本协议不能防止以下情况。兼容实现应当向用户如此说明。

  • 显示名是自报的。识别对手的依据只有玩家密钥的公钥（玩家ID）和确认码（第 3.5 节）。
  • 如果输方不对结果签名，就不会留下双方都已签名的记录。
  • 消耗时间是自报的。无法识别每手最多 10 秒的虚报，以及利用断线拖延时间（每局合计最多 10 分钟）。
  • 无法识别由引擎下的对局或串通的对局。
  • 直接连接时，对方查看通信就能得知 IP 地址（使用仅通过中继的设置可以避免。第 4.6 节）。

2. 记法与通用规则

2.1 值的写法

本文档按如下方式书写 CBOR 的值。

写法含义
uint无符号整数（0〜264−1）
bstr、bstr(32)byte string。括号中的数字是长度（字节）
tstrtext string（UTF-8）
[a, b, ...]数组。元素的个数和顺序是固定的，不得添加未写出的元素
"SBQ-..."该字符串本身的 tstr（表示值的种类的标签）
zero3232 个零字节的 bstr

布尔值用 uint 的 0／1 表示。时刻为 UNIX 秒（uint），时长为毫秒（uint）。十六进制表示使用小写字母。

2.2 确定性CBOR

用于签名、哈希、帧、邀请字符串、凭证的 CBOR，只使用 RFC 8949 的 core deterministic encoding 中的以下部分。读取方必须拒收这里没有列出的一切。

  • 可用的类型只有 4 种：无符号整数（major type 0）、byte string（2）、text string（3）、数组（4）。不使用负整数、map、标记（tag）、浮点数、简单值（true／false／null／undefined）。
  • 长度和整数用最短的形式书写（0〜23 写在首字节中，24〜255 用后续的 1 字节，256〜65535 用 2 字节，65536〜232−1 用 4 字节，更大的用 8 字节）。拒收非最短的形式。
  • 拒收不定长（additional information 31）和保留值（28〜30）。
  • text string 必须是正确的 UTF-8（拒收过长形式、代理项、超过 U+10FFFF 的值）。
  • 嵌套最多 16 层。把最上层的值算作第 1 层，数组中的值即使不是数组，也算深一层（把数组嵌套 16 重，并在最内侧放一个值，就是 17 层，予以拒收）。
  • 输入只能是一个值，后面如有多余的字节则拒收。
  • 读取长度后，先确认它能容纳在剩余的输入中，再分配空间。

遵守这些规则，一个值对应的字节序列就唯一确定。把读取完的值重新编码得到的字节序列，与原来的字节序列一致。以下，CBOR(x) 表示值 x 的这种字节序列。

2.3 哈希

哈希函数 H 为 SHA-256（输出 32 字节）。H(CBOR(x)) 表示值 x 的确定性CBOR字节序列的 SHA-256。本文档中名称带有“……Hash”的值，若无特别说明，均为 H(CBOR(值))。

2.4 签名

签名使用 Ed25519（RFC 8032），公钥 32 字节，签名 64 字节。签名的对象就是值的确定性CBOR字节序列本身（CBOR(值)），不添加前缀或上下文字符串。值开头的标签（"SBQ-START" 等）起到区分签名用途的作用。

只有同时通过以下两项检查时，验证才视为“正确”。

  1. 公钥的检查：公钥是能通过 libsodium 的 crypto_core_ed25519_is_valid_point 的点（是规范编码、在曲线上、属于素数阶子群、不是小阶点）。
  2. 签名的检查：与 libsodium 的 crypto_sign_verify_detached 结果相同（包括拒收非规范签名这一 libsodium 默认的检查）。

第 1 项检查在每次验证签名时都要进行（对 HELLO 中收到的公钥和凭证的验证同样适用）。只进行第 2 项检查的实现，会与 ShogiBoardQ 不同，接受由不属于素数阶子群的公钥所做的签名。私钥按照 RFC 8032 由 32 字节的种子（seed）导出。

2.5 字符串的限制

写作“ASCII 的 tstr”的值，必须只由 0x20〜0x7E 的字符组成。长度的上限写在各节中。拒收超过上限的值、包含范围外字符的值。

3. 网络与标识符

3.1 网络

只有选择了相同 networkName 的实现之间才能对局。网络用由名称决定的 32 字节值 networkId 来区分。

networkId = H(CBOR(["SBQ-NETWORK", 1, networkName]))     ; networkName 为 ASCII 的 tstr（1〜32 字节）
networkName用途networkId（十六进制）
sbq-local-1本地验证用。只在同一电脑、同一局域网内连接（第 4.5 节）83cc9dfdba4b78083aad3ab064df1ef5ba0e18e8c9665f56a95db403dc55b6bf
sbq-limited-1限定测试用。与互联网上的对手连接e2972f65cf26d46415718eb13b8a97e42478963e698c8e550d6ed0d197cb1d93

实现必须持有可加入的 networkName 列表，并拒绝其他名称。ShogiBoardQ 在构建后超过 180 天就不再加入 sbq-limited-1（实验版的使用期限。兼容实现不必有相同的期限）。

libp2p 层中没有设置区分网络的机制（private network 的密钥等）。网络的差异通过邀请字符串（第 5 章）和 HELLO（第 8.2 节）中的 networkId 来确认。

3.2 PeerId

libp2p 节点的密钥必须是 Ed25519。PeerId 的二进制表示，是直接放入 Ed25519 公钥的 identity multihash，共 38 字节。

peerId = 00 24 08 01 12 20 || 公钥（32 字节）

不是这种形式的 PeerId（RSA 的密钥、SHA-256 的 multihash 等），无论在邀请字符串中还是在 HELLO 中都予以拒绝。文字表示为 base58（12D3KooW…）。

PeerId 可以在每次启动节点时重新生成（ShogiBoardQ 每次连接都生成新的密钥）。但是，在一局对局期间必须一直使用同一个 PeerId。这是因为开始协议中包含 PeerId 的哈希，而且重新连接只接受来自同一 PeerId 的连接（第 11 章）。

3.3 玩家密钥与玩家ID

每个用户持有一个长期使用的 Ed25519 密钥。它称为玩家密钥，其公钥（32 字节）称为玩家ID。玩家密钥只用于对开始协议（StartAgreement）和结果（FinalResult）签名。它必须是与 PeerId 的密钥不同的密钥。

在画面上，玩家ID 以小写的 64 位十六进制数显示，每 8 位用空格分隔（例：cf3b0b03 a6e888db …）。不得让用户只凭省略后的显示来判断对方是否为同一个人。

3.4 单局密钥

每次协商都生成一个新的 Ed25519 密钥。它称为单局密钥，用于对对局中状态的认可（StateApproval）和控制消息（Control）签名。对局结束后丢弃，不保存。它必须与玩家密钥和对方的密钥都不同。

3.5 确认码

由 2 人的玩家ID 生成在双方画面上显示相同数字的确认码。用户通过电话或当面等其他途径对照数字，确认对方的玩家ID 是否属于本人。

digest = H(CBOR(["SBQ-VERIFY", 1, keyLow, keyHigh]))    ; 两个公钥按字节序列的字典序（无符号）比较，较小的在前
组 g（0〜5）= 把 digest[5g .. 5g+4] 这 5 个字节作为大端序整数读取，除以 100000 的余数写成 5 位数（补零）

确认码是 6 组这样的 5 位数（共 30 位）。

3.6 显示名

显示名是显示在对方画面上的自报名称，在 HELLO 中发送。它必须满足以下全部规则，接收方要按收到的字节序列原样判定（不得先去掉开头的 BOM 等再判定）。

  • UTF-8 编码不超过 96 字节，1〜32 个字符（码点）
  • 开头和末尾不是空格（U+0020）
  • 所有字符都在下表的范围内（包括两端）

4.2 监听

网络监听
sbq-local-1IPv4 的全部接口。TCP 和 UDP（QUIC）的 48210 号端口。被占用时使用空闲的端口。不在 IPv6 上监听
sbq-limited-1IPv4 和 IPv6 的全部接口。TCP 和 UDP（QUIC）的空闲端口

端口号会放入邀请字符串的地址中，因此即使兼容实现在其他端口监听，也能连接。48210 号是一个默认值，用于让用户可以确定在防火墙中允许哪个端口。

不得在其他进程正在监听的端口上监听。libp2p 的 TCP 监听以允许多个进程共享同一端口的设置（SO_REUSEPORT）打开，因此即使端口已被占用也能打开，到达的连接会被分配给两个进程（同一电脑上的第二个应用，或其他实现）。ShogiBoardQ 会先用不共享的监听试探 TCP 的 48210 号端口，确认未被占用后再打开。如果在确认与打开之间，同时启动的进程也做了同样的事，两者都能打开，因此先打开 UDP（QUIC。不加共享的设置），只有打开了 48210 号 UDP 的进程才在 TCP 上也使用 48210 号。

4.3 Identify

Identify 的 protocolVersion 设为 /shogiboardq/1.0.0，agentVersion 设为实现的名称和版本（ShogiBoardQ 为 shogiboardq-peer/<版本>）。不得根据对方的这些值拒绝连接（网络的差异用 networkId 确认）。

Identify 中公布的自己的地址（listenAddrs）里，不得直接放入监听地址。可以放入的只有已确认或已确定对方实际能到达的地址（在 sbq-limited-1 中，是通过可达性确认验证过的互联网上的地址和经由中继的地址。协作节点也可以放入互联网上的监听地址。第 4.4 节）。在 sbq-local-1 中不放入（Identify 也会发给没有邀请的对方，因此不向只是连接到监听端口的局域网设备公布电脑的私有地址列表。给对方的地址用邀请字符串传递）。不用 Identify 的 push 通知监听地址的变化。

4.4 协作节点与中继

通过互联网（sbq-limited-1）时，用户指定协作节点的地址（/ip4/…/tcp/…/p2p/<PeerId> 的形式。最多 16 个）。协作节点是支持 Circuit Relay v2 的 hop 以及 Identify、Ping（和 AutoNAT 的响应）的 libp2p 节点，不读取对局帧的内容。只要是标准的 Circuit Relay v2 中继节点，就可以用作协作节点。

  • 实现无论自己的可达性如何，都要向 Identify 的 protocols 中有中继 hop 的协作节点预约中继（最多 2 个）。预约被拒绝时，或与协作节点的连接断开而失去预约时，应当稍等后重新请求（ShogiBoardQ 在 30 秒后）。如果不重新请求，在重新连接之前，邀请字符串中都不会有经由中继的地址。
  • 经由中继的自己的地址为 <协作节点的地址>/p2p/<协作节点的 PeerId>/p2p-circuit 的形式，由用户指定的协作节点地址生成，并放入邀请字符串（指定了同一协作节点的对方可以直接使用）。
  • 协作节点必须在预约的响应中返回自己的地址。libp2p 的实现（ShogiBoardQ 使用的 rust-libp2p 等）会把没有地址的响应当作预约失败处理。刚启动的中继节点在可达性确认（AutoNAT）完成之前没有自己的地址，在此期间的预约可能全部失败。协作节点在互联网上的地址上开始监听后，应当不等确认就把它作为自己的地址（ShogiBoardQ 的协作节点就是这样做的）。
  • 对经由中继的地址，也对开头的 IP 地址（协作节点的地址）应用第 4.5 节的规则。
  • ShogiBoardQ 的协作节点（shogiboardq-peer --service --relay）在每条中继达到 30 分钟或 8 MiB 时将其断开。断开后，对局按重新连接的步骤（第 11 章）重新连接。

4.6 不使用直接连接的设置

这是不让对局对手看到自己 IP 地址的设置（是否实现可以自选）。实现此设置时，必须遵守以下各项。

  • 直接连接的地址，只限于用户指定的协作节点的地址（以及该节点在 Identify 中自报的其他地址）。对其他地址的直接连接，无论是从哪条途径开始的，都予以拒绝。
  • 经由中继的地址，只在中继是指定的协作节点时使用（未指定的中继能看到自己的 IP）。
  • 作为自己的地址公布的，只限于经由中继的地址（邀请、Identify）。
  • 不进行 AutoNAT 和 DCUtR。因为两者都会把自己的地址候选交给对方。

对方以此设置发出邀请时，只要正常连接邀请字符串中经由中继的地址即可，协议上没有区别。

采用此设置的一方作为申请方时，只连接邀请字符串的地址中以自己指定的协作节点为中继的地址。因此，邀请方需要向与申请方所指定的相同的协作节点预约中继，并把经由该中继的地址放入邀请字符串（双方指定相同的协作节点）。没有可用的地址时，申请方不开始连接。

5. 邀请字符串

对局的对手由邀请字符串决定。由邀请方生成，用户通过其他途径交给对方。邀请字符串中包含连接邀请方所用的地址，以及只能使用一次的口令（token）。

5.1 格式

invite = "sbqinv1." + base64url(body) + "." + hex(H(body)[0..4])
body   = CBOR(["SBQ-INVITE", 1, networkId, peerId, [addr, ...], token, expiresAt])
项目类型规则
networkIdbstr(32)第 3.1 节
peerIdbstr(38)邀请方 PeerId 的二进制表示（仅限第 3.2 节的形式）
addrbstr可达候选地址的 multiaddr 二进制表示。不加末尾的 /p2p/<邀请方>（保留经由中继的地址中的 /p2p/<协作节点>）。0〜8 个，每个 1〜100 字节
tokenbstr(32)用加密用的随机数生成器生成
expiresAtuint有效期限（UNIX 秒）。生成后 600 秒
  • base64url 使用 RFC 4648 的 URL 用字符，不加 =。
  • 末尾的检查值，是 body 的 SHA-256 的前 4 字节的小写十六进制（8 个字符）。它用于发现输错或缺漏，不是秘密。
  • 整个字符串必须不超过 1024 字节。

5.2 生成方

  • 可达候选地址中只放入对方实际可以使用的地址（第 4.5 节、第 4.6 节）。在 sbq-local-1 中，先放入同一局域网的对方使用的私有地址，最后放入只能在同一电脑上使用的 loopback。
  • 同时有效的邀请最多 4 个，生成第 5 个时使最旧的一个失效。
  • 邀请只能使用一次。接受了口令一致的流后，就把该邀请设为已使用（第 6.3 节）。
  • 不得把 token 输出到日志等中。应提示用户通过只有对方能收到的途径传递邀请字符串（因为其中包含连接地址）。

5.3 读取方

读取前，只去掉前后的空白（ASCII 的空格、制表符、CR、LF）。然后确认以下全部各项，只要有一项不符就不使用。

  1. 整体不超过 1024 字节，前缀为 sbqinv1.，其余部分用 . 恰好分成两部分。
  2. 前一部分能作为 base64url 读取，后一部分与 body 的 SHA-256 前 4 字节的小写十六进制一致。
  3. body 是确定性CBOR，是 7 个元素的数组，标签、版本、各项目的类型和长度符合第 5.1 节。
  4. networkId 与自己当前加入的网络一致。
  5. expiresAt 晚于当前时刻，并且在从现在起 660 秒（600 秒＋时钟偏差 60 秒）以内。
  6. peerId 不是自己的 PeerId。

可达候选地址必须全部能作为 multiaddr 的二进制表示读取。只要有一个无法读取（包含未知协议的编号等），就不使用整个邀请字符串。生成方只用广泛使用的协议（ip4、ip6、tcp、udp、quic-v1、p2p、p2p-circuit）书写。

在读取到的可达候选地址中，只使用在当前网络中可以连接的地址（第 4.5 节），其余丢弃。如果一个可用的地址都没有剩下，就不连接。

6. 对局流与帧

6.1 流

协商和对局的交互，在 libp2p 协议 /shogiboardq/game/1.0.0 的一条流上进行。本文档中说“连接”时，若无特别说明，指的就是这条流。流被关闭或重置称为“断线”。

流中反复传送4 字节大端序的长度和该长度的帧（确定性CBOR）。长度必须为 1〜65536（64 KiB）。接收方先确认长度，再分配空间。

6.3 打开流的步骤与 INVITE_TOKEN

INVITE_TOKEN = [1, 11, 0, zero32, [token]]   ; token 为 bstr(32)

申请方（收到邀请字符串的一方）按以下步骤进行。

  1. 连接邀请字符串中的 peerId 和地址，打开 /shogiboardq/game/1.0.0 的流（ShogiBoardQ 30 秒后放弃）。
  2. 打开后立即把 INVITE_TOKEN 作为首帧发送（requestId 为 0）。
  3. 接着发送 HELLO（第 8.2 节）。

邀请方对到达的流的首帧只等待 5 秒，并按如下方式决定。

  • 首帧是 INVITE_TOKEN，且其 token 与尚未使用且在有效期限内的邀请的 token 一致时，把该邀请设为已使用，并接受该流。核对使用处理时间与内容无关的比较方式，与所有邀请进行。
  • 其他情况（未在时限内到达、不是 INVITE_TOKEN、token 不一致）下，不返回任何内容就关闭流。

INVITE_TOKEN 的 requestId 必须为 0，gameId 必须为 zero32。不得在流的开头以外发送 INVITE_TOKEN（收到时作为外层违规关闭流）。对局中接受的流写在第 11.1 节中。

7.3 着法与局面的写法

为了即使实现不同也能得到相同的字节序列，着法和局面的字符串只使用以下形式。收到的字符串不是这种形式时予以拒收。

  • 着法（moveUsi）：USI 的形式。棋盘上的着法为 <起点><终点>（例 7g7f），升变时在末尾加 +（例 8h2b+）。打入为 <棋子>*<终点>，棋子为大写的 P L N S G B R（例 P*5e）。筋为 1〜9，段为 a〜i。前后不加空格。
  • 局面（sfen）：把 <棋盘> <行棋方> <持驹> <手数> 用一个空格分隔。
    • 棋盘按照 USI 的 SFEN（从第 1 段到第 9 段，各段从 9 筋到 1 筋。空位用数字表示，成驹前置 +，先手为大写、后手为小写）。
    • 行棋方是下一步走棋的一方（先手 b、后手 w）。
    • 持驹按先手的 R B G S N L P，接着后手的 r b g s n l p 的顺序，只写持有的棋子。2 枚以上时在前面加上枚数（例 2P）。双方都没有时为 -。
    • 手数栏为 ply + 1（State0 为 1）。

blackSessionKey、whiteSessionKeybstr(32)单局密钥的公钥
blackPeerIdHash、whitePeerIdHashbstr(32)PeerId 二进制表示（第 3.2 节）的 SHA-256（不用 CBOR 包装，直接对字节序列做哈希）

4 个公钥必须全部不同，2 个 PeerIdHash 必须不同，2 个 nonce 必须不同。拒收不满足这些条件的 StartAgreement。

7.5 认可、控制、结果

StateApproval = ["SBQ-APPROVE", 1, gameId, ply, stateHash]            ; stateHash = H(CBOR(State))
Control       = ["SBQ-CONTROL", 1, gameId, connectionId, sequence, kind, bodyHash]
FinalResult   = ["SBQ-RESULT", 1, gameId, finalStateHash, transcriptHash, ply, outcome, cause]

connectionId   = H(CBOR(["SBQ-CONN", 1, gameId, blackRandom, whiteRandom]))

resultDigest   = H(CBOR(FinalResult))    ; 结果的标识符
值签名所用的密钥含义

StateApproval单局密钥承认该手数的 State 是正确的（走棋的一方作为自己的着手，对方作为收到的着手）

FinalResult 的 ply 为 0〜512，finalStateHash 是最后一个 State 的哈希。outcome 和 cause 的值及允许的组合写在第 10.1 节中。拒收组合不符的 FinalResult。

Control 的 sequence 为 1 以上，kind 为 1〜6。connectionId 是每个连接（流）各不相同的值，blackRandom、whiteRandom 是先手、后手为该连接给出的 32 字节随机数（最初的连接中为开始前 HELLO 的 connectionRandom，重新连接中为重新连接 HELLO 中的随机数）。

8. 开始前的步骤

8.1 流程

设申请方为 A，邀请方为 B。所有帧都在同一条流中传送。

A（申请方）                                   B（邀请方）
  ── INVITE_TOKEN ─────────────────────────→   核对口令（第 6.3 节）
  ── HELLO（role 1, commitA）───────────────→   检查。拒绝时发送 REJECT
  ←─────────────── HELLO（role 2, nonceB, 条件）──
  决定先后手，生成 StartAgreement
  ── START_AGREEMENT ──────────────────────→   检查（第 8.3 节）
            ［双方的用户在条件确认画面上确认对手和条件］
  用户点击“开始”
  ── START_SIGNATURE（A 的签名）───────────→   检查签名
                                                用户点击“开始”
  ←────────────── START_SIGNATURE（B 的签名）──
  检查签名
            ［双方的签名齐全＝对局开始。转到第 9.1 节］
  • A 在发送自己的 START_SIGNATURE 之前，不接受 B 的 START_SIGNATURE。
  • B 在确认 A 的 START_SIGNATURE 之前，不得发送自己的 START_SIGNATURE。如果 B 的用户先点击了“开始”，则在确认 A 的签名时发送。
  • 双方在用户点击“开始”之前，都不得用玩家密钥签名。

8.2 HELLO（开始前）

Frame   = [1, 1, requestId, zero32, payload]
payload = ["SBQ-HELLO", 1, role, networkId, [1], peerId, connectionRandom, playerKey, sessionKey,
           displayName, sidePreference, offerId, coin, conditions]
项目类型规则
roleuint1＝申请方、2＝邀请方
networkIdbstr(32)自己的网络。与对方不同则 REJECT（WRONG_NETWORK）
（支持的版本）uint 的数组支持的协议版本列表（最多 8 个）。v1 为 [1]。不包含 1 则拒收
peerIdbstr自己 PeerId 的二进制表示（1〜64 字节）。接收方确认它与流的对方的 PeerId 一致
connectionRandombstr(32)为该连接生成的随机数。用于最初的 connectionId（第 7.5 节）

displayNametstr显示名（第 3.6 节的规则。不超过 96 字节）

conditions数组申请方为空数组 []。邀请方为 [Rules, TimeControl, NetworkPolicy]（第 7.1 节）

接收方除格式外还要确认以下各项，不符时发送 REJECT（CONDITION_MISMATCH。写有其他编号的则用该编号）。

  • role 符合预期（邀请方收到的是 1，申请方收到的是 2），并且 role 与 conditions 的有无相符。
  • playerKey、sessionKey 是可以用作 Ed25519 公钥的点（第 2.4 节）。
  • playerKey、sessionKey、connectionRandom 与自己的值不同。申请方还要确认对方的 coin（nonceB）与自己的 nonceA 不同。
  • 邀请方：申请时自报的 playerKey 不是用户屏蔽的对手（对屏蔽的对手，不告知其已被屏蔽，而是返回 BUSY）。双方的 sidePreference 可以兼容（第 8.4 节）。

即使在核对口令之后，如果用户在此期间取消了邀请，邀请方也要发送 REJECT（EXPIRED）并关闭流。已经在与其他对手协商时，不返回 HELLO，而是发送 REJECT（BUSY）并关闭流（对局中不接受对局对手以外的流。第 11.1 节）。拒绝时，不返回 HELLO 而返回 REJECT，不让对方知道自己的公钥。

8.3 START_AGREEMENT

Frame   = [1, 2, requestId, zero32, payload]
payload = [StartAgreement, Rules, TimeControl, NetworkPolicy]

申请方通过邀请方的 HELLO 才首次得知条件（用时），决定先后手后生成。startBefore 设为当前时刻的 180 秒后。邀请方确认以下全部各项，不符时发送 REJECT（未写编号的为 CONDITION_MISMATCH）。

  • Rules、NetworkPolicy 为 v1 的值，TimeControl 与自己在 HELLO 中出示的相同。3 个哈希与 StartAgreement 中的值一致。
  • networkId 是自己的网络。
  • 自己的 playerKey、sessionKey、nonce（nonceB）、PeerIdHash 正确地放在同一侧（先手或后手）。对方的 playerKey、sessionKey、PeerIdHash 与对方的 HELLO 及流的对方一致，并放在相反的一侧。
  • 对于对方一侧的 nonce（nonceA），H(CBOR(["SBQ-COMMIT", 1, nonceA])) 与对方 HELLO 中的 coin（commitA）一致。
  • 先后手符合第 8.4 节的决定方法。
  • startBefore 晚于当前时刻，并且在从现在起 210 秒（180 秒＋时钟偏差 30 秒）以内。不符时 REJECT（EXPIRED）。
  • 4 个公钥、2 个 PeerIdHash、2 个 nonce 各不相同（第 7.4 节）。

8.4 先后手的决定方法

先后手根据双方的希望（sidePreference）和双方给出的随机数决定。

  1. 双方都有希望，且希望相同（都希望先手或都希望后手）时，无法兼容，因此 REJECT（CONDITION_MISMATCH）。
  2. 申请方希望先手，或邀请方希望后手时，申请方为先手。
  3. 申请方希望后手，或邀请方希望先手时，申请方为后手。
  4. 双方都“不指定”时，用随机数决定。coinHash = H(CBOR(["SBQ-COIN", 1, nonceA, nonceB])) 的最后一个字节的最低位为 0 时申请方为先手，为 1 时申请方为后手。

为了让一方不能在看到结果后再选择自己的值，随机数按以下顺序给出。申请方生成 32 字节的随机数 nonceA，在 HELLO 中只出示 commitA = H(CBOR(["SBQ-COMMIT", 1, nonceA]))。邀请方在 HELLO 中直接出示 nonceB。申请方在 START_AGREEMENT 中（自己一侧的 nonce 栏）公开 nonceA。即使先后手由希望决定，也同样执行这一步骤（nonce 还起到使对局ID 唯一的作用）。

在 ShogiBoardQ 的画面上，只有邀请方可以提出先后手的希望（申请方总是发送 0）。即使兼容实现作为申请方发送希望，也会按上述规则处理。

8.5 START_SIGNATURE

Frame   = [1, 3, requestId, gameId, payload]
payload = [side, signature]        ; side 为 1＝先手、2＝后手。signature 为 bstr(64)

signature 是用自己的玩家密钥对 CBOR(StartAgreement) 所做的签名。side 是自己一方。接收方确认 side 是对方一方、签名用 StartAgreement 中对方的 playerKey 验证正确、当前时刻早于 startBefore。不符时 REJECT（INVALID_SIGNATURE，过期为 EXPIRED）。

从确认了对方的开始签名时起，可以把对方的 playerKey 作为“已确认的身份”对待。在此之前，在画面上将其显示为对方仅自报的值。

START_SIGNATURE 只发送一次。不得重新发送。在开始前收到第二个的一方以 REJECT（INVALID_SIGNATURE）结束协商，在开始后收到的一方以错误（CONDITION_MISMATCH）终止对局。

双方的开始签名（先手的、后手的）都放入对局记录（凭证）。

8.6 期限

期限长度超过时
从开始协商到双方的开始签名齐全60 秒发送 REJECT（CANCELLED）并取消
StartAgreement 的 startBefore生成后 180 秒此后既不签名，也不接受签名（EXPIRED）
从双方的开始签名齐全，到 State0 的认可和 READY 完成30 秒不开始对局而结束（第 9.1 节）

协商从“接受了流／打开了流”时开始。开始前流断开时，取消协商（不重新连接。需要新的邀请字符串）。

8.7 REJECT

Frame   = [1, 10, requestId, zero32, payload]
payload = [errorCode]              ; errorCode 见第 12 章的表

在开始前（到双方的开始签名齐全为止），拒绝对方或取消时发送。gameId 栏设为 zero32。接收方结束协商。用户在条件确认画面上取消时发送 CANCELLED（12）。

双方的开始签名齐全后，不得发送 REJECT（对局中的错误用 CONTROL 传达）。开始后收到的 REJECT，若 gameId 是对局ID 则忽略，若为 zero32 则作为“对局ID 不同的帧”以错误（CONDITION_MISMATCH）终止（第 9 章开头）。一方取消时发出的 REJECT 与另一方的最后一个开始签名交错时，开始签名已齐全的一方会以此错误结束。无论哪一方，对局都不会开始。

9. 对局中的步骤

双方的开始签名齐全后的帧，全部在 gameId 中放入对局ID。收到对局ID 不同的帧时，以错误（CONDITION_MISMATCH）终止对局（第 9.7 节）。

9.1 开始（State0 与 READY）

先手                                          后手
  ── STATE_PROPOSE（State0, 先手的认可）────→   检查 State0 和签名
  ←────────────── STATE_ACCEPT（0, 后手的认可）──
  ←────────────── CONTROL READY（[state0Hash]）──   从这里开始观测先手第一手的时间
  从收到 READY 时起，开始第一手的计时
  • 后手确认收到的 State0 与第 7.2 节的值完全一致，并且签名用先手的单局密钥验证正确。
  • 先手确认 READY 中的 state0Hash 与自己的 State0 的哈希一致。即使收到两次 READY，也不重新初始化时钟。
  • 如果从双方的开始签名齐全起 30 秒内没有完成到这一步，则不开始对局而结束（成为没有结果的记录）。

9.2 着手的提议（STATE_PROPOSE）

Frame   = [1, 4, requestId, gameId, payload]
payload = [State, signature]       ; signature 是走棋的一方用单局密钥对 StateApproval 所做的签名（bstr(64)）

行棋方决定着法后，生成下一个 State（第 7.2 节），用单局密钥对其 StateApproval 签名后发送。

  • spentMs 是从自己的回合开始到即将生成 State 时为止的时间（按自己的时钟）。
  • 剩余时间按第 9.4 节的计算决定。
  • 在收到对方的认可（STATE_ACCEPT）之前，不得提议下一手。自己未被认可的着手，同时只能有一个。
  • 如果 5 秒后仍未收到认可，就重新发送相同字节序列（requestId 也相同）的帧。从第一次发送起 30 秒后仍未收到，就视为连接已断开，转入重新连接（第 11 章）。

接收方按以下顺序确认。

  1. State 的 gameId 是对局ID。不同则错误（CONDITION_MISMATCH）。
  2. ply 为 0 时，按第 9.1 节处理（State0 与预期的值不同或签名不正确时，错误（INVALID_SIGNATURE））。ply 为 1 以上，但 State0 的认可和 READY 尚未完成时，错误（CONDITION_MISMATCH）。
  3. ply 不大于自己所知的最新 State 时，作为重发处理。若是相同的 State，就用 STATE_ACCEPT 重新发送已保存的自己的认可（不改变棋盘、时钟）。若是同一手数的不同 State，就以错误（STATE_CONFLICT）终止。
  4. ply 是最新的下一手（＋1），是对方的回合，并且自己没有未被认可的着手。不符则错误（STATE_CONFLICT）。
  5. 签名用对方的单局密钥验证正确。不符则错误（INVALID_SIGNATURE）。
  6. previousStateHash 是最新 State 的哈希，并且着法字符串符合第 7.3 节的形式。不符则错误（INVALID_MOVE）。
  7. 申报的 spentMs 不是超时（E ≥ R + B。第 9.4 节）。超时则错误（CLOCK_MISMATCH）。
  8. 着法在最新局面中是合法着法（第 9.6 节），并且 sfen 与按第 7.3 节的形式写出的走棋后局面一致。不符则错误（INVALID_MOVE）。
  9. 剩余时间（blackMainMs、whiteMainMs）符合第 9.4 节的计算。不符则错误（CLOCK_MISMATCH）。
  10. 申报的 spentMs 与自己测得的时间相比不过短（第 9.4 节的容许误差）。不符则错误（CLOCK_MISMATCH）。

全部通过后，先保存认可再发送 STATE_ACCEPT，并反映到棋盘上。payload 格式不符的 STATE_PROPOSE，以错误（INVALID_MOVE）终止。

步骤 3 中的“重新发送认可”，在自己已经提议了下一手之后，可以不进行。流会保持顺序，因此最初发送的认可一定会送达对方（送不到是在断线时，此时由重新连接的核对来补足）。

9.3 认可（STATE_ACCEPT）

Frame   = [1, 5, requestId, gameId, payload]
payload = [ply, stateHash, signature]    ; signature 是接收方用单局密钥对 StateApproval 所做的签名

提议方确认 ply 和 stateHash 与自己未被认可的 State 一致，并且签名用对方的单局密钥验证正确。通过后，该 State 就成为双方已认可的状态，并反映到棋盘上。

  • 对已认可着手的相同认可（ply 和 stateHash 与双方已认可的 State 一致的重发）予以忽略。自己有未被认可的着手时也一样（对方可能会对提议的重发重新发送认可，而它可能在我方提议了下一手之后才到达）。
  • 其他认可（既不是对自己未被认可着手的认可，也不是对已认可着手的认可），以错误（STATE_CONFLICT）终止。
  • payload 格式不符的 STATE_ACCEPT，以错误（INVALID_SIGNATURE）终止。

双方已认可的 State 序列（从 State0 到最新）是对局的正式记录。

9.4 时间规则

用时为“基本用时（R）＋每手读秒（B）”。设回合开始时基本用时的剩余为 R，读秒为 B，这一手所用的时间为 E（均为毫秒）。

  • 可以走棋的条件：E < R + B。E ≥ R + B 即为超时，这一手不能走（与边界相同的值算作超时）。
  • 走棋后的剩余：走棋一方的基本用时为 max(R − E, 0)，对方的不变。把它写入 State 的 blackMainMs、whiteMainMs。

时间由走棋的一方用自己的时钟测量并申报。对方将其与自己时钟观测到的时间对照。

测量的内容起点
自己回合的时间（E）先手的第一手从收到 READY 时起。其他情况从确认对方的着手并发送 STATE_ACCEPT 时起
对对方回合的观测从第一次发送自己的 STATE_PROPOSE 时起。后手观测先手的第一手时，从发送 READY 时起。重新连接后重新发送自己未被认可的着手时，从重新发送时起重新测量（因为对方的回合从对方收到并认可该着手时开始。第 11.5 节）
  • 申报的检查：对于收到的着手，若 观测到的时间 − spentMs > 10,000 ＋ 该回合中断线的时间，以错误（CLOCK_MISMATCH）终止。也就是说，申报的时间可以比观测到的短 10 秒以内（通信延迟的部分）。
  • 自己超时：在自己的回合中，没有未被认可的着手，且按自己的时钟已经 E ≥ R + B 时，申报自己负（提议对方胜且原因为超时的结果。第 10.2 节）。
  • 主张对方超时：对方的着手一直未到达，且 观测到的时间（不含断线时间） > R + B + 10,000 时，可以提议因超时而自己获胜。同一手数只能提议一次。
  • 线路断开期间，行棋方的时钟也继续走。
  • 时钟用单调递增时钟测量。因睡眠或时刻变更而无法确认所测时间连续性的实现，要中断对局（ABORT，理由为 CLOCK_DISCONTINUITY）。ShogiBoardQ 在单调递增时钟与操作系统时刻的走时相差超过 15 秒时中断。

9.5 控制消息（CONTROL）

Frame   = [1, 6, requestId, gameId, payload]
payload = [Control, body, signature]
Control = ["SBQ-CONTROL", 1, gameId, connectionId, sequence, kind, bodyHash]     ; bodyHash = H(CBOR(body))

signature 是发送方用单局密钥对 CBOR(Control) 所做的签名（bstr(64)）。body 是数组，内容按 kind 决定。

kind名称body含义
1READY[state0Hash]后手告知已认可 State0、可以开始对局（第 9.1 节）
2RESUME[latestPly, latestStateHash]重新连接后，告知双方已认可的最新 State（第 11.3 节）
3RESULT_PROPOSEFinalResult 本身结果的提议或同意（第 10.2 节）
4ABORT[latestStateHash, reasonCode]单方面离开对局。结果不确定（第 10.5 节）
5ERROR[errorCode, relatedPly]经检查拒绝对方的输入，终止对局（第 9.7 节）
6RESULT_DECLINE[bodyHash]不同意 RESULT_PROPOSE（所拒绝提议的 bodyHash）

reasonCode、errorCode 是第 12 章的编号，relatedPly 是相关的手数（0〜512）。

编号（sequence）的规则：发送方按每个连接、每个方向，从 1 开始每次加 1。重新连接成为新连接时恢复为 1。接收方按以下方式处理。

  1. 确认 payload 的格式（3 个元素的数组、Control 的格式、kind 为 1〜6、sequence 为 1 以上、body 为数组、bodyHash 与 body 的哈希一致）。不符时，无论属于哪个连接，都以错误（INVALID_SIGNATURE）终止。
  2. Control 的 gameId、connectionId 不属于当前对局或当前连接时，默默丢弃。
  3. sequence 不大于已收到的编号时，作为重发默默丢弃。
  4. sequence 不是“最后收到的编号＋1”时，以错误（STATE_CONFLICT）终止。
  5. 确认签名用对方的单局密钥验证正确。不符则错误（INVALID_SIGNATURE）。通过后，把该编号作为“最后收到的编号”。

在重新连接的核对完成之前收到的 RESUME 以外的控制消息，进行上述检查并推进编号后，不处理其内容而丢弃。

每局收发的控制消息合计最多 4096 条。超过时以错误（LIMIT_EXCEEDED）终止。

9.6 着法的合法性

着法必须按本将棋的规则合法。兼容实现至少必须对以下各项做出相同的判定（判定不一致时，一方会以 INVALID_MOVE 终止对局）。

  • 棋子的走法、升变（进入敌阵、在敌阵内移动、离开敌阵的着法可以升变。仅限可以升变的棋子）
  • 禁止无路可走的棋子（第 1 段的步和香、第 1〜2 段的桂，既不能以不升变的方式走入，也不能打入）
  • 禁止二步、禁止打步将死
  • 禁止让自己的玉仍处于被王手状态的着法、使自己的玉暴露于王手的着法
  • 禁止超过 512 手的着法（ply 为 512 的 State 之后没有下一手）

没有持将棋的宣言（入玉宣言）和“悔棋”。入玉可以经双方同意判为和棋（第 10.2 节）。

9.7 检查失败（ERROR）

对局中对方的输入未通过检查时，发送 CONTROL ERROR（[errorCode, relatedPly]），并把自己一方的对局作为“错误（结果未确定）”结束。收到 ERROR 的一方也同样把对局作为结果未确定结束。不得把检查失败记录为对方负。双方都把到那时为止的记录（到双方已认可的 State 为止）保存为凭证。

获得了对方在同一手数上对两个不同 State 签名的证据（两个 State 和两个签名）的实现，应当将其保存下来。

收到格式不符的 payload（数组的长度、类型、范围不同）时，也同样以 ERROR 终止（STATE_PROPOSE 为 INVALID_MOVE，STATE_ACCEPT、CONTROL、RESULT_SIGNATURE 为 INVALID_SIGNATURE，SYNC_REQUEST、SYNC_CHUNK 为 STATE_CONFLICT）。开始后收到开始前格式的 HELLO、START_AGREEMENT、START_SIGNATURE 时，以 CONDITION_MISMATCH 终止。外层不符的帧，关闭流（第 6.2 节）。

以下情况下，不发送任何内容而结束：在重新连接的核对完成之前（第 11 章）检查失败时；开始的期限（第 9.1 节的 30 秒）已过时；超过断线的上限（第 11.6 节）时；等待结果签名的时间（第 10.4 节）已过时。

结束了对局的实现会关闭流。对方已经结束时，我方发送的帧和重新连接都不会得到响应。

10.2 结果的提议与一致

结果用 CONTROL RESULT_PROPOSE（body 为 FinalResult）提议。双方互相发送了相同 FinalResult 的 RESULT_PROPOSE 时，视为结果一致。同意的一方用 RESULT_PROPOSE 发回与收到的提议相同的 FinalResult。不同意时发送 RESULT_DECLINE，并继续对局。

FinalResult 必须指向当前双方已认可的最新 State。

FinalResult = ["SBQ-RESULT", 1, gameId, H(CBOR(最新的 State)), transcriptHash, 最新的 ply, outcome, cause]
  • 自己有未被认可的着手期间，不提议结果。
  • 手数推进后，此前的提议和正在等待答复的请求都失效。
  • 结果一致后，不同意其他结果的提议（予以忽略）。
  • 结果一致后收到的 STATE_PROPOSE、STATE_ACCEPT 予以忽略（既不认可，也不反映到棋盘上）。如果认可了 FinalResult 所指手数之后的 State，凭证就无法通过第 13.2 节的检查。
  • 在自己提出的“协议和棋、协议中断”请求得到答复之前，应当不提议下一手。提出请求一方的着手与对方的接受交错时，就会出现上述情况（该着手作为没有对方认可的着手，只留在走棋一方凭证的最后）。
  • 在重新连接的核对完成之前（第 11 章），不得接受对方的请求而使结果一致（无法把接受发送给对方）。核对后对方会重新发送提议，届时再答复。

收到 RESULT_PROPOSE 的一方按以下方式决定。

作为用户的操作，协议和棋、协议中断的请求在同一手数上各限一次。但是，接收方即使在同一手数上多次收到相同的提议，也不得将其视为违规（每次都按上表处理）。ShogiBoardQ 会在重新连接后重新发送提议（第 11.5 节），并在超过每局实际时间的上限后，每次被拒绝都重新提议协议中断（第 10.5 节）。

10.3 由棋谱决定的终局

每推进一手（双方已认可的 State 增加）时，双方都按以下顺序判定，若为终局，就用 RESULT_PROPOSE 提议该结果。双方判定相同时，互相发送相同的提议即一致。

  1. 将死：在最新局面（ply ≥ 1）中，行棋方一个合法着法都没有时，行棋方负（cause 2）。没有被王手时也同样处理。
  2. 千日手：与最新局面相同的局面（棋盘、持驹、行棋方相同。不比较手数栏），在从 State0 开始的序列中，包括最新的在内出现 4 次以上时。
    • 从最新局面之前最近一次出现相同局面的 State 的下一个开始，检查到最新的 State 为止。若在此期间先手走的着法全部是王手，则先手负（后手胜，cause 5）。否则，若后手走的着法全部是王手，则后手负（先手胜，cause 5）。“王手”是指在走了该着法后的局面中，对方的玉处于被王手的状态。
    • 两者都不是时，和棋（cause 4）。
  3. 达到 512 手：最新的 ply 为 512 时，和棋（cause 7）。

10.4 对结果的签名（RESULT_SIGNATURE）

Frame   = [1, 9, requestId, gameId, payload]
payload = [FinalResult, side, signature]    ; signature 是用玩家密钥对 CBOR(FinalResult) 所做的签名（bstr(64)）

结果一致后，各方按以下顺序进行。

  1. 保存一致的结果（resultDigest）。此后，在本局中不得对其他结果签名。
  2. 用玩家密钥对 FinalResult 签名，发送 RESULT_SIGNATURE。
  3. 等待对方的 RESULT_SIGNATURE（30 秒）。

接收方确认 side 是对方一方、签名用 StartAgreement 中对方的 playerKey 验证正确、FinalResult 与一致的结果相同。不符则错误（INVALID_SIGNATURE，结果不同则 STATE_CONFLICT）。side 和签名的检查在结果一致之前也会进行。

表示同意的 RESULT_PROPOSE，一定要在 RESULT_SIGNATURE 之前发送。在结果一致之前收到的 RESULT_SIGNATURE，即使通过了检查也会被丢弃，之后也不会使用（该对局以“无对手确定”结束）。

  • 双方的签名齐全时，就成为“双方已确定”的记录。
  • 30 秒后仍未收到对方的签名，或在等待期间线路断开时，作为只有自己签名的记录结束（“无对手确定”）。

10.5 退出对局（ABORT）

用户单方面离开对局时，发送 CONTROL ABORT（[最新的 State 的哈希, reasonCode]），并把自己一方的对局作为“中断（结果未确定）”结束。如果是用户的操作，reasonCode 使用 CANCELLED（12）。收到 ABORT 的一方也把对局作为结果未确定结束。ABORT 不是协议中断（cause 8），也不是对方负。

在重新连接的核对完成之前，以及 State0 的认可齐全之前，不发送 ABORT（不发送，直接结束自己一方的对局）。

每局的实际时间（从双方的开始签名齐全时起计算）超过 24 小时后，提议协议中断。被拒绝时，重新提议。再过 120 秒仍未一致时，以 ABORT（理由为 GAME_TIME_LIMIT）结束。ShogiBoardQ 在超过 24 小时后，不再重新发送未被认可的着手，也不再申报或主张超时。

11. 重新连接

对局中即使流断开，也可以重新连接到同一局对局。重新连接后，先对照双方最新的状态再继续。

11.1 重新连接方与接受方

  • 重新连接的是申请方（最初打开流的一方）。断线期间，每隔 5 秒连接对方的 PeerId，打开 /shogiboardq/game/1.0.0 的流。地址使用最初连接时可用的地址，以及通过 Identify 得知的地址。不发送 INVITE_TOKEN。
  • 申请方打开流后，不等待对方，立即发送重新连接的 HELLO（第 11.2 节）。邀请方在收到首帧之前，不会察觉到新流已建立。首帧的 gameId 必须是对局ID（不同则对局以错误终止）。
  • 判断已断线的一方要关闭旧流。如果不关闭，对方就不会察觉断线，重新连接也不会开始（申请方只在自己的流关闭时，或自己判断已断线时，才重新连接）。
  • 邀请方从对局开始到结束，只接受来自对局对手 PeerId 的流（不接受其他对方的流，以及以 INVITE_TOKEN 开始的流）。等待首帧 5 秒，与第 6.3 节相同。
  • 对方重新连接过来时，即使旧流看起来仍然有效，也要关闭旧流，作为已断线进入下面的步骤。即使刚完成核对也一样，每次有新流到达，都用新的随机数重新进行核对（申请方的连接尝试可能会重叠）。
  • 对局期间不得改变 PeerId（第 3.2 节）。退出应用或节点后，就无法回到同一局对局。

判断“已断线”，是在流被关闭或重置时，或自己的 STATE_PROPOSE 在 30 秒内没有收到认可时（第 9.2 节）。在开始前（双方的开始签名齐全之前，或 READY 完成之前）断线时，不重新连接而结束。在结果一致之后（等待第 10.4 节的签名时）断线时，也不重新连接。此时，如果对方尚未察觉结果已一致（在表示同意的 RESULT_PROPOSE 到达之前断线），对方会尝试重新连接，但得不到响应，对方一方会因第 11.6 节的上限而结束。

11.2 HELLO（重新连接）

Frame   = [1, 1, requestId, gameId, payload]
payload = ["SBQ-RECONNECT", 1, side, connectionRandom]     ; side 为自己一方（1＝先手、2＝后手）

新流建立后，双方都发送放入了新的 32 字节随机数的重新连接 HELLO。收到对方的 HELLO 后，确认 side 是对方一方，并且随机数与自己的不同，然后计算新的 connectionId（第 7.5 节。按先手的随机数、后手的随机数的顺序）。控制消息的编号（sequence）双方都从 1 重新开始。

开始前的 HELLO 与重新连接的 HELLO，通过帧的 gameId（是 zero32 还是对局ID）和 payload 的标签区分。

重新连接的 HELLO 如果是在不处于重新连接期间时到达、side 不是对方一方、随机数与自己的相同，只要符合其中之一，ShogiBoardQ 就默默丢弃（核对不会推进，以第 11.6 节的上限结束）。

11.3 RESUME

收到对方的重新连接 HELLO 后，发送 CONTROL RESUME（[latestPly, latestStateHash]）。latestPly 是自己所持有的、双方已认可的最新 State 的手数，latestStateHash 是它的哈希。这个 CONTROL 带有针对新 connectionId 的单局密钥签名，因此可以重新确认对方与开始时是同一个对方。

在确认 RESUME 之前，不得接受其他帧（着手、认可、结果的提议等默默丢弃）。重新连接期间可以发送的只有重新连接的 HELLO、CONTROL RESUME、SYNC_REQUEST、SYNC_CHUNK。

每次核对只发送一次 RESUME。在不处于重新连接期间时（包括核对完成之后）收到的 RESUME，以错误（STATE_CONFLICT）终止。未请求的 SYNC_CHUNK 也一样。

收到对方的 RESUME 后，与自己的最新手数（myPly）比较。

情况处理
对方的 latestPly ＝ myPly若该手数的自己的 State 的哈希一致，核对即结束。不同则错误（STATE_CONFLICT）
对方的 latestPly ＜ myPly确认该手数的自己的 State 的哈希一致，等待对方的 SYNC_REQUEST
对方的 latestPly ＞ myPly用 SYNC_REQUEST 请求缺少的部分

11.4 SYNC_REQUEST 与 SYNC_CHUNK

SYNC_REQUEST: Frame = [1, 7, requestId, gameId, [fromPly, previousStateHash]]
SYNC_CHUNK:   Frame = [1, 8, requestId, gameId, [[[State, blackApproval, whiteApproval], ...], final]]
  • 较旧的一方用 fromPly ＝ 自己的最新手数＋1、previousStateHash ＝ 自己最新 State 的哈希来请求。
  • 较新的一方确认：已收到对方的 RESUME，fromPly 为 1 以上且不大于自己的最新手数，previousStateHash 是自己第 fromPly − 1 手的 State 的哈希。不符则错误（STATE_CONFLICT）。通过后，把从 fromPly 到最新的 State，连同双方认可的签名（均为 bstr(64)），用每次最多 64 个的 SYNC_CHUNK 依次返回。最后一块为 final ＝ 1，其他为 0。不发送请求范围之外的内容。
  • 较旧的一方对收到的 State 逐个确认：手数连续、双方的认可正确，以及第 9.2 节的步骤 6〜9（前一状态哈希、着法的形式、超时、合法着法、局面、剩余时间的计算），确认后再纳入。任何一项不符，都以错误（STATE_CONFLICT）终止。自己有未被认可的着手，而收到同一手数的不同 State 时，以错误（STATE_CONFLICT）终止（不回退到只有一方签名的另一条着法序列）。若是相同的 State，就把未被认可的着手视为已被认可。
  • 对于通过重新连接才首次得知的对方着手，自己回合的计时从纳入时起开始（不推测丢失的时刻）。

11.5 核对之后

  • 如果还留有没有对方认可的自己的着手，就重新发送相同字节序列的 STATE_PROPOSE。对对方回合的观测（第 9.4 节）从这次重新发送时起重新测量。通过 SYNC 得知未被认可的着手已是“已认可”时，不重新测量（从最初发送时起测量，并扣除断线的时间）。
  • 如果曾提议过结果，就重新发送 RESULT_PROPOSE。如果已达到由棋谱决定的终局（第 10.3 节），核对后必须提议。ShogiBoardQ 不会从通过 SYNC 得知最后一手的一方提议，因此如果原本处于最新状态的一方不重新发送提议，对局就不会结束。
  • 把断线的时间（从判断断线到核对结束）加到该局的断线时间合计中。

11.6 断线的上限

上限长度超过时
一次断线中，到核对结束为止120 秒作为“通信中断（结果未确定）”结束
每局断线时间的合计600 秒作为中断（理由为 DISCONNECT_LIMIT）结束

无法区分自己线路的故障和对方故意的断线。不得把断线视为对方负。

12. 错误编号

REJECT（第 8.7 节）的 errorCode、CONTROL ERROR 的 errorCode、CONTROL ABORT 的 reasonCode 使用同一张表的编号（1〜15）。发送方不得发送表中没有的编号。接收方把表中没有的编号视为原因不明的拒绝或中断（不作为拒绝对方的理由）。

编号名称含义
1UNSUPPORTED_VERSION不支持的版本
2WRONG_NETWORKnetworkId 不同
3BUSY正在与其他对手协商或对局（对屏蔽的对手也返回这个编号）
4EXPIRED已过期（开始协议的期限、开始手续的期限）
5CONDITION_MISMATCH条件、格式、步骤不符
6INVALID_SIGNATURE签名不正确
7INVALID_MOVE着法无法读取、不是合法着法、局面不符
8STATE_CONFLICT状态不一致（同一手数的不同状态、顺序不符的帧）
9CLOCK_MISMATCH时间的计算不符、申报与观测不符
10LIMIT_EXCEEDED超过上限（控制消息的条数等）
11STORAGE_ERROR无法保存记录
12CANCELLED用户取消，或退出了应用
13DISCONNECT_LIMIT断线时间的合计超过上限
14GAME_TIME_LIMIT每局实际时间的上限
15CLOCK_DISCONTINUITY因睡眠或时钟的变更，无法确认计时的连续性

无论以哪个编号结束，检查失败、中断、断线都是“结果未确定”，不判胜负。胜负只在双方对同一 FinalResult 签名时（第 10.4 节），以及由棋谱决定终局时（第 13.3 节）才确定。

13. 对局记录（凭证）

对局结束后（即使结果未确定），各方都把对局的记录保存到一个文件中。这称为凭证。凭证不需要网络，也不需要对方，任何人都可以验证。扩展名为 .sbqmatch，大小不超过 8 MiB。兼容实现写出的凭证，必须能用 ShogiBoardQ 的“对局记录”和 shogiboardq-cli verify-match 验证，反之亦然。

文件的内容只有以下值的确定性CBOR字节序列（前后不附加任何内容）。

FinalResult一致的结果（第 7.5 节）。结果未一致的对局为空数组 []
blackResultSignature、whiteResultSignature先手、后手用玩家密钥对 FinalResult 所做的签名
  • 尚未有签名的签名栏，设为长度 0 的 bstr。签名栏的长度必须为 0 或 64。
  • FinalResult 为 [] 时，两个结果签名栏都设为长度 0。
  • 对方的认可未到达的自己的最后一手，可以作为只附有自己认可的 State 放在序列的最后。只有一方认可的 State 之后，不得放置其他 State。
  • 不放入显示名、IP 地址、PeerId 本身、邀请口令、本地备注名（PeerId 只作为 StartAgreement 中的哈希保留）。

13.2 验证步骤

验证方依次确认以下各项。各项的结果分别显示（不把“签名正确”“棋谱符合规则”“时间计算一致”混在一起）。签名的验证全部按第 2.4 节进行（包括公钥的检查）。

  1. 格式：不超过 8 MiB，是确定性CBOR，符合第 13.1 节的格式。Rules、NetworkPolicy 为 v1 的值，TimeControl 在第 7.1 节的范围内。
  2. 条件：Rules、TimeControl、NetworkPolicy 的哈希与 StartAgreement 中的 3 个哈希一致。
  3. 开始签名：2 个开始签名分别用 StartAgreement 的 blackPlayerKey、whitePlayerKey 验证正确。计算 gameId = H(CBOR(StartAgreement))。
  4. State 的序列：从开头依次确认以下各项。
    • State 的 gameId 是对局ID，ply 与序列中的位置（0, 1, 2, …）一致。
    • 长度不为 0 的认可签名，用对应一方的单局密钥（blackSessionKey、whiteSessionKey）验证正确。不承认双方都没有认可的 State。
    • State0 与第 7.2 节的值一致。此后的 State，按照第 9.2 节的步骤 6〜9（前一状态哈希、着法的形式、超时、合法着法、局面、剩余时间的计算）由前一个 State 生成。
    • 只有一方认可的 State 只能放在序列的最后。
  5. 双方已认可的着法序列：把双方的认可都齐全的 State（从序列开头起连续的部分）作为“双方已认可的着法序列”。若它不为空，就进行第 10.3 节的判定，求出是否由棋谱决定终局。
  6. 结果：若有 FinalResult，确认以下各项。
    • gameId 是对局ID，ply、finalStateHash 指向双方已认可的着法序列的最后一个 State，transcriptHash 与由双方已认可的着法序列计算出的值一致。
    • 长度不为 0 的结果签名，用对应一方的玩家密钥验证正确。
    • 若由棋谱决定终局，FinalResult 的 outcome、cause 与之一致。若不由棋谱决定终局，FinalResult 的 cause 不是由棋谱决定的原因（将死、千日手、连续王手千日手、达到 512 手）。

13.3 记录类别

根据验证的结果，把记录分为以下 3 类。从上往下依次套用。

类别条件能够表明的内容
双方已确定通过步骤 2〜4，有 FinalResult 并指向最后一个 State，且双方的玩家密钥签名都正确双方同意了同一结果
由棋谱决定的结果通过步骤 2〜4，双方已认可的着法序列以由棋谱决定的终局（第 10.3 节）结束根据双方确认过的着法序列，结果已确定

15.1 测试输入

ShogiBoardQ 仓库的 protocol/testvectors/ 中，有用于确认不同实现之间得到相同结果的输入。兼容实现应当在自己的测试中读取它们。跳过以 # 开头的行和空行。

15.2 确认顺序

制作兼容实现时，最好从下层开始依次确认。

  1. 确定性CBOR与哈希：与第 15.1 节的输入和附录 A 的值一致。
  2. 凭证的验证：读取 ShogiBoardQ 保存的 .sbqmatch，第 13.2 节的验证全部通过（这也确认了签名的验证，以及着法、局面、时间的计算是否正确）。
  3. 邀请字符串：能读取 ShogiBoardQ 生成的邀请字符串，并且自己生成的邀请字符串能用 ShogiBoardQ 的“检查邀请字符串”读取。
  4. 连接与协商：把网络设为 sbq-local-1，与同一电脑上的 ShogiBoardQ，分别作为邀请方和被邀请方，进行到条件确认画面。
  5. 对局：在执先手和执后手两种情况下，分别下到认输、将死、超时、协议和棋，双方的凭证都成为“双方已确定”。用 shogiboardq-cli verify-match --input-path <文件> 验证自己写出的凭证，valid 为 true，category 为 mutually_signed。
  6. 重新连接：在对局中切断流，能重新连接并继续（分别在自己是申请方和邀请方时、有和没有未被认可的着手时）。
  7. 拒绝：发送不正确的签名、不合法的着法、时间计算不符的 State、编号跳跃的 CONTROL 等，确认对方不判胜负而终止。自己的实现对相同的输入也同样拒绝。

在同一电脑上启动多个 ShogiBoardQ 时，会按打开的顺序成为不同的玩家（第二个为“第2位玩家”）。与兼容实现的测试可以在同一电脑内进行。
