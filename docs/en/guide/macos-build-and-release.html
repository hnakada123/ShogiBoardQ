macOS Build and Release

Build a macOS app, create a DMG, and prepare a signed release

macOS Qt 6 DMG GitHub Releases

Only the distribution ZIP (ShogiBoardQ-macos.zip) is attached to a release; the Qt source and related documents are not attached separately. For preparing the license documents inside the app, see the Qt distribution notes (Japanese).

The DMG contains only the files needed to run ShogiBoardQ (minimal configuration). As in the Linux package, the Hayanagi USI engine for regular games and the tsume shogi collections are kept outside the DMG and go into the distribution ZIP together with the DMG (5.2). The UI is available in four languages, Japanese, English, and Chinese (Simplified and Traditional), and the four translation files are bundled.

2. Setting up the development environment

2.1 Xcode Command Line Tools

xcode-select --install

2.2 Installing the required tools with Homebrew

brew install cmake ninja create-dmg rust libsodium pkg-config

The distribution script uses create-dmg to create the DMG (you do not need it with --skip-dmg). rust, libsodium and pkg-config are for building P2P games (3.4).

2.3 Installing Qt 6

Method A: Qt Online Installer (recommended)

Download the installer from the official Qt site and select the following components:

  • Qt 6.x > macOS
  • Qt 6.x > Qt Charts
  • Qt 6.x > Qt Multimedia
  • Developer and Designer Tools > CMake

After installing, set the Qt paths in environment variables:

# Add to ~/.zshrc (adjust the Qt installation path to your environment)
export Qt6_DIR="$HOME/Qt/6.x.x/macos/lib/cmake/Qt6"
export PATH="$HOME/Qt/6.x.x/macos/bin:$PATH"

Method B: Homebrew

brew install qt@6

With Homebrew, CMake finds Qt automatically, so in most cases no environment variables need to be set.

2.4 Checking the installation

cmake --version       # 3.16 or later
qmake --version       # Qt 6.x
clang++ --version     # Apple Clang

3. Building

The Hayanagi engine for regular games is a submodule, so clone with --recurse-submodules (without it, CMake stops):

git clone --recurse-submodules https://github.com/hnakada123/ShogiBoardQ.git
cd ShogiBoardQ

If you cloned the repository before its history was rewritten on 2026-11-09, do not run git pull. It stops with an error or produces a large number of conflicts. Clone again into a different folder with the command above. Before deleting the old folder, move any unpushed commits and local settings. To see which history a clone has, run git log -1 --format=%h 2026.11.04. Output starting with 376e4362, or an error that 2026.11.04 cannot be found, means the old history, and output starting with aa9bcc4b means the new one. To keep your build folder, you can instead run git fetch origin --tags --force and then git reset --hard origin/main. This discards uncommitted changes and unpushed commits.

In an existing checkout, run git submodule update --init --recursive to fetch the recorded Hayanagi version.

Build script (recommended)

scripts/build-macos.sh runs everything from the Release build through code signing and DMG creation in one go:

# Normal build + DMG creation
./scripts/build-macos.sh

# Build as a Universal Binary (arm64 + x86_64)
./scripts/build-macos.sh --universal

# Clean build, no DMG
./scripts/build-macos.sh --clean --skip-dmg

# Test DMG when the Qt license documents are not prepared (not for distribution)
./scripts/build-macos.sh --clean --skip-qt-licenses

# Sign with a Developer ID (the default is ad hoc signing)
./scripts/build-macos.sh --sign-identity "Developer ID Application: Your Name (TEAMID)"

# Sign with a Developer ID, notarize the DMG, and then create the ZIP
export APPLE_ID="your@email.com" APPLE_TEAM_ID="TEAMID" APPLE_APP_PASSWORD="app-specific-password"
./scripts/build-macos.sh --sign-identity "Developer ID Application: Your Name (TEAMID)" --notarize
Option Description
--universal Build a Universal Binary (arm64 + x86_64; P2P games are not included, see 3.4)
--deployment-target VER Minimum supported macOS version (default: the MACOSX_DEPLOYMENT_TARGET environment variable, or 26.0 if it is not set)
--sign-identity ID Code signing identity (default: - = ad hoc signing). With a Developer ID, the script signs with Hardened Runtime and a timestamp, and also signs the DMG
--notarize Submit the DMG to Apple for notarization, staple the result, and then create the distribution ZIP. Pass a Developer ID with --sign-identity and set the environment variables APPLE_ID, APPLE_TEAM_ID, and APPLE_APP_PASSWORD (an app-specific password)
--skip-dmg Skip creating the DMG and the distribution ZIP (produce only the .app bundle)
--skip-qt-licenses Skip adding the Qt documents and keep only the short documents bundled by the build (Contents/MacOS/licenses). Do not use it for distribution
--clean Delete the build directory before building
--help Show help

The script performs these steps automatically:

  1. Check that the required tools exist (cmake, ninja, macdeployqt, codesign, vtool, python3, create-dmg, and cargo, pkg-config and libsodium for P2P games)
  2. Configure CMake (with CMAKE_OSX_DEPLOYMENT_TARGET) and build with Ninja
  3. Check the build outputs (the .app, the minimum macOS version of the executable and of the P2P communication process, the .qm translation files, and that the list of Rust library licenses matches Cargo.lock)
  4. Bundle the frameworks with macdeployqt
  5. Remove unused Qt parts and thin the Qt binaries to arm64 (4.4; not thinned with --universal), then verify
  6. Add the Qt license documents (skipped with --skip-qt-licenses)
  7. Sign the P2P communication process and the whole bundle, and verify them with codesign --verify --deep --strict
  8. Create the DMG with create-dmg (with a Developer ID, the DMG is signed as well)
  9. With --notarize, notarize and staple the DMG, then verify
  10. Create the distribution ZIP (ShogiBoardQ-macos.zip) containing the DMG, Hayanagi, and the tsume shogi collections (5.2)

About the minimum macOS version: if no deployment target is given, the macOS version of the build host becomes the minimum supported version (for example, an app built on macOS 27 does not start on macOS 26). The script passes 26.0 by default and stops if the minos of the built executable does not match.

About code signing: macdeployqt rewrites the binaries, so the bundle is left with only linker signatures afterwards and does not pass strict signature verification. The script re-signs the whole bundle after macdeployqt and then creates the DMG.

About the ERROR messages from macdeployqt: it prints .qm: is not an object file (otool was run on a translation file), messages that dependencies of the ODBC / PostgreSQL / Mimer SQL drivers cannot be found, and a signing error from macdeployqt itself. All of them are harmless. Those drivers are removed in the next step, and the script redoes the signing and verifies it strictly.

3.4 P2P games (Rust and libsodium)

P2P games (ENABLE_P2P_PLAY) are enabled by default and are part of the distributed package (scripts/build-macos.sh builds them as well). Building needs the following two items.

  • Rust (1.85 or later). cargo builds the communication process shogiboardq-peer
  • libsodium (1.0.18 or later). It is found through pkg-config
brew install rust libsodium pkg-config

cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON \
    -DCMAKE_PREFIX_PATH="$HOME/Qt/6.x.x/macos"
ninja -C build
ctest --test-dir build -R tst_p2p --output-on-failure
cargo test --locked --workspace

To build without P2P games (Rust and libsodium are then not needed), add -DENABLE_P2P_PLAY=OFF when configuring. A build directory that was configured earlier without P2P games keeps that setting and stays disabled; configure it again with -DENABLE_P2P_PLAY=ON to enable them.

The communication process is built inside the app bundle (ShogiBoardQ.app/Contents/MacOS/shogiboardq-peer) and the app starts it from there. These points differ from Linux and Windows.

  • The communication process puts itself into a sandbox (Seatbelt) right after it starts. Reading and writing files, starting programs, connecting to Unix domain sockets and similar operations are denied, and the denials appear in the Console app log (sender Sandbox)
  • When the local network (same computer, same LAN) is not used, the app starts the process with --no-loopback, and the sandbox also blocks outgoing connections to this Mac itself
  • A debugger (lldb) cannot attach to the communication process
  • If CMAKE_OSX_DEPLOYMENT_TARGET is set, the communication process is built for the same minimum macOS version. Universal Binaries are not supported (the communication process and Homebrew's libsodium exist only for the architecture of the Mac that builds them). scripts/build-macos.sh --universal builds without P2P games
  • libsodium is linked as Homebrew's dynamic library (/opt/homebrew/opt/libsodium), and macdeployqt bundles it in Contents/Frameworks. The distribution script stops if the minimum macOS version of the bundled libsodium is newer than the target of the app (then rebuild it for the target, for example MACOSX_DEPLOYMENT_TARGET=26.0 brew reinstall --build-from-source libsodium)
  • The distribution script signs the communication process on its own before signing the bundle (with the Hardened Runtime and a timestamp for a Developer ID; no entitlements are added)
  • The list of the Rust libraries built into the communication process, with their license texts (resources/licenses/RUST-NOTICES.md), is built into the app ("Licenses of the libraries for P2P games" in the About dialog). After changing the dependencies (Cargo.lock), regenerate it with python3 scripts/rust_licenses.py (the distribution script stops if it is out of date)
  • Storing the player key in the Keychain needs QtKeychain (optional; it must be built with the same Qt as the app. Homebrew's qtkeychain is built for Homebrew's Qt, so do not mix it with Qt from the Qt Online Installer). Without it, the key is kept in a file encrypted with a passphrase
  • A cooperating node (shogiboardq-peer --service) can also be run

4. Creating the app bundle

Note: if you use scripts/build-macos.sh, the steps in this chapter run automatically and you do not need to run them by hand.

4.1 Bundling the Qt frameworks with macdeployqt

A build alone does not put Qt's dynamic libraries into the bundle. Use macdeployqt to copy the required Qt frameworks and plugins into the bundle.

macdeployqt build/ShogiBoardQ.app -verbose=2

macdeployqt does the following automatically:

  1. Copies the Qt frameworks the app depends on (QtWidgets, QtCharts, QtNetwork, QtMultimedia, QtGui, QtCore, and so on) to Contents/Frameworks/
  2. Copies the Qt plugins (platforms/cocoa, imageformats/svg, and so on) to Contents/PlugIns/
  3. Rewrites the @rpath of the libraries (install_name_tool)
  4. Generates qt.conf in Contents/Resources/

4.2 Checking the structure after bundling

# Check that the frameworks are bundled correctly
ls build/ShogiBoardQ.app/Contents/Frameworks/

# Check that the plugins are included
ls build/ShogiBoardQ.app/Contents/PlugIns/

# Check that no external paths remain in the dependencies
otool -L build/ShogiBoardQ.app/Contents/MacOS/ShogiBoardQ

If the otool output still shows paths under /usr/local/ or /opt/homebrew/, the bundle is incomplete.

4.3 Checking the translation files

A CMake post-build step places the .qm files in Contents/MacOS/. Check that the files are still there after running macdeployqt:

ls build/ShogiBoardQ.app/Contents/MacOS/*.qm   # 4 files (ja_JP / en / zh_CN / zh_TW)

The translations of the standard Qt dialogs (qtbase_ja / qtbase_zh_CN / qtbase_zh_TW) are embedded in the executable's resources, so no separate files are needed.

4.4 Removing unused Qt parts (minimal configuration)

macdeployqt deploys every Qt plugin of each kind and, through the virtual keyboard plugin, pulls in Qt Quick / QML as well (about 187 MB). Remove what ShogiBoardQ does not use and, for an Apple Silicon-only distribution, also strip the x86_64 part of Qt (about 89 MB; the DMG is about 50 MB).

What to remove Reason
PlugIns/platforminputcontexts/, QtQml* / QtQuick / QtVirtualKeyboard* The virtual keyboard and QML are not used
Everything in PlugIns/tls/ except SecureTransport, PlugIns/networkinformation/ The “TLS (encrypted)” connection in CSA network play uses the SecureTransport backend, which relies on the macOS Security framework (the OpenSSL backend would need libssl in the bundle). Network information is not used
PlugIns/multimedia/libffmpegmediaplugin.dylib, libav* / libsw* Piece sounds are played with the native macOS darwin backend
Everything in PlugIns/sqldrivers/ except SQLite Only SQLite is used
gif / wbmp / macheif / icns / tga / macjp2 in PlugIns/imageformats/ Only SVG / ICO (icons) and JPEG / TIFF / WebP (board image export) are used 
C=build/ShogiBoardQ.app/Contents
rm -rf $C/PlugIns/platforminputcontexts $C/PlugIns/networkinformation \
  $C/PlugIns/multimedia/libffmpegmediaplugin.dylib $C/Frameworks/libav*.dylib $C/Frameworks/libsw*.dylib \
  $C/Frameworks/QtQml*.framework $C/Frameworks/QtQuick.framework $C/Frameworks/QtVirtualKeyboard*.framework
find $C/PlugIns/tls -name '*.dylib' ! -name libqsecuretransportbackend.dylib -delete
find $C/PlugIns/sqldrivers -name '*.dylib' ! -name libqsqlite.dylib -delete
for p in gif wbmp macheif icns tga macjp2; do rm -f $C/PlugIns/imageformats/libq$p.dylib; done

# Thin Qt to arm64 only (do not do this when distributing a Universal Binary)
find $C -type f \( -perm +111 -o -name '*.dylib' \) | while read -r f; do
  if lipo -archs "$f" 2>/dev/null | grep -q x86_64; then
    lipo "$f" -thin arm64 -output "$f.thin" && chmod "$(stat -f %Lp "$f")" "$f.thin" && mv "$f.thin" "$f"
  fi
done

What remains is 12 Qt frameworks (Charts, Concurrent, Core, DBus, Gui, Multimedia, Network, OpenGL, OpenGLWidgets, Sql, Svg, Widgets) and 10 plugins (cocoa, macstyle, svgicon, darwin multimedia, sqlite, securetransport, ico / jpeg / tiff / webp). After removing files, re-sign the whole bundle (6.4; for ad hoc signing, codesign --force --deep --sign - build/ShogiBoardQ.app).

After starting the app, check that every loaded library comes from inside the bundle:

open build/ShogiBoardQ.app
lsof -p "$(pgrep -x ShogiBoardQ)" | grep -E '/Qt/|homebrew'   # should print nothing

5. Creating the DMG file

Note: if you use scripts/build-macos.sh, the DMG is created automatically with Method B (create-dmg) and you do not need to run these steps by hand. The --skip-dmg option skips the creation of the DMG and the distribution ZIP (only the .app bundle is created).

When creating the DMG by hand, also finish the removal and signing in 4.4 before putting the app into the DMG. With Method A, macdeployqt creates the DMG directly, so the result is not the minimal configuration.

Method A: the -dmg option of macdeployqt (simple)

macdeployqt build/ShogiBoardQ.app -dmg

This creates build/ShogiBoardQ.dmg. It is simple, but the DMG has no background image and no link to the Applications folder.

Method B: create-dmg (recommended - custom DMG)

This creates a good-looking DMG from which users can drag and drop the app onto the Applications folder.

Installation

brew install create-dmg

Creating the DMG

# Create the bundle with macdeployqt (without -dmg)
macdeployqt build/ShogiBoardQ.app

# Create the DMG
create-dmg \
  --volname "ShogiBoardQ" \
  --volicon "resources/icons/shogiboardq.icns" \
  --window-pos 200 120 \
  --window-size 600 400 \
  --icon-size 100 \
  --icon "ShogiBoardQ.app" 150 190 \
  --hide-extension "ShogiBoardQ.app" \
  --app-drop-link 450 190 \
  "ShogiBoardQ.dmg" \
  "build/ShogiBoardQ.app"

Options

Option Description
--volname Volume name when mounted
--volicon Volume icon
--window-pos Position of the DMG window (x y)
--window-size Size of the DMG window (width height)
--icon-size Icon size (px)
--icon Position of the app icon (name x y)
--hide-extension Hide the .app extension
--app-drop-link Position of the link to the Applications folder (x y)

Method C: hdiutil (manual - full control)

# Create a temporary directory
mkdir -p dmg_staging
cp -R build/ShogiBoardQ.app dmg_staging/
ln -s /Applications dmg_staging/Applications

# Create the DMG
hdiutil create -volname "ShogiBoardQ" \
  -srcfolder dmg_staging \
  -ov -format UDZO \
  "ShogiBoardQ.dmg"

# Clean up
rm -rf dmg_staging

5.1 Verifying the DMG

# Mount it and check that the app runs
hdiutil attach ShogiBoardQ.dmg
open /Volumes/ShogiBoardQ/ShogiBoardQ.app

# Unmount
hdiutil detach /Volumes/ShogiBoardQ

5.2 Distribution ZIP

After the DMG, the script creates ShogiBoardQ-macos.zip in the repository root. Its layout follows the Linux ZIP.

ShogiBoardQ-macos/
├── ShogiBoardQ.dmg
├── README.md                      ← resources/platform/README-macos.md
├── LICENSE
├── Hayanagi/
│   ├── hayanagi                   ← USI engine for regular games (arm64; same minimum macOS as the app)
│   ├── book/hayanagi_book.db      ← Hayanagi opening book
│   └── README.md
└── data/tsumeshogi/
    ├── tsume_{3,5,7,9,11,13}ply_1000_YYYYMMDD.txt
    └── README.md
  • There must be exactly one collection file per move count. The script stops if an older version or the like remains.
  • hayanagi is build/Hayanagi/hayanagi after strip -x, signed again with the same identity as the app (ad hoc by default).
  • The opening book hayanagi_book.db, which the build copies to build/Hayanagi/book/, goes to Hayanagi/book/. Hayanagi reads the book from book/ in its working directory, and ShogiBoardQ starts an engine with the engine's own directory as the working directory, so the book is used as extracted.
  • A downloaded hayanagi carries the quarantine attribute, so the README tells users to run xattr -d com.apple.quarantine Hayanagi/hayanagi.
unzip -l ShogiBoardQ-macos.zip
# Hayanagi answers and reads the book (started in Hayanagi/, as ShogiBoardQ does)
(cd build/ShogiBoardQ-macos/Hayanagi && (printf 'usi\nisready\nposition startpos\ngo movetime 300\n'; sleep 1.5; echo quit) | ./hayanagi | grep -E 'book|usiok|readyok|bestmove')

6. Code signing and notarization

For distribution, code signing and notarization are required to pass Apple's Gatekeeper. The app also works without notarization, but the first time a downloaded app is opened, a Gatekeeper warning appears and the user has to allow it (6.6).

6.1 Joining the Apple Developer Program

Code signing and notarization require membership in the Apple Developer Program ($99 per year).

6.2 Getting the signing certificates

Create the following certificates from Xcode > Settings > Accounts:

  • Developer ID Application — for signing the app itself
  • Developer ID Installer — for signing a pkg (optional; a DMG is signed with Developer ID Application)

6.3 Creating a signed bundle with macdeployqt

macdeployqt build/ShogiBoardQ.app \
  -sign-for-notarization="Developer ID Application: Your Name (TEAMID)"

With this option, macdeployqt:

  1. Bundles the Qt frameworks and plugins
  2. Signs all frameworks, plugins, and the executable
  3. Enables --options=runtime (Hardened Runtime)

6.4 Signing by hand

If you do not use the signing option of macdeployqt:

# Sign all binaries in the bundle recursively
codesign --deep --force --verify --verbose \
  --sign "Developer ID Application: Your Name (TEAMID)" \
  --options runtime --timestamp \
  build/ShogiBoardQ.app

# Verify the signature
codesign --verify --deep --strict --verbose=2 build/ShogiBoardQ.app

Notarization requires a signature with a timestamp (--timestamp) and Hardened Runtime (--options runtime).

6.5 Notarization

With the script, pass a Developer ID to --sign-identity and add --notarize; the script submits the DMG for notarization, staples it, and then creates the distribution ZIP (3. Building). If notarization does not pass, the script prints the submission ID and stops. The steps below are for doing it by hand.

# Create the DMG (from the signed bundle)
# ... (create the DMG with one of the methods in chapter 5)

# Submit for notarization
xcrun notarytool submit ShogiBoardQ.dmg \
  --apple-id "your@email.com" \
  --team-id "TEAMID" \
  --password "app-specific-password" \
  --wait

# Staple (embed the notarization result in the DMG)
xcrun stapler staple ShogiBoardQ.dmg

# Verify the staple
xcrun stapler validate ShogiBoardQ.dmg

Note: for --password, use an app-specific password, not your Apple ID password.

6.6 Distributing without notarization

Without notarization, Gatekeeper blocks the downloaded app the first time it is opened. Since macOS 15, Control-clicking (right-clicking) the app in Finder and choosing Open no longer opens it, so give users the following steps:

  1. Open the app, and close the warning when it appears
  2. Open System Settings > Privacy & Security, click Open Anyway, and follow the prompts to allow the app

Alternatively, remove the Gatekeeper quarantine attribute in Terminal (use this method too if Open Anyway does not appear):

xattr -cr /Applications/ShogiBoardQ.app

7. Publishing on GitHub Releases

7.1 Creating the tag

Update the version only on the day of a release, to that date (Versioning and releases (Japanese)). Before building the packages, change APP_VERSION in CMakeLists.txt and commit it, build the packages from that commit, and then tag the same commit with the same version. Do not put a v in front of the tag.

git tag -a 2026.10.07 -m "ShogiBoardQ 2026.10.07"
git push origin main 2026.10.07

7.2 Creating the release with GitHub CLI

Use GitHub CLI (gh):

# Install
brew install gh

# Log in (first time only)
gh auth login

Create the release and upload the asset:

gh release create 2026.10.07 \
  --title "ShogiBoardQ 2026.10.07" \
  --notes-file RELEASE_NOTES.md \
  ShogiBoardQ-macos.zip

To publish the Windows ZIP at the same time, add it as another asset:

gh release create 2026.10.07 \
  --title "ShogiBoardQ 2026.10.07" \
  --notes-file RELEASE_NOTES.md \
  ShogiBoardQ-macos.zip \
  ShogiBoardQ-windows.zip

Generating the release notes automatically

If you do not prepare a release notes file, GitHub generates the notes:

gh release create 2026.10.07 \
  --title "ShogiBoardQ 2026.10.07" \
  --generate-notes \
  ShogiBoardQ-macos.zip

Adding an asset to an existing release

If the release has already been created on the Windows side, add the macOS ZIP:

gh release upload 2026.10.07 ShogiBoardQ-macos.zip

7.3 Creating the release from the web UI (alternative)

  1. GitHub repository → Releases → Draft a new release
  2. Choose a tag → type a new tag (for example 2026.10.07) and create it
  3. Enter the Release title (for example ShogiBoardQ 2026.10.07)
  4. Write the release notes in Description
  5. Drag and drop ShogiBoardQ-macos.zip onto Attach binaries
  6. Click Publish release

8. Troubleshooting

Qt is not found

CMake Error: Could not find a package configuration file provided by "Qt6"

Pass the Qt installation path explicitly:

cmake -B build -S . -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH="$HOME/Qt/6.x.x/macos"

macdeployqt is not found

# Check the Qt installation path
which macdeployqt

# If it is not found, add it to PATH
export PATH="$HOME/Qt/6.x.x/macos/bin:$PATH"

# With Homebrew
export PATH="$(brew --prefix qt@6)/bin:$PATH"

Qt Charts is not bundled by macdeployqt

macdeployqt sometimes fails to detect Qt Charts automatically. In that case it has to be copied by hand:

# Check whether it is missing from the bundle
otool -L build/ShogiBoardQ.app/Contents/MacOS/ShogiBoardQ | grep Charts

# Copy it by hand (if needed)
cp -R "$HOME/Qt/6.x.x/macos/lib/QtCharts.framework" \
  build/ShogiBoardQ.app/Contents/Frameworks/

# Fix the reference path with install_name_tool
install_name_tool -change \
  @rpath/QtCharts.framework/Versions/A/QtCharts \
  @executable_path/../Frameworks/QtCharts.framework/Versions/A/QtCharts \
  build/ShogiBoardQ.app/Contents/MacOS/ShogiBoardQ

The app does not open the first time (without notarization)

Tell the users of the package to do one of the following:

  • Click Open Anyway in System Settings > Privacy & Security (first time only; since macOS 15, Control-clicking (right-clicking) the app in Finder and choosing Open no longer opens it)
  • Run xattr -cr /Applications/ShogiBoardQ.app in Terminal

Translations are not loaded

Check that the .qm files exist in the bundle:

find build/ShogiBoardQ.app -name "*.qm"

If there are no .qm files in Contents/MacOS/, copy them by hand:

cp build/ShogiBoardQ_{ja_JP,en,zh_CN,zh_TW}.qm build/ShogiBoardQ.app/Contents/MacOS/

Creating a Universal Binary (Intel + Apple Silicon)

With the distribution script, you can build one with ./scripts/build-macos.sh --universal (the Qt binaries are not thinned to arm64 (4.4), and P2P games are not included).

To create a binary that supports both architectures:

cmake -B build -S . -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_OSX_ARCHITECTURES="arm64;x86_64"

cmake --build build --config Release

Note: the installed Qt itself must also be a Universal Binary build.
