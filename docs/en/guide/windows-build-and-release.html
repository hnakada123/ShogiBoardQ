Requirements and setup

Install Visual Studio 2022 with the Desktop development with C++ workload, Git, CMake 3.16 or later, Ninja, and Python 3. Use Developer PowerShell for VS 2022 with the x64 toolchain enabled.

Install a Qt 6.7 or later MSVC desktop kit matching your compiler architecture. Required modules are Widgets, Charts, Network, Concurrent, Multimedia, Sql, and LinguistTools. Include Qt Charts, Qt Multimedia, Qt SVG, and the SQLite plugin in your Qt installation.

The examples use the official Qt 6.7.3 MSVC 2022 64-bit SDK. Set these paths to your installed kit:

$env:CMAKE_PREFIX_PATH = "C:\Qt\6.7.3\msvc2022_64"
$env:PATH = "C:\Qt\6.7.3\msvc2022_64\bin;" + $env:PATH
cmake --version
cl
windeployqt --version
python --version

Keep the compiler, Qt DLLs, and application on the same architecture. The packaging script uses the Visual C++ runtime supplied by the Visual Studio developer environment.

Get the source and build

Clone the repository with its Hayanagi submodule. An ordinary clone without submodules is incomplete.

git clone --recurse-submodules https://github.com/hnakada123/ShogiBoardQ.git
cd ShogiBoardQ

For an existing checkout, initialize the recorded submodule version with git submodule update --init --recursive.

cmake -B build -S . -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
.\build\ShogiBoardQ.exe

These commands build for local development. If you use the Visual Studio generator instead of Ninja, select Release when building and use the executable in build\Release. Start with a separate build directory when changing generators.

To enable and run the test suite:

cmake -B build -S . -DBUILD_TESTING=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure

Prepare Qt notices and corresponding sources

A normal local CMake build does not download Qt sources. The distribution scripts additionally require prepared license documents for the exact Qt build they deploy. They include those documents and source information in the package and stop if validation fails.

For the unmodified official Qt 6.7.3 SDK, run the following from the repository root. These commands use the version and SHA-256 recorded in the release workflow. For a different Qt build, use its matching full source archive, checksum, and provenance instead.

python scripts/qt_licenses.py fetch --version 6.7.3 --sha256 a3f1d257cbb14c6536585ffccf7c203ce7017418e1a0c2ed7c316c20c729c801 --output build/qt-sources
python scripts/qt_licenses.py prepare --version 6.7.3 --archive build/qt-sources/qt-everywhere-src-6.7.3.tar.xz --sha256 a3f1d257cbb14c6536585ffccf7c203ce7017418e1a0c2ed7c316c20c729c801 --source-url https://download.qt.io/archive/qt/6.7/6.7.3/single/qt-everywhere-src-6.7.3.tar.xz --provenance "Official Qt 6.7.3 SDK, unmodified; build scripts in source archive" --output build/qt-licenses

The source archive is a large separate download, roughly 900 MB. The preparation command does not overwrite an existing output directory. A clean build deletes build; if using the script's clean option, prepare the sources and notices outside that directory and set SHOGIBOARDQ_QT_LICENSE_DIR to the notices directory.

Publish the matching application source, including Hayanagi, and Qt sources alongside the binaries. GitHub's automatically generated source ZIP does not include submodule contents. For patched Qt builds, preserve the patches and build instructions too. The repository's Qt distribution notes (Japanese) describe the packaging policy and source manifests.

Create a ZIP package

After preparing the Qt notices and source archive, run the distribution script from Developer PowerShell:

.\scripts\build-windows.ps1

The script builds Release, uses windeployqt, copies translations, the Visual C++ runtime, and license documents, and checks the Qt DLLs and SQLite plugin. It produces deploy\ and ShogiBoardQ-windows.zip in the repository root.

Use -SkipZip to prepare only the deploy folder or -Help to show the options. The deploy folder still requires the Qt license preparation.

Extract the ZIP into an empty folder on a Windows machine without the development SDK and run ShogiBoardQ.exe. Check language switching, pieces, sound, and tsume progress. Distribute the complete folder; the executable alone does not contain Qt.

Code signing

If you sign your Windows release, sign the executable in the deploy folder before creating the final ZIP. The repository's release workflow uses SignTool from the Windows SDK with a certificate supplied through repository secrets, then packages the signed files.

Configure the workflow's Windows certificate, password, and timestamp settings in repository secrets. Keep certificates and passwords out of source control. Test the final signed archive, not only the executable in the build directory.

Publish on GitHub Releases

The repository includes a release workflow that builds all three platforms, prepares corresponding sources and license documents, and uploads binaries, source archives, checksums, and an SBOM to the same GitHub Release.

For maintainers with push access, pushing a release tag beginning with v triggers this workflow. It can also be run from the Actions tab with an existing release tag. Choose the intended release commit and tag, then review the workflow results and attached files.

For a manual release, open the repository's Releases page and create a release for the intended tag. Attach the tested ZIP, the application source archive containing Hayanagi, the matching Qt source archive, and source/build information and checksums. Retain these source downloads while the binaries remain available. The application package must contain its prepared license documents as well.

Troubleshooting

  • The compiler or Windows SDK cannot be found: open Developer PowerShell and confirm that the Desktop development with C++ workload is installed.
  • Qt6Config.cmake or Qt Charts is missing: check the kit path and install the required modules. Do not mix MinGW and MSVC Qt libraries.
  • Hayanagi source files are missing: run git submodule update --init --recursive.
  • windeployqt is not found: add the selected Qt kit's bin directory to PATH.
  • A DLL or plugin is missing on another PC: distribute the entire deploy folder and inspect the packaging log. Check sqldrivers\qsqlite.dll if puzzle history is unavailable.
  • PowerShell blocks the script: review your execution policy and the script before enabling it under your system's policy.
  • Qt notice validation fails: use the notices for the exact Qt build being deployed. For a clean build, store prepared notices outside build and set the notice-directory environment variable.
