Tsume Shogi Generator

Generate tsume shogi with a USI engine, from short random positions to long mates via retrograde editing

Random / Retrograde & Edit Cook, Surplus & Piece Checks Checkpoint Save & Resume CLI and Python

Screenshots were captured on Linux with the English interface.

Overview

Generate puzzles with Random Placement for short mates or Retrograde & Edit for long mates, verifying uniqueness and piece necessity before output

1

Features

The tsume shogi generator automatically performs the following steps.

  • Switch between two methods: Random Placement for short mates and Retrograde & Edit from Mate (Long Mates) for longer puzzles up to 301 plies.
  • In Random Placement, screen candidates with the built-in mate search; in Retrograde & Edit, grow positions from mate endings or seed positions via retrograde moves, mutations, and cook repair, confirming mates of the target length with a USI engine (go mate).
  • Check the main line for alternative mates, remove unnecessary pieces (all single-piece removals), and in Retrograde & Edit mode optionally disallow surplus pieces and exclude similar problems.
  • Save and resume Retrograde & Edit runs using JSON checkpoints that preserve the search frontier and strict-verification cache.
  • List the results as SFEN for saving to a file or copying to the clipboard.

Mate searches can use KomoringHeights, a tsume shogi engine developed and published by komori-n. Download the engine separately, register it under Settings → Engine Settings… (Registering an Engine), and select it as the Engine in the generator dialog. Use it with settings that return the shortest solution (PostSearchLevel = MinLength for KomoringHeights, the default).

3

How Random Positions Are Generated

In Random Placement mode, positions are built automatically as follows.

  1. Place White's king on a random square of the 9×9 board.
  2. Place attacking pieces around the king, randomly assigning them to the board or the attacker's hand.
  3. Place defending pieces around the king.
  4. Leave out the attacker's king and add all other unused pieces to the defender's (White's) hand.
  5. Confirm that the king is not in check in the starting position.

Generated positions are first screened by the built-in mate search, which removes positions proven not to mate in the target length and positions with several mating first moves. Candidates the built-in search cannot decide are also sent to the USI engine, and only positions whose mate of the requested length the engine confirms proceed to the alternative-mate check. The Searched count includes positions removed by the built-in screening.

Retrograde & Edit from Mate (Long Mates)

For long mates of 15+ plies, or when you want to save and resume long runs across sessions, select Retrograde & Edit from Mate (Long Mates) in Method.

Retrograde & Edit mode settings (example configured for a 15-move mate)

Mode-specific settingDescription
Beam widthMaximum promising positions kept per ply layer (1–2000, default 16). Larger values maintain greater variety.
Search time/stepTime limit per position during retrograde growth (1–300 sec, default 5 sec). Automatically extended up to 3× (capped at 60 sec) during strict proof and piece trimming.
Branch factorNumber of candidate positions generated per expansion via retrograde moves and board mutations (4–200, default 32).
Verify budgetMaximum total time budget per candidate for strict proof and all-single-piece-removal trimming (5–86400 sec, default 300 sec).
Disallow surplus piecesOn by default. Accepts only positions where the attacker has no remaining hand pieces on every longest defense and final mating move.
Exclude similar problemsOn by default. Excludes translated, mirrored, and single-move-different middle-line variants.
Seed file (optional)An optional file containing starting positions (one SFEN or SFEN moves … per line; lines beginning with # are ignored). When empty, positions are grown automatically from 0-ply mate endings. Use Browse... and Clear to choose or clear the file.
Exclude file (optional)Specify an existing puzzle collection to skip already-included positions and similar lines while generating new puzzles (one SFEN or SFEN moves … per line; # lines ignored). Also applies when resuming from a checkpoint.
Checkpoint (optional) / Resume from checkpointPeriodically writes the search frontier, accepted puzzles, and strict-verification cache atomically to a JSON file. After stopping or interrupting a run, check Resume from checkpoint and click Start to restore already-accepted puzzles into the results list and continue (Seed file is disabled while Resume from checkpoint is checked).

Retrograde & Edit mode grows and certifies long mates through the following pipeline.

  1. Expand candidates from 0-ply mate endings or seed positions using defender/attacker retrograde moves and board mutations, keeping promising positions in each ply layer via multi-layer beam search.
  2. When a candidate has an alternative mate, attempt targeted cook repair (adding or adjusting pieces to block the cook line).
  3. Once a candidate reaches the target length, prove the exact shortest mate with natural completion of go mate infinite, verify every main-line attacking move, check zero surplus when enabled, and verify all single-piece removals before accepting the position.

Remove Unnecessary Pieces

Trimming automatically removes decorative pieces from generated positions: pieces that do not affect the mating solution.

  • Try removing the attacking and defending pieces on the board and the pieces in the attacker's hand, one at a time.
  • Keep a removal if the position still mates in the target length with a unique main line (and zero surplus when enabled in Retrograde & Edit mode).
  • Move removed pieces to the defender's hand to keep all 40 pieces.
  • Check again after each removal to find pieces that have become unnecessary.
  • Do not output a puzzle if a check after a removal times out or is inconclusive, or if trimming is interrupted by stopping or an error.

This check establishes that no single piece can be removed while keeping a puzzle with the same conditions. It does not guarantee the minimum number of pieces when several pieces are removed at once or the placement itself changes.

Generate Tsume Shogi with the CLI

Set up generate-tsume and grow-tsume, save/resume checkpoints, run parallel Python workers, and audit collections

1

Prepare the CLI and a mate-search engine

shogiboardq-cli shares the GUI generation pipeline and provides two subcommands: generate-tsume for short random-placement puzzles and grow-tsume for long mates via retrograde search, mutation, and strict verification. Both emit JSON Lines after checking mate length, main-line uniqueness, and unnecessary pieces. Python can launch the CLI directly as a child process; no MCP server is needed.

The examples below use a Linux shell and Python 3. Run them from the repository root. See Building on Linux for prerequisites. On other platforms, adjust the CLI executable name and path for your environment.

Build the CLI and list registered engines

cmake -B build -S . -DCMAKE_BUILD_TYPE=Release
cmake --build build --target shogiboardq-cli --parallel 4
./build/shogiboardq-cli list-engines

First register an engine that supports go mate. Pass the exact registered name returned by list-engines to --engine, not an executable path. Replace the example name below with your actual name, including spaces.

For KomoringHeights, a starting configuration for parallel generation is Threads=1, USI_Hash=256 (or 64–128 with many workers or grow-tsume), PostSearchLevel=MinLength, and GenerateAllLegalMoves=true. Configure these through Engine Settings and check which options your engine supports.

2

Generate one batch with generate-tsume and inspect JSON Lines

Start with up to ten 3-ply puzzles using generate-tsume to check your engine configuration and output. The JSON Lines event log is a different format from the puzzle collection text file.

Generate up to ten 3-ply puzzles

./build/shogiboardq-cli generate-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --target-moves 3 --max-positions 10 \
  --timeout-ms 5000 --max-attack 4 --max-defend 1 \
  --attack-range 3 --stdin-control > tsume-batch.jsonl
OptionMeaning and range
--target-movesMate length: an odd number from 1 to 301; default 3
--max-positionsLimit per process: 1–10000 positions; default 10
--timeout-msTime budget for candidate searches, trimming, and verification: 1000–300000 ms; default 5000
--max-attackMaximum attacking pieces on board and in hand combined: 1–10; default 4
--max-defendMaximum defending pieces on the board, excluding the king: 0–10; default 1
--attack-rangeAttacking-piece placement range around the king: 1–8 squares; default 3
--stdin-controlStop on a line containing stop or on end-of-file on stdin
--no-final-alternativesRequire a unique final mating move (canonical name --no-allow-final-move-alternatives); final-move alternatives are allowed by default
--no-remaining-to-handDo not give unused pieces to the defender; omit this for standard tsume shogi

started reports settings, progress reports generated, found, rejected, and inconclusive counts, position supplies an accepted puzzle, and finished marks completion. Read the SFEN and solution from position.sfen and position.pv, an array of USI moves. Also check error events and the process exit code.

Key fields of a position event

{"event":"position","sfen":"9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1","pv":["2c2b+","1b1c","2e2c+"]}

With --stdin-control, type stop and press Enter to stop. Closing stdin also stops generation, so Python must keep stdin=PIPE open until it sends a stop request. An environment that starts the process with closed stdin may cause it to stop immediately.

3

Generate and resume long mates with grow-tsume

Use grow-tsume to construct 15–301 ply mates under strict criteria (every main-line attacking move including the final move unique, zero surplus attacker hand pieces, zero unnecessary pieces across all single-piece removals, and natural completion of go mate infinite). Every file-path option requires an absolute path.

Generate 15-ply puzzles with checkpoint and output files

./build/shogiboardq-cli grow-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --target-moves 15 --max-positions 5 \
  --beam-width 16 --branch-factor 32 \
  --max-attack 18 --max-defend 12 \
  --step-timeout-ms 5000 --verify-query-timeout-ms 15000 \
  --verify-budget-seconds 300 --hash-mb 64 --threads 1 \
  --checkpoint "$PWD/tsume-work/grow15.ckpt.json" \
  --output "$PWD/tsume-work/grow15.txt" \
  --stdin-control > tsume-work/grow15.jsonl

Resume from an interrupted checkpoint

./build/shogiboardq-cli grow-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --checkpoint "$PWD/tsume-work/grow15.ckpt.json" --resume \
  --output "$PWD/tsume-work/grow15.txt" \
  --hash-mb 64 --threads 1 --stdin-control >> tsume-work/grow15.jsonl
OptionMeaning and range
--target-movesTarget mate length: odd number from 1 to 301; default 101
--max-positionsMaximum certified positions to emit: 1–1000; default 1
--beam-width / --branch-factorBeam nodes kept per ply layer (1–2000, default 12) and candidates per expansion (4–200, default 24)
--max-attack / --max-defendAttacking pieces limit (1–38, default 20) and defending board pieces excluding king (0–38, default 14). Total board pieces use --max-total-board-pieces (2–39, default 30)
--step-timeout-msEngine query limit during growth: 100–600000 ms; default 5000
--verify-query-timeout-ms / --verify-budget-secondsPer-query limit (500–600000 ms, default 15000) and per-candidate total budget (5–86400 sec, default 1800) for strict certification and trimming
--hash-mb / --threadsOverride engine USI_Hash (0–65536 MiB) and Threads (0–256); 0 keeps registered values
--seed-sfen / --seed-fileOptional starting SFEN or seed file (absolute path; accepts SFEN or SFEN moves …). When omitted, grows automatically from 0-ply mate endings
--exclude-file / --no-exclude-similarExisting puzzle file (absolute path) to skip duplicates and similar lines; pass --no-exclude-similar to disable similarity filtering

--outputAppend certified puzzles as SFEN moves … to this file (absolute path)
--allow-final-move-alternatives / --no-require-no-surplus / --no-strict-min-lengthRelax strict defaults. By default, final moves must be unique, attacker surplus pieces are forbidden, and go mate infinite must complete naturally
--stdin-controlStop on stop or EOF; also accepts live exclude <SFEN moves …> and seed <SFEN> lines for multi-worker synchronization

To build multi-ply long-mate collections (such as 15–31 plies) across parallel workers, use the bundled scripts/generate_long_tsume_collections.py orchestrator. It provides a shared similarity filter across workers, real-time exclude/seed synchronization over stdin, automatic skipping of already-expanded parent seeds, per-puzzle JSONL checkpointing, and resumable runs.

Parallel long-mate collection generation and resume (bundled script)

python3 scripts/generate_long_tsume_collections.py \

  --work-dir tsume-work/long-run \
  --publish-dir tsume-work/published \
  --plies 15 17 19 --count 100 --workers 4 --hash-mb 64
4

Run parallel workers from Python and save progress

This minimal script runs generate-tsume workers in parallel for short mates. Save the code below as generate_tsume_parallel.py and run python3 generate_tsume_parallel.py from the repository root. It only uses the Python standard library. Start with TARGET=10 and WORKERS=1, then increase concurrency if CPU and memory capacity allow.

PLIES is the mate length, TARGET is the combined collection target, and WORKERS is the number of concurrent processes. Adjust TIMEOUT_MS, piece limits, and placement range at the top. Collection runs in bounded batches until the target is reached.

Show Python code: collect 100 three-ply puzzles with four workers

generate_tsume_parallel.py

import asyncio
import json
import os
from pathlib import Path

CLI = str(Path("build/shogiboardq-cli").resolve())
ENGINE = "KomoringHeights  1.1.0 64ZEN2"  # Use the exact name from list-engines
PLIES = 3
TARGET = 100
WORKERS = 4
TIMEOUT_MS = 5000
MAX_ATTACK = 4
MAX_DEFEND = 1
ATTACK_RANGE = 3
ALLOW_FINAL_ALTERNATIVES = True
OUTPUT = Path(f"tsume-work/tsume_{PLIES}ply_candidates.txt")
ENV = dict(os.environ)
# Optional: use a separately prepared configuration on Linux
# ENV["XDG_CONFIG_HOME"] = "/path/to/tsume-config"

positions = {}
active = set()


def remember(sfen, pv):
    fields = sfen.split()
    if len(fields) != 4 or len(pv) != PLIES:
        raise ValueError("Invalid SFEN or PV length")
    key = " ".join(fields[:3])  # Board, turn, and hands; ignore the move number
    if key not in positions and len(positions) < TARGET:
        positions[key] = sfen + " moves " + " ".join(pv)


def checkpoint():
    temporary = OUTPUT.with_suffix(".tmp")
    text = "# CLI candidates (before independent collection validation)\n"
    text += "\n".join(positions.values()) + "\n"
    temporary.write_text(text, encoding="utf-8")
    temporary.replace(OUTPUT)


async def stop(process):
    if process.returncode is None:
        try:
            process.stdin.write(b"stop\n")
            await process.stdin.drain()
        except (BrokenPipeError, ConnectionResetError):
            pass


async def close_process(process):
    await stop(process)
    try:
        await asyncio.wait_for(process.wait(), timeout=15)
    except asyncio.TimeoutError:
        process.kill()
        await process.wait()
    active.discard(process)


async def worker(number):
    while len(positions) < TARGET:
        args = [
            CLI, "generate-tsume", "--engine", ENGINE,
            "--target-moves", str(PLIES),
            "--max-positions", str(min(100, TARGET - len(positions))),
            "--timeout-ms", str(TIMEOUT_MS),
            "--max-attack", str(MAX_ATTACK), "--max-defend", str(MAX_DEFEND),
            "--attack-range", str(ATTACK_RANGE), "--stdin-control",
        ]
        if not ALLOW_FINAL_ALTERNATIVES:
            args.append("--no-final-alternatives")
        log_path = OUTPUT.parent / f"worker-{PLIES}ply-{number}.jsonl"
        err_path = OUTPUT.parent / f"worker-{PLIES}ply-{number}.stderr.log"
        with log_path.open("a", encoding="utf-8") as log, err_path.open("ab") as err:
            process = await asyncio.create_subprocess_exec(
                *args, env=ENV,
                stdin=asyncio.subprocess.PIPE,
                stdout=asyncio.subprocess.PIPE, stderr=err,
            )
            active.add(process)
            try:
                # Another worker may have reached the target during startup.
                if len(positions) >= TARGET:
                    await stop(process)
                async for raw in process.stdout:
                    line = raw.decode("utf-8")
                    log.write(line)
                    log.flush()
                    event = json.loads(line)
                    if event["event"] == "error":
                        raise RuntimeError(event["message"])
                    if event["event"] != "position":
                        continue
                    remember(event["sfen"], event["pv"])
                    checkpoint()
                    print(f"{len(positions)}/{TARGET}", flush=True)
                    if len(positions) == TARGET:
                        await asyncio.gather(*(stop(p) for p in list(active)))
                if await process.wait() != 0:
                    raise RuntimeError(f"CLI failed; see {err_path}")
            finally:
                await close_process(process)


async def main():
    if TARGET < 1 or WORKERS < 1:
        raise ValueError("TARGET and WORKERS must be positive")
    OUTPUT.parent.mkdir(parents=True, exist_ok=True)
    if OUTPUT.exists():
        for line in OUTPUT.read_text(encoding="utf-8").splitlines():
            if line and not line.startswith("#"):
                sfen, moves = line.split(" moves ", 1)
                remember(sfen, moves.split())
    tasks = [asyncio.create_task(worker(i)) for i in range(WORKERS)]
    try:
        await asyncio.gather(*tasks)
    finally:
        for task in tasks:
            task.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)
        await asyncio.gather(*(close_process(p) for p in list(active)))
        checkpoint()
    print(f"Collected: {OUTPUT} (validate the collection separately)")


if __name__ == "__main__":
    asyncio.run(main())

All workers share a dictionary keyed by the SFEN board, turn, and hands. Results are saved through temporary-file replacement after each discovery and reloaded on restart. JSON Lines and stderr logs are kept separately for each mate length and worker. Once the target is reached, all CLI processes receive a stop request. After Ctrl+C, restart to resume from saved results.

This code collects positions and removes duplicate SFENs. It does not exclude similar puzzles with the same solution but different piece types, or mirrored positions. Independent validation of the whole collection is a separate step.

5

Notes on running, stopping, and resuming

  • Total runtime: --timeout-ms and --verify-budget-seconds are not deadlines for the entire command. Long mates or strict settings may yield few positions, so time to reach the target is not guaranteed. Start with a small target, inspect progress, and stop to adjust settings if needed. Inconclusive results are neither proof of no mate nor successful verification.
  • CPU and memory: Both the worker count and the engine thread count and hash size affect resource use. Running multiple workers with KomoringHeights defaults (e.g., USI_Hash=4096, Threads=4) can quickly exhaust RAM; pass --hash-mb 64 --threads 1 to grow-tsume or configure lower values in Engine Settings beforehand.
  • Configuration: If CLI engines differ from those in the GUI, check that you are using the same user and settings. On Linux, when changing XDG_CONFIG_HOME, prepare engine registrations and options in ShogiBoardQ/ShogiBoardQ.ini under that directory. Use the same environment for list-engines and Python.
  • Resuming: Do not let multiple processes write to the same OUTPUT or --checkpoint file at once. The generate_tsume_parallel.py example does not reverify existing lines; if mate length, engine, or alternative-mate policy changes, use a new output file or reverify existing entries. Settings are also recorded in the started event logs.
  • Alternative mates and surplus: generate-tsume allows multiple final mating moves by default (pass --no-final-alternatives to forbid them). In contrast, grow-tsume defaults to strict uniqueness on the final move, zero surplus pieces, and natural completion of go mate infinite. Keep verification flags consistent when reverifying.
  • Output files: tsume-batch.jsonl and grow15.jsonl are event logs. Use the puzzle text files written by --output or Python for collections. If a CLI process fails, inspect its JSON Lines and stderr logs.
6

Save solution text and validate the collection

Use UTF-8 and one puzzle per line in the form SFEN moves USI-moves…. Comments beginning with # can record the date, engine, mate length, piece limits, time budgets, and alternative-mate policy.

A three-ply puzzle, saved as one line

9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1 moves 2c2b+ 1b1c 2e2c+

Use verify-tsume (supports odd lengths from 1 to 301) to recheck main-line uniqueness. This example checks one position; for a collection, pass each SFEN in turn.

Recheck main-line uniqueness

./build/shogiboardq-cli verify-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --target-moves 3 --timeout-ms 15000 \
  --sfen '9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1'

The JSON field ok reports command success. Also require status to be unique before accepting the result, and defer or retry unknown results. This command checks main-line uniqueness; it does not replace auditing every saved PV move and the necessity of each piece.

For independent collection validation, the tools included in the source check shortest mate length, legal solutions, main-line uniqueness, and every single-piece removal. Their --engine argument takes an engine executable path, unlike the CLI registered name.

Independently audit the collected file

cmake -B build -S . -DBUILD_TESTING=ON
cmake --build build --target tsumeshogi_collection_auditor --parallel 4
python3 scripts/audit_tsume_collections.py tsume-work/tsume_3ply_candidates.txt \
  --engine /path/to/KomoringHeights-by-gcc \
  --output-dir tsume-work/audit-3ply --workers 4 --timeout-ms 30000

Inspect statuses, unique_minimal, and changed in summary.json. Do not count unknown entries as complete; retry with a larger budget or exclude them. Verified results are saved in tsume_3ply_minimal.txt. If trimming or duplicate/similarity filtering reduces the count, replenish and audit again. See the collection README (Japanese) for detailed validation conditions.

The piece audit establishes that no single-piece removal preserves the acceptance conditions. It does not guarantee the minimum piece count under simultaneous removals or changes of piece type.

Build a Varied Puzzle Collection

Check solution similarity and puzzle order as well as position validity

1

Check solution similarity as well as duplicate positions

Different SFENs can still produce similar solving experiences through the same king chase, reflection, translation, or substitutions such as gold and promoted knight. Removing duplicate positions with generate-tsume and the Python example does not guarantee variety in a collection.

2

Filter and replenish with collection-editing tools

For 3–13 ply collections, scripts/refill_diverse_tsume.py takes verified collections, shares a similarity index across workers, and generates replacements for missing entries. After replenishment, run an independent audit with scripts/audit_tsume_collections.py, and once all results are conclusive, use scripts/publish_diverse_tsume.py to order puzzles to reduce overlap with the preceding ten solutions.

For 15–31 ply long-mate collections, grow-tsume’s built-in similarity filter and scripts/generate_long_tsume_collections.py (with a cross-worker similarity index and spread ordering) are used before running the same independent audit.

Similarity filtering is an editorial rule based on the main line, not a complete assessment of a puzzle’s value including variations and misleading alternatives. See the collection README (Japanese) for input requirements, resuming, exclusions, and publication.
