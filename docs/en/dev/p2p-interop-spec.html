1. About This Document

1.1 Purpose and Scope

This document is a specification for building, as a separate implementation, software that can play against the "P2P games" of ShogiBoardQ (a build with P2P games enabled). It defines the byte sequences that travel over the network, the procedures, the checks, the time rules, and the file format of game records (evidence). Implementations built according to this document can connect to each other by passing an invitation string, play a game, and keep a game record confirmed by both sides.

It covers protocol version 1 (frame version 1, and version 1 of each value). The following are out of scope, and each implementation may decide them freely.

  • The screens and controls, how settings are saved, and how the player key is stored (the OS keychain, an encrypted file, and so on)
  • How the part that handles communication is separated from the part that handles the game and the screens (ShogiBoardQ splits them into separate processes connected by JSON IPC, but this has no bearing on compatibility)
  • Safety measures inside the implementation, such as restricting privileges (sandboxing)

1.2 Requirement Wording

An implementation that receives input that this document says to "refuse" or "reject" must not treat it as valid input. How the refusal is signaled (sending REJECT, closing the stream, or silently discarding it) is stated in each section.

1.3 Overall Flow

There are two players. The side that invites is called the inviter (the "host" inside the protocol, role = 2), and the side that receives the invitation and connects is called the joiner (role = 1).

  1. Connection: Both sides start a libp2p node (section 4). Over the Internet, each also connects to the cooperating nodes the user specified (nodes that provide relaying and the reachability check).
  2. Invitation: The inviter creates an invitation string, and the user passes it to the opponent by another channel (such as a message) (section 5).
  3. Stream: The joiner connects to the addresses in the invitation string, opens a game stream, and first sends the invitation token (INVITE_TOKEN) (section 6).
  4. Start negotiation: The sides exchange HELLO, decide the conditions and the sides, and both sign the start agreement (StartAgreement) with their player keys (section 8).
  5. Game: For each move, the side that moved proposes a state (State), and the opponent checks and approves it. Both sign with their per-game keys (section 9).
  6. Game end: The sides compare the result (FinalResult), and both sign it with their player keys (section 10).
  7. Record: Each side saves the start agreement, all the moves, and the signatures in one file (the evidence). Anyone can verify it (section 13).

There is no game server. The correctness of the game is maintained by each side checking the values it receives itself, without trusting the opponent's app. When the connection drops, the sides can reconnect to the same game (section 11).

1.4 What Cannot Be Prevented

This protocol does not prevent the following. Compatible implementations should explain this to their users.

  • Display names are self-declared. The only grounds for telling opponents apart are the public key of the player key (the player ID) and the verification code (section 3.5).
  • If the losing side does not sign the result, no record signed by both sides remains.
  • Time used is self-reported. Padding of up to 10 seconds per move and stalling by disconnecting (up to 10 minutes in total per game) cannot be detected.
  • Games played by engines and arranged games cannot be detected.
  • With a direct connection, the opponent can learn your IP address by examining the traffic (this can be avoided with the setting that uses only the relay; section 4.6).

2. Notation and Common Rules

2.1 How Values Are Written

This document writes CBOR values as follows.

NotationMeaning
uintUnsigned integer (0 to 264−1)
bstr, bstr(32)Byte string. The number in parentheses is the length (in bytes)
tstrText string (UTF-8)
[a, b, ...]Array. The number and order of the elements are fixed, and elements not listed must not be added
"SBQ-..."A tstr of exactly that string (a label that indicates the kind of value)
zero32A bstr of 32 zero bytes

Booleans are written as the uint 0 or 1. Times are UNIX seconds (uint), and durations are milliseconds (uint). Hexadecimal is written in lowercase.

2.2 Deterministic CBOR

The CBOR used for signatures, hashes, frames, invitation strings, and evidence uses only the following subset of the core deterministic encoding of RFC 8949. The reading side must reject everything not listed here.

  • Only four types can be used: unsigned integers (major type 0), byte strings (2), text strings (3), and arrays (4). Negative integers, maps, tags, floating-point numbers, and simple values (true/false/null/undefined) are not used.
  • Lengths and integers are written in the shortest form (0 to 23 in the initial byte, 24 to 255 in one following byte, 256 to 65535 in two bytes, 65536 to 232−1 in four bytes, and anything larger in eight bytes). Forms that are not the shortest are rejected.
  • Indefinite lengths (additional information 31) and reserved values (28 to 30) are rejected.
  • Text strings must be valid UTF-8 (overlong forms, surrogates, and values above U+10FFFF are rejected).
  • Nesting is limited to 16 levels. The top-level value counts as level 1, and a value inside an array counts as one level deeper, even if it is not an array (nesting arrays 16 deep and putting one value in the innermost array makes 17 levels, which is rejected).
  • The input is exactly one value; if any bytes remain after it, it is rejected.
  • After reading a length, check that it fits in the remaining input before allocating memory.

With these rules, the byte sequence for a given value is unique. Re-encoding a value that has been read yields the original byte sequence. Below, CBOR(x) denotes this byte sequence of the value x.

2.3 Hashes

The hash function H is SHA-256 (32-byte output). H(CBOR(x)) denotes the SHA-256 of the deterministic CBOR byte sequence of the value x. In this document, a value whose name ends in "…Hash" is H(CBOR(value)) unless stated otherwise.

2.4 Signatures

Signatures are Ed25519 (RFC 8032), with 32-byte public keys and 64-byte signatures. What is signed is exactly the deterministic CBOR byte sequence of the value (CBOR(value)), with no prefix or context string added. The label at the start of the value (such as "SBQ-START") serves to separate the purposes of signatures.

A signature is "valid" only when it passes both of the following.

  1. Public key check: The public key is a point that passes libsodium's crypto_core_ed25519_is_valid_point (canonically encoded, on the curve, in the prime-order subgroup, and not of small order).
  2. Signature check: The result is the same as libsodium's crypto_sign_verify_detached (including libsodium's default check that rejects non-canonical signatures).

Check 1 is performed for every signature verification (it applies both to public keys received in HELLO and to evidence verification). An implementation that performs only check 2 accepts, unlike ShogiBoardQ, signatures by public keys that are not in the prime-order subgroup. The secret key is derived from a 32-byte seed as specified in RFC 8032.

2.5 String Restrictions

A value described as an "ASCII tstr" must consist only of the characters 0x20 to 0x7E. The maximum length is given in each section. Values that exceed the maximum or contain characters outside the range are rejected.

3. Networks and Identifiers

3.1 Networks

Only implementations that chose the same networkName can play each other. A network is identified by networkId, a 32-byte value determined by its name.

networkId = H(CBOR(["SBQ-NETWORK", 1, networkName]))     ; networkName is an ASCII tstr (1 to 32 bytes)

sbq-limited-1Limited test. Connects with opponents on the Internete2972f65cf26d46415718eb13b8a97e42478963e698c8e550d6ed0d197cb1d93

An implementation must keep a list of the networkNames it can join and refuse any other name. ShogiBoardQ does not join sbq-limited-1 once 180 days have passed since the build (the expiry of the experimental build; compatible implementations do not need to have the same expiry).

The libp2p layer has no mechanism for separating networks (such as a private network key). The network is checked by the networkId in the invitation string (section 5) and in HELLO (section 8.2).

3.2 PeerId

The key of the libp2p node must be Ed25519. The binary representation of the PeerId is the 38-byte identity multihash that contains the Ed25519 public key as is.

peerId = 00 24 08 01 12 20 || public key (32 bytes)

A PeerId that does not have this form (an RSA key, a SHA-256 multihash, and so on) is refused, both in invitation strings and in HELLO. Its text form is base58 (12D3KooW…).

The PeerId may be created anew each time the node starts (ShogiBoardQ creates a new key for every connection). However, the same PeerId must be used throughout a game, because the start agreement contains a hash of the PeerIds and reconnection is accepted only from the same PeerId (section 11).

3.3 Player Key and Player ID

Each user has one long-lived Ed25519 key. It is called the player key, and its public key (32 bytes) is called the player ID. The player key is used only to sign the start agreement (StartAgreement) and the result (FinalResult). It must be a different key from the PeerId key.

On screen, the player ID is shown as 64 lowercase hexadecimal digits, separated by a space every 8 digits (example: cf3b0b03 a6e888db …). Users must not be made to judge whether an opponent is the same person from a shortened display alone.

3.4 Per-Game Key

A new Ed25519 key is created for each negotiation. It is called the per-game key and is used to sign state approvals (StateApproval) and control messages (Control) during the game. It is discarded when the game ends and is not saved. It must be different from both the player key and the opponent's keys.

3.5 Verification Code

From the two player IDs, a verification code is made that shows the same digits on both screens. The users compare the digits through another channel, such as a phone call or in person, to confirm that the opponent's player ID belongs to that person.

digest = H(CBOR(["SBQ-VERIFY", 1, keyLow, keyHigh]))    ; the two public keys, the smaller first in lexicographic (unsigned) byte order
group g (0 to 5) = read the 5 bytes digest[5g .. 5g+4] as a big-endian integer, and write the remainder after dividing by 100000 as 5 digits (zero-padded)

The verification code is six groups of these 5 digits (30 digits in total).

  • Does not start or end with a space (U+0020)
  • Every character is in one of the ranges in the following table (both ends inclusive)

4.2 Listening

NetworkListening
sbq-local-1All IPv4 interfaces. TCP and UDP (QUIC) port 48210. If it is in use, a free port is used. Does not listen on IPv6
sbq-limited-1All IPv4 and IPv6 interfaces. A free TCP and UDP (QUIC) port

The port number is included in the addresses in the invitation string, so connections work even if a compatible implementation listens on a different port. Port 48210 is a default so that users can decide which port to allow in their firewall.

An implementation must not listen on a port on which another process is listening. libp2p's TCP listener is opened with the setting that lets multiple processes share the same port (SO_REUSEPORT), so it can be opened even when the port is in use, and incoming connections are then distributed between two processes (a second app on the same PC, or another implementation). ShogiBoardQ first tries TCP port 48210 with a non-shared listener to confirm that it is not in use, and only then opens it. If a process started at the same time does the same between the check and the opening, both could open it, so UDP (QUIC; opened without the sharing setting) is opened first, and only the process that opened UDP port 48210 also uses port 48210 for TCP.

4.3 Identify

The Identify protocolVersion is /shogiboardq/1.0.0, and agentVersion is the name and version of the implementation (for ShogiBoardQ, shogiboardq-peer/<version>). A connection must not be refused because of the peer's values of these (the network is checked by networkId).

The own addresses advertised via Identify (listenAddrs) must not include the listen addresses as they are. Only addresses that have been confirmed or determined to be actually reachable by peers may be included (on sbq-limited-1, Internet addresses confirmed by the reachability check and addresses through a relay; a cooperating node may also include its listen addresses on the Internet; section 4.4). On sbq-local-1, none are included (Identify also reaches peers that have no invitation, so the list of the PC's private addresses is not handed out to LAN devices that merely connected to the listening port; the addresses for the opponent are passed in the invitation string). Changes to the listen addresses are not announced with Identify push.

4.4 Cooperating Nodes and Relays

Over the Internet (sbq-limited-1), the user specifies the addresses of cooperating nodes (of the form /ip4/…/tcp/…/p2p/<PeerId>; up to 16). A cooperating node is a libp2p node that supports the Circuit Relay v2 hop, Identify, and Ping (and answers AutoNAT); it does not read the contents of game frames. Any standard Circuit Relay v2 relay node can be used as a cooperating node.

  • An implementation reserves a relay slot on each cooperating node whose Identify protocols include the relay hop, regardless of its own reachability (up to 2 reservations). When a reservation is refused, or is lost because the connection to the cooperating node dropped, the implementation should wait a little and request it again (ShogiBoardQ waits 30 seconds). Unless it requests again, invitation strings contain no address through the relay until it reconnects.
  • The own address through a relay has the form <cooperating node address>/p2p/<cooperating node PeerId>/p2p-circuit; it is built from the cooperating node address that the user specified and put in the invitation string (an opponent who specified the same cooperating node can use it as is).
  • A cooperating node must return its own addresses in the reservation response. libp2p implementations (such as rust-libp2p, which ShogiBoardQ uses) treat a response without addresses as a failed reservation. A relay node that has just started has no addresses of its own until the reachability check (AutoNAT) completes, and can fail every reservation in the meantime. A cooperating node should take an Internet address it listens on as its own address without waiting for the check (ShogiBoardQ's cooperating node does so).
  • For addresses through a relay as well, the rules of section 4.5 are applied to the leading IP address (that of the cooperating node).
  • ShogiBoardQ's cooperating node (shogiboardq-peer --service --relay) cuts each relayed connection at 30 minutes or 8 MiB. When it is cut, the game reconnects using the reconnection procedure (section 11).

4.6 The Do Not Use Direct Connections Setting

This is a setting for not showing your IP address to the opponent (implementing it is optional). An implementation of this setting must observe the following.

  • Direct connections go only to the addresses of the cooperating nodes the user specified (and other addresses those nodes announced via Identify). Direct connections to any other address are refused, whatever path initiated them.
  • Addresses through a relay are used only when the relay is a specified cooperating node (a relay that was not specified would see your IP).
  • Only addresses through a relay are advertised as your own (invitations and Identify).
  • AutoNAT and DCUtR are not performed, because both hand candidates of your own address to the peer.

When the opponent invites with this setting, simply connect normally to the relay addresses in the invitation string; there is no difference in the protocol.

When the side with this setting is the joiner, it connects only to those addresses in the invitation string whose relay is a cooperating node it specified. Therefore the inviter needs to reserve a relay slot on the same cooperating node that the joiner specified and put the address through that relay in the invitation string (both sides specify the same cooperating node). If there is no usable address, the joiner does not start a connection.

5. Invitation Strings

The opponent of a game is decided by an invitation string. The inviter creates it, and the user passes it to the opponent by another channel. The invitation string contains the addresses for connecting to the inviter and a token that can be used only once.

5.1 Format

invite = "sbqinv1." + base64url(body) + "." + hex(H(body)[0..4])
body   = CBOR(["SBQ-INVITE", 1, networkId, peerId, [addr, ...], token, expiresAt])
FieldTypeRules
networkIdbstr(32)Section 3.1
peerIdbstr(38)Binary representation of the inviter's PeerId (only the form in section 3.2)
addrbstrBinary representation of a candidate multiaddr for reaching the inviter. The trailing /p2p/<inviter> is not appended (the /p2p/<cooperating node> inside an address through a relay is kept). 0 to 8 entries, each 1 to 100 bytes
tokenbstr(32)Created with a cryptographic random number generator
expiresAtuintExpiry time (UNIX seconds). 600 seconds after creation
  • base64url uses the URL-safe alphabet of RFC 4648, without = padding.
  • The check value at the end is the first 4 bytes of the SHA-256 of body in lowercase hex (8 characters). It is for catching typos and truncation and is not a secret.
  • The whole string must be at most 1024 bytes.

5.2 The Creating Side

  • Only addresses that the opponent can actually use are included as candidates (section 4.5, section 4.6). On sbq-local-1, the private addresses used by an opponent on the same LAN come first, and the loopback addresses, usable only on the same PC, come last.
  • Up to 4 invitations can be valid at the same time; creating a fifth invalidates the oldest.
  • An invitation can be used only once. When a stream with a matching token is accepted, that invitation is marked as used (section 6.3).
  • The token must not be written to logs or the like. Users are advised to pass the invitation string by a channel that reaches only the opponent (because it contains the addresses to connect to).

5.3 The Reading Side

Before reading, remove only leading and trailing whitespace (ASCII space, tab, CR, LF). Then check all of the following; if any one of them fails, the invitation is not used.

  1. The whole is at most 1024 bytes, the prefix is sbqinv1., and the rest splits at . into exactly two parts.
  2. The first part can be read as base64url, and the second part matches the first 4 bytes of the SHA-256 of body in lowercase hex.
  3. body is deterministic CBOR, an array of 7 elements, and the label, the version, and the type and length of each field are as in section 5.1.
  4. networkId matches the network you are currently joined to.
  5. expiresAt is later than the current time and no more than 660 seconds from now (600 seconds + 60 seconds of clock skew).
  6. peerId is not your own PeerId.

The candidate addresses must all be readable as binary multiaddrs. If even one cannot be read (because it contains an unknown protocol code, for example), the whole invitation string is not used. The creating side writes them using only widely used protocols (ip4, ip6, tcp, udp, quic-v1, p2p, p2p-circuit).

Of the candidates read, only the addresses that may be connected to on the current network (section 4.5) are used, and the rest are discarded. If no usable address remains, no connection is made.

6. Game Stream and Frames

6.1 Stream

The negotiation and the game exchanges take place on a single stream of the libp2p protocol /shogiboardq/game/1.0.0. In this document, "connection" refers to this stream unless stated otherwise. The stream being closed or reset is called "disconnection".

The stream repeatedly carries a 4-byte big-endian length followed by a frame (deterministic CBOR) of that length. The length must be 1 to 65536 (64 KiB). The receiving side checks the length before allocating memory.

6.3 Opening a Stream and INVITE_TOKEN

INVITE_TOKEN = [1, 11, 0, zero32, [token]]   ; token is bstr(32)

The joiner (the side that received the invitation string) does the following.

  1. Connect to the peerId and addresses in the invitation string and open a /shogiboardq/game/1.0.0 stream (ShogiBoardQ gives up after 30 seconds).
  2. As soon as it is open, immediately send INVITE_TOKEN as the first frame (requestId 0).
  3. Then send HELLO (section 8.2).

The inviter waits only 5 seconds for the first frame of an incoming stream and decides as follows.

  • If the first frame is INVITE_TOKEN and its token matches the token of an unused invitation within its expiry, the inviter marks that invitation as used and accepts the stream. The comparison is made against all invitations, with a comparison whose processing time does not depend on the contents.
  • Otherwise (it does not arrive in time, it is not INVITE_TOKEN, or the token does not match), the inviter closes the stream without returning anything.

INVITE_TOKEN must have requestId 0 and gameId zero32. INVITE_TOKEN must not be sent anywhere but as the first frame of a stream (if one is received elsewhere, the stream is closed as an envelope violation). Streams accepted during a game are described in section 11.1.

7.3 Encoding Moves and Positions

So that different implementations produce the same byte sequences, move and position strings use only the following forms. A received string that is not in this form is rejected.

  • Move (moveUsi): USI form. A move on the board is <from><to> (e.g. 7g7f), with a trailing + when promoting (e.g. 8h2b+). A drop is <piece>*<to>, where the piece is one of the uppercase P L N S G B R (e.g. P*5e). Files are 1 to 9, and ranks are a to i. No leading or trailing spaces.
  • Position (sfen): <board> <side to move> <pieces in hand> <move number>, separated by single spaces.
    • The board follows USI SFEN (rank 1 to rank 9, each rank from file 9 to file 1; empty squares as digits, promoted pieces prefixed with +, Black in uppercase and White in lowercase).
    • The side to move is the side that moves next (Black b, White w).
    • Pieces in hand are written in the order of Black's R B G S N L P, then White's r b g s n l p, listing only the pieces held. A count is prefixed for 2 or more (e.g. 2P). If neither side holds any, -.
    • The move number field is ply + 1 (1 for State0).

8. Steps Before the Start

8.1 Flow

Let A be the joiner and B the inviter. All frames go over the same stream.

A (joiner)                                        B (inviter)
  ── INVITE_TOKEN ────────────────────────────→   check the token (section 6.3)
  ── HELLO (role 1, commitA) ─────────────────→   check; to refuse, send REJECT
  ←─────── HELLO (role 2, nonceB, conditions) ──
  decide the sides, build the StartAgreement
  ── START_AGREEMENT ─────────────────────────→   check (section 8.3)
            [both users check the opponent and conditions on the confirmation screen]
  user clicks Start
  ── START_SIGNATURE (A's signature) ─────────→   check the signature
                                                  user clicks Start
  ←────────── START_SIGNATURE (B's signature) ──
  check the signature
            [both signatures present = the game starts; go to section 9.1]
  • A does not accept B's START_SIGNATURE until after it has sent its own START_SIGNATURE.
  • B must not send its own START_SIGNATURE until it has verified A's START_SIGNATURE. If B's user clicked Start first, B sends it at the moment it has verified A's signature.
  • Each side must not sign with its player key until its user clicks Start.

  • playerKey and sessionKey are points that can be used as Ed25519 public keys (section 2.4).
  • playerKey, sessionKey, and connectionRandom are not the same values as one's own. The joiner also checks that the opponent's coin (nonceB) is not the same as its own nonceA.
  • Inviter: the playerKey claimed by the joiner is not an opponent the user has blocked (BUSY is returned to a blocked opponent without saying that it is blocked). Both sidePreferences are compatible (section 8.4).

If it is already negotiating with another opponent, it sends REJECT (BUSY) without returning HELLO and closes the stream (during a game, no stream other than the game opponent's is accepted; section 11.1). When refusing, it returns REJECT without returning HELLO, and does not reveal its own public keys.

8.3 START_AGREEMENT

Frame   = [1, 2, requestId, zero32, payload]
payload = [StartAgreement, Rules, TimeControl, NetworkPolicy]

The joiner, which first learns the conditions (the time control) from the inviter's HELLO, decides the sides and builds it. startBefore is set to 180 seconds after the current time. The inviter checks all of the following, and if any check fails, it sends REJECT (CONDITION_MISMATCH where no code is stated).

  • Rules and NetworkPolicy are the v1 values, and TimeControl is the same as the one presented in its own HELLO. The three hashes match the values in the StartAgreement.
  • networkId is its own network.
  • Its own playerKey, sessionKey, nonce (nonceB), and PeerIdHash are placed correctly on the same side (Black or White). The opponent's playerKey, sessionKey, and PeerIdHash match the opponent's HELLO and the peer on the stream, and are placed on the opposite side.
  • For the nonce on the opponent's side (nonceA), H(CBOR(["SBQ-COMMIT", 1, nonceA])) matches the coin (commitA) in the opponent's HELLO.
  • The sides follow the method of section 8.4.
  • startBefore is later than the current time and no more than 210 seconds from now (180 seconds + 30 seconds of clock skew). If not, REJECT (EXPIRED).
  • The 4 public keys, the 2 PeerIdHashes, and the 2 nonces are each different (section 7.4).

8.4 Deciding the Sides

The sides are decided by both sides' preferences (sidePreference) and by the random values both sides produced.

  1. If both sides state a preference and they are the same (both Black, or both White), they are incompatible: REJECT (CONDITION_MISMATCH).
  2. If the joiner prefers Black, or the inviter prefers White, the joiner is Black.
  3. If the joiner prefers White, or the inviter prefers Black, the joiner is White.
  4. If both have "No preference", the random values decide. If the least significant bit of the last byte of coinHash = H(CBOR(["SBQ-COIN", 1, nonceA, nonceB])) is 0, the joiner is Black; if it is 1, the joiner is White.

The random values are revealed in the following order, so that neither side can choose its own value after seeing the outcome. The joiner creates a 32-byte random value nonceA and shows only commitA = H(CBOR(["SBQ-COMMIT", 1, nonceA])) in HELLO. The inviter shows nonceB as is in HELLO. The joiner reveals nonceA in the START_AGREEMENT (in the nonce field of its own side). The same procedure is followed even when the preferences decide the sides (the nonces also serve to make the game ID unique).

On ShogiBoardQ's screens, only the inviter can state a side preference (the joiner always sends 0). If a compatible implementation sends a preference as the joiner, it is handled according to the rules above.

8.5 START_SIGNATURE

Frame   = [1, 3, requestId, gameId, payload]
payload = [side, signature]        ; side is 1 = Black, 2 = White. signature is bstr(64)

signature is the signature by one's own player key over CBOR(StartAgreement). side is one's own side. The receiver checks that side is the opponent's side, that the signature is valid for the opponent's playerKey in the StartAgreement, and that the current time is before startBefore. If not, REJECT (INVALID_SIGNATURE; EXPIRED when the deadline has passed).

From the moment the opponent's start signature has been verified, the opponent's playerKey may be treated as a "verified identity". Until then, it is shown on screen as a value the opponent has merely claimed.

START_SIGNATURE is sent only once. It must not be resent. A side that receives a second one before the start ends the negotiation with REJECT (INVALID_SIGNATURE), and a side that receives one after the start stops the game with an error (CONDITION_MISMATCH).

Both start signatures (Black's and White's) are put in the game record (evidence).

9. Steps During the Game

After both start signatures are present, every frame carries the game ID in gameId. On receiving a frame with a different game ID, the receiver stops the game with an error (CONDITION_MISMATCH) (section 9.7).

9.1 Start (State0 and READY)

Black                                                 White
  ── STATE_PROPOSE (State0, Black's approval) ────→   check State0 and the signature
  ←────────── STATE_ACCEPT (0, White's approval) ──
  ←──────────────── CONTROL READY ([state0Hash]) ──   from here, observe the time of Black's first move
  start timing the first move on receiving READY
  • White checks that the received State0 exactly matches the value in section 7.2 and that the signature is valid for Black's per-game key.
  • Black checks that the state0Hash in READY matches the hash of its own State0. Even if READY is received twice, the clock is not reinitialized.
  • If this has not been completed within 30 seconds after both start signatures are present, the game ends without starting (it becomes a record with no result).

9.2 Proposing a Move (STATE_PROPOSE)

Frame   = [1, 4, requestId, gameId, payload]
payload = [State, signature]       ; signature is the signature by the moving side's per-game key over StateApproval (bstr(64))

When the side to move has decided on a move, it builds the next State (section 7.2), signs its StateApproval with its per-game key, and sends it.

  • spentMs is the time from the start of one's own turn until just before the State is built (by one's own clock).
  • The remaining time is determined by the calculation in section 9.4.
  • The next move must not be proposed until the opponent's approval (STATE_ACCEPT) arrives. There is only one unapproved move of one's own at a time.
  • If the approval has not arrived after 5 seconds, the frame is resent with the same bytes (including the same requestId). If it has not arrived 30 seconds after the first send, the connection is treated as dropped and the side moves on to reconnection (section 11).

The receiving side checks in the following order.

  1. The gameId of the State is the game ID. If not, error (CONDITION_MISMATCH).
  2. If ply is 0, it is handled as in section 9.1 (if State0 differs from the expected value or the signature is not valid, error (INVALID_SIGNATURE)). If ply is 1 or more but the approval of State0 and READY are not yet done, error (CONDITION_MISMATCH).
  3. If ply is at or below that of the latest State one knows, it is treated as a resend. If it is the same State, one's saved approval is resent with STATE_ACCEPT (without moving the board or the clocks). If it is a different State at the same ply, the game stops with an error (STATE_CONFLICT).
  4. ply is the next one after the latest (+1), it is the opponent's turn, and one has no unapproved move of one's own. If not, error (STATE_CONFLICT).
  5. The signature is valid for the opponent's per-game key. If not, error (INVALID_SIGNATURE).
  6. previousStateHash is the hash of the latest State, and the move string is in the form of section 7.3. If not, error (INVALID_MOVE).
  7. The reported spentMs is not a time loss (E ≥ R + B; section 9.4). If it is a time loss, error (CLOCK_MISMATCH).
  8. The move is legal in the latest position (section 9.6), and sfen matches the position after the move written in the form of section 7.3. If not, error (INVALID_MOVE).
  9. The remaining times (blackMainMs, whiteMainMs) follow the calculation in section 9.4. If not, error (CLOCK_MISMATCH).
  10. The reported spentMs is not too short compared with the time one measured (the tolerance in section 9.4). If not, error (CLOCK_MISMATCH).

If all checks pass, the receiver saves the approval, then sends STATE_ACCEPT and applies the move to the board. A STATE_PROPOSE whose payload has the wrong form stops the game with an error (INVALID_MOVE).

The "resending of the approval" in step 3 need not be done once one has already proposed one's next move. The stream preserves order, so the approval sent first always reaches the opponent (it fails to arrive only when the connection drops, and in that case the reconnection comparison makes up for it).

9.3 Approval (STATE_ACCEPT)

Frame   = [1, 5, requestId, gameId, payload]
payload = [ply, stateHash, signature]    ; signature is the signature by the receiving side's per-game key over StateApproval

The proposing side checks that ply and stateHash match its own unapproved State and that the signature is valid for the opponent's per-game key. If they pass, that State becomes a state approved by both sides and is applied to the board.

  • A repeated approval of a move that is already approved (a resend whose ply and stateHash match a State approved by both sides) is ignored. The same applies while one has an unapproved move of one's own (the opponent can resend its approval in response to a resent proposal, and that approval can arrive after one has proposed the next move).
  • Any other approval (one that is neither for one's own unapproved move nor for an already approved move) stops the game with an error (STATE_CONFLICT).
  • A STATE_ACCEPT whose payload has the wrong form stops the game with an error (INVALID_SIGNATURE).

The sequence of States approved by both sides (from State0 to the latest) is the official record of the game.

9.4 Time Rules

The time control is "main time (R) + byoyomi for each move (B)". Let R be the remaining main time at the start of the turn, B the byoyomi, and E the time used for that move (all in milliseconds).

  • Condition for moving: E < R + B. E ≥ R + B is a time loss, and the move cannot be made (a value equal to the boundary is a time loss).
  • Remaining time after the move: the moving side's main time becomes max(R − E, 0), and the other side's does not change. These are written in the State's blackMainMs and whiteMainMs.

The moving side measures the time with its own clock and reports it. The opponent compares it with the time it observed with its own clock.

What is measuredStart
Time of one's own turn (E)For Black's first move, the moment READY is received. Otherwise, the moment one checked the opponent's move and sent STATE_ACCEPT
Observation of the opponent's turnThe moment one first sent one's own STATE_PROPOSE. When White observes Black's first move, the moment it sent READY. After a reconnection, when one resends one's own unapproved move, the measurement restarts from the moment of the resend (because the opponent's turn starts when the opponent receives and approves that move; section 11.5)
  • Checking the report: for a received move, if observed time − spentMs > 10,000 + time disconnected during that turn, the game stops with an error (CLOCK_MISMATCH). In other words, the report may be up to 10 seconds shorter than the observation (to allow for communication delay).
  • Own time loss: when it is one's own turn, one has no unapproved move, and E ≥ R + B by one's own clock, one declares one's own loss (proposes the result "opponent wins, cause time loss"; section 10.2).
  • Claiming the opponent's time loss: if the opponent's move has not arrived and observed time (excluding time disconnected) > R + B + 10,000, one may propose one's own win by time loss. Only once at the same ply.
  • The clock of the side to move keeps running even while the connection is down.
  • Clocks are measured with a monotonic clock. An implementation that can no longer confirm the continuity of the measured time because of sleep or a change of the system time interrupts the game (ABORT, reason CLOCK_DISCONTINUITY). ShogiBoardQ interrupts the game when the advance of the monotonic clock and that of the OS clock differ by more than 15 seconds.

9.5 Control Messages (CONTROL)

Rules for the number (sequence): the sender increases it by 1, starting from 1, per connection and per direction. When a reconnection makes a new connection, it goes back to 1. The receiver handles it as follows.

  1. Check the form of the payload (an array of 3 elements, the form of Control, kind 1 to 6, sequence 1 or more, body an array, and bodyHash matching the hash of body). If not, stop with an error (INVALID_SIGNATURE), whichever connection it belongs to.
  2. If the gameId or connectionId of the Control is not that of the current game and the current connection, discard it silently.
  3. If sequence is at or below a number already received, discard it silently as a resend.
  4. If sequence is not "the last received number + 1", stop with an error (STATE_CONFLICT).
  5. Check that the signature is valid for the opponent's per-game key. If not, error (INVALID_SIGNATURE). If it is, make that number the "last received number".

Control messages other than RESUME that arrive before the reconnection comparison is complete go through the checks above and advance the number, and are then discarded without their contents being processed.

The control messages sent and received in one game are limited to 4096 in total. Beyond that, the game stops with an error (LIMIT_EXCEEDED).

9.6 Move Legality

Moves must be legal under the rules of standard shogi. Compatible implementations must judge at least the following in the same way (if their judgments differ, one side stops the game with INVALID_MOVE).

  • Piece movement and promotion (a move that enters the promotion zone, moves within it, or leaves it can promote; only pieces that can promote)
  • Prohibition of pieces with no legal moves (a pawn or lance on the farthest rank, or a knight on the farthest two ranks, can be neither moved there without promoting nor dropped there)
  • Prohibition of two unpromoted pawns on the same file (nifu), and of checkmate by a pawn drop (uchifuzume)
  • Prohibition of moves that leave one's own king in check or expose one's own king to check
  • Prohibition of moves beyond 512 (there is no move after a State whose ply is 512)

There is no impasse declaration (entering-king declaration) and there are no takebacks. An entering-king game can be ended in a draw by agreement of both sides (section 10.2).

9.7 Check Failures (ERROR)

If the opponent's input fails a check during the game, send CONTROL ERROR ([errorCode, relatedPly]) and end the game on one's own side as "Error (unconfirmed)". The side that receives ERROR also ends the game as unconfirmed. A failed check must not be recorded as a loss for the opponent. Both sides save the record up to that point (up to the States approved by both sides) as evidence.

An implementation that obtains proof that the opponent signed two different States for the same ply (the two States and the two signatures) should keep it.

When a payload with the wrong form (wrong array length, type, or range) is received, the game is likewise stopped with ERROR (INVALID_MOVE for STATE_PROPOSE; INVALID_SIGNATURE for STATE_ACCEPT, CONTROL, and RESULT_SIGNATURE; STATE_CONFLICT for SYNC_REQUEST and SYNC_CHUNK). When a HELLO, START_AGREEMENT, or START_SIGNATURE in the pre-start form is received after the start, the game is stopped with CONDITION_MISMATCH. A frame whose envelope is wrong closes the stream (section 6.2).

In the following cases, the game ends without sending anything: when a check fails before the reconnection comparison is complete (section 11), when the start deadline (the 30 seconds of section 9.1) passes, when the disconnection limit (section 11.6) is exceeded, and when the time to wait for the result signatures (section 10.4) passes.

An implementation that has ended the game closes the stream. When the opponent has already ended the game, frames sent to it and attempts to reconnect get no response.

10.2 Proposing and Matching the Result

A result is proposed with CONTROL RESULT_PROPOSE (whose body is the FinalResult). The result has matched at the moment both sides have sent each other RESULT_PROPOSE with the same FinalResult. The agreeing side sends back RESULT_PROPOSE with the same FinalResult as the proposal it received. When it does not agree, it sends RESULT_DECLINE and the game continues.

The FinalResult must refer to the current latest State approved by both sides.

FinalResult = ["SBQ-RESULT", 1, gameId, H(CBOR(latest State)), transcriptHash, latest ply, outcome, cause]
  • While one has an unapproved move of one's own, one does not propose a result.
  • When the ply advances, earlier proposals and offers awaiting an answer become invalid.
  • After the result has matched, a proposal of a different result is not agreed to (it is ignored).
  • STATE_PROPOSE and STATE_ACCEPT that arrive after the result has matched are ignored (they are neither approved nor applied to the board). Approving a State after the ply that the FinalResult refers to would make the evidence fail the checks of section 13.2.
  • Until an answer to one's own offer of a "draw or abort by agreement" arrives, one should not propose the next move. If the offering side's move crosses the opponent's acceptance, the situation above arises (that move remains only at the end of the moving side's evidence, as a move without the opponent's approval).
  • Before the reconnection comparison is complete (section 11), one must not accept the opponent's offer and make the result match (the acceptance cannot be sent to the opponent). The opponent resends its proposal after the comparison, so answer it then.

However, the receiving side must not treat the same proposal arriving repeatedly at the same ply as a violation (it handles each one according to the table above). ShogiBoardQ resends its proposal after a reconnection (section 11.5), and once the real-time limit of one game has been exceeded, it proposes an abort by agreement again each time it is declined (section 10.5).

10.3 Game Ends Determined by the Moves

Each time the game advances by one move (the States approved by both sides increase), both sides judge in the following order, and if it is a game end, they propose that result with RESULT_PROPOSE. If both sides judge the same way, they send each other the same proposal and the result matches.

  1. Checkmate: if in the latest position (ply ≥ 1) the side to move has no legal move at all, the side to move loses (cause 2). This is handled the same way even when the side to move is not in check.
  2. Repetition: when the same position as the latest one (the same board, pieces in hand, and side to move; the move number field is not compared) appears 4 or more times in the sequence from State0, counting the latest one.
    • Examine the States from the one after the previous occurrence of that position up to the latest State. If all the moves Black made in this span were checks, Black loses (White wins, cause 5). Otherwise, if all the moves White made were checks, White loses (Black wins, cause 5). A "check" means that, in the position after the move, the opponent's king is in check.
    • If neither, a draw (cause 4).
  3. 512 moves reached: if the latest ply is 512, a draw (cause 7).

10.4 Signing the Result (RESULT_SIGNATURE)

Frame   = [1, 9, requestId, gameId, payload]
payload = [FinalResult, side, signature]    ; signature is the signature by the player key over CBOR(FinalResult) (bstr(64))

When the result has matched, each side does the following in order.

  1. Save the matched result (resultDigest). From then on, it must not sign a different result in this game.
  2. Sign the FinalResult with the player key and send RESULT_SIGNATURE.
  3. Wait for the opponent's RESULT_SIGNATURE (30 seconds).

The receiver checks that side is the opponent's side, that the signature is valid for the opponent's playerKey in the StartAgreement, and that the FinalResult is the same as the matched result. If not, error (INVALID_SIGNATURE; STATE_CONFLICT if the result differs). The checks of side and the signature are performed even before the result has matched.

The RESULT_PROPOSE that indicates agreement is always sent before RESULT_SIGNATURE. A RESULT_SIGNATURE that arrives before the result has matched is discarded even if it passes the checks, and is not used later (that game ends as "Without opponent's confirmation").

  • When both signatures are present, the record is "Confirmed by both".
  • If the opponent's signature has not arrived after 30 seconds, or the connection drops while waiting, the game ends as a record with only one's own signature ("Without opponent's confirmation").

10.5 Leaving the Game (ABORT)

When the user leaves the game unilaterally, the implementation sends CONTROL ABORT ([hash of the latest State, reasonCode]) and ends the game on its own side as "Interrupted (unconfirmed)". For a user operation, CANCELLED (12) is used as the reasonCode. The side that receives ABORT also ends the game as unconfirmed. ABORT is not an abort by agreement (cause 8), nor is it a loss for the opponent.

ABORT is not sent before the reconnection comparison is complete, or before the approvals of State0 are in place (in those cases the game ends on one's own side without sending it).

If the real time of one game (counted from the moment both start signatures are present) exceeds 24 hours, an abort by agreement is proposed. If it is declined, it is proposed again. If the result still has not matched after a further 120 seconds, the game ends with ABORT (reason GAME_TIME_LIMIT). Once 24 hours have passed, ShogiBoardQ no longer resends unapproved moves and no longer declares or claims time losses.

11. Reconnection

Even if the stream drops during a game, the sides can reconnect to the same game. After reconnecting, they compare their latest states before continuing.

11.1 The Reconnecting Side and the Accepting Side

  • The side that reconnects is the joiner (the side that opened the stream first). While disconnected, it connects to the opponent's PeerId every 5 seconds and opens a /shogiboardq/game/1.0.0 stream. It uses the addresses that worked for the first connection and those learned via Identify. INVITE_TOKEN is not sent.
  • Once the joiner has opened the stream, it immediately sends the reconnection HELLO (section 11.2) without waiting for the opponent. The inviter does not notice that a new stream exists until it receives the first frame. The gameId of the first frame must be the game ID (otherwise the game stops with an error).
  • The side that decides that the connection has dropped closes the old stream. Otherwise the opponent does not notice the drop, and reconnection does not start (the joiner reconnects only when its own stream has closed or when it has itself decided that the connection dropped).
  • From the start of the game until its end, the inviter accepts only streams from the PeerId of the game opponent (it does not accept streams from anyone else, or streams that begin with INVITE_TOKEN). It waits 5 seconds for the first frame, as in section 6.3.
  • When the opponent reconnects, even if the old stream still seems to be alive, the old one is closed and the steps below are followed as for a dropped connection. The same applies right after a comparison has completed: each time a new stream arrives, the comparison is redone with new random values (the joiner's connection attempts can overlap).
  • The PeerId must not change during a game (section 3.2). If the app or the node exits, the same game cannot be resumed.

The connection is judged to have "dropped" when the stream is closed or reset, or when no approval has arrived for one's own STATE_PROPOSE for 30 seconds (section 9.2). If it drops before the start (before both start signatures are present, or before READY is done), the game ends without reconnecting. It is also not reconnected if it drops after the result has matched (while waiting for the signatures of section 10.4). In that case, if the opponent has not yet noticed that the result matched (the connection dropped before the agreeing RESULT_PROPOSE arrived), the opponent tries to reconnect but gets no response, and its side ends at the limit of section 11.6.

11.2 HELLO (Reconnection)

Frame   = [1, 1, requestId, gameId, payload]
payload = ["SBQ-RECONNECT", 1, side, connectionRandom]     ; side is one's own side (1 = Black, 2 = White)

Once the new stream exists, both sides send a reconnection HELLO containing a new 32-byte random value. On receiving the opponent's HELLO, a side checks that side is the opponent's side and that the random value differs from its own, and computes the new connectionId (section 7.5; Black's random value first, then White's). Both sides restart the control message number (sequence) from 1.

A HELLO before the start and a reconnection HELLO are told apart by the frame's gameId (zero32 or the game ID) and by the payload label.

If a reconnection HELLO arrives when no reconnection is in progress, if its side is not the opponent's side, or if its random value is the same as one's own, ShogiBoardQ discards it silently (the comparison does not progress, and the game ends at the limit of section 11.6).

11.3 RESUME

On receiving the opponent's reconnection HELLO, a side sends CONTROL RESUME ([latestPly, latestStateHash]). latestPly is the ply of its own latest State approved by both sides, and latestStateHash is the hash of that State. This CONTROL carries a per-game key signature over the new connectionId, so each side can reconfirm that the opponent is the same one as at the start.

Until RESUME has been verified, other frames must not be accepted (moves, approvals, result proposals, and so on are discarded silently). The only frames that may be sent during reconnection are the reconnection HELLO, CONTROL RESUME, SYNC_REQUEST, and SYNC_CHUNK.

RESUME is sent only once per comparison. A RESUME that arrives when no reconnection is in progress (including after the comparison has completed) stops the game with an error (STATE_CONFLICT). The same applies to a SYNC_CHUNK that was not requested.

On receiving the opponent's RESUME, a side compares it with its own latest ply (myPly).

CaseHandling
Opponent's latestPly = myPlyIf the hash of one's own State at that ply matches, the comparison is done. If not, error (STATE_CONFLICT)
Opponent's latestPly < myPlyCheck that the hash of one's own State at that ply matches, and wait for the opponent's SYNC_REQUEST
Opponent's latestPly > myPlyRequest the missing part with SYNC_REQUEST

11.4 SYNC_REQUEST and SYNC_CHUNK

SYNC_REQUEST: Frame = [1, 7, requestId, gameId, [fromPly, previousStateHash]]
SYNC_CHUNK:   Frame = [1, 8, requestId, gameId, [[[State, blackApproval, whiteApproval], ...], final]]
  • The side that is behind requests with fromPly = its own latest ply + 1 and previousStateHash = the hash of its own latest State.
  • The side that is ahead checks that it has already received the opponent's RESUME, that fromPly is 1 or more and at or below its own latest ply, and that previousStateHash is the hash of its own State at ply fromPly − 1. If not, error (STATE_CONFLICT). If the checks pass, it returns the States from fromPly to the latest, together with the signatures of both approvals (each bstr(64)), in order, in SYNC_CHUNKs of up to 64 entries each. The last chunk has final = 1, and the others 0. Nothing outside the requested range is sent.
  • The side that is behind checks each received State, one at a time, before taking it in: that the plies are consecutive, that both approvals are valid, and steps 6 to 9 of section 9.2 (previous state hash, move format, time loss, legal move, position, remaining-time calculation). If any check fails, it stops with an error (STATE_CONFLICT). If it has an unapproved move of its own and a different State arrives at the same ply, it stops with an error (STATE_CONFLICT) (it does not roll back to a different line signed by only one side). If it is the same State, the unapproved move is treated as approved.
  • For an opponent's move first learned through the reconnection, the timing of one's own turn starts from the moment the move is taken in (the lost time is not guessed).

11.5 After the Comparison

  • If a move of one's own without the opponent's approval remains, STATE_PROPOSE is resent with the same bytes. The observation of the opponent's turn (section 9.4) restarts from the moment of this resend. When a move that was unapproved turns out through SYNC to be "approved", the measurement is not restarted (it is measured from the moment the move was first sent, minus the time disconnected).
  • If one had proposed a result, RESULT_PROPOSE is resent. If a game end determined by the moves (section 10.3) has been reached, it must be proposed after the comparison. ShogiBoardQ does not propose from the side that learned the last move through SYNC, so unless the side that was up to date resends the proposal, the game does not end.
  • The time disconnected (from deciding that the connection dropped until the comparison completes) is added to the total disconnection time of that game.

13. Game Record (Evidence)

When a game ends (even when the result was not confirmed), each side saves the record of the game in one file. This is called the evidence. Anyone can verify the evidence without using the network or the opponent. The extension is .sbqmatch, and the size is at most 8 MiB. Evidence written by a compatible implementation must be verifiable with ShogiBoardQ's Game Records tab and with shogiboardq-cli verify-match, and vice versa.

13.2 Verification Steps

The verifier checks the following in order. Each result is reported separately ("the signatures are valid", "the moves follow the rules", and "the time arithmetic matches" are not mixed). All signature verification is done as in section 2.4 (including the public key check).

  1. Format: at most 8 MiB, deterministic CBOR, and in the form of section 13.1. Rules and NetworkPolicy are the v1 values, and TimeControl is within the ranges of section 7.1.
  2. Conditions: the hashes of Rules, TimeControl, and NetworkPolicy match the three hashes in the StartAgreement.
  3. Start signatures: the two start signatures are valid for blackPlayerKey and whitePlayerKey in the StartAgreement, respectively. Compute gameId = H(CBOR(StartAgreement)).
  4. Sequence of States: from the beginning, check the following in order.
    • The gameId of the State is the game ID, and ply matches its position in the sequence (0, 1, 2, …).
    • Each approval signature that is not of length 0 is valid for the per-game key of the corresponding side (blackSessionKey, whiteSessionKey). A State with neither approval is not accepted.
    • State0 matches the value in section 7.2. Each later State has been built from the previous State according to steps 6 to 9 of section 9.2 (previous state hash, move format, time loss, legal move, position, remaining-time calculation).
    • A State with only one approval can be placed only at the end of the sequence.
  5. Moves approved by both sides: the States that have both approvals (a contiguous part from the beginning of the sequence) are called "the moves approved by both sides". If they are not empty, perform the judgment of section 10.3 to find whether the game end is determined by the moves.
  6. Result: if there is a FinalResult, check the following.
    • Its gameId is the game ID, ply and finalStateHash refer to the last State of the moves approved by both sides, and transcriptHash matches the value computed from the moves approved by both sides.
    • Each result signature that is not of length 0 is valid for the player key of the corresponding side.
    • If the game end is determined by the moves, the outcome and cause of the FinalResult match it. If the game end is not determined by the moves, the cause of the FinalResult is not one of the causes determined by the moves (checkmate, repetition, perpetual check, 512 moves reached).

  1. Deterministic CBOR and hashes: the inputs of section 15.1 and the values in Appendix A match.
  2. Evidence verification: read a .sbqmatch saved by ShogiBoardQ, and all the verification of section 13.2 passes (this confirms the signature verification and that the moves, positions, and time calculations agree).
  3. Invitation strings: you can read invitation strings created by ShogiBoardQ, and ShogiBoardQ's Check Invitation can read invitation strings you created.
  4. Connection and negotiation: with the network set to sbq-local-1, get as far as the confirmation screen with ShogiBoardQ on the same PC, both as the inviting side and as the invited side.
  5. Game: as both Black and White, play games to resignation, checkmate, time loss, and draw by agreement, and the evidence of both sides becomes "Confirmed by both". Verify the evidence you wrote with shogiboardq-cli verify-match --input-path <file>; valid is true and category is mutually_signed.
  6. Reconnection: cut the stream during a game, and the game can be reconnected and continued (when you are the joiner and when you are the inviter, and with and without an unapproved move).
  7. Refusal: send invalid signatures, illegal moves, States with wrong time calculations, CONTROL messages with skipped numbers, and so on, and confirm that the opponent stops without assigning a win or loss. Your own implementation refuses the same inputs in the same way.

When ShogiBoardQ is started several times on the same PC, each copy becomes a different player in the order it was opened (the second is "Player 2"). Tests against a compatible implementation can be done within one PC.
