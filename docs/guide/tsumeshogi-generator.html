詰将棋局面生成

ランダム局面生成とUSIエンジンによる詰み検証で詰将棋を自動生成

自動生成 不要駒トリミング SFEN出力

概要

ランダムに詰将棋の候補局面を生成し、USIエンジンで詰みを検証します

1 機能の特徴

詰将棋局面生成機能は、以下の処理を自動で行います。

  • ランダムに詰将棋の候補局面を生成
  • USIエンジン（go mate コマンド）で詰み探索を実行し、指定手数の詰みがある局面を発見
  • 発見した局面に対して不要駒トリミング処理を行い、最小限の駒で構成された局面に最適化
  • 結果をSFEN形式で一覧表示し、ファイル保存やクリップボードへのコピーが可能

詰み探索には、komori-n氏が開発・公開している詰将棋エンジンKomoringHeightsを利用できます。エンジンを別途用意してShogiBoardQに登録し、生成ダイアログの「エンジン設定」で選択してください。配布物やソースコードは、リンク先のリポジトリで公開されています。

局面生成の設定

生成ダイアログで各種パラメータを設定して局面生成を開始します

1 詰将棋局面生成ダイアログ

メニューの「対局」→「詰将棋局面生成…」からダイアログを開きます。以下の項目を設定できます。

  • エンジン設定：詰み探索に使用するUSIエンジンの選択・設定
  • 目標手数：生成する詰将棋の手数（例：3手詰、5手詰）
  • 攻め駒上限：攻方の駒数の上限（盤上＋持駒の合計）
  • 守り駒上限：守方の駒数の上限（玉を除く）
  • 配置範囲：玉を中心とした攻め駒の配置範囲（マス数）
  • 探索時間/局面：1局面あたりのエンジン探索時間
  • 生成上限：発見する局面数の上限
  • 最終手の複数解を許容する：主手順の最終手に複数の詰手があっても採択するか。オフにすると最終手も一意な局面だけを出力します（初手など主手順の途中の余詰は常に除外）

詰将棋局面生成ダイアログ：エンジン・生成パラメータを設定して「開始」で生成開始

2 ランダム局面生成のしくみ

局面生成は以下の手順で自動的に行われます。

  • 後手の玉を9x9盤面のランダムな位置に配置
  • 攻め駒を玉の周辺に配置（盤上または持駒としてランダムに振り分け）
  • 守り駒を玉の周辺に配置
  • 攻方の玉を省略し、その他の未使用駒は全て受方（後手）持駒に追加
  • 初期局面で王手がかかっていないことを検証

生成された局面はまず内蔵の詰み探索で選別され、目標手数で詰まないと分かった局面や、複数の詰む初手が見つかった局面を除外します。標準実装では、内蔵探索で判定できなかった候補もUSIエンジンに送信します。エンジンが指定手数の詰みを確認した局面だけが余詰検査に進みます。「探索済み」には内蔵探索で除外した局面も含まれます。

生成結果

発見された詰将棋局面が一覧表示されます

1 結果一覧

指定手数の詰みが発見されると、不要駒トリミング処理が行われた後、結果一覧に追加されます。トリミング処理により、詰み手数を変えずに除去可能な駒が自動的に取り除かれ、最小限の駒で構成された局面が出力されます。

結果一覧では以下の操作が行えます。

  • 盤面ボタン：クリックすると読み筋表示ウィンドウで詰み手順を確認
  • ファイル保存：結果をSFEN形式のテキストファイルに保存。先頭にShogiBoardQのバージョン・生成日時・生成設定を「#」始まりのコメント行として記録します（局面集ビューアや詰将棋対局の読み込みでは読み飛ばされます）
  • 選択コピー：選択した局面のSFENをクリップボードにコピー
  • 全コピー：全局面のSFENをクリップボードにコピー

生成結果：10局面の3手詰を発見（探索済み3877局面、経過時間00:00:20、検査で除外18局面）

2 不要駒トリミング

不要駒トリミングは、ランダム生成された局面に含まれる「飾り駒」（取り除いても詰み手順に影響しない駒）を自動的に除去する処理です。

  • 盤上の攻方・守方の駒、攻方の持駒を1枚ずつ試行的に除去
  • 除去しても同じ手数で詰む場合は除去を確定
  • 除去した駒は後手持駒に移動し、駒の総数を維持
  • 1枚除去するたびに再チェックし、新たに不要になった駒も除去

詰み手順の確認

生成された詰将棋の手順を読み筋表示ウィンドウで確認できます

1 読み筋表示ウィンドウ

結果一覧の「盤面」ボタンをクリックすると、読み筋表示ウィンドウが開きます。詰み手順を将棋盤上で1手ずつ再生して確認できます。「1手進む」「1手戻る」ボタンで手順を前後に移動できます。

読み筋表示：生成された3手詰の局面を盤面上で確認（手数 0/3）

各1000題の問題集を作成した方法

2026年9月26日に行った、3・5・7・9・11・13手詰、計6000題の生成事例です

1 作成した問題集と実行経路

この作業では、PythonからCLIの generate-tsume を直接、並列実行しました。ShogiBoardQのMCPサーバーは使用していません。生成された問題集は、リポジトリの data/tsumeshogi/ に、1行1題のSFENとUSI形式の詰め手順を組み合わせたテキストとして保存しています。

問題集作成時の主な工夫
3手詰・1000題ランダム配置で300題を作成し、既存の300題を保持したまま700題を追加。
5手詰・1000題ランダム配置を並列実行し、エンジンの探索時間を0.5～20秒の範囲で比較。
7手詰・1000題駒数・配置範囲を比較。一時実行版で事前選別を5msに短縮し、詰みを確認できた候補に限定。
9手詰・1000題事前選別を1・3・5・10・25msで比較。玉が盤端に近い候補を優先し、並列数を8から16へ変更。
11手詰・1000題ランダム配置に、生成済みの7・9・11手詰の駒配置や持駒を変更する近傍探索を追加。
13手詰・1000題7・9・11・13手詰を種局面に利用。駒移動・駒種変更の比率を増やし、採択後の独立した詰み確認も実施。

全問題集で、主手順の途中の余詰を除外し、最終手の複数解は許容しました。最終的な1000題について、最短手数・手順の合法性・局面の重複を別途確認しています。具体的な生成条件は各ファイルの先頭コメントにも記録しています。

2 標準機能と、作業用に追加した処理

標準のGUIとCLIは、共通の TsumeshogiGenerator を使って、候補生成、USIエンジンの詰み探索、主手順の余詰検査、不要駒トリミングを行います。長手数の大量生成では、この処理を利用する作業用の一時実行版を /tmp に作成し、候補の作り方と事前選別を調整しました。

以下の短時間選別、玉位置による絞り込み、近傍探索は、この作業の一時実行版に追加した処理です。標準CLIのオプションとしては提供されていません。一時実行版と補助検証プログラムは配布物に含まれないため、これらの工夫を再現するには候補生成側への実装が必要です。後述のPython例は、標準CLIを使った並列実行と候補収集の方法を示します。

一時実行版を作成した箇所

src/analysis/tsumeshogicandidatescreener.cpp の作業用コピーで generateBatch() を変更しました。build/compile_commands.json とビルド時のリンクコマンドを参照してコンパイルし、変更したオブジェクトを既存の静的ライブラリより先にリンクしたCLIを /tmp に出力しました。近傍探索用の局面読込・駒変更処理も同じ作業用ディレクトリに置きました。

リポジトリのアプリケーションソースや標準CLIの実行ファイルは変更せず、外部エンジンによる余詰検査・トリミング処理をそのまま使用しました。

3 短時間の事前選別と、生成条件の比較

長手数では、ランダムに作った局面をすべて詳しく探索すると時間がかかります。一時実行版では、内蔵の有限深さ探索で目標手数ちょうどの詰みを確認でき、複数の詰む初手が検出されなかった候補だけを外部エンジンへ渡しました。時間切れなどで判定できない Unknown は候補から外しました。

7手詰では5ms、9手詰では1～25ms、11・13手詰では主に1msと3msを比較しました。ここでの時間は内蔵探索の事前選別の予算です。CLIの --timeout-ms で指定する外部エンジンの探索・検査の予算とは別です。短い時間で確認できない局面を取りこぼす代わりに、採択につながる候補を速く集める方針です。

9手詰では、玉の位置を盤端からの最短距離が0マス（盤端のみ）、1マス以内、4マス以内（盤全体）で比較しました。駒数・配置範囲・並列数も変え、採択数、重複数、判定不能数を見て条件を選びました。特定の時間や盤端への絞り込みが、すべての手数で最も速いという意味ではありません。

一時実行版では SHOGIBOARDQ_BATCH_SCREEN_MS と SHOGIBOARDQ_BATCH_KING_EDGE という環境変数でこれらを切り替えました。この2つは作業用に追加した変数で、標準CLIに設定しても事前選別は変わりません。

4 生成済み局面の駒配置を変更する近傍探索

11手詰以降では、生成済みの問題を「種局面」として読み込み、一部の駒を変更して新しい候補を作りました。11手詰では7・9手詰と収集中の11手詰、13手詰では7・9・11手詰と収集中の13手詰を使用しました。元の詰め手順は流用せず、変更後の局面を目標手数で改めて探索します。

  • 候補を作る試行の約10%でランダム配置、約90%で近傍探索を選択。
  • 近傍探索では、収集中の目標手数の局面がある場合は約60%でそこから選び、残りを既存の問題集から選択。
  • 1候補につき、約75%で1回、約25%で2回の駒変更を試行。
  • 駒を現在位置から縦横それぞれ±2マスの範囲で移動、駒種や成・不成を変更、玉周辺へ駒を追加、盤上の駒を削除、攻方の持駒を増減。
  • 行き所のない歩・香・桂は成駒に補正し、二歩、駒数上限、玉の数、初期王手を確認。未使用駒は玉方の持駒に戻してSFENを再構成。

13手詰の途中では、不要駒を追加してもトリミングで元の局面に戻り、重複になる例を減らすため、変更操作の選択比率を次のように調整しました。比率は変更の試行時の値であり、採択された問題の構成比ではありません。

変更操作当初13手詰の調整後
盤上の駒の移動45%60%
駒種・成不成の変更20%25%
盤上への駒の追加20%5%
攻方の持駒の増減10%5%
盤上の駒の削除5%5%

13手詰の後半で使用した処理の流れ

ランダム配置、または種局面の盤上・持駒を変更
  → 局面の制約を確認し、SFENを作成
  → 内蔵探索で目標手数の候補を選別
  → 外部エンジンで詰み・主手順の余詰を検査
  → 不要駒トリミングと再検査
  → 最終局面の重複除外・独立した詰み確認
  → 1000題が揃うまで収集
5 採択後の確認と、不足分の補充

詰め手順の長さだけでは最短手数を確定できません。作業用の検証プログラムでは、TsumeCollection::parse() と validMateLine() で読み込み・全手の合法性・攻方の連続王手・終端の詰みを確認し、Hayanagiの TsumeSearch::solve() による有限深さの反復深化探索で最短手数を確かめました。

13手詰では、トリミング後の局面の確認が時間切れになる例があったため、生成済み489題を1局面1秒の独立探索で再確認し、479題を残して補充しました。その後は新しい探索表を使って最短13手詰と手順を確認できた局面だけを1000題の件数に加えました。時間切れは不詰の証明ではなく、この問題集では採択を見送る判断として扱いました。

全件が揃った時点で、正規化したSFENの重複、手順の合法性、最短手数をまとめて再検証しました。11・13手詰では、二歩・行き所のない駒・駒の総数も保存前に確認しています。候補数ではなく、これらの確認を通った重複のない問題数が1000題になることを完了条件としました。

CLIをPythonから並列実行する方法

CLIのJSON Linesを読み取り、複数バッチの結果を重複なしでまとめます

1 CLIとエンジン設定の準備

リポジトリのルートで以下を実行し、CLIをビルドして登録済みエンジンを確認します。--engine にはエンジンの実行ファイルのパスではなく、list-engines に表示される登録名を指定します。

標準CLIのビルドと登録名の確認

cmake -B build -S . -DCMAKE_BUILD_TYPE=Release
cmake --build build --target shogiboardq-cli --parallel 4
./build/shogiboardq-cli list-engines

今回使用したエンジンはKomoringHeights 1.1.0 64ZEN2です。並列実行用に Threads=1、USI_Hash=256、PostSearchLevel=MinLength、GenerateAllLegalMoves=true を設定しました。Linuxでは、作業用の XDG_CONFIG_HOME の下に ShogiBoardQ/ShogiBoardQ.ini を用意し、エンジン登録とエンジンオプションの設定をコピーして、全子プロセスで同じ設定を使用しました。

並列数は主に8、一部の長手数では16を使用しました。16プロセスでハッシュを各256MiBにするとハッシュだけで約4GiBを使うため、CPUとメモリに合わせて並列数を選びます。

2 1バッチの実行とJSON Linesの読み取り

次は標準CLIで3手詰を最大100題生成する例です。登録名は使用環境に合わせて置き換えてください。今回の登録名では KomoringHeights と 1.1.0 の間に空白が2つあります。

generate-tsumeの実行例

./build/shogiboardq-cli generate-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --target-moves 3 --max-positions 100 \
  --timeout-ms 5000 --max-attack 4 --max-defend 1 \
  --attack-range 3 --stdin-control > tsume-batch.jsonl

--target-moves は1～19の奇数、--max-positions は1～100です。1000題は複数の起動結果をまとめて作成します。--timeout-ms は候補探索・トリミング・余詰検査に使う予算で、コマンド全体の終了時間ではありません。

標準出力は1行1JSONのJSON Linesです。started、progress、position、finished などのイベントが出力されます。採択された局面は position の sfen と pv（USI手順の配列）から取り出します。error は処理失敗として記録します。

positionイベントの主要フィールド

{"event":"position","sfen":"9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1","pv":["2c2b+","1b1c","2e2c+"]}

--stdin-control を付けると、標準入力へ stop\n を送るか、標準入力を閉じると停止します。Pythonから起動するときは標準入力のパイプを開いたまま保持し、必要数が揃ってから停止要求を送ります。

3 Pythonで並列起動・重複除外・途中保存

実作業では asyncio.create_subprocess_exec() でCLIを起動し、各プロセスの標準出力を非同期に読み取りました。バッチが100題に達して終了しても、全体で1000題に届かなければ次のバッチを起動します。全ワーカーで共通の辞書に局面を集約し、盤面・手番・持駒の一致をキーにして重複を除きます。

以下を generate_tsume_parallel.py として保存し、リポジトリのルートで python3 generate_tsume_parallel.py を実行できます。標準CLIで候補を集める例で、今回の一時実行版の近傍探索や独立した最短手数の検証器は含みません。出力は最終検証前の収集ファイルとし、次の確認を終えてから問題集として保存します。

並列実行用のPythonコードを表示

標準CLIを8並列で実行する例

import asyncio
import json
import os
from pathlib import Path

CLI = str(Path("build/shogiboardq-cli").resolve())
ENGINE = "KomoringHeights  1.1.0 64ZEN2"  # list-engines の登録名
PLIES = 3
TARGET = 1000
WORKERS = 8
OUTPUT = Path(f"tsume-work/tsume_{PLIES}ply_candidates.txt")
ENV = dict(os.environ)
# 別途準備した設定を使う場合（Linux）:
# ENV["XDG_CONFIG_HOME"] = "/path/to/tsume-config"

positions = {}
active = set()


def remember(sfen, pv):
    fields = sfen.split()
    if len(fields) != 4 or len(pv) != PLIES:
        raise ValueError("SFEN または手順長が不正です")
    key = " ".join(fields[:3])  # 盤面・手番・持駒。開始手数を除く
    if key not in positions and len(positions) < TARGET:
        positions[key] = sfen + " moves " + " ".join(pv)


def checkpoint():
    temporary = OUTPUT.with_suffix(".tmp")
    text = "# CLI収集結果（最終検証前）\n"
    text += "\n".join(positions.values()) + "\n"
    temporary.write_text(text, encoding="utf-8")
    temporary.replace(OUTPUT)


async def stop(process):
    if process.returncode is None:
        try:
            process.stdin.write(b"stop\n")
            await process.stdin.drain()
        except (BrokenPipeError, ConnectionResetError):
            pass


async def worker(number):
    while len(positions) < TARGET:
        args = [
            CLI, "generate-tsume", "--engine", ENGINE,
            "--target-moves", str(PLIES),
            "--max-positions", str(min(100, TARGET - len(positions))),
            "--timeout-ms", "5000",
            "--max-attack", "4", "--max-defend", "1",
            "--attack-range", "3", "--stdin-control",
        ]
        log_path = OUTPUT.parent / f"worker-{number}.jsonl"
        err_path = OUTPUT.parent / f"worker-{number}.stderr.log"
        with log_path.open("a", encoding="utf-8") as log, err_path.open("ab") as err:
            process = await asyncio.create_subprocess_exec(
                *args, env=ENV,
                stdin=asyncio.subprocess.PIPE,
                stdout=asyncio.subprocess.PIPE, stderr=err,
            )
            active.add(process)
            try:
                # 他のワーカーが起動待ちの間に目標数へ達した場合にも停止する。
                if len(positions) >= TARGET:
                    await stop(process)
                async for raw in process.stdout:
                    line = raw.decode("utf-8")
                    log.write(line)
                    log.flush()
                    event = json.loads(line)
                    if event["event"] == "error":
                        raise RuntimeError(event["message"])
                    if event["event"] != "position":
                        continue
                    remember(event["sfen"], event["pv"])
                    checkpoint()
                    print(f"{len(positions)}/{TARGET}", flush=True)
                    if len(positions) == TARGET:
                        await asyncio.gather(*(stop(p) for p in list(active)))
                if await process.wait() != 0:
                    raise RuntimeError(f"CLI が異常終了しました: {err_path}")
            finally:
                await stop(process)
                try:
                    await asyncio.wait_for(process.wait(), timeout=15)
                except asyncio.TimeoutError:
                    process.kill()
                    await process.wait()
                active.discard(process)


async def main():
    OUTPUT.parent.mkdir(parents=True, exist_ok=True)
    if OUTPUT.exists():
        for line in OUTPUT.read_text(encoding="utf-8").splitlines():
            if line and not line.startswith("#"):
                sfen, moves = line.split(" moves ", 1)
                remember(sfen, moves.split())
    tasks = [asyncio.create_task(worker(i)) for i in range(WORKERS)]
    try:
        await asyncio.gather(*tasks)
    finally:
        for task in tasks:
            task.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)
        checkpoint()
    print(f"収集完了: {OUTPUT}（最終検証は別途実施）")


if __name__ == "__main__":
    asyncio.run(main())

この例は発見のたびに一時ファイルから置換して途中結果を保存し、再起動時に読み戻します。標準出力のJSON Linesと標準エラーはワーカー別に残します。実作業ではさらにバッチごとの設定、採択数、重複数、判定不能数を記録し、設定変更時には全CLIへ stop を送って、収集済み局面を保持したまま再開しました。

13手詰の後半では、position を受け取って重複を除外した後、別の常駐検証プロセスへ SFEN moves … を送りました。最短13手詰と手順の合法性を確認できた場合にだけ辞書へ追加し、確認できない局面のキーも記録して再採択を防ぎました。

4 全件検証して、手順付きテキストとして保存

収集後には、件数が1000であること、正規化したSFENが1000種類あること、各手順の長さが目標手数と一致することを確認します。さらに、手順を実際に適用した合法性・連続王手・終端の詰みと、目標より短い手数では詰まないことを探索で確認します。文字列の手数チェックだけで最短手数の検証を代用しないことが大切です。

主手順の余詰を再検査する場合は、標準CLIの verify-tsume も利用できます。これは今回別途作成した有限深さの検証器とは別の処理です。JSONの ok はコマンド処理の成否なので、詰将棋の判定は status が unique であることまで確認します。unknown は検証成功として扱いません。

保存する局面の余詰検査例

./build/shogiboardq-cli verify-tsume \
  --engine 'KomoringHeights  1.1.0 64ZEN2' \
  --target-moves 3 --timeout-ms 15000 \
  --sfen '9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1'

最終ファイルには、生成日時、エンジン、駒数や探索時間などの条件、余詰の扱いを # 始まりのコメントとして付けました。各問題は以下の形式で保存し、例えば13手詰なら moves の後に13個のUSI指し手を記録します。

3手詰の保存例（1行1題）

9/8k/7P1/9/7R1/9/9/9/9 b r2b4g4s4n4l17p 1 moves 2c2b+ 1b1c 2e2c+

保存先は data/tsumeshogi/tsume_13ply_1000_20260926.txt のように、手数・件数・生成日をファイル名に含めています。今回の例は最終手の複数解を許容しています。最終手も一意にしたい場合は、生成・余詰再検査の両方で --no-final-alternatives を指定します。
