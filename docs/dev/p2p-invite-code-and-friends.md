# P2P対局: 合言葉による招待と友だち一覧（設計案）

作成日: 2026-11-11

状態: 案（未実装）。[実装仕様](p2p-game-spec.md)の第5版で公開募集をやめた後の、後続の機能の案である。内容を確かめてから実装仕様へ取り込む。

## 1. ねらいと範囲

第5版では、対局の相手を招待文字列だけで決める。安全だが、次の不便がある。

- 招待文字列は長く（230文字ほど）、電話や通話で伝えられない。
- 招待文字列に招待した側の接続先が入る。直接つなぐ設定では IP アドレスが入るので、送るのに使ったサービスにも残る。
- 対局のたびに招待文字列を渡し直す。3人以上の知り合いの中から相手を選ぶ仕組みがない。

この案は、知り合いどうしの範囲のまま、次の2つを足す。

| 記号 | 機能 | 効果 |
|---|---|---|
| A | 合言葉による招待 | 10文字ほどの合言葉を伝えるだけでつながる。合言葉には接続先が入らない |
| B | 友だち一覧 | 一度つながった相手は、次から一覧で「オンライン」と分かり、選んで申し込める。渡すものが要らない |

扱わないもの:

- 不特定の相手とのマッチング（実装仕様 2.3節の「採らなかった技術」のまま）。
- 協力ノードの運営者に対する匿名性。運営者には、利用者の IP と、どの IP どうしが待ち合わせたかが見える（5章）。
- 同じ LAN の自動発見（mDNS）。A・B の後に、利用者が有効にしたときだけ動く形で検討する（7章）。

## 2. 前提（第5版の実装）

- インターネット越しの対局には、招待でも協力ノードが1つは要る（到達性の確認と中継）。A・B はその協力ノードを待ち合わせにも使うので、サーバーの種類は増えない。
- 通信プロセスは鍵もファイルも持たない。秘密を扱う計算（鍵の導出・暗号化）は対局・UI側（libsodium）で行う。
- PeerId は通信プロセスの起動ごとに変わる。変わらないのはプレイヤー鍵（プレイヤーID）だけである。
- 既知の相手（`P2pKnownPeers`）は、プレイヤーID ごとに手元の名前・確認済み・ブロック・対局数を持つ。

## 3. 待ち合わせの仕組み（A・B で共通）

協力ノード（`--service`）に、小さな待ち合わせのプロトコル `/shogiboardq/meet/1.0.0` を足す。ノードは、利用者が預けた小さなデータを、短い時間だけ、番号で引けるように持つ。

```text
put(slot, blob, ttlSeconds, oneTime)   ; 預ける
get(slot) -> blob または「無い」        ; 引き取る
```

| 項目 | 内容 |
|---|---|
| `slot` | 32バイト。預ける側と引き取る側だけが計算できる番号（4章・5章）。ノードには意味が分からない |
| `blob` | 512バイト以下。対局・UI側が認証付き暗号（XChaCha20-Poly1305）で暗号化したもの。ノードには読めない |
| `ttlSeconds` | 600秒以下。過ぎたら消す |
| `oneTime` | 真なら、1回引き取られたら消す（A で使う） |

ノードの側の決まり:

- メモリにだけ持ち、ディスクとログに書かない（slot も書かない）。再起動で消える。
- 上限を置く: 全体の件数、1ピアが預けられる件数（256）、1件の大きさ、ピアごと・アドレス帯ごとの頻度。上限を超えた要求は断る。
- 同じ slot への上書きは、預けたピアだけができる。

利用者の側の決まり:

- `get` で受けた blob は、認証付き暗号の検証に通ったものだけを読む。鍵を知らないノードや第三者が作ったデータは、読む前に捨てられる。第4版までの公開募集（だれが作ったか分からないデータを全員が読む）と違い、読むのは招待した相手・友だちが作ったデータだけになる。
- 協力ノードを複数指定しているときは、すべてに預け、すべてから引き取る。

DHT を使わない理由: 第5版で外した（不特定のピアとつながる必要がある）。待ち合わせは、もともと必要な協力ノードで足りる。

## 4. A: 合言葉による招待

### 4.1 使い方

1. 招待する側が「合言葉を作る」を押すと、`K7MP2-QXD9F` のような合言葉が出る（10分・1回限り）。
2. 電話・通話・メッセージで相手に伝える。
3. 相手は「合言葉で接続」に入力する。
4. 双方に条件確認画面が出る（今の招待と同じ。相手はプレイヤーID で確かめる）。

長い招待文字列も残す（協力ノードの無い同じ LAN の対局で使える）。

### 4.2 合言葉の形

- 10文字。紛らわしい文字（I・L・O・U）を除いた英数字32種（Crockford の Base32）で、50ビットの乱数を表す。入力では大文字と小文字、区切りのハイフンを区別しない。
- 通信プロセスではなく、対局・UI側が CSPRNG（libsodium）で作る。

### 4.3 仕組み

```text
(slot, key) = Argon2id(合言葉, salt = H(CBOR(["SBQ-MEET-CODE", 1, networkId])))   ; 64バイトを前後32バイトに分ける
blob        = XChaCha20-Poly1305(key, 招待文字列の本体)
```

1. 招待する側: 通信プロセスの `createInvite` で招待（到達候補と1回用トークン）を作る。対局・UI側が合言葉から `slot` と `key` を作り、招待を暗号化して、`meetPut(slot, blob, 600, oneTime=true)` で協力ノードに預ける。
2. 招待される側: 合言葉から同じ `slot` と `key` を作り、`meetGet(slot)` で引き取って復号し、今の `connectInvite` と同じ手順でつなぐ。

### 4.4 安全性

| 相手 | できること | 対策・残ること |
|---|---|---|
| 合言葉を期限内に知った第三者 | 招待された人より先につなぐ | 今の招待文字列と同じ。条件確認画面のプレイヤーID で見分ける。合言葉は1回・10分 |
| 協力ノードの運営者 | 預かった slot と blob を保存して、合言葉を総当たりする | slot も鍵も Argon2id（メモリを多く使う導出）で作るので、1回の試行に 0.1〜0.5 秒かかる。50ビットの総当たりは現実的でない。当てても分かるのは、すでに見えている招待した側の接続先だけ |
| ネットワーク越しの第三者 | slot を当てずっぽうで引く | 50ビットの番号は当たらない。ノードが頻度を制限する |
| 合言葉を期限の後に知った人 | 何もできない | 期限で消える。合言葉そのものには接続先が入っていない |

PAKE（合言葉から、盗み聞きされても総当たりできない鍵を作る方式）は採らない。待ち合わせで双方のメッセージを何往復も中継する仕組みが要り、上の対策で足りるためである。

## 5. B: 友だち一覧

### 5.1 使い方

1. 一度つながった相手（「相手の管理」に並ぶ相手）を「友だちに追加」する。確認コードで確認済みにした相手に勧める。
2. P2P対局に接続している間、友だちが接続していれば一覧に「オンライン」と出る（友だちの側も自分を追加しているときだけ）。
3. 友だちを選んで「対局を申し込む」を押すと、相手に知らせが出る。相手が受ければ、双方に条件確認画面が出る。

3人以上の知り合いは、互いに友だちに追加すれば、一覧から相手を選べる。

### 5.2 2人だけの秘密

友だちどうしは、相手のプレイヤーID を知っている。追加の受け渡しなしに、2人だけが計算できる秘密を作る。

```text
pairSecret = X25519(自分のプレイヤー鍵を変換した秘密鍵, 相手のプレイヤーID を変換した公開鍵)
```

- プレイヤー鍵（Ed25519）を鍵交換用（X25519）に変換して使う（libsodium の変換関数）。同じ鍵を署名と鍵交換の両方に使うことになるので、用途ごとにラベルを分けたハッシュを通す。別に鍵交換用の長期鍵を持つ案もあるが、保管する鍵が増える。**どちらにするかは、実装の前に決める（9章）。**
- 片方だけが友だちに追加しても、何も起きない（相手は在席を預けず、引き取りもしない）。

### 5.3 在席の知らせ

接続している間、友だちごとに、10分ごとに変わる番号へ、自分の接続先を預ける。

```text
epoch = floor(現在時刻 / 600秒)
slot  = H(CBOR(["SBQ-PRESENCE", 1, pairSecret, 預ける側のプレイヤーID, epoch]))
key   = H(CBOR(["SBQ-PRESENCE-KEY", 1, pairSecret, 預ける側のプレイヤーID, epoch]))
blob  = XChaCha20-Poly1305(key, [PeerId, 到達候補, 申し込み用のトークン, 期限])
```

- 預ける: 60〜90秒ごとに `meetPut(slot, blob, 180, oneTime=false)`。
- 引き取る: ウィンドウを開いている間、60秒ごとに、友だちごとの `slot` を `meetGet` する。復号できれば「オンライン」と出す。
- 友だちは64人まで。対局中・交渉中は、在席を預けない（一覧には「対局中」と出さず、単にオフラインに見える）。
- 「直接接続を使わない」設定では、到達候補は協力ノードの中継を経由するアドレスだけになる。

### 5.4 申し込み

- 申し込む側は、在席の blob の到達候補へつなぎ、最初のフレームでトークンを送る（今の INVITE_TOKEN と同じ扱い）。
- 受ける側の通信プロセスは、今の在席のトークンと一致するストリームだけを受け付ける。対局・UI側は、HELLO のプレイヤーID がその友だちのものかを確かめ、違えば断る。
- 受ける側には「（手元の名前）さんが対局を申し込んでいます」と出し、受けたときだけ条件確認画面へ進む。条件（持ち時間・先後の希望）は、受ける側の「接続と条件」の値を使う（今の招待と同じく、申し込む側は条件確認画面で初めて見る）。

### 5.5 見えるもの

| 相手 | 見えるもの |
|---|---|
| 友だち | 接続しているかどうか。申し込んでつながれば、今の対局と同じ（直接つなぐ設定では、調べれば IP が分かる） |
| 友だちでない人 | 何も見えない（slot を計算できない） |
| 協力ノードの運営者 | 利用者の IP、預けられた slot の数（友だちの数の目安）、どの IP が預けた slot をどの IP が引き取ったか（＝どの IP どうしが友だちか）。プレイヤーID・名前・接続先の中身は見えない |

協力ノードの運営者に「どの IP どうしが友だちか」が見える点は、この方式では避けられない（対局を中継するときにも、同じことが見える）。**これを受け入れるかは、実装の前に決める（9章）。**

設定: 「友だちに在席を知らせる」（全体の切り替え。既定は 9章で決める）と、友だちごとの切り替え。

## 6. 追加・変更するもの

| 場所 | 内容 |
|---|---|
| 協力ノード（`peer/` の `--service`） | 待ち合わせのプロトコルと上限（3章）。`--meet` で有効にする |
| 通信プロセスの IPC（`protocol/ipc.md`） | `meetPut`・`meetGet`、在席のトークンの設定（`setFriendTokens`）。slot と blob は対局・UI側が作った値をそのまま運ぶ |
| 対局・UI側 | 合言葉の生成と導出（Argon2id はワーカースレッド）、暗号化と復号、友だちの記録（`P2pKnownPeers` に「友だち」「在席を知らせる」を足す）、在席の預け入れと引き取りの周期 |
| 画面 | 「招待で接続」タブに「合言葉を作る」「合言葉で接続」。「相手の管理」タブに「友だちに追加」・オンラインの表示・「対局を申し込む」。申し込みの知らせ |
| 文書 | 実装仕様（3章・4章・10章・11章・12章）、`protocol/`、ガイド |

通信プロセスは、これまでどおり鍵を持たない。増えるのは、意味の分からないバイト列を協力ノードとやり取りする2つの要求だけである。

## 7. 同じ LAN の自動発見（後で検討）

mDNS で同じ LAN の利用者を見つければ、協力ノードなしで相手を選べる。ただし、LAN にいる全員に「このアプリを使っている」ことが伝わる。入れる場合は、利用者が有効にしたときだけ動かし、見つけた相手とも条件確認画面を通す。A・B の後に検討する。

## 8. 進める順番と試験

1. A（合言葉）: 協力ノードの待ち合わせ、IPC、対局・UI側の導出と暗号化、画面。
2. B（友だち一覧）: 2人だけの秘密、在席、申し込み、画面。

試験:

- 待ち合わせ: 期限、1回限り、上限、頻度の制限、別のピアによる上書きの拒否、ノードの再起動。
- 合言葉: 大文字小文字とハイフンの扱い、違う合言葉、期限切れ、2回目の入力、別のネットワーク、復号できない blob（改ざん）を読まないこと。
- 友だち: 片方だけが追加したときに何も起きないこと、双方が追加したときの在席、10分の切り替わりをまたぐ在席、友だちでないピアが申し込めないこと、HELLO のプレイヤーID が友だちと違うときに断ること、対局中に在席を預けないこと、ブロック・友だちの解除。
- 「直接接続を使わない」設定で、A・B のどちらでも相手の直接のアドレスへつながないこと。
- 本物の通信プロセス2つと協力ノード1つで、合言葉から対局、友だち一覧から対局まで。

## 9. 決めること

| 項目 | 選択肢 | 案 |
|---|---|---|
| 合言葉の形 | 10文字の英数字（50ビット）／単語を並べる形／もっと短くする | 10文字の英数字。読み上げやすく、総当たりに十分強い |
| 2人だけの秘密の作り方 | プレイヤー鍵を変換して使う／鍵交換用の長期鍵を別に持つ | プレイヤー鍵を変換して使う（保管する鍵を増やさない）。暗号の使い方として問題がないかを、実装の前に確かめる |
| 協力ノードに「どの IP どうしが友だちか」が見えること | 受け入れる／B をやめて A だけにする | 受け入れる。対局を中継するときにも見える情報で、ガイドに明記する |
| 「友だちに在席を知らせる」の既定 | 有効／無効 | 無効（利用者が有効にする） |
| 協力ノードの運用 | 開発者が運用する／参加者に協力してもらう | 実装仕様 14章の「ブートストラップ・中継運営者」と合わせて決める。A・B とも、協力ノードが無ければ使えない |
