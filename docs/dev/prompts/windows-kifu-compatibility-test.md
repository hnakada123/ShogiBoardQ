# Windows上での棋譜の相互読み込み検証を依頼するプロンプト

以下の依頼文をWindows側の作業エージェントに渡してください。「対象環境」の欄は、分かる範囲で実際の名前とパスに置き換えてください。

---

ShogiBoardQと、Windowsにインストールされている別の将棋対局ソフトとの間で、棋譜の相互読み込みを検証してください。対象ソフトは全ての棋譜形式に対応しているとは限りません。実際の対応範囲を調べ、その範囲で網羅的にテストしてください。

計画の提示だけで終わらず、Windows版の実行ファイルを使った検証、結果の照合、不具合の原因調査まで実施してください。ShogiBoardQ側に原因がある不具合は修正し、回帰テストを追加して再検証してください。結果と進捗は日本語で報告してください。

## 対象環境

- 対象ソフト名：`<ソフト名>`
- 対象ソフトの実行ファイル：`C:\<インストール先>\<実行ファイル>.exe`
- ShogiBoardQのリポジトリ：`C:\<作業フォルダ>\ShogiBoardQ`
- ShogiBoardQのGUI実行ファイル：`<Windows版ShogiBoardQ.exeのパス>`
- ShogiBoardQのCLI実行ファイル：`<Windows版shogiboardq-cli.exeのパス>`
- 検証成果物の保存先：`<作業用フォルダ>\kifu-compatibility`

未記入の情報は作業環境から確認してください。対象ソフトを一意に特定できない場合など、作業に必須の情報だけを質問し、それ以外の準備は進めてください。リポジトリの `AGENTS.md` を読み、既存の変更を保持してください。

Windowsのバージョン、両ソフトのバージョンと実行ファイルのパス、ShogiBoardQのコミット、ビルド構成、検証日時を記録してください。実行バイナリと検証するソースの対応を確認してください。以前の別OSでの結果は参考にし、今回の合否はWindowsで実行した結果から判定してください。

## 1. 対応範囲の確認

対象ソフトの「開く」「名前を付けて保存」「棋譜の貼り付け」「棋譜・局面のコピー」のメニュー、ファイルフィルター、設定、付属ヘルプを確認してください。必要なら公式の仕様・説明も確認してください。

次の候補を棚卸しし、形式・拡張子・文字コード・版ごとに対応表を作ってください。表の各欄は「対応」「未対応」「未確認」とし、判断の根拠を添えてください。

| 候補 | 確認する違い |
|---|---|
| KIF | `.kif` / `.kifu`、Shift_JIS・CP932 / UTF-8 |
| KI2 | `.ki2` / `.ki2u`、Shift_JIS・CP932 / UTF-8 |
| CSA | `.csa`、選択可能な版、文字コード指定、消費時間の精度 |
| JKF | `.jkf` / `.json`、初期局面、分岐、終局情報 |
| USI | `.usi`、`position startpos` / `position sfen`、全手順 / 現在の手まで |
| USEN | ファイル / テキスト、初期局面と分岐 |
| SFEN | `.sfen` / テキスト、現在局面 / 局面集 |
| BOD | テキスト局面図のコピー・貼り付け |

対応表には「ファイル読み込み」「ファイル保存」「テキスト貼り付け」「テキストコピー」の4欄を設けてください。読み込み可能でも保存できない場合や、貼り付けだけ可能な場合を区別してください。BODなどにファイル入出力機能があると仮定しないでください。

未対応の形式・機能は対象外として数え、失敗件数には含めないでください。対応を確認できた形式については、既知の一例が通っただけで検証を終了しないでください。SFEN・BODは局面の交換として扱い、棋譜全体の保持を要求しないでください。

## 2. 検証データの準備

`tests/fixtures/` の棋譜と、以下の既存テストを調べ、入力ケースと期待値を再利用してください。別環境の一時フォルダや過去の検証ログが存在することを前提にせず、リポジトリから再生成できるようにしてください。

- `tests/tst_kifu_conversion_service.cpp`
- `tests/tst_kifu_format_compliance.cpp`
- `tests/tst_kifconverter.cpp`、`tests/tst_ki2converter.cpp`、`tests/tst_csaconverter.cpp`
- `tests/tst_jkfconverter.cpp`、`tests/tst_jkfexporter.cpp`
- `tests/tst_usiconverter.cpp`、`tests/tst_usenconverter.cpp`
- `tests/tst_app_kifu_load.cpp`

既存の棋譜を正常棋譜、記録された反則手、破損・不正入力に分類してください。不足するケースを追加し、対応する形式と両手番で次を確認してください。

| 分類 | 主なケース |
|---|---|
| 開始局面 | 平手、駒落ち、任意局面、先手番・後手番、持駒あり、0手、終局行だけ |
| 指し手 | 全駒種、駒取り、駒打ち、成り、不成、成駒の移動、「同」、右・左・上・引・寄・直などの修飾語 |
| 過去の不具合に関係する表記 | `同　銀(79)` のような移動元付き表記、成れる場面で成らない手、連続した「同」、分岐の最初の「同」、打の省略 |
| 分岐 | 複数の変化、変化内の分岐、本譜と共通する手順、同じ局面から異なる終局理由へ分かれる変化 |
| 終局 | 投了、中断、詰み、不詰、千日手、連続王手の千日手、持将棋、引き分け、時間切れ、反則勝ち・負け、入玉宣言、不戦勝・敗、最大手数、トライ、独自の終局理由 |
| 付帯情報 | 対局者名、棋戦、日時、場所、持ち時間、独自ヘッダー、開始局面・各手・分岐・終局のコメント、複数行コメント、しおり |
| 消費時間 | 0秒、通常の消費時間、先後別の累計、長い時間表記、形式が対応する小数秒 |
| 境界条件 | 短い棋譜、長い棋譜、ヘッダーのみ、未終局、末尾改行の有無 |
| 反則手・不正入力 | 二歩、王手放置、持駒不足の打ち、駒の飛び越し、移動元不明・候補複数、空の移動元、手番不整合、駒数超過、壊れた終局欄 |

表記の検証に使う棋譜は、その直前までの局面も用意してください。断片的な1行だけで移動先や成・不成の正しさを判断しないでください。例えば、`tests/fixtures/test_nonpromotion_branch.kifu` も回帰確認に利用してください。

通常の棋譜と反則手・不正入力の合否基準を分けてください。記録された反則手の再現と、対局中の合法手判定は別の機能です。移動元を一意に決められない棋譜を推測で補ったり、駒数の妥当性検査を無効にしたりして合格にしないでください。

## 3. 両方向の実機検証

### A. ShogiBoardQから対象ソフトへ

1. 元の棋譜・局面について、指し手、各局面、分岐、終局、付帯情報の期待値を記録してください。
2. ShogiBoardQの実際の保存機能で、対象ソフトが読み込める各形式に保存してください。コピー・貼り付けの検証では、実際のコピー機能が出力したテキストを使用してください。
3. 対象ソフトのWindows版GUIで開く、または貼り付けてください。エラーだけでなく警告と途中打ち切りも記録してください。
4. 開始局面から最終手まで進め、棋譜欄と盤面が一致することを確認してください。分岐、コメント、しおり、時間表示も対応範囲内で確認してください。
5. 対象ソフトが再保存できる形式では再保存し、ShogiBoardQで読み戻してください。元の情報と比較し、どの段階で差が生じたか調べてください。

### B. 対象ソフトからShogiBoardQへ

1. 対象ソフト上で棋譜・局面を作成、編集、または読み込んだ後、対象ソフトの実際の保存機能で対応する全形式に保存してください。コピー機能も利用可能な範囲で確認してください。
2. ShogiBoardQ由来の棋譜の再保存に加えて、対象ソフト自身で作った指し手、終局理由、コメント、時間・対局情報も含めてください。
3. 保存したファイルを対象ソフト自身で再読み込みし、保存前の画面・状態と照合してください。保存前にはあった情報がファイルに書かれているかも確認してください。
4. 同じ未加工のファイル・テキストをShogiBoardQのGUIで読み込み、指し手、全局面、分岐、終局、付帯情報を照合してください。
5. ShogiBoardQで再保存し、再読み込み後にも、形式が保持できる情報が残ることを確認してください。

CLI、MCP、自動化API、WindowsのUI自動化は、生成・操作・照合を効率化するために使ってください。GUIの読み込み成功は、実際にGUIの読み込み処理を通した結果で確認してください。ファイルダイアログとクリップボードの経路も、対応する形式ごとに実際に操作してください。

ShogiBoardQのCLIの `convert-kifu`、自動化APIの `kifu.load` / `kifu.get`、MCPの `load_kifu` / `get_kifu` は利用候補です。引数と返却値は現在の実装・ヘルプで確認してください。Windowsの接続方法は現在の実装に合わせ、Unixドメインソケットの操作をそのまま持ち込まないでください。

自動化API経由の保存とGUIダイアログ経由の保存で文字コードなどの経路が異なる場合は、それぞれ確認してください。CLIで全ファイルを変換できたことだけで、対象ソフトのGUI検証を済ませた扱いにしないでください。

## 4. Windows特有の条件

- 両ソフトが実際に出力する文字コードと改行を調べ、保存されたバイト列を変更せず読み込んでください。
- 対応する範囲でCP932・Shift_JIS、UTF-8のBOMあり・なし、CRLF・LFを確認してください。拡張子だけから文字コードを決めつけないでください。
- 文字コードや改行を変えて作る追加ケースは「加工した派生ケース」と明記し、ソフトが実際に保存した原本と分けてください。
- 日本語・空白を含むフォルダ名とファイル名を使用し、パスの受け渡しとファイルダイアログの動作を確認してください。
- 日本語の対局者名・コメントを確認し、CP932で表現できない文字も別ケースにしてください。警告、置換、UTF-8への切り替えなど、実際の挙動を記録してください。
- Windowsの実際のクリップボードを経由し、全角空白、改行、手番記号、日本語文字が保持されるか確認してください。
- PowerShellなどのスクリプトで保存・採取する場合は文字コードを明示し、シェルが原本の文字コードや改行を変えないようにしてください。

作業用の設定・データフォルダを利用し、利用者の棋譜や設定を上書きしないでください。既存の起動プロセスと検証用に起動したプロセスを区別してください。

## 5. 比較方法と判定

ファイルの文字列全体の一致だけでなく、棋譜としての意味を比較してください。元の情報、保存ファイルに含まれる情報、読み込み後の状態を別々に記録してください。

- 本譜と各分岐の指し手列、開始局面、各手後の盤面・持駒・手番を比較してください。SFENの手数欄の扱いは盤面の一致と分けて報告してください。
- 分岐は配列の順番だけで照合せず、分岐点と指し手列で対応付けてください。
- 終局の種類、原文、記録した側、分かる場合の勝敗を比較してください。独自の終局理由を既知の語の部分一致で別の結果に変えないかも確認してください。
- コメント・しおりの内容と付く位置、対局情報の値、消費時間と累計を確認してください。
- 形式が表現できない情報や時間精度の差は、対応表に基づいて判定してください。比較時に正規化する項目と理由を明示し、未説明の差を一括で無視しないでください。
- JKFなど別形式への変換結果を比較に使う場合、その変換で情報が失われないか確認してください。必要ならGUIの構造化データや、該当情報を保持する別の出力でも照合してください。
- 表記の別名や空白の違いと、移動先・成り・手番・結果が変わる意味上の差を区別してください。
- CLIが不正局面を拒否し、GUIが棋譜表示用に受け付ける場合など、入口の仕様差を記録してください。CLIの結果からGUIの合否を推測しないでください。

各ケースの状態は「成功」「期待どおりの拒否・警告」「不具合」「仕様による情報欠落」「未対応」「未実施」「原因未確定」に分けてください。未実施を成功として数えないでください。

不具合は、ShogiBoardQの読み込み・書き出し、対象ソフトの読み込み・書き出し、検証スクリプトの問題に切り分けてください。対象ソフト自身で再読み込みできない場合も、原因を確定するまでは観測結果として報告してください。保存ファイルに既に存在しない情報を、ShogiBoardQの読み込み不具合と判定しないでください。

## 6. 修正と再検証

ShogiBoardQ側の不具合には、最小の再現データと回帰テストを追加して修正してください。関連する読み込み・表示・保存の経路を確認し、修正ケースに加えて影響する形式・方向も再検証してください。

ビルドと関連テストを実行し、警告も可能な範囲で修正してください。共通処理を変更した場合は全体の回帰テストも実行してください。Windowsのビルド構成に合わせ、必要なら `--config Release` や `ctest -C Release` を使用してください。対象ソフト側の問題は、再現ファイルと観測結果を残してください。

## 7. 成果物と最終報告

再実行用スクリプト、入力ファイル、両ソフトの出力原本、期待値、比較結果、ログ、必要なスクリーンショットを指定の保存先にまとめてください。各ケースにIDを付け、ファイルの生成元、生成手順、文字コード、SHA-256を記録してください。回帰テストはリポジトリの既存構成に従って追加してください。

結果表には最低限、次の項目を含めてください。

| ケースID | 方向 | 入出力経路 | 形式・版・文字コード | 合否分類 | 警告・エラー | 最初の差分位置と期待値・実値 | 証拠ファイル |
|---|---|---|---|---|---|---|---|

最終報告には、次を記載してください。

1. 実行環境、両ソフトのバージョン、検証したShogiBoardQのコミット・ビルド。
2. 入出力経路ごとの対応表と、対象外にした形式・機能の理由。
3. 方向・形式・経路ごとの実行数と各分類の件数。論理的な棋譜ケース数と、文字コードなどを変えたファイル数も分ける。
4. 不具合の再現方法、原因、修正内容、修正前後の結果。
5. 仕様上保持できない情報、対象ソフト側の問題、未解決・未実施の項目。
6. ビルド・回帰テストの結果、成果物の場所、再実行方法。

完了条件は、確認した対応範囲に対して両方向の検証が済み、全ての差分が説明され、ShogiBoardQ側で修正できる不具合が修正・再検証されていることです。対応形式が少ない場合も、その形式の表記・局面・終局・付帯情報のケースを省略しないでください。実行環境の制約で検証できない項目は理由を示し、実施済みの範囲と明確に分けて報告してください。
