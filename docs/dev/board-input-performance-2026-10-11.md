# 盤のドラッグ・クリック・着手と思考情報の表示の高速化（2026-10-11）

「駒をマウスでドラッグして指すときの描画速度は、起動直後と、エンジンと人間の対局中とで変わるか。高速化できる箇所があれば高速化する」という依頼から始め、続けてクリック・ドラッグ・解放（着手）の処理全体を見直した。最後に、エンジンの思考情報の表示（項目12）、読み筋ウィンドウ・局面集ビューア・詰将棋対局の盤（項目13）、将棋盤の拡大・縮小と盤面の回転（項目14）、残っていた課題のうち表の行の追加とエンジン情報の表の幅の計算（項目15）、Fusion のアイコンの読み込み（項目16）、スクロールバーの出入りでの表の描き直しと持駒をつまむときの駒の描画（項目17）、対局者の名前・時計の枠のスタイルと USI通信ログの追記（項目18）、表の見出しと項目の位置の計算（項目19）、ドックの中身の大きさの変化の伝わり方（項目20）、Qt の塗りのスレッド分け（項目21）、思考表の縦のスクロールバーの出入り（項目22）も高速化した。続けて、思考タブの読み筋の変換と描画を監査し、思考表の行数の上限での削除（項目23）、英語表記の読み筋の表示と棋譜解析の結果の表（項目24）、読み筋のセルの文字の描画（項目25）、読み筋の漢字への変換（項目26）を高速化した。さらに、残っていた課題を測り直し、読み筋以外の表の文字の描画（項目27）、エンジン情報の表の書体の比べ方（項目28）、評価値グラフの現在の手の移動（項目29）、コメント欄の設定し直し（項目30）を高速化した。問題点と改善内容を項目別にまとめる。

計測は Linux（Arch）、Qt 6.11.2（項目19からは Qt 6.12.0）、Release ビルド、Xvfb 上で行った。実際の画面では絶対値が変わるが、変更前後の比は同じ傾向になる。

## 1. ドラッグ中の描画（マウスが動くたびの全面再描画）

### 問題点

- `ShogiView::mouseMoveEvent` が、ドラッグ中にマウスが少し動くたびに `update()` で盤面ウィジェット全体を描き直していた。
- 全体の描き直しには、地色、木肌と影（アンチエイリアスの角丸を6枚重ねる）、罫線、全駒、駒台、段・筋の座標、子ウィジェット（対局者カード・名前・時計）がすべて含まれる。1フレームに 4.7〜27ms かかり、高DPI（2倍表示）では 60fps に届かなかった。
- **対局中は起動直後より15〜40%遅かった。** 描画処理そのものは同じで、描く物が増えるのが原因。
  - 持駒とその枚数表示（文字の配置計算を含む）
  - 手番の表示、対局者カードの枠
  - 直前の指し手と合法手のハイライト
- さらに先読み中のエンジンが CPU を使い切ると、Qt が描画の一部（全体の約4割）を任せる作業スレッドと CPU を取り合う。

### 改善内容

- ドラッグ中は、駒の移動前と移動後の範囲（影を含む）だけを描き直す。
  - `ShogiViewInteraction::draggingPieceRect`
  - `PiecePainter::paintedRect`
- 描き直す範囲（`QPaintEvent::region()`）に掛からない駒・持駒・段筋の座標・ハイライトは、描画命令ごと省く（`ShogiView::intersectsPaintRegion`）。

### 効果（1フレームの描画時間）

| 条件 | 起動直後 | 対局中 |
|---|---|---|
| マス50px・1倍 | 4.7ms → 0.12ms | 5.5ms → 0.15ms |
| マス80px・1倍 | 9.1ms → 0.19ms | 12.7ms → 0.23ms |
| 2倍表示 | 23.3ms → 0.18ms | 26.9ms → 0.26ms |

2倍表示の変更前はマス60px、変更後はマス50pxで計測した。

## 2. 候補手の矢印による不要な全面再描画（エンジン対局中）

### 問題点

- エンジンの候補手が変わるたびに `CandidateArrowController` が `ShogiView::setArrows` を呼ぶ。矢印が前と同じ（先読みの矢印を表示しない設定で、空のまま）でも、盤全体を描き直していた。
- ドラッグ中にこの全面再描画が割り込むと、引っ掛かりの原因になる。

### 改善内容

- `ShogiView::Arrow` に比較演算子を追加した。
- `ShogiViewHighlighting::setArrows` は矢印が変わらなければ何もしない。`clearArrows` も空のときは何もしない。

## 3. 対局外で指したときの棋譜欄の作り直し（手数の2乗で遅くなる）

### 問題点

- 対局していないときに盤上で指した手は、棋譜の変化として記録される。
  - 経路: `BranchTreeEditController::recordBoardMove` → `KifuBranchTree::addMove` → `treeChanged`
- そのたびに `KifuDisplayPresenter::populateRecordModel` が棋譜欄を全部作り直していた。
- 作り直しでは行を1行ずつ追加していた。行を足すたびに次の2つが全行の文字幅を測り直すため、処理量が手数の2乗に比例していた。
  - `RecordPane::onKifuRowsInserted` の `resizeColumnToContents(0)`
  - 列幅の自動調整（`QHeaderView::ResizeToContents`）
- 1手の処理時間（実アプリ）は、1〜20手目で 25ms、81〜100手目で 135ms、141〜160手目で 244ms、330手前後で約0.6秒だった。プロファイルでは処理時間の72%がこの部分だった。
- 同じ作り直しは、次の場面でも起きていた。
  - 棋譜の読み込み、分岐の切り替え（`populateRecordModelFromPath`）
  - 現在の局面から対局を始めるとき（`PreStartCleanupHandler`）

### 改善内容

- 3か所とも、行を `QList` に集めてから `appendItems` でまとめて追加するようにした。行追加の通知は1回だけになる。

## 4. 評価値グラフの横軸を1手ごとに2回作り直していた

### 問題点

- `EvaluationGraphController::setCurrentPly` は、先に SFEN 履歴の長さを記録の長さとして渡し（`setRecordLength`）、次に現在の手数を渡していた（`setCurrentPly`）。
- 対局外で指した手は SFEN 履歴に入らないので、記録の長さは0のままになる。そのため1手ごとに次のことが起きていた。
  1. 横軸がいったん「20手まで」に縮む。
  2. すぐ「170手まで」などに戻る。
  3. Qt Charts が目盛りの文字を2回作り直す（`QTextDocument::setHtml` を含む）。
- 項目3を直した後のプロファイルでは、処理時間の28%がこの部分だった。

### 改善内容

- 記録の長さとして `max(SFEN 履歴の長さ, 現在の手数)` を渡す。2つの呼び出しを終えた後の状態は変更前と同じで、途中で横軸が縮まなくなる。

### 効果（項目3・4の合計。実アプリでの対局外の着手1手）

| 手数 | 変更前 | 変更後 |
|---|---|---|
| 1〜20手目 | 25ms | 17.5ms |
| 81〜100手目 | 135ms | 24ms |
| 141〜160手目 | 244ms | 29.5ms |

## 5. 駒をつまむ・戻すときと、全面の描き直しが重い

### 問題点

- 1回目のクリックで駒をつまむと、次の処理がそれぞれ `update()` で盤全体を描き直す。Qt が1回の描画にまとめても、毎回全面を描いていた。
  - `ShogiView::startDrag`
  - 選択マスのハイライトの追加
  - 合法な移動先（数マス〜数十マス）のハイライトの追加
- 合法手の判定そのものは軽く、時間のほとんどは全面の描き直しだった。
- 全面の描き直しでは、木肌の影の角丸（盤全体の大きさで塗りを計算する）と罫線のアンチエイリアスが重い。この描き直しは着手、エンジンの着手、棋譜をたどる操作のたびに起きる。

### 改善内容

- **変わらない部分を画像にする:** 局面によらない地色・木肌と縁・影・罫線・駒台・星を1枚の画像に描いておき、全面の描き直しでも貼るだけにした（`ShogiView::drawStaticLayer`）。
  - 次のいずれかが変わったときだけ作り直す。作り直しの呼び忘れが起きないよう、条件を比較する方式にした。
    - ウィジェットの寸法、マスの大きさ、盤・駒台の位置
    - 配色（地・盤・駒台・罫線）、木目の有無
    - 画面倍率、物理画素に対する位置の端数
  - 端数倍率（125%・150%）では盤の左上が物理画素の途中に来る。画像もその端数だけずらして描き、物理画素の境目に合わせて貼ることで、直接描いたときと同じ画素にした。
  - 局面編集中だけ表示する駒箱は、ラベルの文字も含むため画像に入れない。
  - 項目1で入れた「木肌・罫線を範囲内だけ描く」処理は不要になったので、元の単純な描画に戻した。
- **変わったマスだけを描き直す:**
  - ハイライトの追加・削除は、そのマスだけを描き直す（`ShogiViewHighlighting::updateHighlightArea`）。
  - `startDrag` は、つまんだマスと持ち上げた駒の部分だけを描き直す。
- **マスの位置計算をまとめる:** 盤・駒台（疑似座標 10/11）・駒箱（12）のマスの位置を `ShogiView::fieldRect` にまとめ、ハイライト側にあった同じ計算を置き換えた。
- **ドラッグの終了は全体を描き直したまま:** `endDrag` は全体の描き直しを残した。`ShogiBoard` は駒台・駒箱の枚数だけが変わったときに通知を出さず、局面編集で駒台どうしを移す操作などが `endDrag` の全面描き直しに頼っているため。（その後、項目7で `ShogiBoard` に駒台の通知を加え、変わった所だけを描き直すようにした）

### 効果（マス60px、単体ベンチ。起動直後・対局中・反転表示の3場面の範囲）

| 操作 | 1倍表示 | 2倍表示 |
|---|---|---|
| つまむ | 5.8〜6.9ms → 0.8〜3.4ms | 18〜24ms → 2.1〜7.3ms |
| 戻す（同じマスをクリック） | 5.0〜6.8ms → 1.5〜2.4ms | 18〜22ms → 5.6〜7.0ms |
| 全面の描き直し | 5.0〜6.8ms → 1.9〜2.5ms | 18〜19ms → 6.9〜7.5ms |

実アプリでも、つまむ・戻すの1クリックは 6.3ms → 2.3ms になった（自動化 API の通信時間を含む）。2倍表示でつまむ時間に幅があるのは、持駒の角は打てるマスが約45あり、その分だけ描き直す範囲が広いため。

## 6. 対局外の着手で残っていた重さ（棋譜欄の列幅・分岐ツリー・指し手の表記）

### 問題点

項目3・4を直した後も、対局外の着手は160手で1手約30msかかり、手数に比例して増えていた。

- **棋譜欄の列幅:** 列幅の自動調整（`QHeaderView::ResizeToContents`）は、行を足したときだけでなく、現在行の強調を変えたとき（`setCurrentHighlightRow` → `dataChanged`）にも全行の大きさを測り直す。1行ごとに Qt のスタイルで文字を配置するので重い（約20%）。
- **分岐ツリー:** `treeChanged` を受けるたびに `BranchTreeManager::setBranchTreeRows` が図形を全部作り直していた（約17%）。ライブ対局用には1手だけ描き足す `appendNodeToRow` があったが、対局外の着手では使われていなかった。
- **指し手の表記:** `KifuPresentation::status` が呼ばれるたびに、16個の終局語を UTF-8 から文字列へ変換し直していた（約5%）。棋譜欄の表示のたびに呼ばれる。

### 改善内容

- **セルの大きさのキャッシュ:** 棋譜欄・分岐候補欄の描画クラス（`RecordHighlightDelegate`、`src/widgets/recordhighlightdelegate.*` に分離）で、セルの大きさを文字・書体・スタイル・状態・配置ごとに覚えて使い回す。大きさの計算方法は変えないので、列幅は変更前と同じになる。書体は `QFont::key()`（文字列にする処理が重い）ではなく `QFont` のまま比べる。
- **分岐ツリーの差分追加:** `setBranchTreeRows` は、新しい行が「1つの行の末尾に1手増えただけ」のとき、既存の `appendNodeToRow` でその手だけを描き足す（`BranchTreeManager::appendSingleMove`）。行の並びや他の手が変わったとき、表記の切り替えなど何も増えていないときは、従来どおり全体を作り直す。
- **終局語の変換:** `status()` の終局語の原文は1回だけ文字列にして使い回す。訳は表示言語に合わせて毎回引く。

### 効果（実アプリでの対局外の着手1手）

| 手数 | 最初 | 項目3・4の後 | 今回 |
|---|---|---|---|
| 1〜20手目 | 25ms | 17.5ms | 10.0ms |
| 81〜100手目 | 135ms | 24ms | 11.5ms |
| 141〜160手目 | 244ms | 29.5ms | 11.0ms |

手数によらずほぼ一定になった。

## 7. 駒を置く・戻すときと、着手のたびの全面の描き直し

### 問題点

- `ShogiBoard` は盤上のマスが変わったとき（`setData`）だけ通知（`dataChanged`）を出し、駒台の枚数の増減（`addStandPiece`・`consumeStandPiece`）は通知していなかった。駒箱の枚数は盤と駒台から数えるので、これも通知がない。
- そのため次の2つが全面の描き直しのままだった。
  - `ShogiView` は `dataChanged` を受けると盤面全体を描き直していた。着手のたびの全面描き直しになる。
  - `ShogiView::endDrag` も全面を描き直していた。局面編集で駒台どうしを移すなど、通知のない変化を描くためにこれに頼っていた。
- `endDrag` は、手番が替わるたびに呼ばれる `BoardInteractionController::finalizeDrag` からも、ドラッグしていないときに呼ばれていた。

### 改善内容

- **駒台の通知:** `ShogiBoard` に `standChanged(Piece)` を加え、駒台の枚数が実際に変わったときに出す（`initStand` は駒台全体を表す `Piece::None`）。
- **変わった所だけ描き直す:** `ShogiView` は `dataChanged` を受けたらそのマス（はみ出す駒の影を含む）だけを、`standChanged` を受けたらその駒の駒台のセルだけを描き直す。局面編集中は駒箱も一緒に描き直す。
- **ドラッグの終了:** `endDrag` は、持ち上げた駒とつまんだマスだけを描き直す。ドラッグしていないときは何もしない。

### 効果（マス60px、単体ベンチ。起動直後・対局中・反転表示の3場面の範囲）

| 操作 | 1倍表示 | 2倍表示 |
|---|---|---|
| つまむ | 0.8〜3.4ms → 0.19〜2.3ms | 2.1〜7.3ms → 0.3〜6.3ms |
| 戻す（同じマスをクリック） | 1.5〜2.4ms → 0.12〜1.0ms | 5.6〜7.0ms → 0.2〜3.3ms |

いずれも項目5の後からの変化。実アプリの対局中では、つまむ・戻すの1クリックが 2.3ms → 0.6ms になった。

## 8. 時計の文字サイズ合わせ

### 問題点

- `ShogiView::fitLabelFontToRect` は、時計と手番の表示に収まる文字サイズを、毎回18回の二分探索（そのたびに `QFontMetrics` を作る）で求めていた。
- 時計は1秒ごと、手番の表示は手番が替わるごとに合わせ直すので、対局中の着手の約9%を占めていた。

### 改善内容

- 文字・収める大きさ・大きさ以外の書体が同じなら、前に求めた文字サイズを使い回す。探索の方法は変えないので、選ばれる文字サイズは変更前と同じ。

### 効果（項目7・8の合計。実アプリでの対局中の着手1手）

序盤で 10〜12ms → 5〜9ms。

## 9. 盤を描き直すたびに親の下地を塗っていた

### 問題点

- `ShogiView` は背景の画像（項目5）で自分の範囲をすべて塗っている。それでも Qt は不透明なウィジェットだと知らないため、描き直しのたびに親ウィジェットの下地を同じ範囲に塗っていた（`QWidgetPrivate::paintBackground`）。
- 持駒の角をつまむ場合（2倍表示）の約16〜19%を占めていた。

### 改善内容

- `ShogiView` に `Qt::WA_OpaquePaintEvent` を付けた。
- 盤が無いときやエラーのときは、今まで見えていた親の下地と同じ色で塗る。

### 効果（マス60px・2倍表示、単体ベンチ）

- 全面の描き直し: 6〜8.3ms → 5.2〜6.2ms
- 対局中に持駒の角を戻す: 3.3ms → 2.5ms

1倍〜2倍で、変更前と画素が一致した。

## 10. 局面を丸ごと替えるとき（棋譜をたどる・待った・読み込み）

### 問題点

- `ShogiBoard::setSfen` は局面全体を替え、`boardReset` を出す。`ShogiView` はこれを受けると盤全体を描き直していた。
- 局面を替えるたびに、全面の描き直し（1倍で約1〜2ms、2倍で約5〜8ms）がかかっていた。

### 改善内容

- **画面に出ている駒の記録:** `ShogiView` は、画面に出ている駒を記録する（盤はマスごと、駒台は駒ごとの枚数）。描いたときに記録するので、通知の無い変更や全体の描き直しが間に入っても食い違わない。
- **`boardReset` のとき:** 局面と記録を比べ、違うマス・駒台のセル（局面編集中は駒箱も）だけを描き直す（`ShogiView::onBoardReset`）。
- **一部だけ描き直したマスの扱い:** 隣のマスを描き直すと、影のはみ出しの分だけこのマスも一部が描き直される。このとき、記録と同じ駒なら記録を保ち、違う駒なら不明にする。初めは一部だけのマスをすべて不明にしていたが、それでは不明なマスが差し替えのたびに外側へ広がり、毎回マス約52個分を描き直していた。
- **`initStand` の通知を止める:** `setSfen` の中で呼ぶ `initStand` は駒台の通知（`standChanged`）を出さない。`setSfen` の最後の `boardReset` で駒台の差分も描き直すため。

### 効果（マス60px、単体ベンチ。1手違う局面への差し替え）

| 表示 | 全面の描き直し | 今回 |
|---|---|---|
| 1倍 | 1.0〜1.4ms | 0.10〜0.13ms |
| 2倍 | 6.8〜7.9ms | 0.22ms |

描き直す範囲は1回でマス約2.8個分になった。

## 11. 対局外の着手と、棋譜をたどるときの棋譜欄・コメント欄・盤の更新

### 問題点

一時的にイベントを記録する処理を入れ、1手ごとにどのウィジェットが描き直しやレイアウトの再計算を受け取るかを調べた。gdb で盤への `update()` の呼び出し元も調べた。

- **盤全体の描き直し:** 着手や手数の移動のたびに盤を読み込み直す `ShogiView::applyBoardAndRender` が、変わっていない駒の画像28種類を設定し直し、盤全体を描き直していた。エンジンの着手でも呼ばれる。
- **レイアウトの再計算の連鎖:** コメント欄の見出し（「N手目」）を `QLabel::setText` で書き換えるたびに、Qt がレイアウトの再計算を親へ伝えていた。伝わる順は、ツールバー → コメント欄 → コメント欄のドック → `MainWindow` で、最後に全ドックの配置を計算し直していた。Fusion スタイルはこの計算のたびに、ドックのタイトルのボタンのアイコンを画像ファイルから読み直す。
- **棋譜欄の全行の作り直し:** 項目3でまとめて追加するようにしたが、1手ごとに全行を作り直していた。続けて表示領域全体の強制更新（`KifuDisplayCoordinator::updateRecordView`）と、全行の分岐の印の変更通知（`setBranchPlyMarks`）も出していた。
- **分岐候補欄のリセット:** 候補が元から空でもモデルをリセット（`clearBranchCandidates`）し、表全体を描き直していた。

### 改善内容

- **盤の読み込み直し:** `applyBoardAndRender` は、盤そのもの・マスの大きさが変わったときだけ全体を描き直す。`loadPieceImages` は、画像が実際に変わったときだけ描き直す。局面の変化は `ShogiBoard` の通知（項目7・10）で、変わったマスだけを描き直す。
- **コメント欄の見出し:** 大きさを、とりうる最も長い表示（「開始局面」「9999手目」）に合わせて固定した（`CommentEditorPanel::fixPositionLabelSize`）。
  - Qt は、大きさが固定されたウィジェットからはレイアウトの再計算を親へ伝えない。
  - 後ろに伸縮スペースがあるので、余った幅はそこで吸収され、見た目は変わらない。
  - 縦方向は Qt が中央に置く。
  - 文字サイズが変わったときは計算し直す。
- **棋譜欄:**
  - 今の行の後ろに手が増えただけなら、増えた行だけを足す。それ以外は従来どおり全行を作り直す。行を削る差分更新はしない。現在行が消えると選択の変更通知が出て、棋譜の移動が起きるため。
  - 表示領域の強制更新は、全行を作り直したときだけにした。強制更新は分岐のバグ修正（2026-01-31）で入ったもので、分岐の切り替えでは全行を作り直すので残る。
  - 分岐の印が変わらなければ、変更通知を出さない。
- **分岐候補欄:** 既に空なら消去でリセットしない。

### 効果（実アプリ。変更前と変更後を交互に2回ずつ起動して計測）

ほかのプログラムが CPU を使っていて時間がぶれたため、ぶれにくい「実行した命令数」でも比べた。

| 操作 | 変更前 | 変更後 |
|---|---|---|
| 対局外の着手（160手を指した後の80手の平均） | 4840万命令、CPU 13〜17ms | 3060万命令（-37%）、CPU 8.4〜10.7ms |
| 手数の移動（`kifu.goto` で100手目と101手目を往復） | 2220万命令、CPU 6.2〜9.0ms | 1240万命令（-44%）、CPU 3.6〜4.6ms |

## 12. エンジンの思考情報の表示

### 問題点

エンジン同士の対局（Hayanagi、秒読み1秒、41手）で GUI の処理を `perf record` で調べ、一時的にイベントを記録する処理で、どのウィジェットが描き直しやレイアウトの再計算を受け取るかを数えた。

- **ドックとメインウィンドウまでの描き直し:**
  - 思考タブの表は、背景色をスタイルシートで付けている。このとき Qt は表示領域の自動の塗りつぶしを止めるので、表示領域は不透明と見なされない。縦スクロールバーとエンジン情報の表の見出しも背景を塗らない。
  - そのため、思考情報が届いて表が変わるたびに、下にある思考ドックと `MainWindow` まで描き直していた。ドックを描くたびに、Fusion スタイルがタイトルのボタンのアイコンを画像ファイルから読み直す（項目11）。
  - 41手の対局で、思考ドックを329回、`MainWindow` を380回描き直していた。棋譜欄も、行が増えるたびに棋譜ドックまで描き直していた。
- **エンジン情報の表（エンジン名・予想手・探索手・深さ・ノード数など）:**
  - `info` 行1つで最大6つの値が変わる。値ごとに、値が同じでも、列幅と表の大きさを計算し直していた。
  - 表の幅が変わると、レイアウトの再計算がエンジン情報の表 → 思考タブ → 思考ドック → `MainWindow` と伝わる。
- **読み筋の列:**
  - Qt は項目の文字を「…」で省略する前に、文字列全体の文字配置を2〜3回計算する。
  - 読み筋は表示幅の数倍の長さになることがある。行が増えるたびに、見えている全行を描き直すので重い。
- **USI通信ログ:** 1行追記するたびに、カーソルの位置決めを5回していた。位置決めのたびに Qt はその行の文字配置を計算し直す。ログのタブが隠れていても起きる。

### 改善内容

- **ドックの中身を不透明にする（`OpaqueBackground::keep`）:**
  - 対局情報・思考・検討・USI通信ログ・CSA通信ログ・棋譜コメント・分岐ツリー・棋譜の各ドックの中身に、親と同じ背景色を自分で塗らせる。中の部品を描き直しても、ドックと `MainWindow` は描き直さない。
  - 塗るのは、メインウィンドウに収まっていて、背景色が親とメインウィンドウと同じときだけ。見た目は変わらない。
    - 切り離したドックは、ドックの枠が少し明るい色で背景を描くので塗らない。
    - 分岐ツリーの中身（枠付きの表示領域）は背景色が違い、塗ると枠の角の色が変わるので塗らない。
    - 塗るかどうかは、スタイルの適用・パレットの変更・ドックの切り離しと戻しのたびに判断し直す。
- **エンジン情報の表:**
  - 値が変わらなければ何もしない。
  - 列幅と表の大きさの計算は、`info` 行の値をすべて反映した後に1回だけ行う。キューに積んだ呼び出しにするので、描画より先に処理され、古い幅で描かれることはない。
- **読み筋の列（`PvTextDelegate`、思考と検討の表）:**
  - 表示幅より十分先（最大の文字幅4つ分）で切った文字列を Qt に渡す。省略の位置は表示幅の内側で決まるので、結果は全文を渡した場合と同じ。
  - 切る位置は文字列ごとに一度だけ計算して覚える。
  - 切ると行の高さが変わる場合（後ろにだけ別のフォントの文字がある）、改行や書字方向の制御文字を含む場合は切らない。
- **USI通信ログ:**
  - 末尾への移動を、追記の編集の中で行う。編集の外で移ると、最終行の文字配置を計算し直す。
  - 利用者のカーソルが末尾にないときは、カーソルの保存と復元を省く。末尾への追記で動くのは末尾にあるカーソルだけで、先頭のログの削除にはカーソル自身が追従する。

### 効果

エンジン同士の対局（Hayanagi、秒読み1秒、41手で終局）を、変更前と変更後で交互に3回ずつ行い、GUI プロセスだけの CPU 時間と命令数を測った。

| 計測 | 変更前 | 変更後 |
|---|---|---|
| GUI の1手あたりの命令数 | 1億600万〜1億800万 | 7100万〜7300万（-33%） |
| GUI の1手あたりの CPU 時間 | 41〜44ms | 30〜35ms |
| 思考ドックの描き直し（41手） | 329回 | 3回 |
| `MainWindow` の描き直し（41手） | 380回 | 58回（ドックの境目の幅6pxの帯やツールバーのボタンなど、小さな範囲だけ） |

部分ごとの単体ベンチ（命令数）:

| 計測 | 変更前 | 変更後 |
|---|---|---|
| USI通信ログに3000行を追記（ログのタブが隠れているとき、起動分を除く） | 25.2億 | 17.5億（-31%） |
| 思考表に300行を1行ずつ追加（読み筋6〜19手、起動分を除く） | 83.7億 | 80.9億（-3%） |
| 同（読み筋20〜39手） | 123.2億 | 89.7億（-27%） |

読み筋が表示幅に収まる程度なら効果は小さく、長い読み筋ほど効く。

## 15. 表の行の追加と、エンジン情報の表の幅の計算

### 問題点

項目14の後にエンジン同士の対局をもう一度 `perf record` で調べた。

- **表の行の追加:**
  - Qt の `QTableView` は行数が変わると、表示領域全体の描き直しを頼む（`rowCountChanged` → `doItemsLayout` → `viewport()->update()`）。
  - 棋譜欄は1手ごとに末尾へ、思考表は思考情報が届くたびに先頭へ行を足すので、見えている全行を毎回描き直していた。
  - GUI の処理のうち、棋譜欄の描画が約11%、思考表などの表の描画が約15%を占めていた。
- **対局中の棋譜欄の全体の描き直し:** 1手ごとに `LiveGameSession::recordModelUpdateRequired` を受けて、棋譜欄の表示領域全体の描き直しを頼んでいた。今はモデルが行の追加と現在行の強調の変更を知らせるので、要らなかった。
- **エンジン情報の表の幅の計算（項目12）:** 値が変わらない列の文字の幅も毎回測っていた。また列幅が変わるたびに、見出しの大きさも測り直していた。GUI の処理の約4%だった。

### 改善内容

- **行の追加で、変わった所だけを描き直す表（`IncrementalTableView`）:** 棋譜欄と思考表（2つ）で使う。
  - 末尾への追加（棋譜欄）: 追加した行と、その間に内容が変わった行（現在行の強調の移動など）だけを描き直す。
  - 先頭への追加（思考表。一番上を表示しているとき）: 既にある行を画面のずらし（blit）で下げ、空いた上の行だけを描く。
  - 行が増えて表示位置が変わる場合（一番下まで表示していると、最後の行を下端に合わせていたのを行の上端に合わせ直す）は、その分も画面のずらしで動かす。
  - Qt は配置のやり直しを待つ間、内容が変わった行を描き直さない（全体を描き直す前提のため）。その行を覚えておいて描き直す。
  - 追加の種類は、追加前の通知（`rowsAboutToBeInserted`）で記録する。棋譜欄は追加の直後にスクロールして配置をその場でやり直すので、追加後の通知では間に合わない。
  - 描き直しの予約は、スクロールが済んでから入れる。予約が残ったまま画面をずらすと、ずらした所が古いまま残ることがあった。
  - 削除・並べ替え・リセット・列の変更や、文字の大きさ・描画クラス・スタイルの変更が重なったときは、これまでどおり全体を描き直す。
  - 画面のずらしには、表示領域が不透明である必要がある。スタイルシートで背景色を付けた表では、Qt が表示領域の自動の塗りつぶしを止めるので、整数倍率のときだけ戻す。小数倍率では表示領域の端が物理画素の途中に来て、塗ると枠線の画素が変わる（項目31）ので戻さない。そのときの画面のずらしは、Qt が全体の描き直しに切り替える。
- **対局中の棋譜欄の全体の描き直しをやめた:** `recordModelUpdateRequired` シグナルと、その受け取り（`KifuDisplayCoordinator::onLiveGameRecordModelUpdateRequired`）を外した。コメント・しおりの編集など、行をモデルの外で書き換える処理も変更を知らせていることを確かめた。
- **エンジン情報の表:**
  - 列ごとに前回測った文字と幅を覚え、文字と書体が同じなら測り直さない。
  - 見出しの高さは、書体・スタイルシート・見出し・表示する列が同じなら前回の値を使う。

### 効果（エンジン同士の対局、Hayanagi、秒読み1秒、41手。変更前後を交互に3回ずつ）

| 計測 | 項目14まで | 項目15の後 |
|---|---|---|
| GUI の1手あたりの命令数 | 約7,170万 | 約5,660万（-21%） |
| GUI の1手あたりの CPU 時間 | 30〜33ms | 25〜28ms |
| 棋譜欄の描き直し（41手） | 48回すべて表示領域全体、約931万画素 | 全体は11回、約281万画素（-70%） |
| 思考表の先頭への追加 | 表示領域全体 | 追加した1行分（表示中の約3行のうち1行） |

思考表は、手ごとの消去（リセット）と、その後に縦のスクロールバーが出るときは全体を描き直す。表示領域の幅が変わるので、必要な描き直し。

## 16. Fusion のアイコンの読み込み

### 問題点

- Qt の Fusion スタイルは、ドックのタイトルのボタン（閉じる・切り離す）のアイコンを頼まれるたびに、内蔵の画像6枚（10〜64px）を読み込んで作る（Qt 6.11 の `QFusionStyle::iconFromTheme`）。作ったアイコンを使い回す仕組みはない。
- アイコンはボタンを描くときだけでなく、タイトルの文字やボタンの位置を計算するとき（`QCommonStyle::subElementRect`）にも作られる。ドックを描き直すときと、ドックの配置を計算し直すときに何度も呼ばれる。

### 改善内容

- **Fusion を包んでアイコンを使い回す（`ApplicationStyle::create`）:**
  - Fusion を `QProxyStyle` で包む。内蔵の画像から作る4種類のアイコン（`SP_TitleBarNormalButton`・`SP_TitleBarMinButton`・`SP_TitleBarCloseButton`・`SP_DockWidgetCloseButton`）は、1回だけ作って使い回す。
  - これらの画像は部品や設定によらないので、見た目は変わらない。ほかはすべて Fusion に任せる。
  - アプリ（`main.cpp`）と GUI 機能テスト（`tst_gui_functional`）の両方で、このスタイルを使う。
- **見送っていた理由を調べ直した:**
  - 項目11の時点では、Fusion を包むと見た目が変わると考えて採らなかった（項目31）。
  - Qt 6.11 のソースでは、ウィジェット側で Fusion かどうかを見ているのは、既定のスタイルシートの `QComboBox[readOnly="true"] { -qt-background-role: button; }` だけだった。
  - `QComboBox` には `readOnly` という属性がなく、アプリでも付けていない。この規則は今も何にも当てはまっていないので、包んでも見た目は変わらない。

## 17. スクロールバーの出入りでの表の描き直しと、持駒をつまむときの駒の描画

### 問題点

項目16の後に残っていた課題（項目33）を、エンジン同士の対局（Hayanagi、秒読み1秒、41手）と単体ベンチで調べ直した。描き直しとレイアウトの再計算は、一時的に入れたイベントの記録（ウィジェットごとの回数・範囲・処理時間）で数えた。

- **思考表のスクロールバーの出入り:**
  - 思考表は手ごとに消して足し直すので、縦のスクロールバーが消えたり出たりし、表示領域の幅と最後の列（読み筋）の幅が変わる。
  - 幅が変わると、Qt は表示領域全体を描き直す。それとは別に、Qt の列幅の処理（`QTableView::columnResized`）が0msのタイマーで表示領域全体の描き直しを頼む。このタイマーは描画の後に動くので、同じ内容を2回続けて描いていた。
  - 41手の対局で、思考表（2つ）の表示領域の描き直しは241回、うち全体が178回あり、合わせて約152msだった。行が入っている表を全体で描くと1回1.6ms前後かかる。
- **思考表の列幅の保存:** 最後の列が伸び縮みするたびに、列幅を設定ファイルに書き込んでいた（1手に2回）。検討タブは、最後の列を保存の対象から外していた。
- **持駒をつまむとき（単体ベンチ、マス60px）:**
  - 持駒の角をつまむ処理は1倍で2.47msかかり、盤全体の描き直し（1.65ms）より重かった。打てるマス（約45）ごとに、背景の画像・ハイライトの塗りと枠・駒を描く。
  - 駒を描くたびに、駒画像のキャッシュのキーを文字列で組み立てていた（つまむ・戻す処理の約5%）。
- **小数倍率での表の描き直し:** Qt は、画面のずらしの量が物理画素の整数でないと、ずらさずに全体を描き直す（Qt 6.11 の `QBackingStore::scroll`）。思考表の行の高さ（標準の文字の大きさで23px）は、1.25倍で28.75画素、1.5倍で34.5画素になる。棋譜欄も、1.25倍では行の高さが4の倍数でなければ同じになる。表示領域を不透明にしても、行を足して表示がずれるときは全体を描き直すしかない。
- **エンジン情報の表の幅:** 41手の対局で、思考ドックの最小幅はエンジン情報の表の幅に合わせて580〜630pxの間で変わっていた。ドックの最小幅が実際に変わるので、`MainWindow` の配置の計算（1回約1ms）は省けない。表の幅を測るときの書体の読み込み（`QFontDatabasePrivate::load`）は、「と」「九」などを初めて測るときの各8.6msの1回限りで、毎回ではなかった。

### 改善内容

- **スクロールバーの出入りでの二重の描き直しをやめる（`IncrementalTableView`）:**
  - 見出しの列幅の変化（`sectionResized`）を受ける Qt の接続を外し、自分の処理を通してから Qt の処理（`columnResized`）を呼ぶ。
  - 表示領域の大きさの変化を処理している間に列幅が変わり、前回描いたときから表示領域の大きさが変わっている場合は、Qt の処理を呼ばない。大きさの変化で表示領域全体の描き直しが予約済みで、配置（見出し・スクロールバー）もその処理の続きで直るため。
  - それ以外（列の境目のドラッグ、内容に合わせた列幅の変化など）は、これまでどおり Qt に任せる。
- **最後の列の伸び縮みだけでは列幅を保存しない（`EngineAnalysisPresenter`）:** 表示領域いっぱいまで伸ばしている最後の列の幅の変化では保存しない。ほかの列の幅を変えたときは、これまでどおりすべての列の幅を保存する。検討タブと同じ扱い。
- **駒画像のキャッシュのキー（`PiecePainter`）:** 駒・大きさ・倍率・影の有無の組から `QPixmapCache::Key` を引く表を持ち、文字列を組み立てない。画像そのものは、これまでどおり `QPixmapCache` に任せる。

## 18. 対局者の名前・時計の枠のスタイルと、USI通信ログの追記

- **対局者のスタイルシート（`ShogiViewHighlighting`）:**

  - 枠と手番の札は、一度見つけたら覚えておく（`QPointer`）。
- **USI通信ログ（`UsiLogPanel`）:**
  - 表示欄の文書に、`QPlainTextDocumentLayout` を派生させた行の配置を使う。
  - 末尾に区切りと新しい行を足しただけの変化は、新しい行だけの変化として渡す。直前の行の配置はそのまま使う。
  - 文書は、`QPlainTextEdit` が自分で作るものと同じ設定（既定の書体・描画先）にして差し替える。

## 19. 表の見出しと項目の位置の計算

### 問題点

項目18の後に残っていた課題（項目33）を、エンジン同士の対局（Hayanagi、秒読み1秒、41手）と単体ベンチで調べ直した。この項目からは、Qt 6.12.0 で測った。

- **表の見出しの大きさの計算（GUI の処理の約4.9%）:**
  - Qt の `QHeaderView` は、自分の大きさが変わるたびに見出しの高さの覚えを捨てる。次に聞かれたとき、すべての見出しの文字を測り直す（`sectionSizeFromContents`）。
  - 思考表は縦のスクロールバーが出入りするたびに見出しの幅が変わり、エンジン情報の表は表の幅が変わるたびに見出しの幅が変わる。同じ見出しを何度も測っていた。
- **棋譜欄の見出しの描き直し:**
  - Qt の見出しは、選択に掛かる列と、列全体が選ばれた列を描き分ける。そのため表の選択が変わるたびに、変わった範囲の見出しを描き直す。
  - 棋譜欄は1手ごとに選ぶ行が替わるので、見出し全体を描き直していた（41手で45回）。行単位の選択なので、描き分けは変わらない。

  - 絵を文字の左右に置く配置（表の既定）では、位置は文字の大きさによらず「文字があるか」だけで決まる（`QCommonStylePrivate::viewItemLayout`）。
- **手番の交代での「編集終了」ボタン:** 局面編集の間だけ表示するボタンの配置と文字の大きさ合わせ（文字を何度も測る）を、隠れている間も手番が替わるたびにしていた（単体ベンチで手番の交代の約2.4%）。

### 改善内容

- **表の見出し（`TableHeaderView`）:** 棋譜欄・思考表（`IncrementalTableView`）とエンジン情報の表で使う。設定は Qt の表の既定の見出しと同じ。

  - 見出しを描いたときの、選択による描き分け（選択に掛かるか、列全体が選ばれたか）を見出しごとに覚える。選択が変わっても、描き直す範囲の見出しの描き分けが描いたときと同じなら描き直さない。
- **項目の各部の位置（`ApplicationStyle`）:**
  - 文字があり、絵を文字の左右に置く項目では、位置を決める値ごとに、Fusion が求めた位置を項目の左上からの位置として覚えて使い回す。値は、項目の大きさ・チェックと絵の有無と絵の大きさ・配置・文字の向き・解像度。
  - 初めての条件は、文字を英字1文字にして Fusion に求めさせる。項目をずらしてもう一度求め、位置が一緒に動くか、動かないか（チェックの印の無い項目のチェックの位置）を確かめてから覚える。
  - スタイルシートで項目の枠を描く表（思考表）は、Qt がスタイルシートの処理の中で位置を求めるので、この経路を通らない。
- **「編集終了」ボタン（`ShogiView::relayoutTurnLabels`）:** ボタンが隠れている間は配置しない。表示する処理（`PositionEditController::showEditExitButtonOnBoard`）は表示の直前に配置し直すので、表示したときの位置は同じ。

## 20. ドックの中身の大きさの変化の伝わり方

### 問題点

項目19の後に残っていた課題（項目33）のうち、エンジン情報の表の幅の変化を調べ直した。

- **思考ドックからメインウィンドウへの配置のやり直し:**
  - エンジン情報の表は、探索手などの文字が変わると幅が変わる。思考ドックには、2つのエンジンの情報の表が縦に並んでいる。
  - Qt のレイアウトは、中の部品の大きさが変わると、自分の大きさの条件（推奨の大きさ・最小の大きさなど）が変わらなくても、親に配置のやり直しを伝える（`QLayout::activate`）。そのため表の幅が変わるたびに、思考ドックを通ってメインウィンドウの配置の計算まで起きていた。
  - メインウィンドウの配置の計算では、すべてのドックのタイトルの大きさの計算（項目31）とドックの配置をやり直し、ドックの間の区切りを描き直す。
  - エンジン同士の対局（41手）で、メインウィンドウの配置の計算は57回あった。そのうち28回は、どのドックの最小の大きさ・推奨の大きさも前回と同じだった（もう一方のエンジンの表のほうが広いときなど）。
- **調べたが対象外としたもの:**
  - エンジン情報の表の幅の計算で、書体の読み込み（fontconfig への問い合わせ）が目立った。gdb で呼び出しを記録すると、対局中は表を初めて測るときの2回だけで、毎手のものではなかった。
  - 思考表のスクロールバーは、行が増えるたびにつまみの大きさが変わるので描き直す（必要な描き直し）。

### 改善内容

- **中身の大きさの条件が変わったときだけ親に伝える入れ物（`LayoutBoundaryWidget`）:**
  - 中身を自分の大きさいっぱいに置く、中身1つだけのレイアウトを持つ。
  - 中身の `updateGeometry` は、表示中かどうかにかかわらず、その場で親のレイアウトの `invalidate` を呼ぶ（`QWidgetPrivate::updateGeometry_helper`）。そこで中身の大きさの条件を前回と比べ、変わったときだけ入れ物の `updateGeometry` を呼ぶ。中身をドックに直接置いた場合に、ドックへ伝わるのと同じ時点になる。
  - 比べるのは、推奨の大きさ・最小の大きさの目安・明示した最小と最大の大きさ・伸び縮みの方針・伸びる向き・幅に応じた高さの有無。
  - 親のレイアウトには、前回伝えた値を見せる。明示した大きさと伸び縮みの方針は、入れ物にも写す。レイアウトに置いたときの見え方は中身そのものと同じになる。
- 思考ドックと検討ドック（どちらもエンジン情報の表を持つ）の中身を、この入れ物に入れた。思考ドックの最小幅が実際に変わるときは、これまでどおりメインウィンドウまで伝わる。

## 21. Qt の塗りのスレッド分け

### 問題点

項目20の後に残っていた課題（項目33）を調べ直した。持駒をつまむときの残り（項目17、項目31）と、棋譜欄のスクロールバーの描き直しで、Qt が塗りを別のスレッドに分けて頼む受け渡しが重かった。

- **Qt の塗りの分け方:**
  - Qt のラスタ描画は、1回の塗りの区間（行ごとの横の並び）が96以上あると、約64ずつに分けて GUI 用のスレッドプールに頼み、すべて終わるまで待つ（`QT_THREAD_PARALLEL_FILLS`）。画像の滑らかな縮小や形式の変換も、同じスレッドプールを使う。
  - 分けた仕事が小さいと、スレッドを起こして終わりを待つ受け渡しのほうが重い。

## 23. 思考表の行数の上限での削除

### 問題点

「思考タブの描画で高速化できる箇所はあるか。読み筋の列はエンジンの読み筋を漢字の棋譜に変換して大量に処理するが、高速化されているか」という依頼で、読み筋の変換と思考表の描画を監査した（項目23〜26）。実際のエンジン（やねうら王）の info 行を使い、変換と描画の段階ごとの命令数を単体ベンチで測った。

- 思考表は500行を上限にしている（`Usi::onThinkingInfoUpdated` の `trimToMaxRows`）。行を先頭に足すたびに、末尾の1行を消す。
- `IncrementalTableView` は行の削除をすべて「その他の変更」として扱い、表示領域全体を描き直していた。そのため500行に達すると、変わった所だけを描き直す仕組み（項目15）が毎回働かなくなっていた。
- 思考表は思考を始めるたびに消すので、対局では500行に達しない。検討（`go infinite`）では消さずに足し続ける。やねうら王の検討で候補手を10にすると、10秒で180行届いた。数十秒で500行に達し、その後は info 行が届くたびに全体を描き直していた。

### 改善内容

- 一番上を表示していて、消す行が表示領域より下にあるときは、見えている行の位置も内容も変わらないので、部分描画を続ける（`IncrementalTableView::onRowsAboutToBeRemoved`）。
- 行の位置は、見出しが行の追加をその場で反映しているので、追加した後の位置で比べられる。
- 先頭への追加と下の行の削除が重なったとき（思考表の上限の処理）は、追加した行だけを描き直す。削除だけのときは描き直さない。
- 消す行が見えているとき、下へスクロールしているとき、末尾への追加（棋譜欄）と重なったときは、これまでどおり全体を描き直す。

## 25. 読み筋のセルの文字の描画

### 問題点

項目23の監査で、思考表のセルごとの描画の命令数を測った（日本語表記、24手の読み筋、表示幅259px）。

- 読み筋のセル1つが約57万命令で、ほかの列のセル（約10〜14万命令）の4〜5倍だった。行1つの描画の約半分を占めた。英語表記では約94万命令（欧文の書体と▲△の書体が手ごとに切り替わるため）。
- そのうち枠・背景・選択の色の描画は約3万命令で、残りはすべて文字だった。
- Qt の項目の描画（`QCommonStyle` の `CE_ItemViewItem`）は、セルを描くたびに、文字の範囲を決める（文字の大きさを測る）、省略（…）するかを決める、省略後の文字列を作る、描くための配置をする、と文字配置を何度も計算する。項目12で長い読み筋を表示幅の先で切って渡すようにしたが、渡す文字列（約41文字）も、実際に表示される文字（約18文字）の2倍以上あった。
- 残っている課題（項目33）に挙げていた「表の文字の描画」のうち、読み筋の列の分にあたる。

### 改善内容

- **`ItemTextPainter`（`PvTextDelegate` から使う）:**
  - 枠・背景・選択の色は、文字を空にした項目として Qt に描かせる。
  - 文字だけを、Qt と同じ手順で描く。Qt と同じく項目の文字の範囲から左右の余白を除いた幅で、切った文字列を並べ、収まらなければ同じ方法（`QFontMetrics::elidedText`）で右端を省略する。縦の位置は、Qt と同じく切った文字列の配置の大きさで決める。描く関数（`QTextLayout::draw`）・文字色（パレットの Text、選択中は HighlightedText）・切り抜き（項目の範囲）も Qt と同じ。
  - 省略後の文字列の配置と、縦の位置を決める大きさは、文字列ごとに一度だけ求めて覚える。描くたびの処理は、文字の範囲の問い合わせ（1文字で求める）と、覚えた配置を描くことだけになる。
  - 文字の範囲は、アイコン・チェックが無ければ文字があるかどうかだけで決まる（`QCommonStylePrivate::viewItemLayout`）ので、短い文字で求める。
  - 自分で描けない設定（折り返し・右端以外の省略・右から左・アイコンやチェック・上下に置く配置・フォーカスの枠・改行や書字方向の制御文字を含む文字列）は、これまでどおり切った文字列を Qt に渡す。フォーカスの枠は、Qt が文字の範囲に合わせて描くので、フォーカスのある項目は Qt に任せる。
  - 文字色は、スタイルシートの `::item` で文字色を変えない表で使う前提。思考表・検討タブ・棋譜解析の表の `TableStyles::thinking` は、選択中の色を `selection-color` と同じにしている。
- 監査では、省略した後の文字列を Qt に渡す方法（約39万命令、-30%）も測った。文字だけを自分で描くほうが効果が大きく、縦の位置の扱いも Qt と同じにできるので、こちらを採った。

## 27. 表の文字の描画（数値の列・エンジン情報の表・棋譜欄）

### 問題点

項目26の後に、エンジン同士の対局（Hayanagi、秒読み1秒、41手）と検討（やねうら王、候補手5、20秒）の GUI のスレッドの処理の内訳を取り直した（項目33）。残っている課題の中で最も大きいのは、読み筋の列以外の表のセルの描画だった。対局の1倍で約11%、1.25倍で約17%、検討で約10〜13%を占めた。

- 対象の列と表:
  - 思考表・検討タブ・棋譜解析の結果の表の数値の列（`NumericRightAlignCommaDelegate`）
  - エンジン情報の表（既定のデリゲートと、指し手の列の `KifuMoveDelegate`）
  - 棋譜欄・分岐候補欄（`RecordHighlightDelegate`）
- Qt の項目の描画は、セル1つで文字配置を3〜5回計算する。文字の範囲を求めるたびに文字の大きさを測り（`subElementRect`）、省略するかを決め、描く。項目25で読み筋の列は文字を自分で描くようにしたが、ほかの列はそのままだった。

### 改善内容

- **`ItemTextDelegate` を加えた:**
  - `QStyledItemDelegate` と同じく項目の設定を作り、描くのは `ItemTextPainter`（項目25）に任せる。
  - `PvTextDelegate`・`NumericRightAlignCommaDelegate`・`KifuMoveDelegate`・`RecordHighlightDelegate` は、これから派生させた。エンジン情報の表の既定のデリゲートにも使う。
  - 定跡ウィンドウ・定跡のマージの表の指し手の列（`KifuMoveDelegate`）も、同じ描き方になる。
- **`ItemTextPainter` を広げた:**
  - 折り返す設定でも、1行に収まる文字列は自分で描く。Qt も、1行に収まれば折り返さない場合と同じく、その1行を描く（`QCommonStylePrivate::calculateElidedText`）。アイコン・チェックが無ければ、文字の範囲は文字の中身に左右されない（`viewItemLayout`）。2行以上になる・切れ目が無くはみ出す文字列は、Qt に描かせる。
  - 省略しない文字列（数値などの短い文字列）は、縦の位置を決めるために並べた配置を、そのまま描く。初めて描く文字列でも、文字配置の計算が1回で済む。
  - 文字の切り方（`ItemTextCutter`）で、書体を文字列の形（`QFont::key`）にせずに比べる。
- 見た目は変わらない（項目32）。

## 31. 採らなかった方法

- **Fusion スタイルを包んでアイコンを使い回す（項目11の時点）:** `QProxyStyle` で Fusion を包み、ドックのタイトルのアイコンを覚えておく方法を検討した。Qt は、スタイルが Fusion なら読み取り専用のコンボボックスの背景をボタン色にする既定の規則を加える（`qstylesheetstyle_default.cpp` の `baseStyle()->inherits("QFusionStyle")`）。包むとこの判定が外れて見た目が変わると考え、採らなかった。代わりに、項目11でアイコンの読み込みが起きる回数を減らした。項目16で調べ直し、この規則は何にも当てはまっていないと分かったので採用した。
- **スタイルシートでボタンのアイコンを指定する（項目16）:** `QDockWidget { titlebar-close-icon: ...; titlebar-normal-icon: ...; }` で指定しても、Fusion のアイコンの読み込みは減らなかった。タイトルの配置の計算は、スタイルシートを通らずに Fusion を直接呼ぶため。
- **思考表・棋譜欄の表示領域を、どの倍率でも不透明にする（項目12、項目33も参照）:** スタイルシートの背景色のまま、表示領域の自動の塗りつぶしを戻す方法を試した。1倍では画面が一致したが、1.25倍では表示領域の端が物理画素の途中に来るため、表の枠線の画素が白で上書きされた。項目12では、ドックの中身を不透明にするだけで描き直しの連鎖は止まるので採らなかった。項目15では、画面のずらしに必要なので、整数倍率のときだけ不透明にした。
- **エンジン情報の表の列幅を固定する・広げる一方にする（項目12）:** 探索手の列は手によって幅が変わる（「▲同歩(23)」と「▲７六歩(77)」など）。そのため1手に約1回、表の幅が変わり、レイアウトの再計算が `MainWindow` まで伝わる。列幅の決め方を変えると見た目が変わるので、採らなかった。
- **ドックが動くアニメーションをやめる（項目14）:** 盤の拡大・縮小でウィンドウの大きさが変わると、ドックがアニメーションで動き、そのたびに配置の計算と描き直しが起きる。やめると見た目（動き）が変わるので、採らなかった。
- **USI通信ログのタブが隠れている間は追記を後回しにする（項目12）:** 自動化 API（`widget.text`）でログの表示内容を読む使い方があり、隠れている間の内容が古くなるので採らなかった。
- **持駒をつまむときは、変わったマスを囲む矩形を描き直す（項目17）:** Qt は描き直す範囲を矩形の集まりとして持ち、矩形ごとに切り抜いて描く。ばらばらのマスが多いと切り抜きが重いと考え、範囲の矩形が8個を超えたら囲む矩形を描き直す方法を試した。1倍では変わらず（2.47ms → 2.45ms）、2倍では描く面積が増えて遅くなった（6.18ms → 7.88ms）ので採らなかった。重いのは切り抜きではなく、描く面積だった。
- **入れ物を表示するときに、中身の大きさの条件を比べ直す（項目20）:** 最初の作りでは、入れ物はレイアウトを持たず、中身の配置が変わったときに届く通知（`LayoutRequest`）で比べていた。入れ物が隠れている間はこの通知が届かないので、表示するときにも比べ直していた。GUI 機能テストで、検討ドックを切り離して縮めた画面の幅が変わった（678px → 750px）。切り離すと中身が表示し直され、まだ伝わっていなかったエンジン情報の表の幅の変化を、入れ物の無い場合より早くドックに伝えていた。エンジン情報の表の幅は「中身の幅」と「今の幅」の小さいほうなので、伝わる時点が変わると、縮めたときに落ち着く幅が変わる。中身の `updateGeometry` と同じ時点で比べる今の作りに改めた。
- **ドックへの配置のやり直しの通知をイベントフィルタで止める（項目20）:** 中身の大きさの条件が変わらないとき、ドックに届く配置のやり直しの通知を捨てる方法を検討した。捨てるとドックのレイアウトが「やり直し待ち」のまま残り、Qt はその後の通知を送らなくなる（`QLayout::update` は、やり直し済みのレイアウトにしか通知を送らない）。ドックの大きさが変わっても中身を配置し直さなくなるので、採らなかった。代わりに、ドックと中身の間に入れ物を挟んだ。
- **ドックのタイトルの大きさの計算を軽くする（項目19）:** `MainWindow` の配置の計算のたびに、Qt（`QDockWidgetLayout`）がドックごとにボタンの大きさ・書体・スタイルの値を問い合わせる。タイトルを自前の部品にすれば省けるが、見た目が変わるので採らなかった。
- **USI通信ログの表示欄を、ドックが裏のタブにある間は隠す（項目18）:** 新しい行の文字配置も省けるが、隠している間に足した行は、表示したときに必要な分しか配置されない。最も長い行の幅で決まる横のスクロールバーの範囲が、これまでと変わるので採らなかった。
- **手番の交代でのスタイルの付け直しを軽くする（項目18）:** 色ごとの規則を1つのスタイルシートにまとめ、属性の切り替えで選ぶと、スタイルシートの解析は省ける。ただ、解析は手番の交代の処理の約4%で、ほかは付け直しに伴う処理と描画なので、採らなかった。
- **ハイライトの枠を4本の塗りで描く（項目17）:** 幅2pxの枠（`drawRect`）は輪郭の計算と塗りになる。Qt は塗る区間（行ごとの横の並び）が96以上あると別のスレッドに分けて頼むので（`QT_THREAD_PARALLEL_FILLS`）、マス1つの枠でも受け渡しが起き、つまむ・戻す処理の約15%を占めた。4本の塗りに分けると角（面取りした接合）と小数倍率での画素の丸めが変わるので、採らなかった。受け渡しは、項目21で塗りをスレッドに分けさせないようにしてなくした。
- **エンジン情報の表の幅を測る書体を持ち続ける（項目17）:** 書体の読み込みが毎回起きていると考えて試したが、読み込みは初めて測る文字での1回限りで、効果がなかった。
- **エンジン情報の表の幅の変化を `MainWindow` まで伝えない（項目17）:** 思考ドックの最小幅は表の幅に合わせて実際に変わる（580〜630px）。伝えないと、利用者がドックを狭められる幅が変わるので採らなかった。
- **小数倍率でも表の表示領域を不透明にする（項目17）:** 表示領域を不透明にしても、行の高さが物理画素の整数にならない倍率では Qt が画面のずらしを使わない（項目17）。省けるのは下にあるドックと表の枠の描き直し（1.25倍で1手あたり約0.3ms）だけなので、見た目を変えないための確認の手間に見合わず、採らなかった。
- **小数倍率で行の高さを物理画素の整数に合わせ、行の追加で画面をずらす（項目21の後）:**
  - 試したこと:
    - 行の高さを、倍率を掛けて物理画素の整数になる高さに切り上げた（標準の文字の大きさで、1.25倍・1.5倍・1.75倍とも23px → 24px）。
    - 小数倍率では、表示領域の端が物理画素の途中に来て、端の画素を表の枠やスクロールバーと分け合う。自動の塗りつぶしで表示領域を不透明にすると、表の位置と大きさのずれ方256通りのうち約200通りで、右端か下端の枠線の1画素の線が白くなった。Qt は不透明な表示領域の下に表自身を描かず、その画素を表示領域が背景色で塗るため。
    - 代わりに、表示領域を不透明と宣言し（`WA_OpaquePaintEvent`）、Qt が表自身を描くとき（`QWidgetPrivate::paintBackground` と `QFrame::paintEvent`）と同じものを表示領域の中で同じ位置に描いてから、表示領域の背景を重ねた。1.25倍・1.5倍・1.75倍の256通りすべてで、今の画面と画素まで一致した。
    - 画面をずらすと端の画素も動き、枠線やスクロールバーの画素が中身で置き換わった。スクロールバーの画素には、全体を描くときだけ描かれ、表示領域やスクロールバーを描き直しても戻らないものがあった。四辺から1pxを除いた内側だけをずらし、除いた帯を描き直すと、描き残しはなくなった。実験用の表で行を足したとき、描き直す範囲は表示領域の約25%になった。
    - 棋譜欄は、一番下を表示しているときに行を足すと、表示位置を「下端合わせ」から「行の上端合わせ」に直し、続く一番下までのスクロールで「下端合わせ」に戻す。2回のずらしはどちらも物理画素の整数にならないが、合わせると行の高さの分になる。1回目のずらしを次のスクロールにまとめると、実験用の表で描き直す範囲は約15%になった。
    - 検証の注意: 縦のスクロールバーが現れる瞬間は、スクロールバーの矢印の付近が、全体を描き直した画面と違う。普通の `QTableView` でも、1倍でも同じなので、Qt 自身の差。
  - 採らなかった理由:
    - Qt の表は、描き直す範囲にかかるセルを丸ごと描く（はみ出した分は切り取るだけ）。右端の帯は読み筋の列のセルに表示中の全行でかかるので、部分的な描き直しが、全体を描くのと同じくらい重かった。1.25倍のエンジン同士の対局で、思考表2つの描き直しは41手で約174ms → 約168msにしかならなかった。
    - 棋譜欄の一番下までのスクロールは、Qt の処理（`QTableView::scrollContentsBy`）の中で表示領域全体をずらすので、内側だけをずらせない。実アプリでは、棋譜欄の描き直しは減らなかった。
    - 表示領域を不透明にすると、利用者のスクロールでも端の画素ごとずらされ、1.25倍で描き残しが出た（`tst_incremental_table_view` の描き直す範囲の検証を、小数倍率にも広げて見つけた）。
    - 対局全体では、1.25倍の GUI の1手あたりの命令数が約2.6%減っただけで、1局ごとのぶれ（±3%）と区別できなかった。続けるには、帯にかかるセルでは文字を描かないよう表の描画クラスを変え、棋譜欄と利用者のスクロールも自前で行う必要がある。Qt が小数倍率で座標を丸める細かな作りに頼るので、Qt の版が変わると壊れやすく、行の高さ（見た目）も変わる。
- **エンジン情報の表の折り返しをやめる（項目27）:**
  - 項目25の描き方は折り返す設定を Qt に任せるので、表の折り返し（`wordWrap`）をやめる方法を考えた。
  - 保存した狭い列幅では、値が折り返されて1行目だけが見えている（例: 「△同」）。折り返しをやめると「△同　歩(…」のように省略表示になり、見た目が変わる。
  - 代わりに、折り返す設定でも1行に収まる文字列は自分で描くようにした。

## 33. 残っている課題

項目30の後に、エンジン同士の対局（Hayanagi、秒読み1秒、41手）の GUI のスレッドの処理の内訳を取り直した。割合は1倍の値。GUI のスレッドの処理は1手あたり約16msで、1.25倍の命令数は1倍の約1.4倍になる。

- **小数倍率での表の描き直し:**
  - 行を足して表示がずれるとき、ずれの量が物理画素の整数にならない倍率（思考表は標準の文字の大きさで1.25倍・1.5倍）では、Qt が表示中の全行を描き直す（項目17）。表示領域を不透明にしても変わらない。
  - 1.25倍の GUI の命令数は、1手あたり約4,670万で、1倍（約3,360万）の約1.4倍。項目21の調査では、思考表2つと棋譜欄の描き直しが、1倍より41手で約113ms多かった。これは余分にかかっている描画の総量で、省ける分ではない。描く面積が1倍より広い分は、画面のずらしを使っても残る。
  - 行の高さを物理画素の整数に合わせて画面のずらしを使う方法は試したが、表示領域の端の画素の扱いが難しく、効果も小さかったので採らなかった（項目31）。続けるには、ずらした後に描き直す端の帯にかかるセルで文字を描かないようにし、棋譜欄と利用者のスクロールも自前で行う必要がある。効果は1.25倍で GUI の処理の1割前後と見込む。
- **思考表を消すときの描き直し:**
  - 縦のスクロールバーの出入りは、常に出しておくことでなくした（項目22）。
  - 表を消すたびに、Qt は見出しの全体を描き直す（モデルの作り直しを受けた `QHeaderView` の処理。1手に1〜2回、1回約0.3ms）。見出しの文字と幅は変わらないので、描き分けと同じように省ける見込み（項目19）。見出しの描画は、すべての表を合わせて GUI の処理の約2〜2.5%。
  - 表を消した直後に複数行がまとめて届くと、配置のやり直しがまとまって表示領域の全体を描き直す（41手で約14回、1回約1.2ms）。
- **エンジン情報の表の幅の変化:** 思考ドックの最小幅が実際に変わるとき（41手で約23回）は、`MainWindow` の配置の計算（1回約1ms、GUI の処理の約4%）が起きる。その多くは、Qt がドックのタイトルの大きさを計算する処理（`QDockWidgetLayout::sizeFromContent`）。最小幅の決め方を変えない限り省けない（項目31）。最小幅が変わらないときの分は省いた（項目20）。
- **表の文字の描画:**
  - 思考表を手ごとに消して足し直すと、見えている行がすべて新しくなるので、全体を描く（必要な描き直し）。
  - 読み筋の列（項目25）と、ほかの列・エンジン情報の表・棋譜欄（項目27）は、文字を自分で描き、文字配置を覚えるようにした。
  - セルの描画は、まだ GUI の処理の約12%を占める。内訳は、枠・背景・選択の色の描画（Qt の `drawControl`）、文字の範囲の問い合わせ（`subElementRect`）、初めて描く文字列の文字配置、文字を描く処理。
  - 枠・背景は、スタイルシートで項目の枠を描く表（思考表など）では、Qt のスタイルシートの処理を通る。自分で描くとスタイルシートの規則を読み直すことになり、見た目を保つのが難しい。
  - 位置を決めるための文字配置の計算は、Fusion を通る経路では省いた（項目19）。
- **持駒をつまむとき:** 残りは、打てるマスごとの画素の処理（背景の画像・ハイライトの塗りと枠・駒）。スレッドの受け渡しは項目21でなくした（実アプリの2倍表示で、つまむ・戻す1回が約4.7msから約2.2msに。自動化 API の処理を除いた値）。
- **手番の交代:**
  - 枠の太さ・色と時計の色が実際に変わるので、スタイルの付け直しと描画が残る（項目18）。GUI の処理の約4.5%。
  - 重いのは Qt の `setStyleSheet` の中。付け直すたびに、部品とその祖先ごとにスタイルシートを探す（`QObject::property("styleSheet")`）。省くには、枠と文字の色をスタイルシートを使わずに描く必要があり、見た目が変わらないかの確認が要る。
  - 手番の交代のたびに、名前・時計・手番の札の位置と書体の大きさを計算し直す処理（`ShogiView::relayoutTurnLabels`、約1%）もある。隠れている「編集終了」ボタンの分は省いた（項目19）。
- **棋譜欄への1手の追加:** 対局で1手ごとに、棋譜欄に行を足し、列幅を内容に合わせ、一番下までスクロールし、現在行を選ぶ（約4.6%）。評価値グラフの現在の手の移動（項目29）とコメント欄（項目30）の分は省いた。
- **USI通信ログの追記:**
  - ドックが裏のタブにあっても、Qt が表示中として扱うので、新しい行の文字配置を計算する（項目18、項目31）。GUI の処理の約5.5〜6.7%（検討では約8〜9%）。
  - 約4分の3は新しい行の文字配置で、`QPlainTextEdit` を使う限り省けない（スクロールバーの範囲を決めるときに最後の行を配置する。`QPlainTextDocumentLayout::blockBoundingRect`）。
  - 残りの1行ごとの処理（カーソルとスクロールバーの更新など）は、1回の読み取りで届いた行をまとめて足せば減らせる（約1%、推定。1回に何行届くかで変わる）。
- **塗りをスレッドに分けない設定の確認:** 4K の画面全体を描き直すような大きな塗りと、Windows・macOS での効果は測っていない（項目21）。

## 計測方法

- **実アプリ:**
  - `scripts/docs/launch.sh` で `--automation` 付きで起動する。
  - `board.click` を JSON-RPC で送り、時間を測る。
  - `perf stat -e task-clock -p <pid>` / `perf record -g -p <pid>` で内訳を見る。
  - GUI のスレッドだけを記録すると（`perf record -t`）、Qt が塗りを頼む作業用のスレッドの処理と、その終わりを待つ時間が見えない。スレッドの受け渡しの重さは、プロセス全体の CPU 時間と実時間で比べる（項目21）。
- **単体ベンチ:**
  - `libshogiboardq_static.a` にリンクした小さなプログラムで、`ShogiView` と `BoardInteractionController` を直接動かす。
  - `QT_SCALE_FACTOR` を変えて各倍率を測る。
  - `QScreen::grabWindow` で実際に画面へ出た内容を取り、画素を比べる。
