- 対象のコミットは ba72e1fe。本文の行番号はこの時点のもの。
- 前回の監査から増えたもの（主な対象）
  - 同じ LAN の合言葉（12文字）と、協力ノードを使う合言葉（10文字。`--meet` の待ち合わせ）
  - 友だち一覧と在席の知らせ（X25519 の2人だけの秘密）
  - 自分の手をエンジンに指させる対局（HELLO 版 2・対局者の種別）

## 全体の評価

**今配布しているアプリには影響しない。** 最新のリリース 2026.11.09 は、P2P対局を既定で有効にした 2026-11-14 より前のものである。次のリリースから P2P対局が配布物に入るので、その前に直すのがよい。

**High はない。Medium が2件ある。**
- **S1（A）**: 対局相手は、着手の承認を返さずに再接続を繰り返すだけで、1手に何分でも考えられる。双方の署名がそろった、検証に通る記録として残る。仕様の「ACK の保留による考慮時間の水増し」の対策が、再接続をはさむと効かない。前回の監査より前（互換仕様を書いた 11-11）からある。
- **S2（F）**: 協力ノードの接続の上限が、利用者のアプリと同じ全体32本のままである。数個のアドレス帯から接続を張るだけで、協力ノードを使う合言葉・友だちの在席・中継を止められる。

**Winny 型の心配について**
- ファイルが流出する経路は、新しい機能にもない。合言葉・待ち合わせ・在席の知らせで運ぶのは、接続先と招待の秘密だけである。
- 遠隔からのメモリ破壊は見つからなかった。
  - Rust の新しい読み取りに変異入力を入れて、panic は0だった。
  - C++ の IPC の読み取りは、すべてのフィールドを確かめていた。
- 協力ノードを使う合言葉の暗号の作りは健全である。番号と鍵は、どちらも Argon2id の出力から作っている。運営者が番号から合言葉を総当たりするには、2^45 回の Argon2id が要る。
- 渡る情報が説明より多い所が3つある。
  - S11: 在席の知らせで、友だちには接続先の IP が届く。
  - S10: 在席を知らせていなくても、照会だけで、協力ノードの運営者に友だちの組が分かる。
  - S15: 公開しているガイドの画像に、開発に使った PC の LAN のアドレスが写っている。

**新しい問題の型は2つある。**
1. **「測り直す」「数え直す」が、相手の操作で起こせる**（S1・S4・S5）
   - 再接続の照合で観測時間を0から数え直す（S1）。
   - 合言葉の失敗の回数を、全体で1つの枠で数える（S4）。
   - 待ち合わせの要求を、接続元が分かる前は PeerId ごとに数える（S5）。
   - どれも、正しい相手のための救済や数え方を、悪意のある相手が自分の都合で起こせる。
2. **協力ノードの役割が増えたのに、資源の上限が利用者のアプリのまま**（S2）
   - 協力ノードは、中継に加えて、待ち合わせと友だちの在席も受け持つようになった。
   - それでも、接続の上限は全体32本のままである。

## 2. 詳細

### S1【Medium】着手の承認を返さずに再接続を繰り返すと、1手に何分でも考えられる

**場所**

| 箇所 | 内容 |
|---|---|
| `src/game/p2p/p2pmatch.cpp:877-889`（`finishResume`） | 照合の後、未承認の自分の手を `m_pending->sent = false` にして送り直す |
| `p2pmatch.cpp:410-420`（`resendPending`） | `sent` が false なら `m_timer.startObserving(now())` で、相手の手番の観測 O を今から数え直す |
| `p2pmatch.cpp:455-462`（`tick`） | 承認が30秒来なければ、自分で再接続へ移る |
| `p2pmatch.cpp:466-479` | 自分の手が未承認の間は `isMyTurn()` が真なので、相手の時間切れを主張しない |
| `src/network/p2p/p2pgamecoordinator.cpp:233-243` | 相手が新しい接続を開くだけで、照合をやり直させられる |

**手順**
1. 被害者 V が指す（STATE_PROPOSE）。
2. 相手 A は手の内容を読むが、STATE_ACCEPT を返さずに考え続ける。
3. 30秒の前に、A が新しい接続を開く（V が30秒で自分で検知するのを待ってもよい）。
4. 照合の RESUME で、A は「前の手数が最新」と答える。
5. V は同じ提案を送り直し、そこから O を数え直す。それまで保留された時間は、O にも、切れていた時間 D にも入らない。
6. 1〜5 を何度でも繰り返す。最後に承認を返し、短い消費時間を申告して指す。

**確認**
- 区画の担当が状態機械の試験台で再現し、主担当がもう一度動かした（試験台は公開していない。修正の後に足した `tst_p2p_match::withheldAcceptanceCountsTowardTheDisconnectLimit` が同じ手順を試す）。結果は次のとおり。

  | 形 | 持ち時間 | A の実際の考慮 | 記録 | 結果 |
  |---|---|---|---|---|
  | A が29.9秒ごとにつなぎ直す（20回） | 60秒＋秒読み10秒 | 603秒 | spentMs=5000・残り 55,000ms・D=0 | V は時間切れを主張しない。証跡は `valid` |
  | A は何もしない（V が30秒で検知、つなぎ直しに0.5秒） | 同じ | 624秒 | D=10秒 | 同じ |
  | 対照: 再接続しない | 同じ | — | — | CLOCK_MISMATCH で止まる |

- 司令塔と通信プロセスを通した実際の対局では試していない。新しい接続で照合をやり直すことは、司令塔のコードで確かめた。
- この振る舞いは前回の監査より前からある（11-11 の互換仕様と、組み替える前の `p2pmatch_control.cpp` の `m_pendingSent = false`）。前回の監査は見落としていた。

**仕様との関係**
- 実装仕様は、この攻撃を防ぐとしている。
  - 7.1節（`docs/dev/p2p-game-spec.md:638`）: O は「自分の STATE_PROPOSE を最初に送信キューへ渡した時点」から測り、「相手が STATE_ACCEPT を遅らせて考える時間も O に入る」。
  - 脅威の表（`:1014`）: 「ACK の保留による考慮時間の水増し」を対策済みとしている。
  - 7.2節（`:655`）: 切断の合計の上限（10分）を、切断を繰り返して時間を延ばすことの対策にしている。ところが保留した時間は D に入らないので、この上限も効かない。
- 互換仕様は、逆の動きを定めている。9.4節（`docs/dev/p2p-interop-spec.html:989`）と 11.5節（`:1177`）に「送り直した時点から測り直す」とある。実装は互換仕様のほうに合っている。
- 2つの仕様が食い違っている。

**影響**
- 偽の結果に署名させることはできない。
- ただし、自己申告の時間をプロトコルで確かめる唯一の仕組みが無効になる。長考した手やエンジンで考えた手を、時間内に指した手として、双方が署名した記録に残せる。
- 被害者の画面では、相手の手番が長く続き、再接続の表示が出るだけである。

**直し方の案**
- 照合の後に送り直しても、O の起点を最初に送った時点のままにする（`sent` とは別に、一度でも送ったかを持つ）。
- 本当に届いていなかった場合の救済が要るなら、未承認の間から切断を検知するまでの時間を D に足し、1局10分の上限にも数える。悪用できる時間は10分までに収まる。
- 互換仕様の 9.4節・11.5節を直し、版の決まり（1.5節）に従って変更履歴を足す。互換実装の修正が要る。
- 試験台の `ackWithholdingWithResyncResetsObservation` を、`tst_p2p_match` の回帰試験にする。

### S2【Medium】協力ノードの接続の上限が小さく、数個のアドレス帯で待ち合わせ・在席・中継を止められる

**場所**

| 箇所 | 値 |
|---|---|
| `peer/src/swarm.rs:137-141` | 確立した接続は全体で32本、確立前の受けは8本。`Role::Service` でも同じ値 |
| `peer/src/node/peerlinks.rs:17`・`events.rs:125-131` | 同じアドレス帯（IPv4 は /24、IPv6 は /48）からは8本まで |
| `peer/src/behaviours.rs:122-145` | 確立前の受けは、同じ IP から3本まで（IPv6 も /128 単位） |
| `peer/src/meet.rs:21-23` | 処理中の待ち合わせの要求は、全体64本・PeerId ごとに4本 |
| `peer/src/meetstore.rs:15-22` | 預かりは全体4096件・接続元ごとに256件。頻度は接続元ごとに 64件まとめて＋毎秒4件 |

**攻撃のしかた**
- アドレス帯が4つ（/24 か /48）あれば、確立した接続の32本をすべて持てる。
  - その間、だれも協力ノードにつなげない。
  - 協力ノードを使う合言葉・友だちの在席・中継・到達性の確認が止まる。
- 待ち合わせだけを止めるなら、帯が2つで足りる。
  - 8接続×4本で、何も送らないストリームを張り、5秒ごとに張り直せばよい。
  - PeerId はいくらでも作れるので、PeerId ごとの上限は効かない。
- 協力ノードが IPv6 で待ち受けていれば、確立前の枠（全体8）は1台の /64 で埋まる。
- 攻撃がなくても、在席を知らせる利用者が32人を超えると溢れる。

**IPv6 の束ね方**
- /48 単位なので、1人がアドレスを替えて上限を逃れることはできない。
- 一方で、束ね方が広すぎる。日本の IPoE（共有の /48 から /56・/64 を配る）や IPv4 の CGNAT（/24）の利用者どうしが、8接続・256件・毎秒4件を分け合う。
- 友だちが64人いる利用者は、「相手」タブを開いている間、毎秒2〜3件の要求を出す。同じ帯の2人で枠を超える。

**確認**
- 区画の担当がコードを読んだ。主担当は、上の表の値と、上限が役割で変わらないことを読み直した。
- 動かしての確認はしていない。

**直し方の案**
- 協力ノードの役割には別の上限を使う。接続は数百本にし、帯ごとの上限は残す。
- 処理中の要求の枠を接続元（帯）ごとに数え、最初の読み取りを1〜2秒で打ち切る。
- 帯ごとの上限を2段にする（/64 で厳しく、/48 で緩く）。
- ガイドの「協力ノードを起動する」に、資源の目安（接続数）を書く。

### S3【Low】同じ LAN の合言葉で、最初に応えた相手にトークンを渡し、招待した側を確かめない

**場所**
- `peer/src/node/conns.rs:254-264`: 最初につながった相手を採り、2本目からの接続は閉じる。
- `peer/src/node/codes.rs:205-208`、`peer/src/node/streams.rs:139-141`

**起きること**
- 合言葉の宛先で応えた機器が、招待した側に成りすませる。つなぐ側は、条件確認まで進む。
  - 例1: ARP の偽装。
  - 例2: 合言葉に入った VPN・docker のアドレスを、つなぐ側の網で持つ別の機器。
- 同時に、本物の招待した側への接続は「余分」として閉じられる。
- 成りすました機器は、トークン H(鍵, 自分の PeerId, つなぐ側の PeerId) を受け取る。これは、オフラインで総当たりする材料になる。
- トークンは双方の PeerId に結び付くので、本物の招待した側へ中継して割り込むことはできない。
- 実装仕様の既知の限界（`protocol/README.md` 3.1節、`p2p-game-spec.md` の 1008行あたり）の内側である。ただし、相手を確かめる手段は確認コードしかなく、初めての相手では弱い。

**総当たりの量**（区画の担当の実測。argon2 0.5.3、64MiB・回数2・並列1）
- Argon2id は1コア1回 91ms。秘密は34〜38ビット（192.168 のアドレス1件なら34）。
- 2^34 回は約50コア年。GPU は記憶の帯域が上限で、1台で毎秒2,500回以下と見積もった。
- その見積もりでは80 GPU日以上かかり、期限の10分で終えるには約1万台が要る。現実の脅威ではない。

**確認**: 区画の担当がコードを読んだ。主担当は、総当たりの前提（秘密のビット数・KDF の設定）を `protocol/rust/src/code.rs:14-25` で読み直した。

**直し方の案**
- 招待した側は、正しいトークンを確かめた後に H("SBQ-CODE-CONFIRM", 鍵, 招待した側, つなぐ側) を返す。つなぐ側の通信プロセスは、それを確かめてから `connectionOpened` を出す。
  - 返すのは正しいトークンを送った相手だけなので、新しい総当たりの材料にはならない。
- 本格的には、CPace などの PAKE にする。

### S4【Low】合言葉の照合に失敗してよい回数が全体で1つで、LAN の機器が正しい合言葉を断らせ続けられる

**場所**: `peer/src/node/invites.rs:9-12`（8回、4秒で1回戻る）、`:102-132`（回数が0なら、正しいトークンも照合しない）

**起きること**
- LAN の機器が、48210 に誤ったトークンを4秒に1回送り続ければ、残りの回数を0に保てる。PeerId は新しく作ればよい。
- その間、つなぐ側には「合言葉が違う・期限切れ・使用済み」と出る。招待した側には何も見えない。

**総当たりの成功率**
- 10分で試せるのは 8＋150＝158回。
- 合言葉が1件なら 158/2^34 ≈ 9×10⁻⁹ である。

**確認**: 既存の試験 `code_guesses_are_limited` が、回数を使い切ると正しいトークンも断ることを示している。主担当がコードを読み直した。

**直し方の案**
- 接続元の IP ごとの枠を足す。
- 全体の枠を大きくする。招待1件あたり1000回でも、成功率は 6×10⁻⁸ 程度で済む。
- S3 の確認の値を返すようにすれば、失敗の知らせを細かく出し分けられる。

### S5【Low】待ち合わせの要求を、接続元を覚える前は PeerId ごとに数える

**場所**: `peer/src/meet.rs:118`、`peer/src/node/events.rs:49-52, 62-65`

**起きること**
- libp2p-stream は、届いたストリームを接続のタスクから直接渡す。一方、接続元を覚える処理（`set_source`）は主ループで走る。そのため、ストリームが先に届くことがある。
- 接続元の分からない要求は PeerId ごとに数えるので、PeerId を替えながら競争に勝てば、帯ごとの件数と頻度の上限を逃れられる。
- `admit_inbound` で断って閉じる接続の上でも、閉じる前に処理された要求は同じ扱いになる。

**確認**: 区画の担当がコードを読んだ。動かしての確認はしていない。

**直し方の案**: 接続元の分からない要求には `Limit` を返す。協力ノードは中継経由の接続を受けないので、正しい利用者への影響はない。

### S6【Low】申し出の箱の「承諾」を1秒止める対策が、続けて申し出を送られると効かない

**場所**: `src/ui/controllers/p2poffercontroller.cpp:52`（`QTimer::singleShot(kAcceptDelayMs, this, &P2pOfferController::enableAccept)`）、`:56-60`（`enableAccept` は今の `m_offerBox` を有効にする）

**起きること**
- タイマーを受けるのが箱ではなく controller なので、前の箱のタイマーが、新しく出た箱の「承諾」を有効にする。
- 相手が引き分けを申し出て、約0.95秒後に中断を申し出ると、中断の箱の「承諾」は出てから約50〜80msで押せる。
- 引き分けを承諾するつもりのクリックが、中断の承諾になる。前回の I-t で防いだことが、そのまま起きる。

**確認**
- 区画の担当が試験台で再現した（2つ目の箱が出てから80ms後に `enabled=1`）。
- 主担当がコードで経路を確かめた。

**直し方の案**: `singleShot` の文脈を箱にする（`QTimer::singleShot(kAcceptDelayMs, m_offerBox, ...)`）。または、箱を出すたびにメンバの QTimer を start し直す。

### S7【Low】申し出の連打で、人間の被害者の手番を妨げられる

**場所**
- `src/game/p2p/p2pmatch.cpp:702-708`: 同じ手数の引き分け・中断の申し出を、1局の件数の上限（4096件）まで何度でも受け、そのたびに `OfferReceived` を出す。
- `p2poffercontroller.cpp:39-54`: 知らせのたびに箱を閉じて作り直し、`noticeParent`（多くは盤のある本体）の上に出す。
- `p2pmatch.cpp:510-513` → `src/network/p2p/p2precordstore.cpp:100-109`: 受けた制御メッセージは1件ごとに、GUI のスレッドで fsync する。監査に使った PC の NVMe で、2000件に2.15秒かかった。

**起きうること**
1. 被害者の秒読み中に、相手が申し出を毎秒数回送る。
2. 盤の上で箱が出直し続け、手を指すのを妨げる。
3. 時間が切れると、被害者自身の `tick` が時間切れ負けを提案し、相手が同意する。双方の署名がそろう。

**確認**: 区画の担当と主担当がコードを読んだ。実際の画面で、どれだけ妨げられるかは試していない。

**直し方の案**
- 同じ手数・同じ種類の申し出は、答えるか手数が進むまで1回だけ尋ねる（同じ申し出の繰り返しは無視する）。
- 箱を盤に重ねない、前面に出さない。
- 制御メッセージのジャーナルへの書き込みは、まとめて fsync する。

### S8【Low】切断すると保存先のロックを手放すのに、その保存先を使い続ける

**場所**
- ロックを手放す: `src/network/p2p/p2plobbyservice.cpp:109`（`end()` → `P2pPlayerProfile::close()`。`p2pplayerprofile.cpp:74-79` が `m_lock` を解放する）
- 保存先は最初に1回だけ取る: `src/ui/controllers/p2pgameuicontroller.cpp:103`（`acquire` は `ensureLobby` の1回だけ）

**起きること**
- 同じ PC のアプリ X が接続して切断した後に、Y が「P2P対局」を開くと、Y も1人目（`p2p/`）になる。
- X はロックを持たないまま、次のことができる。
  - 「相手」タブの記録（ブロック・友だち・名前）を書き換え、対局記録を削除する（`p2ppeerspanel.cpp:202-268`、`p2pknownpeers.cpp:122-135`）。
  - 「プレイヤー鍵を作り直す」（`p2pgameuicontroller.cpp:234-251` はロビーの状態しか見ない。`p2pidentitystore.cpp:445-451` の `remove()` はロックを確かめない）。Y が使っている鍵のファイルと、鍵の保管庫の項目が消える。
- X の次の「接続」は、ロックを取れずに失敗し続ける。

**確認**
- 区画の担当が、本物の `P2pPlayerProfile` の試験台で再現した。
  - `close()` の後の2回目の `acquire` も1人目になった。
  - Y が付けたブロックが、X の古い内容の書き込みで消えた。
- 主担当がコードで経路を確かめた。
- 攻撃というより、同じ PC で2つのアプリを使う利用者が記録を失う不具合に近い。

**直し方の案**
- ロックは、保存先を持っている間ずっと持つ（`close()` は鍵をメモリから消すだけにする）。
- または、`!isOpen()` の間は書き込みと鍵の操作を断り、`begin` で取れなければ `acquire` し直す。

### S9【Low】友だちからの申し込みは前触れなく前面に出て、Enter 1回で開始できる

**場所**: `src/ui/controllers/p2pgameuicontroller.cpp:322-327`、`src/dialogs/p2pconfirmdialog.cpp:92, 130-133, 189-190`、`src/network/p2p/p2pgamecoordinator.cpp:108-119`

**起きること**
- 在席を知らせている間、友だちが申し込むたびに条件確認画面が出る。
  - 画面は `raise`・`activateWindow` で前面に出て、フォーカスを取る。
  - 「開始」は既定のボタンで、人間が指す設定ではすぐ押せる。
- 申し込んだ側が先に署名していれば、受ける側が別の作業で押した Enter 1回で対局が始まり、時計が動く。
- 申し込みのトークンは期限（300秒）まで何度でも使え（`peer/src/node/presences.rs`）、C++ 側に間隔の制限はない（`p2plobbyservice.cpp:350-364`）。
- 「対局者」がエンジンなら、HELLO の照合の前にエンジンを起動する。
- 「友だちからの対局の申し込みです」は、相手の ID を確かめる前から出る。これは前回の P14 の考え方から少し逸れている。ただし、トークンは友だちしか持てず、開始署名は偽れない。

**確認**: 区画の担当がコードを読んだ（既定のボタンは試験台で確認）。

**直し方の案**
- 友だちの申し込みでは前面に出さないか、「開始」を既定のボタンにしない。申し出の箱と同じく、出してから少し遅らせて押せるようにする。
- 友だちごとに、受け付ける間隔を空ける。
- エンジンは HELLO の照合の後に起動する。

### S10【Low】在席の照会は「友だちに在席を知らせる」の設定によらず送る

### S11【Low】在席の知らせで、友だちに接続先（直接接続なら IP）が届く

**場所**

### S12【Low、E、要実機】macOS の規則が sysctl の読み取りを制限なく許す

**場所**: `peer/src/sandbox.rs:363`（`(allow sysctl-read)`）、`:364`（configd）

**起きうること**
- `kern.proc.all`（プロセスの一覧）と `kern.procargs2` を、サンドボックスでは止めない。`kern.procargs2` では、同じ利用者のほかのプロセスの引数と環境変数を読める。
- XNU が `procargs` を別に止めていなければ、E は端末などの環境変数にあるトークンを読み、外へ送れる。
- configd からは、コンピュータ名（実名を含むことが多い）・DNS の検索ドメイン・プロキシの設定を読める（Info）。

**確認**: 区画の担当がコードと Apple の規則の意味を読み、主担当が規則の文を読み直した。macOS の実機では試していない。

**直し方の案**
- Chromium・Apple のプロファイルと同じく、sysctl の名前を許可リストにする（`hw.activecpu`・`hw.ncpu`・`kern.osversion`・`net.routetable` の接頭辞など）。
- 自己試験に、親の `kern.procargs2` の読み取りを足す。

## 4. 問題がなかった点

**合言葉と待ち合わせ**
- 同じ LAN の合言葉
  - 秘密は回線に流れない。
  - 照合は、処理時間が中身によらない比較である。招待文字列と合わせて1回だけ使える。
  - 鍵の導出は相手の入力では起きない（招待した側は鍵を覚えておく）。
  - 同じ PC のほかの利用者が、決まったポートを横取りすることはできない（QUIC は SO_REUSEADDR なし、TCP は独占の bind で確かめる）。
- 協力ノードを使う合言葉
  - 番号と鍵は、どちらも Argon2id の出力から作る。
  - 暗号は XChaCha20-Poly1305。nonce は預けるたびに乱数で作り、AAD は networkId である。
  - 運営者は中身を作れず、すり替えもできない。招待した側は、本体の PeerId と Noise で確かめられる。
  - 1回限りの預けものは、引き取りで消える。消去と置き換えは、預けた PeerId だけができる。
- 細工した合言葉で向けられるのは、私設アドレスか 127.0.0.1 の4件までへの、QUIC の初回パケットだけである。ローカルの招待文字列でできることから増えていない。協力ノードから引き取った招待・在席の知らせの宛先も、`filter_addrs` と `FilteredTransport::dial`（宛先の形と profile）を通る。
- 新しい読み取りに変異入力を各300万件入れ、panic は0だった。招待・在席・接続・待ち合わせの数には、どれも上限と期限がある。

**友だち**
- 鍵の変換は、位数の小さい点・主部分群にない点・全部0の出力・自分自身との組み合わせを断る（試験台で確認）。
- pairSecret は、2人の ID を順序によらずに並べ、ラベル付きで作る。
- slot と key は、ラベル・networkId・預ける側・期間で分かれる。AAD にも、預ける側・期間・ネットワークが入る。
  - 試験台で、次の読み方がすべて失敗した: A→B の預かりものを B→A として読む、別の期間で読む、別のネットワークで読む、書き換えたものを読む。
- `expectedPlayerKey` は、受ける側が自分の HELLO を送る前に照合する。受ける側は、申し込んだ側の開始署名を確かめてから署名する。
- 友だちから外すと、トークンを無効にする。`acceptApplication` は、友だちか・ブロックしていないか・作った知らせかを確かめ直す。
- 復号した中身は 1024 バイトまで、友だちのファイルは64件・8MiB まで。

**IPC と画面**
- IPC は、全フィールドの型・範囲・件数を確かめ、知らないフィールドを断る。base64 は厳格に読み、世代を照合し、送っていない要求への応答では通信プロセスを kill する。`QPointer` で守っている。
- 通信プロセス・相手が起こす知らせ（失敗・接続の失敗・交渉の終わり・エンジンの知らせ・終局・申し出）は、すべて待たない箱である。前回の P4 の型は残っていない。
- 相手・通信プロセスからの文字列は PlainText で出す。

**状態機械とエンジン**
- 1つの手数に署名するのは1状態だけ。結果への署名は1回だけで、提案と同意は READY の後の Playing の間だけ。
- 棋譜から終局が決まった後は、着手・照合・投了・時間切れ・申し出をすべて断る。
- 時計の値には上限があり、算術は溢れず、残りは負にならない。
- エンジンに送る手は、双方が署名した状態の手を `UsiMove` に読み直したものである。印字できる ASCII で5文字以下であることを確かめ、局面の文は `UsiPosition::commandFor` で作るので、改行やコマンドを差し込めない。
- 表示名は、エンジンにもファイルの場所にも渡らない。エンジンの思考は相手へ送らない。
- 交渉の版 2: 申し込んだ側をエンジンと書けるのは、版 2 に対応した相手だけである。Rules は、自分の種別を照合する。
- ジャーナルの読み戻しは、自分が書いた件だけを読む。
- 検証器は、手順・承認・終局の後に続く状態・棋譜との食い違いを正しく判定する。CBOR の上限は効いている。

**権限の制限**
- Windows
  - ジョブにはプロセスを作る時点で入れる（`PROC_THREAD_ATTRIBUTE_JOB_LIST`）。CREATE_SUSPENDED の競合はない。
  - BREAKAWAY は許さない。KILL_ON_JOB_CLOSE、プロセスは1つ、UI の制限は8種類すべて。
  - 引き継ぐハンドルは標準入出力だけ。途中で失敗すれば起動しない。
  - 環境変数のブロックは正しく終わり、実行ファイルは絶対パスで起動する。
  - 通信プロセスは、標準入力を読む前に制限を確かめ、なければ終了コード 3 で終わる。
- macOS
  - 既定ですべて拒否する。Unix ドメインのソケット・ファイル・exec・fork・ほかの Mach のサービスは許さない。
  - 制限は、ランタイム・スレッド・標準入力より前に掛ける。`CString` の検査、`sandbox_free_error`、掛けた後の `sandbox_check` は正しい。
- Linux: `sandbox.rs` の Linux の部分は前回の監査から変わっていない。退行はない。
- 前回の P13 の修正（終了コード 3 を権限の失敗とみなすのは hello の前だけ、診断は ASCII の1行）は残っている。

**依存**
- 新しく入ったのは argon2 0.5.3・password-hash 0.5.0・chacha20poly1305 0.10 で、知っている勧告はない（`cargo audit` のデータベースは、外へつながないので引いていない）。
- `ENABLE_P2P_DOCS_AUTOMATION` は、Release・MinSizeRel ではビルドできず、インストールもできない。さらに環境変数がなければ動かない。リリースのスクリプトは付けていない。
- 招待文字列・合言葉のコピーには、クリップボードの履歴に残さない印を付け、期限が過ぎたら消す。
