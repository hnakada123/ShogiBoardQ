# セキュリティ監査：P2P対局（2026-11-13）

「P2P対局のソースコードのセキュリティ監査。Winny のように情報漏洩にならないかも確認」の依頼で、P2P対局（実験版、`ENABLE_P2P_PLAY`）を監査した。

- 対象のコミットは 0aec36d9。本文の行番号はこの時点のもの。
- 対象
  - Rust の通信プロセス `peer/`・`protocol/rust/`（約5,400行）
  - C++ の `src/game/p2p/`・`src/network/p2p/`（約8,300行）
  - 画面 `src/dialogs/p2p*`・`src/ui/controllers/p2pgameuicontroller.*`
  - 証跡の検証 `src/headless/matchverificationservice.cpp`・`src/cli/clicommands_p2p.cpp`
  - ビルドと配布の設定、公開しているガイドの P2P のページと画像
- 想定した攻撃者
  - A: 招待文字列を持つ者・対局相手（改造したクライアント）
  - B: 協力ノード（中継）の運営者、通信の観測者
  - C: 同じ LAN の機器、同じ PC の別ユーザー（待受のポートにつなげる者）
  - D: 細工した証跡ファイル（.sbqmatch）を利用者に渡す者
  - E: 通信プロセスを乗っ取った者（サンドボックスの中から）
  - F: 招待を持たない、インターネット上の任意のピア
  - 仕様 1.2節で「受け入れる」と明記した限界（直接つなぐと相手に IP が見える、など）は、実装が仕様どおりなら指摘にしていない。
- 「確認」の欄の意味
  - 「再現＋」: 区画の担当が実行で再現し、主担当がコード・ライブラリのソース・実行の出力でもう一度確かめた
  - 「再現」: 区画の担当が実行で再現した
  - 「コード」: 経路を読んで確かめた
- 使った手段
  - libFuzzer＋ASan/UBSan
    - C++ のフレーム・証跡の読み取り: 約2,700万回
    - 交渉の状態機械: 約147万回
    - 対局の状態機械: 6並列で合計23分
  - Rust の読み取りの変異入力: 各300万回
  - ASan 付きの IPC の試験台と偽の通信プロセス
  - `unshare -rn` で外へ出られないネットワーク名前空間を作り、その中で AutoNAT・Identify の probe を動かした
  - 本物の通信プロセス2つを loopback でつないだ
  - 外部のネットワークには接続していない
- 監査ではソースを変更していない。

## 全体の評価

**今配布しているアプリには影響しない。** リリースのワークフローとスクリプトは `ENABLE_P2P_PLAY` を付けておらず、配布物に P2P対局は入っていない。影響を受けるのは、自分でビルドして試す人だけである。

**High が1件ある（P1）。** 改造したクライアントの相手が、被害者に1手も指させずに、検証に通る「被害者の時間切れ負け」の記録を作れる。これは双方の署名がそろった記録である。証跡の中心の保証（双方が合意した結果だけに署名する）が破れている。情報漏えいやコードの実行ではない。

**Winny 型の心配（後述の「Winny との比較」）について**
- ファイルが流出する経路はない。
- 遠隔からのメモリ破壊も見つからなかった。
- ただし、アドレスが仕様より多く渡る経路が2つある（P2・P10）。
- 招待を細工すると、利用者の PC から LAN 内や loopback へ接続させられる経路が1つある（P3）。

**新しい問題の型は3つある。**
1. **状態機械が「段階」を確かめずに結果の提案を受ける**（P1・P7）。
   - 結果の提案に同意する条件が、対局の段階（READY の前か）を見ていない。
   - 棋譜から決まった終局も見ていない。
2. **libp2p の部品の既定値が、仕様の前提と合っていない**（P2・P3・P5）。
   - AutoNAT v1 のクライアントは、待受のアドレスを全部送る。
   - libp2p-tcp は、multiaddr の末尾の IP へつなぐ。
   - 手で組んだ Transport には、確立の期限がない。
   - どれも、ライブラリの中で起きることをコードの側が想定していなかった。
3. **前回の V1・V2 と同じ型が P2P の画面にもある**（P4）。
   - 通信プロセスからの知らせを処理している最中に、モーダルの `exec()` に入る。
   - その入れ子のループの中で、通信プロセスの部品が解放される。

## Winny との比較

Winny で問題になったのは、次の3つだった。
1. ファイル共有の仕組みに暴露ウイルス（Antinny）が乗り、利用者の文書・画像が不特定多数に流出した。
2. 不特定多数のノードに IP アドレスが露出した。
3. 遠隔から突けるバッファオーバーフローがあった。

| Winny の問題 | P2P対局 | 根拠 |
|---|---|---|
| (1) ファイルの流出 | **経路はない。** ファイルを読んで相手へ送る口（Winny の共有フォルダに当たるもの）が、アプリにも通信プロセスにもない。<br>・相手へ送るのは、招待の合言葉と、盤と状態機械の値（指し手・局面のハッシュ・時間・結果・署名）だけ。<br>・棋譜のコメント・対局情報・証跡ファイル・パスは送らない。<br>・通信プロセスは Landlock でファイルを読めない。<br>・IPC にファイルパスやコマンドを運ぶ口もない。<br>・証跡を他人に渡すのは、利用者が書き出して自分で渡したときだけ。 | `peer/src/node/streams.rs:133`、`peer/src/game.rs:195`、`peeripc.cpp:340-405`、`peer/src/sandbox.rs` |
| (2) IP の露出 | **相手は招待で決める**（不特定の相手との公開募集・DHT・GossipSub は仕様の第5版で外した）。直接つなぐと、対局相手に IP が見える（仕様で受け入れた限界で、ガイドで伝えている）。「直接接続を使わない」では中継のアドレスだけになる。<br>**ただし、仕様より多く渡る経路が2つある。**<br>・P2: インターネットの既定の設定で、全インターフェースのアドレスが協力ノードと直接つながった相手に渡る。LAN・VPN・docker のアドレスと IPv6 の link-local（環境によっては MAC 由来）を含む。<br>・P10: ローカル検証用のネットワークで、LAN の機器に渡る。<br>**逆向きの危険もある**（P3）。細工した招待で、利用者の PC から LAN 内・loopback へ接続を始めさせられる。 | P2・P3・P10 |
| (3) 遠隔からのメモリ破壊 | **見つからなかった。**<br>・相手が送るバイト列は、まず Rust の通信プロセス（unsafe 禁止・panic を起こす書き方を禁止・リリースでも溢れの検査）が形を確かめる。そのうえで C++ が決定的 CBOR として読み直す。<br>・C++ の読み取り部を ASan・UBSan 付きでファジングし、違反はなかった（約2,700万回）。<br>・解放後の使用が1件ある（P4）。相手が送るフレームでは起こせない。起こすのは、通信プロセスの版違い・異常終了・乗っ取り（E）である。 | 「4. 問題がなかった点」、P4 |

このほか、情報の扱いについて次を確かめた。
- ログ: Release 版は何も書かない。Debug 版の P2P の文は定型文だけである。通信プロセスの stderr はメモリに 64 KiB 持つだけで保存しない。どこにも、IP・招待文字列・合言葉・鍵・プレイヤーID の対応表・棋譜全文は出ない。
- 保存先の権限: 鍵・ジャーナル・証跡・既知の相手のファイルは 0600、フォルダは 0700 だった。
- 設定ファイル: 鍵・パスフレーズ・招待文字列は書かない。
- 公開しているガイドの画像: 開発者の実際の IP は写っていない。ローカル版の招待文字列は作り物（2本とも検査の値が同じ）で、インターネット版は撮影用コンテナの実験用アドレス（192.88.99.0/24）だけである。

## 2. 詳細

### P1【High】開始の手続きの途中に相手が出した「こちらの時間切れ」の提案に同意し、0手目の時間切れ負けに双方の署名がそろう

**場所**

| 箇所 | 内容 |
|---|---|
| `src/game/p2p/p2pmatch.cpp:174-217`（`Match::receive`）・`src/game/p2p/p2pmatch_control.cpp:29-60`（`handleControl`） | 開始の段階（`Phase::Opening`、READY の前）の CONTROL を断らない |
| `p2pmatch_control.cpp:211-228` | 時間切れの提案を受ける分岐。対局の段階も、READY を交わしたか（`m_readyDone`）も見ない |
| `p2pmatch_control.cpp:241-`（`agree`） | 段階を見ずに署名する |
| `src/game/p2p/p2pmatchtimer.h:25,59` | `mySpentMs = now − m_myTurnStart`。`m_myTurnStart` の初期値は 0 で、先手は READY を受けるまで `startMyTurn` を呼ばない（`p2pmatch_control.cpp:86`） |
| `src/network/p2p/p2pgamecoordinator.cpp:49` | `now()` の基準の `m_elapsed` は、司令塔を作ったとき（アプリの起動時）に start する。消費時間は「アプリを起動してからの時間」になる |

**手順**
1. 改造したクライアントの相手が、後手になる。招待した側なら後手を希望し、申込側なら HELLO で後手を希望すればよい。
2. 相手は State0 に STATE_ACCEPT を返すが、READY は送らない。
3. 相手は、CONTROL の seq 1 で `RESULT_PROPOSE {Timeout, 後手の勝ち, ply 0}` を送る。
4. 先手（被害者）の手元では次のとおり判定される。
   - `isMyTurn()` は真、未確認の手もない。
   - 消費時間は「起動してからの時間」になる。
   - 起動から持ち時間＋秒読み（既定 10分30秒）を超えていれば、`canMoveWithin` が偽になる。
5. 先手は時間切れに同意し、プレイヤー鍵で FinalResult に署名して送る。
6. 相手が RESULT_SIGNATURE を返すと、確定のしかたは MutuallySigned になる。

被害者がすることは、条件確認で「開始」を押すことだけである。

**確認**
- 区画の担当が、状態機械の試験台で再現した。

  | 起動からの時間 | 条件 | 結果 |
  |---|---|---|
  | 700秒 | 10分＋30秒 | 成立（`valid=1`・`mutually_signed`） |
  | 100秒 | 1分＋10秒 | 成立 |
  | 100秒 | 10分＋30秒 | 成立しない |

- 対局の状態機械のファズに「結果に同意するのは READY の後だけ」という条件を足すと、6つのワーカーがすべて独立に約500回以内でこれを見つけた。
- 主担当は、上の経路をコードで確かめた。あわせて、作られた証跡を `shogiboardq-cli verify-match` に渡し、次の出力を確かめた。
  - `"valid": true`、`"category": "mutually_signed"`
  - `"result": {"cause":"timeout","outcome":"white_wins","ply":0,"black_signed":true,"white_signed":true}`
- 司令塔と通信プロセスを通した実際の対局では試していない。司令塔の時計とフレームの振り分けは、コードで確かめた。

**影響**
- 記録に入るのは、双方の署名がそろい、第三者の検証にも通る「負け」である。証跡の中心の保証が破れている。
- 公式のレーティングや賭けは対象外（仕様1章）なので、損害は記録の信頼に限られる。

**直し方の案**
- 結果の提案を受ける・同意する（`handleResultPropose`・`agree`・`answerOffer`）のは、`Phase::Playing` で READY を交わした後に限る。
- `MatchTimer` に「自分の手番が始まったか」を持たせ、始まる前の消費時間は 0 にする。
- 回帰試験を足す。既存の試験の時計は 1,000,000 ms から始まるので、試験でもこの経路が時間切れになりうる。

### P2【Medium】AutoNAT の問い合わせに、全インターフェースのアドレスが入る

**場所**
- `peer/src/swarm.rs:116-126`: `autonat::Config` で変えているのは `only_global_ips: true` だけで、ほかは既定（`use_connected: true`）。`only_global_ips` が効くのはサーバー側だけである。
- `peer/src/node.rs:232`: インターネットの profile で relayOnly でないとき（既定）に有効になる。
- `peer/src/listen.rs:57-62`: 0.0.0.0 と :: で待ち受けるので、待受のアドレスがインターフェースの数だけ増える。
- libp2p-autonat 0.15.0 `src/v1/behaviour/as_client.rs:190-196, 248-, 289-292`: 問い合わせ（DialRequest）に、`other_candidates ∪ listen_addresses` を絞り込まずに入れる。問い合わせ先は、登録したサーバーと、つながっているピア（`use_connected`）から選ぶ。

**何がだれに渡るか**
- 渡るもの
  - 私設 IPv4（LAN・VPN・docker）
  - 127.0.0.1・::1
  - IPv6 のグローバル・link-local
  - それぞれのポート
- link-local が MAC から作る形（EUI-64）の環境では、MAC アドレスも分かる。
- 受け取るのは次のとおり。
  - 協力ノード（B）
  - 直接つながった対局相手（A）
  - こちらの待受につないできたピア（F。`use_connected` で依頼先の候補になる）
- 仕様4章の「自分が広告するアドレスからも私設アドレスを除く。LAN の構成を配らない」に反する。
- ガイド p2p-relay の「協力ノードの運営者に見えるもの」にも書かれていない。
- `node.rs:229-231` の注記では、relayOnly のときに AutoNAT を止める理由として、問い合わせにアドレスの候補が入ることを挙げている。その危険が、直接接続の既定の設定では残っている。

**確認**
- 区画の担当が再現した。
  - 外へ出られないネットワーク名前空間を作り、その中に 8.8.8.8・192.168.50.2・172.17.0.1・10.8.0.5・2400:4050::1234 を置いた。
  - 協力ノードに見立てた probe へ、通信プロセスから約15秒で問い合わせが届いた。
  - 問い合わせには、私設・loopback・link-local（`fe80::…ff:fe…`）を含む17件の候補があった。
- Rust の区画の担当も、同じ結果を別の道具で得た。
- 主担当は、ライブラリのソースと出力を確かめた。

**直し方の案**
- `use_connected: false` にし、`add_server` で協力ノードだけを問い合わせ先にする。
- そのうえで、待受のアドレスを送らない方式（AutoNAT v2、または観測されたグローバルなアドレスを1件ずつ確かめる自前の方式）に替える。v1 のままでは、協力ノードに LAN の構成が渡る。
- 上の名前空間の試験を、回帰試験にする。
- 仕様とガイドの説明を、実装に合わせる。

### P3【Medium】宛先の規則は先頭の IP しか見ないが、TCP は末尾の IP へつなぐ

**場所**
- `peer/src/addr.rs:229-239`: `profile_allows` は `first_ip`（:93）だけを見て、その後ろの部品を調べない。`usable`・`allows_dial`・私設アドレスの判定（:248, 253, 264, 276, 318）も同じ。
- libp2p-tcp 0.44.1 `src/lib.rs:682-`: `multiaddr_to_socketaddr` は、末尾から IP とポートを取り、前の部品を無視する。

**手順**
- インターネットの profile で「私設アドレスへの接続を許可」を求めない設定のまま、招待の宛先に `/ip4/1.2.3.4/tcp/1/ip4/127.0.0.1/tcp/<port>` を書く。
  - inspectInvite は `usableAddressCount: 1` を返し、`privateAddresses` は空になる。そのため利用者に許可を求める画面が出ない。
  - connectInvite の後、127.0.0.1 の待受に `/multistream/1.0.0` と `/noise` が届いた。
- ローカルの profile では `/ip4/127.0.0.1/tcp/1/ip6/<グローバルIPv6>/tcp/<port>` と書くと、インターネット上のアドレスへつながった。
- 協力ノード・対局相手が Identify で名乗る宛先も同じ規則を通る（`events.rs:160, 163`）。
  - relayOnly のときの「協力ノードが名乗った別の宛先」への直接接続の許可にも入る（B）。

**影響**
- 仕様4章・12章の「招待や Identify に他人のアドレスを書き込んで、利用者の PC から LAN 内の機器や第三者へ接続させる使い方を防ぐ」が成り立っていない。
- 送られるのは libp2p の決まったバイト列だけなので、任意の要求を送らせる手段ではない。LAN 内の機器・ポートの探索には使える。

**確認**
- 区画の担当が再現した。
- 主担当が、規則とライブラリのコードを確かめた。

**直し方の案**
- 受け付ける形を、決めた並びだけにする。
  - `ip/tcp[/p2p]`
  - `ip/udp/quic-v1[/p2p]`
  - 上の2つに `/p2p/<中継>/p2p-circuit[/p2p/<宛先>]` を付けた形
- 宛先の中に出てくる IP を、すべて区分で確かめる。
- 知らない部品を含む宛先は断る。

### P4【Medium】失敗の知らせのモーダルの中で `PeerProcess` が解放され、戻った先で解放後の使用

**場所**
- 読む側: `src/network/p2p/peerprocess.cpp:178`（`onReadyReadStdout` の `while (m_buffer.size() >= 4 && m_process)`）
- 失敗の知らせ: `peerprocess.cpp:291-304`（`fail` が kill して `failed` を出す）
- 解放する側: `src/network/p2p/p2plobbyservice.cpp:164-171`（`onPeerStopped` の `deleteLater`）
- モーダル: `src/ui/controllers/p2pgameuicontroller.cpp:344`（`NotificationPresenter::warning` は閉じるまで待つ）、`src/dialogs/p2pwindow.cpp:634`（`DialogUtils::warning`）

**起きること**
1. 受信の処理の中で `handleMessage` が `fail()` を呼ぶ。
2. `failed` が直接の接続で警告の箱に届き、`exec()` に入る。
3. 入れ子のループで、kill したプロセスの `finished` から `onPeerStopped` の `deleteLater` までが走り、`PeerProcess` が解放される。
4. 箱を閉じると、外側の `onReadyReadStdout` が解放済みの `this` を読む。

**悪意のない起こし方**
- 版の違う通信プロセス: hello の `ipcVersion` が違う。
- 招待の接続が開けなかったという普通の知らせ（`connectionClosed`）の箱を開いている間に、通信プロセスが異常終了する（OOM killer など）。

**確認**
- 区画の担当が、本物の `PeerProcess`・`P2pLobbyService`・`NotificationPresenter` を ASan 付きでつないだ試験台で、3通りの起こし方を再現した。
- 主担当は、ASan の `heap-use-after-free READ at peerprocess.cpp:178`（解放は `~PeerProcess`）の出力と、経路のコードを確かめた。
- ASan なしでは、解放したメモリが使い回されていなければループを抜けるだけである。使い回されていると、`m_buffer.remove` が書き込む可能性がある。
- 悪用できることは確かめていない。

**直し方の案**
- 通信プロセスから届いた知らせの中では `exec()` しない。`onPeerFailed`・`onConnectFailed` は `Wait::No`、またはモードレスにする。申し出の確認を直したとき（B2）と同じ直し方である。
- `onReadyReadStdout` に `QPointer<PeerProcess> self(this)` を置き、`handleMessage` の後で `if (!self || m_failed) return;` とする。これで P11・Info の I-a も直る。
- `onPeerStopped` の後始末は、次のイベントループで行う。

### P5【Medium】Transport に確立の期限がなく、何も送らない TCP の接続8本で受け付けが止まる

**場所**
- `peer/src/swarm.rs:57-71`: Transport を手で組んでいて、`TransportTimeout`（`.timeout()`）が無い。SwarmBuilder なら既定で10秒の期限が付く。
- `swarm.rs:75`: `with_max_pending_incoming(Some(8))` は全体で8件。

**手順**
- 待受の TCP に、connect するだけの接続を8本張る。ローカル検証用なら、ポートは 48210 に決まっている。
- その後、正しい招待での connectInvite が `connectionClosed: unreachable` になる。
- 200秒後も状態は変わらなかった。
- QUIC や中継で届く接続も、確立前の8枠に当たるので止まる。
- 対局中の再接続も、同じ理由で受けられないと推測する（再接続は未試験）。

**確認**
- 区画の担当が再現した。
- 主担当がコードを確かめた。

**直し方の案**
- 組んだ Transport を `TransportTimeout`（10〜20秒）で包む。
- 接続元の IP ごとに、確立前の接続の数に上限を置く。

### P6【Medium】招待を持たない相手の対局ストリーム8本で、招待を持つ相手のストリームが捨てられる

**場所**
- `peer/src/node/streams.rs:301-325`: `accept_task` は確立前のストリームを全体で8件まで数え、超えた分を捨てる。
- 招待の合言葉と相手の確認（`on_inbound`、245-265）は、最初のフレームを読んだ後に行う。
- 最初のフレームを待つ時間（`FIRST_FRAME_TIMEOUT`）は10秒（:22）。

**手順**
- libp2p の接続を張り、`/shogiboardq/game/1.0.0` を8本開いて、長さの1バイトだけ送って止める。10秒で閉じられたら開き直す。
- その間、正しい招待での接続は3回とも失敗した。
- PeerId は1つあれば足りる。
- 仕様 1.2節の「招待は渡した範囲にしか影響しない」に当たらない。
- 対局中の再接続のストリームも、同じ枠で止まる（コードで確認）。

**確認**
- 区画の担当が再現した（対照として、攻撃しないときは成功した）。

**直し方の案**
- 待ちの枠を、相手ごとに1件までにする。
- 対局中（setGamePeer の後）は、対局相手以外のストリームを読む前に閉じる。
- 対局相手のために枠を取っておく。

### P7【Medium】棋譜から終局が決まった局面でも、相手の投了・時間切れの申告に同意して署名する

**場所**
- `p2pmatch_control.cpp:187-194`（投了）・`:211-228`（時間切れの申告）
- 合意の申し出（`:229-236`）も、利用者が承諾すると同じことになる。

**起きること**
- 自分の `GameRules::judge` が終局（千日手・詰みなど）と判定していても、投了や「相手が自分の時間切れを申告」の提案には、棋譜を見ずに同意して署名する。
- 自分の検証器は、その証跡を「署名された結果が棋譜と食い違う」として `valid=false` にし、手元の履歴は「検証に失敗」と出す。
- 相手が何もせずに去れば、勝った側には `determined_by_record` の正しい記録が残る。ところが相手が投了を送るだけで、その記録を「検証に失敗」に変えられる。

**仕様との関係**
- 実装仕様 8.1節は「自分の判定と一致しない提案には同意しない」としている。
- 互換仕様（`docs/dev/p2p-interop-spec.html`）は、10.2節の表で投了に棋譜を見る条件を書いていない。一方、13.2節の検証は、棋譜から決まる終局との一致を求めている。合意の規則と検証の規則が食い違っている。

**確認**
- 区画の担当が、千日手の例で再現した（`scenarios` の S1 で `valid=0 conflicts=1`）。
- 詰みの局面は、同じ分岐を通ることをコードで確かめた。

**直し方の案**
- `judge(m_confirmed)` が終局を返すときは、それと違う提案をすべて断る。申し出も、利用者に尋ねずに断る。
- 互換仕様も合わせて直す。

### P8【Medium、前提は E】seccomp の拒否の表が x32 の番号を見ない

**場所**
- `peer/src/sandbox.rs:66-135`: 拒否の表で、既定の動作は Allow。
- `sandbox.rs:193-194`: 表を掛ける箇所。
- seccompiler 0.5 は、アーキテクチャの値（AUDIT_ARCH_X86_64）しか確かめない。x32 も同じ値になる。

**起きること**
- x32 の番号（0x40000000 を立てた番号）で呼ぶと、拒否の表に当たらない。
- x32 の `socket(AF_UNIX)` と `clone(SIGCHLD)`（fork）が成功した。
- fork した子は、親の終了の通知（PDEATHSIG）を引き継がない。そのため、アプリを閉じた後も通信を続けるプロセスを残せる。
- Landlock の ABI が 8 以下の古いカーネルを模すと、x32 のソケットから、ファイルシステム上の Unix ソケットへ connect できた。
  - D-Bus のセッションバスを経由した脱出は推定で、試していない。
  - ABI 9（監査に使った PC）では Landlock が止める。
- `protocol/ipc.md` 6章の「socket は AF_INET・AF_INET6・AF_NETLINK 以外を拒否」は、x32 が有効なカーネルでは成り立たない。

**確認**
- 区画の担当が、本体と同じ表・同じ版の crate を使う試験プログラムで再現した。
- 主担当は、表の既定の動作と、監査に使った PC（Arch Linux の標準カーネル）の `CONFIG_X86_X32_ABI=y` を確かめた。
- ほかの配布物のカーネルで x32 が有効かは、確かめていない。

**直し方の案**
- 番号に 0x40000000 が立った呼び出しを拒否する BPF を足す。`sock_filter` の列を作って `seccompiler::apply_filter` に渡せば、unsafe なしで書ける。
- または、許可したものだけを通す表に切り替える。
- `--sandbox-self-test` に x32 の試行を足す。

### P9【Low、E】seccomp の表の漏れ

すべて区画の担当が試験プログラムで再現した。

| 漏れ | 起きること |
|---|---|
| シグナル: `tgkill`・`tkill`・`rt_sigqueueinfo`・`rt_tgsigqueueinfo` が表に無い | Landlock の ABI が 6 未満（Linux 6.12 より前）では、ほかのプロセス（親）へシグナルを送れた |
| 属性の変更: `fchmodat`・`utimensat` が通る | 0600 のファイルを 0666 にできた。仕様 10.4節の「ファイルは読み書きなし」に対して、属性は書き換えられる。プレイヤー鍵のファイルをほかの利用者に読めるようにする、といった使い方ができる |
| `AF_NETLINK` のプロトコルを絞っていない | `NETLINK_SOCK_DIAG`・`NETLINK_GENERIC`・`KOBJECT_UEVENT` を作れた。`NETLINK_ROUTE` でも、隣の機器の表（LAN の機器の MAC アドレス）を読める |
| ICMP の datagram ソケット | 作れた |

**直し方の案**
- シグナルの4つは、自分の PID 宛てだけ許す。
- chmod・chown・utime・xattr の系統の呼び出しを拒否する。
- netlink は、プロトコルが 0 のときだけ許す。

### P10【Low】ローカル検証用で、招待のない LAN の機器にも Identify で私設アドレスのすべてを配る

### P12【Low、E】networkId の不一致を失敗にするが、通信プロセスを止めない

### P13【Low、E】SandboxFailed の知らせに、通信プロセスの stderr を出す

### P15【Low】開いたままの P2P のウィンドウの「接続」が、ほかの動作状態を取り上げる

- 場所:
  - `src/dialogs/p2pwindow.cpp:423`: 「接続」のボタンは、P2P の司令塔の `isBusy` だけを見る。

### P16【Low、D】CBOR の読み取りの reserve が確保を増幅する

- 場所: `src/game/p2p/p2pcbor.cpp:131-133`
- 内容: 配列の要素数を「残りのバイト数以下か」だけ確かめて `reserve(要素数)` する。要素1つは64バイトである。
- 細工した 8 MiB の証跡を `verify-match` に渡した結果（Debug 版）:

  | 中身 | 結果 |
  |---|---|
  | 全体が `[0,0,…]` | RSS 582MB |

  - 証跡全体の要素の総数に上限を置く。

### P17【Low、A】再接続を1回した後は、SYNC_REQUEST に何度でも全状態を送り返す

- 場所: `p2pmatch_control.cpp:365`（`m_resumeReceived` が照合の後も真のまま残り、段階も見ない）
- 起きること: 対局中に要求を50回送ると、50フレーム・153,644バイトが返った（再現）。返す先は要求した相手だけなので、中継の量の上限を減らす程度である。

### P18【Low、A】受けた CONTROL を、形を確かめる前にジャーナルへ書き、書けなくても続ける

- 場所: `p2pmatch_control.cpp:41-43`
- 起きること:
  - 約60KBの body を付けた RESULT_DECLINE を100件送ると、ジャーナルが約6MB増え、対局は続いた（再現）。

  - その後に届く矛盾の証明は、ジャーナルに残らない。
- 相手はもともと ABORT で対局を終えられるので、新しく得る力は小さい。
- 直し方の案:
  - 形を確かめてから書く。
  - 書けなければ、仕様4章のとおり STORAGE_ERROR で中断する。

### P19・P20【Low】Rust の資源の上限

- **P19**（C・F、コード）: 宛先の覚え `addr_book`（64ピア）を消さない（`peer/src/node.rs:39, 307-320`、`events.rs:163-164`）。

  - 埋まると、対局相手の宛先を覚えなくなる。

## 4. 問題がなかった点

**読み取り（Winny の (3) に当たる部分）**
- C++ の CBOR は次を拒否する。
  - map・tag・浮動小数・負の整数・不定長
  - 最短でない形
  - 残りを超える長さ（長さを確かめてから読む）
  - 不正な UTF-8（過長・サロゲート）
  - 17段以上の入れ子
  - 余りのバイト
- フレームは 64KiB、証跡は 8MiB の上限を、読む前に確かめている。
- libFuzzer＋ASan/UBSan で約2,700万回入力し、違反はなかった。読み直したものが元のバイト列に戻ること、符号化し直すと一致すること（署名の対象がずれないこと）を毎回確かめた。
- Rust の `frame::check`・`cbor::decode`・`Invite::decode`・`Multiaddr::try_from` に、各300万回の変異入力を入れ、panic は0だった。
- clippy の deny（unwrap・添字・算術）は通る。
- IPC の受信について
  - 長さを確かめてから待つ。
  - 64bit の値は10進の文字列で受け、base64 は厳格に読む。
  - 知らない形・古い世代を拒否し、違反があれば通信プロセスを kill する。

**署名・状態機械**
- 公開鍵と署名の長さ・点の正しさを確かめてから検証する。位数の小さい点・正規でない S は拒否する（既存の試験）。
- ラベル・gameId・ply・connectionId・sequence で、別の対象への署名の流用を防いでいる。
- 募集側は、申込側の開始署名を確かめてから自分の開始署名を作る。
- commit-reveal を照合している。
- 自分は、同じ手数の2つの状態にも、2つの結果にも署名しない。
- 状態機械のファズ（P1 の条件を除く）で、確定した手順・自分の証跡の検証・時計の計算に違反はなかった。

**招待と接続**
- 招待の合言葉
  - OS の乱数から32バイトで作る。
  - 処理時間の変わらない比較で照合する。
  - 1回で消え、期限は10分。同時に4件まで。
  - Noise で認証した招待元へのストリームでだけ送る。
  - ログ・IPC のエラーに出ない。
- relayOnly のとき
  - DCUtR・AutoNAT を動かさない（実測）。
  - 直接の接続を断る規則は、すべての接続に掛かる。
  - 自分のアドレスとして出すのは、中継経由のアドレスだけ。
- Identify に、OS・ホスト名・利用者名は入らない。
- ローカル検証用では、接続元が私設でない接続を、証明書やバイトを送る前に閉じる。

**通信プロセスの起動**
- 実行ファイルは、アプリのフォルダからの絶対パスで起動する。差し替えの口は Debug 版だけにある。
- 環境変数は空にし、標準入出力以外の記述子は閉じ、作業フォルダは `/` にする。
- 終了は、shutdown → 2秒で terminate → さらに2秒で kill で、どれも非同期。
- サンドボックスは、入力を読む前・スレッドを作る前に掛け、失敗すれば終了する。

**情報の扱い**
- HELLO・招待文字列に、OS・ホスト名・時刻・表示名・プレイヤーID は入らない（招待文字列の場合）。
- 証跡に、表示名・IP・PeerId・パス・利用者名は入らない（実物を読んで確かめた）。
- 画面に IP は出ない。例外は、仕様どおりの「私設アドレスの許可の確認」だけ。
- 相手の文字列は PlainText で出し、ツールチップは `plainToolTip` で包む。
- 棋譜は自動保存しない。
- `--automation` では P2P の部品を作らない。MCP に P2P の道具は無い。
- P2P対局中は、検討・詰み探索・棋譜解析・定跡の表示を止める。
- 依存（`Cargo.lock`）は、知っている勧告の版より新しい。dns・mdns・kad・gossipsub・upnp はビルドされない。

## 5. 調べきれなかった範囲

- 本物の NAT・協力ノード・中継を使ったインターネット越しの対局
  - P2 は、隔離したネットワークの probe で起こした。
  - relayOnly で相手に IP が見えないことは、コードで確かめただけ。
- P1・P7 は、状態機械の試験台で再現した。司令塔と通信プロセスを通した実際の対局では試していない。
- 外へ接続できないため、`cargo audit` の勧告のデータベースを引けなかった。依存の版を読んで、知っている勧告と照らしただけ。
- libp2p の内部（noise・yamux・quinn・protobuf）の本格的なファジング
- P8 の D-Bus 経由の脱出。ほかの配布物のカーネルで x32 が有効か
- QtKeychain の実際の保管庫（利用者の保管庫に触れないため）
- Windows・macOS 全般（P2P は Linux 以外では UnsupportedOs）
- `--service`（協力ノード）は、コードを読んだだけ
- ファジングは合計で数十分と短い

| I-e | 撮影用のビルドでも、環境変数 `SHOGIBOARDQ_P2P_DOCS_LAB=1` を付けて起動したときだけ、自動化 API から P2P対局を動かせる（`AutomationActionPolicy::allowsP2pPlay`）。撮影のスクリプト（`launch.sh`・`p2p_internet/inside.sh`）が付ける | `tst_automation_security::p2pPlayIsDrivableOnlyInTheDocsBuild`（環境変数がなければ、撮影用のビルドでも許可しない） |
| I-l | 実験版（ShogiBoardQ-P2P）が隣のフォルダに残した `peers.cache`（ほかの参加者の IP）を、保存先を開くときに消す。鍵と記録は利用者のものなので消さない | `tst_p2p_identity::legacyPeerCacheIsRemoved` |
| I-g（鍵の保管庫・パスフレーズ） | 鍵の保管庫のジョブと共有している種の領域を、切り離さずにその場で0にする（書き終えたとき・読んだとき）。パスフレーズの入力欄も、鍵の処理が終わった後に共有の領域ごと0にしてから空にする。所有者のファイルは、Qt の内部の書き込み用の領域を使わずに書く | `tst_p2p_identity` |
| I-p（192.88.99.0/24） | 廃止された 6to4 の中継の範囲として使わない。撮影用コンテナの「インターネット」を 11.88.99.0/24 に替えた | `addr.rs` の試験。撮影用コンテナで、日本語の撮影の手順（招待・直接接続への切り替え・中継だけの対局）が最後まで通ることを確かめた |
| I-u（知らないネットワーク・状態0件） | 知らないネットワークの証跡は無効にした（このビルドでは、そのネットワークの規則を確かめられない）。状態が0件の証跡（開始局面の承認の前に終わった対局）は結果未確定の正しい記録なので有効のままにし、CLI の `checks` に `has_record` と `known_network` を足して区別できるようにした | `tst_p2p_protocol::evidenceOfUnknownNetworkIsNotValid` |

QtKeychain がライブラリの内部で一時的に作る写し（OS の鍵の保管庫へ送る途中の形式の変換など）は、アプリから触れない。これは、同じ利用者の権限で動くマルウェアを防げないという仕様 1.2節の限界の内側にある。
