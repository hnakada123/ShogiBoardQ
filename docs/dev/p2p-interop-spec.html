1. この文書について

1.1 目的と適用範囲

この文書は、ShogiBoardQ（将棋盤Q。P2P対局を有効にしたビルド）の「P2P対局」と相互に対局できるソフトウェアを、別の実装として作るための仕様書である。ネットワークを流れるバイト列、手順、検査、時間の決まり、対局記録（証跡）のファイルの形を定める。この文書どおりに作った実装どうしは、招待文字列を渡して接続し、対局し、双方で確定した対局記録を残せる。

対象は、プロトコルの版 1（フレームの version が 1、各値の版が 1）である。次のものは対象外で、実装ごとに自由に決めてよい。

  • 画面と操作、設定の保存、プレイヤー鍵の保管の方法（OS の鍵の保管庫・暗号化したファイルなど）
  • 通信を受け持つ部分と対局・画面の部分の分け方（ShogiBoardQ は別プロセスに分け、JSON の IPC でつなぐが、互換性には関係しない）
  • 権限の制限（サンドボックス）などの、実装の中の安全対策

1.2 言葉の使い方

書き方意味
〜しなければならない／〜する互換性と安全のために必ず守る（MUST）
〜してはならない必ず避ける（MUST NOT）
〜することが望ましい特別な理由がなければ従う（SHOULD）
〜してよい実装が選べる（MAY）

この文書で「断る」「拒否する」と書いた入力を受け取った実装は、それを正しい入力として扱ってはならない。どう知らせるか（REJECT を送る・ストリームを閉じる・黙って捨てる）は、各節に書く。

1.3 全体の流れ

対局者を2人とし、招待する側を招待側（プロトコルの中では「募集側」、role = 2）、招待を受けて接続する側を申込側（role = 1）と呼ぶ。

  1. 接続：双方が libp2p のノードを起動する（4章）。インターネット越しでは、利用者が指定した協力ノード（中継と到達性の確認を受け持つノード）にもつなぐ。
  2. 招待：招待側が招待文字列を作り、利用者が別の経路（メッセージなど）で相手に渡す（5章）。
  3. ストリーム：申込側が招待文字列の宛先へ接続し、対局ストリームを開いて、最初に招待の合言葉（INVITE_TOKEN）を送る（6章）。
  4. 開始の交渉：HELLO を交換し、条件と先後を決め、開始合意（StartAgreement）に双方がプレイヤー鍵で署名する（8章）。
  5. 対局：1手ごとに、指した側が状態（State）を提案し、相手が確かめて承認する。どちらも一局用鍵で署名する（9章）。
  6. 終局：結果（FinalResult）を照らし合わせ、双方がプレイヤー鍵で署名する（10章）。
  7. 記録：それぞれが、開始合意・全手順・署名を1つのファイル（証跡）に保存する。だれでも検証できる（13章）。

対局サーバーはない。対局の正しさは、相手のアプリを信用せずに、受け取った値を自分で確かめることで保つ。回線が切れたときは、同じ対局へつなぎ直せる（11章）。

1.4 防げないこと

このプロトコルは、次のことを防がない。互換実装は、利用者にそう説明することが望ましい。

  • 表示名は自己申告である。相手を見分ける根拠は、プレイヤー鍵の公開鍵（プレイヤーID）と確認コード（3.5節）だけである。
  • 負けた側が結果に署名しなければ、双方が署名した記録は残らない。
  • 消費時間は自己申告である。1手あたり 10 秒までの水増しと、切断を使った時間稼ぎ（1局で合計10分まで）は見分けられない。
  • エンジンが指した対局や、示し合わせた対局は見分けられない。
  • 直接つなぐと、相手は通信を調べて IP アドレスを知ることができる（中継だけを使う設定で避けられる。4.6節）。

2. 記法と共通の規則

2.1 値の書き方

この文書では、CBOR の値を次のように書く。

書き方意味
uint符号なし整数（0〜264−1）
bstr、bstr(32)byte string。括弧の数は長さ（バイト）
tstrtext string（UTF-8）
[a, b, ...]配列。要素の数と順序は固定で、書いていない要素を足してはならない
"SBQ-..."その文字列そのものの tstr（値の種類を表すラベル）
zero32ゼロ 32 バイトの bstr

真偽は uint の 0／1 で表す。時刻は UNIX 秒（uint）、時間の長さはミリ秒（uint）である。16進表記は小文字とする。

2.2 決定的CBOR

署名・ハッシュ・フレーム・招待文字列・証跡に使う CBOR は、RFC 8949 の core deterministic encoding のうち、次の部分だけを使う。読む側は、ここにないものをすべて拒否しなければならない。

  • 使える型は4つだけ：符号なし整数（major type 0）、byte string（2）、text string（3）、配列（4）。負の整数・map・タグ・浮動小数・単純値（true／false／null／undefined）は使わない。
  • 長さと整数は最短の形で書く（0〜23 は先頭バイトに、24〜255 は続く1バイト、256〜65535 は2バイト、65536〜232−1 は4バイト、それ以上は8バイト）。最短でない形は拒否する。
  • 不定長（additional information 31）と、予約の値（28〜30）は拒否する。
  • text string は正しい UTF-8 でなければならない（過長な形・サロゲート・U+10FFFF を超える値を拒否する）。
  • 入れ子は 16 段まで。最上位の値を1段目と数え、配列の中の値は、配列でなくても1段深いと数える（配列を 16 重にして、いちばん内側に値を1つ置くと 17 段になり、拒否する）。
  • 入力は値1つだけで、後ろに余りのバイトがあれば拒否する。
  • 長さを読んだら、残りの入力に収まるかを確かめてから領域を確保する。

この規則を守ると、1つの値に対するバイト列は1通りに決まる。読み終えた値を符号化し直したバイト列は、元のバイト列と一致する。以下、CBOR(x) は値 x のこのバイト列を表す。

2.3 ハッシュ

ハッシュ関数 H は SHA-256（出力 32 バイト）である。H(CBOR(x)) は、値 x の決定的CBORのバイト列の SHA-256 を表す。この文書で「〜Hash」と名の付く値は、断りがなければ H(CBOR(値)) である。

2.4 署名

署名は Ed25519（RFC 8032）で、公開鍵 32 バイト、署名 64 バイトである。署名の対象は、値の決定的CBORのバイト列そのもの（CBOR(値)）で、前置きや文脈の文字列を足さない。値の先頭のラベル（"SBQ-START" など）が、署名の用途を分ける役目を持つ。

検証は、次の2つの両方に通ったときだけ「正しい」とする。

  1. 公開鍵の検査：公開鍵が、libsodium の crypto_core_ed25519_is_valid_point に通る点である（正規の符号化で、曲線上にあり、素数位数の部分群に属し、小さな位数でない）。
  2. 署名の検査：libsodium の crypto_sign_verify_detached と同じ結果になる（正準でない署名を拒否する、という libsodium の既定の検査を含む）。

1 の検査は、署名の検証のたびに行う（HELLO で受けた公開鍵にも、証跡の検証にも掛かる）。2 だけを行う実装は、素数位数の部分群に属さない公開鍵による署名を、ShogiBoardQ と違って受け付けてしまう。秘密鍵は 32 バイトの種（seed）から RFC 8032 のとおりに導く。

2.5 文字列の制限

「ASCII の tstr」と書いた値は、0x20〜0x7E の文字だけでなければならない。長さの上限は各節に書く。上限を超える値・範囲外の文字を含む値は拒否する。

3. ネットワークと識別子

3.1 ネットワーク

対局できるのは、同じ networkName を選んだ実装どうしだけである。ネットワークは名前から決まる 32 バイトの値 networkId で見分ける。

networkId = H(CBOR(["SBQ-NETWORK", 1, networkName]))     ; networkName は ASCII の tstr（1〜32 バイト）
networkName用途networkId（16進）
sbq-local-1ローカル検証用。同じ PC・同じ LAN の中だけでつなぐ（4.5節）83cc9dfdba4b78083aad3ab064df1ef5ba0e18e8c9665f56a95db403dc55b6bf
sbq-limited-1限定試験用。インターネット上の相手とつなぐe2972f65cf26d46415718eb13b8a97e42478963e698c8e550d6ed0d197cb1d93

実装は、参加できる networkName の一覧を持ち、ほかの名前を断らなければならない。ShogiBoardQ は、ビルドから 180 日を過ぎると sbq-limited-1 に参加しない（実験版の使用期限。互換実装が同じ期限を持つ必要はない）。

libp2p の層には、ネットワークを分ける仕組み（private network の鍵など）を置いていない。ネットワークの違いは、招待文字列（5章）と HELLO（8.2節）の networkId で確かめる。

3.2 PeerId

libp2p のノードの鍵は Ed25519 でなければならない。PeerId のバイナリ表現は、Ed25519 の公開鍵をそのまま入れた identity multihash の 38 バイトである。

peerId = 00 24 08 01 12 20 || 公開鍵（32 バイト）

この形でない PeerId（RSA の鍵・SHA-256 の multihash など）は、招待文字列でも HELLO でも断る。文字での表記は base58（12D3KooW…）である。

PeerId はノードを起動するたびに作り直してよい（ShogiBoardQ は、接続するたびに新しい鍵を作る）。ただし、1局の間は同じ PeerId を使い続けなければならない。開始合意に PeerId のハッシュが入り、再接続は同じ PeerId からしか受け付けないためである（11章）。

3.3 プレイヤー鍵とプレイヤーID

利用者ごとに、長く使う Ed25519 の鍵を1つ持つ。これをプレイヤー鍵と呼び、その公開鍵（32 バイト）をプレイヤーIDと呼ぶ。プレイヤー鍵は、開始合意（StartAgreement）と結果（FinalResult）への署名にだけ使う。PeerId の鍵とは別の鍵でなければならない。

画面では、プレイヤーID を小文字の16進 64 桁で、8 桁ごとに空白で区切って出す（例：cf3b0b03 a6e888db …）。相手が同じ人かどうかを、省略した表示だけで利用者に判断させてはならない。

3.4 一局用鍵

1回の交渉ごとに、新しい Ed25519 の鍵を作る。これを一局用鍵と呼び、対局中の状態の承認（StateApproval）と制御メッセージ（Control）への署名に使う。対局が終わったら捨て、保存しない。プレイヤー鍵・相手の鍵のどれとも違う鍵でなければならない。

3.5 確認コード

2人のプレイヤーID から、双方の画面に同じ数字が出る確認コードを作る。利用者は、電話や対面など別の経路で数字を見比べて、相手のプレイヤーID が本人のものかを確かめる。

digest = H(CBOR(["SBQ-VERIFY", 1, keyLow, keyHigh]))    ; 2つの公開鍵を、バイト列の辞書順（符号なし）で小さいほうを先に
組 g（0〜5）= digest[5g .. 5g+4] の 5 バイトをビッグエンディアンの整数として読み、100000 で割った余りを 5 桁（ゼロ詰め）で書く

確認コードは、この 5 桁の数字 6 組（計 30 桁）である。

3.6 表示名

表示名は、相手の画面に出る自己申告の名前で、HELLO で送る。次の規則をすべて満たさなければならず、受け取った側は、受け取ったバイト列のまま判定する（先頭の BOM などを取り除いてから判定してはならない）。

  • UTF-8 で 96 バイト以下、1〜32 文字（コードポイント）
  • 先頭と末尾が空白（U+0020）でない
  • すべての文字が、次の表の範囲にある（両端を含む）
範囲（16進）内容
0020..007EASCII の印字できる文字（空白を含む）
3001..3003、。〃
3005..3007々〆〇
3041..3096ひらがな（結合する濁点・半濁点 U+3099・U+309A は含まない）
309B..309E゛゜ゝゞ
30A1..30FEカタカナ（・ーヽヾ を含む）
4E00..9FFFCJK 統合漢字
FF01..FF5E全角の英数字と記号

表は、結合文字を含まず、NFC で形の変わらない文字だけから選んである。実装は、この表だけで判定し、OS や言語の Unicode の表を使ってはならない（実装によって結果が変わるため）。表示名は対局記録（証跡）には入らない。

4. 通信の層（libp2p）

4.1 使うプロトコル

通信には libp2p を使う。ShogiBoardQ は rust-libp2p 0.56 で作ってあり、互換実装は次のプロトコルで相互に接続できなければならない。

4.2 待受

ネットワーク待受
sbq-local-1IPv4 の全インターフェース。TCP と UDP（QUIC）の 48210 番。使用中なら空いているポートを使う。IPv6 では待ち受けない
sbq-limited-1IPv4 と IPv6 の全インターフェース。TCP と UDP（QUIC）の空いているポート

ポート番号は招待文字列の宛先に入るので、互換実装が別のポートで待ち受けても接続できる。48210 番は、ファイアウォールで許可するポートを利用者が決められるようにするための既定値である。

ほかのプロセスが待ち受けているポートで待ち受けてはならない。libp2p の TCP の待受は、同じポートを複数のプロセスで共有できる設定（SO_REUSEPORT）で開くので、使用中でも開けてしまい、届いた接続が2つのプロセス（同じ PC の2つ目のアプリや、別の実装）に振り分けられる。ShogiBoardQ は、TCP の 48210 番を共有しない待受で試して使用中でないことを確かめてから開く。確かめてから開くまでの間に、同時に起動したプロセスも同じことをすると両方が開けてしまうので、UDP（QUIC。共有の設定を付けない）を先に開け、48210 番の UDP を開けたプロセスだけが TCP でも 48210 番を使う。

4.3 Identify

Identify の protocolVersion は /shogiboardq/1.0.0、agentVersion は実装の名前と版（ShogiBoardQ は shogiboardq-peer/<版>）にする。相手のこれらの値で接続を断ってはならない（ネットワークの違いは networkId で確かめる）。

Identify で配る自分のアドレス（listenAddrs）には、待受のアドレスをそのまま入れてはならない。入れてよいのは、相手が実際に届くと確かめた・決めたアドレスだけである（sbq-limited-1 では到達性の確認で確かめたインターネット上のアドレスと中継経由のアドレス。協力ノードは、インターネット上の待受のアドレスも入れてよい。4.4節）。sbq-local-1 では入れない（Identify は招待を持たない相手にも届くので、待受のポートにつないだだけの LAN の機器に、PC の私設アドレスの一覧を配らない。相手への宛先は招待文字列で渡す）。待受のアドレスが変わったことを Identify の push で知らせない。

4.4 協力ノードと中継

インターネット越し（sbq-limited-1）では、利用者が協力ノードのアドレス（/ip4/…/tcp/…/p2p/<PeerId> の形。16 件まで）を指定する。協力ノードは、Circuit Relay v2 の hop と Identify・Ping（と AutoNAT の応答）に対応した libp2p のノードで、対局のフレームの中身は読まない。標準の Circuit Relay v2 の中継ノードであれば、協力ノードとして使える。

  • 実装は、Identify の protocols に中継の hop がある協力ノードに、自分の到達性によらず中継の予約を取る（2件まで）。予約を断られたとき・協力ノードとの接続が切れて予約を失ったときは、少し待ってから頼み直すことが望ましい（ShogiBoardQ は 30 秒後）。頼み直さないと、つなぎ直すまで招待文字列に中継経由の宛先が入らない。
  • 中継経由の自分のアドレスは <協力ノードのアドレス>/p2p/<協力ノードの PeerId>/p2p-circuit の形で、利用者が指定した協力ノードのアドレスから作り、招待文字列に入れる（同じ協力ノードを指定した相手が、そのまま使える）。
  • 協力ノードは、予約の応答で自分のアドレスを返さなければならない。アドレスの無い応答を、libp2p の実装（ShogiBoardQ の使う rust-libp2p など）は予約の失敗として扱う。起動した直後の中継ノードは、到達性の確認（AutoNAT）が済むまで自分のアドレスを持たず、その間の予約をすべて失敗させることがある。協力ノードは、インターネット上のアドレスで待ち受けたら、確認を待たずにそれを自分のアドレスにすることが望ましい（ShogiBoardQ の協力ノードはそうする）。
  • 中継経由の宛先にも、先頭の IP アドレス（協力ノードのもの）に 4.5節の規則を掛ける。
  • ShogiBoardQ の協力ノード（shogiboardq-peer --service --relay）は、中継1本あたり 30 分・8 MiB までで切る。切れたら、対局は再接続の手順（11章）でつなぎ直す。

4.6 直接接続を使わない設定

対局の相手に自分の IP アドレスを見せないための設定である（実装するかは任意）。この設定の実装は、次を守らなければならない。

  • 直接つなぐ宛先は、利用者が指定した協力ノードの宛先（と、そのノードが Identify で名乗った別の宛先）だけにする。ほかの宛先への直接の接続は、どの経路で始まったものも断る。
  • 中継経由の宛先は、中継が指定した協力ノードのときだけ使う（指定していない中継には自分の IP が見える）。
  • 自分のアドレスとして出すのは、中継経由のアドレスだけにする（招待・Identify）。
  • AutoNAT と DCUtR を行わない。どちらも、自分のアドレスの候補を相手に渡すためである。

相手がこの設定で招待してきたときは、招待文字列の中継経由の宛先へ普通に接続すればよく、プロトコルの上の違いはない。

この設定の側が申込側になるときは、招待文字列の宛先のうち、自分が指定した協力ノードを中継とするものにしか接続しない。そのため、招待側は、申込側が指定しているのと同じ協力ノードに中継の予約を取り、その中継経由のアドレスを招待文字列に入れておく必要がある（双方が同じ協力ノードを指定する）。使える宛先がなければ、申込側は接続を始めない。

5. 招待文字列

対局の相手は、招待文字列で決める。招待側が作り、利用者が別の経路で相手に渡す。招待文字列には、招待側への接続先と、1回だけ使える合言葉（token）が入る。

5.1 形

invite = "sbqinv1." + base64url(body) + "." + hex(H(body)[0..4])
body   = CBOR(["SBQ-INVITE", 1, networkId, peerId, [addr, ...], token, expiresAt])
項目型規則
networkIdbstr(32)3.1節
peerIdbstr(38)招待側の PeerId のバイナリ表現（3.2節の形だけ）
addrbstr到達候補の multiaddr のバイナリ表現。末尾の /p2p/<招待側> は付けない（中継経由のアドレスの中の /p2p/<協力ノード> は残す）。0〜8 件、1件 1〜100 バイト
tokenbstr(32)暗号用の乱数生成器で作る
expiresAtuint有効期限（UNIX 秒）。作成から 600 秒後
  • base64url は RFC 4648 の URL 用の文字で、= を付けない。
  • 末尾の検査の値は、body の SHA-256 の先頭4バイトの小文字16進（8 文字）である。打ち間違い・欠けを見つけるためのもので、秘密ではない。
  • 文字列全体は 1024 バイト以下でなければならない。

5.2 作る側

  • 到達候補には、相手が実際に使えるアドレスだけを入れる（4.5節・4.6節）。sbq-local-1 では、同じ LAN の相手が使う私設アドレスを先に、同じ PC でしか使えない loopback を最後に入れる。
  • 同時に有効な招待は 4 つまでとし、5つ目を作ったら最も古いものを無効にする。
  • 招待は1回だけ使える。合言葉が一致したストリームを受け付けたら、その招待を使用済みにする（6.3節）。
  • token をログなどに出してはならない。招待文字列は、相手だけに届く経路で渡すよう利用者に案内する（接続先が入っているため）。

5.3 読む側

読む前に、前後の空白（ASCII の空白・タブ・CR・LF）だけを取り除く。そのうえで、次をすべて確かめ、1つでも外れれば使わない。

  1. 全体が 1024 バイト以下で、接頭辞が sbqinv1. であり、残りが . でちょうど2つの部分に分かれる。
  2. 前の部分が base64url として読め、後ろの部分が body の SHA-256 の先頭4バイトの小文字16進と一致する。
  3. body が決定的CBORで、7 要素の配列であり、ラベル・版・各項目の型と長さが 5.1節のとおりである。
  4. networkId が、自分が今参加しているネットワークと一致する。
  5. expiresAt が今の時刻より後で、今から 660 秒後（600 秒＋時計のずれ 60 秒）以内である。
  6. peerId が自分の PeerId でない。

到達候補は、どれも multiaddr のバイナリ表現として読めなければならない。読めないものが1件でもあれば（知らないプロトコルの番号を含むなど）、招待文字列の全体を使わない。作る側は、広く使われているプロトコル（ip4・ip6・tcp・udp・quic-v1・p2p・p2p-circuit）だけで書く。

読めた到達候補のうち、今のネットワークで接続してよい宛先（4.5節）だけを使い、ほかは捨てる。使える宛先が1つも残らなければ接続しない。

6. 対局ストリームとフレーム

6.1 ストリーム

交渉と対局のやり取りは、libp2p のプロトコル /shogiboardq/game/1.0.0 のストリーム1本の上で行う。この文書で「接続」と書くときは、断りがなければこのストリームを指す。ストリームが閉じる・リセットされることを「切断」と呼ぶ。

ストリームには、4 バイトのビッグエンディアンの長さと、その長さのフレーム（決定的CBOR）を、繰り返し流す。長さは 1〜65536（64 KiB）でなければならない。受ける側は、長さを確かめてから領域を確保する。

6.3 ストリームを開く手順と INVITE_TOKEN

INVITE_TOKEN = [1, 11, 0, zero32, [token]]   ; token は bstr(32)

申込側（招待文字列を受け取った側）は、次のようにする。

  1. 招待文字列の peerId と宛先へ接続し、/shogiboardq/game/1.0.0 のストリームを開く（ShogiBoardQ は 30 秒で諦める）。
  2. 開いたら直ちに、最初のフレームとして INVITE_TOKEN を送る（requestId は 0）。
  3. 続けて HELLO を送る（8.2節）。

招待側は、届いたストリームの最初のフレームを 5 秒だけ待ち、次のように決める。

  • 最初のフレームが INVITE_TOKEN で、その token が、まだ使われていない有効期限内の招待の token と一致すれば、その招待を使用済みにして、ストリームを受け付ける。照合は、処理時間が中身によらない比較で、すべての招待と行う。
  • それ以外（時間内に届かない・INVITE_TOKEN でない・token が一致しない）は、何も返さずにストリームを閉じる。

INVITE_TOKEN の requestId は 0、gameId は zero32 でなければならない。INVITE_TOKEN を、ストリームの最初以外で送ってはならない（受けたら外枠の違反として閉じる）。対局中に受け付けるストリームについては 11.1節に書く。

6.4 頻度と大きさの上限

7. 署名とハッシュの対象になる値

ここに挙げる値は、決定的CBORのバイト列がそのまま署名・ハッシュの対象になる。要素の順序・型・ラベルを1つでも変えると、署名が合わなくなる。

7.1 条件

Rules         = ["SBQ-RULES", 1, initialSfen, 512, "fourfold-draw", "perpetual-check-loss",
                 "no-declaration", "human", "human"]
TimeControl   = ["SBQ-TIME", 1, mainMs, byoyomiMs, 0, 0]
NetworkPolicy = ["SBQ-NET", 1, 10000, 30000, 120000, 5000, 86400000, 10000, 600000]
  • Rules：v1 で使える値は1つだけである。initialSfen は平手の初期局面 lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b - 1。意味は、平手・512 手で引き分け・千日手は引き分け・連続王手の千日手は王手をかけた側の負け・入玉宣言なし・人間どうし、である。
  • TimeControl：mainMs は基本の持ち時間（0〜86,400,000）、byoyomiMs は秒読み（0〜600,000）。両方 0 は拒否する。後ろの 2 つの 0 は予約（加算・遅延。v1 では 0 だけ）。
  • NetworkPolicy：v1 で使える値は1つだけである。順に、ping の間隔 10 秒・着手の確認が届かないと切断とみなす時間 30 秒・再接続を待つ時間 120 秒・再送の間隔 5 秒・1局の実時間の上限 24 時間・消費時間の許容差 10 秒・1局の切断時間の合計の上限 600 秒。
rulesHash         = H(CBOR(Rules))          = e3c568385b6f6372b7f9ae8fe7d8e62b8a3ea15309ba2b0708d1ea9b8a07f9c7

State0 = ["SBQ-STATE", 1, gameId, 0, zero32, "", initialSfen, 0, mainMs, mainMs]

手番は ply で決まる。ply が偶数の State の次は先手が指し、奇数の次は後手が指す。

7.3 指し手と局面の書き方

実装が違っても同じバイト列になるよう、指し手と局面の文字列は次の形だけを使う。受け取った文字列がこの形でなければ拒否する。

  • 指し手（moveUsi）：USI の形。盤上の手は <移動元><移動先>（例 7g7f）、成るときは末尾に +（例 8h2b+）。駒打ちは <駒>*<移動先> で、駒は大文字の P L N S G B R（例 P*5e）。筋は 1〜9、段は a〜i。前後に空白を付けない。
  • 局面（sfen）：<盤> <手番> <持ち駒> <手数> を空白1個で区切る。
    • 盤は USI の SFEN のとおり（1段目から9段目、各段は9筋から1筋。空きマスは数字、成り駒は + を前置、先手は大文字・後手は小文字）。
    • 手番は、次に指す側（先手 b・後手 w）。
    • 持ち駒は、先手の R B G S N L P、続けて後手の r b g s n l p の順に、持っている駒だけを書く。2 枚以上は枚数を前に付ける（例 2P）。どちらも持っていなければ -。
    • 手数の欄は ply + 1（State0 は 1）。

8. 開始までの手順

8.1 流れ

申込側を A、招待側を B とする。フレームはすべて同じストリームに流す。

A（申込側）                                   B（招待側）
  ── INVITE_TOKEN ─────────────────────────→   合言葉を照合（6.3節）
  ── HELLO（role 1, commitA）───────────────→   検査。断るなら REJECT
  ←─────────────── HELLO（role 2, nonceB, 条件）──
  先後を決め、StartAgreement を作る
  ── START_AGREEMENT ──────────────────────→   検査（8.3節）
            ［双方の利用者が、条件確認画面で相手と条件を確かめる］
  利用者が「開始」を押す
  ── START_SIGNATURE（A の署名）───────────→   署名を検査
                                                利用者が「開始」を押す
  ←────────────── START_SIGNATURE（B の署名）──
  署名を検査
            ［両方の署名がそろった＝対局開始。9.1節へ］
  • A は、自分の START_SIGNATURE を送った後でなければ、B の START_SIGNATURE を受け付けない。
  • B は、A の START_SIGNATURE を確かめるまで、自分の START_SIGNATURE を送ってはならない。B の利用者が先に「開始」を押していたら、A の署名を確かめた時点で送る。
  • どちらも、利用者が「開始」を押すまで、プレイヤー鍵で署名してはならない。

8.2 HELLO（開始前）

Frame   = [1, 1, requestId, zero32, payload]

受けた側は、形のほかに次を確かめ、外れれば REJECT（CONDITION_MISMATCH。別の番号を書いたものはその番号）を送る。

  • role が期待どおり（招待側が受けるのは 1、申込側が受けるのは 2）で、role と conditions の有無が合っている。
  • playerKey・sessionKey が Ed25519 の公開鍵として使える点である（2.4節）。
  • playerKey・sessionKey・connectionRandom が、自分のものと同じ値でない。申込側は、相手の coin（nonceB）が自分の nonceA と同じでないことも確かめる。
  • 招待側：申込みで名乗った playerKey が、利用者がブロックした相手でない（ブロックした相手には、そうと知らせずに BUSY を返す）。双方の sidePreference が両立する（8.4節）。

招待側は、合言葉を照合した後でも、利用者がその間に招待を取り消していれば、REJECT（EXPIRED）を送ってストリームを閉じる。すでにほかの相手と交渉中のときは、HELLO を返さずに REJECT（BUSY）を送ってストリームを閉じる（対局中は、対局の相手のほかのストリームを受け付けない。11.1節）。断るときは、HELLO を返さずに REJECT を返し、自分の公開鍵を知らせない。

8.3 START_AGREEMENT

Frame   = [1, 2, requestId, zero32, payload]
payload = [StartAgreement, Rules, TimeControl, NetworkPolicy]

申込側が、招待側の HELLO で初めて条件（持ち時間）を知り、先後を決めて作る。startBefore は今の時刻の 180 秒後にする。招待側は、次をすべて確かめ、外れれば REJECT を送る（番号を書いていないものは CONDITION_MISMATCH）。

  • Rules・NetworkPolicy が v1 の値で、TimeControl が自分の HELLO で示したものと同じである。3 つのハッシュが StartAgreement の中の値と一致する。
  • networkId が自分のネットワークである。
  • 自分の playerKey・sessionKey・nonce（nonceB）・PeerIdHash が、同じ側（先手か後手か）に正しく入っている。相手の playerKey・sessionKey・PeerIdHash が、相手の HELLO・ストリームの相手と一致し、反対の側に入っている。
  • 相手の側の nonce（nonceA）について、H(CBOR(["SBQ-COMMIT", 1, nonceA])) が、相手の HELLO の coin（commitA）と一致する。
  • 先後が 8.4節の決め方どおりである。
  • startBefore が今の時刻より後で、今から 210 秒後（180 秒＋時計のずれ 30 秒）以内である。外れれば REJECT（EXPIRED）。
  • 4 つの公開鍵・2 つの PeerIdHash・2 つの nonce がそれぞれ異なる（7.4節）。

8.4 先後の決め方

先後は、双方の希望（sidePreference）と、双方が出した乱数で決める。

  1. 双方が先後を希望し、それが同じ（どちらも先手・どちらも後手）なら、両立しないので REJECT（CONDITION_MISMATCH）。
  2. 申込側が先手を希望、または招待側が後手を希望していれば、申込側が先手。
  3. 申込側が後手を希望、または招待側が先手を希望していれば、申込側が後手。
  4. どちらも「指定なし」なら、乱数で決める。coinHash = H(CBOR(["SBQ-COIN", 1, nonceA, nonceB])) の最後のバイトの最下位ビットが 0 なら申込側が先手、1 なら申込側が後手。

乱数は、片方が結果を見てから自分の値を選べないように、次の順で出す。申込側は、32 バイトの乱数 nonceA を作り、HELLO では commitA = H(CBOR(["SBQ-COMMIT", 1, nonceA])) だけを見せる。招待側は、HELLO で nonceB をそのまま見せる。申込側は、START_AGREEMENT の中（自分の側の nonce の欄）で nonceA を明かす。希望で先後が決まるときも、この手順は同じように行う（nonce は対局ID を一意にする役目も持つ）。

ShogiBoardQ の画面では、先後の希望を出せるのは招待側だけである（申込側は常に 0 を送る）。互換実装が申込側で希望を送っても、上の規則どおりに扱われる。

8.5 START_SIGNATURE

Frame   = [1, 3, requestId, gameId, payload]
payload = [side, signature]        ; side は 1＝先手、2＝後手。signature は bstr(64)

signature は、自分のプレイヤー鍵による CBOR(StartAgreement) への署名である。side は自分の側。受けた側は、side が相手の側であること、署名が StartAgreement の相手の playerKey で正しいこと、今の時刻が startBefore より前であることを確かめる。外れれば REJECT（INVALID_SIGNATURE、期限切れは EXPIRED）。

相手の開始署名を確かめた時点から、相手の playerKey を「確かめた身元」として扱ってよい。それまでは、相手が名乗っただけの値として画面に出す。

START_SIGNATURE は、1回だけ送る。送り直してはならない。開始前に2つ目を受けた側は REJECT（INVALID_SIGNATURE）で交渉を終え、開始後に受けた側はエラー（CONDITION_MISMATCH）で対局を止める。

両方の開始署名（先手・後手のもの）は、対局記録（証跡）に入れる。

8.7 REJECT

Frame   = [1, 10, requestId, zero32, payload]
payload = [errorCode]              ; errorCode は 12章の表

開始前（両方の開始署名がそろうまで）に、相手を断る・取りやめるときに送る。gameId の欄は zero32 にする。受けた側は交渉を終える。利用者が条件確認画面で取りやめたときは CANCELLED（12）を送る。

両方の開始署名がそろった後は、REJECT を送ってはならない（対局中のエラーは CONTROL で伝える）。開始後に届いた REJECT は、gameId が対局ID なら無視し、zero32 なら「対局ID の違うフレーム」としてエラー（CONDITION_MISMATCH）で止める（9章の冒頭）。片方が取りやめた REJECT と、もう片方の最後の開始署名が行き違うと、開始署名がそろった側はこのエラーで終わる。どちらの側でも対局は始まらない。

9. 対局中の手順

両方の開始署名がそろった後のフレームは、すべて gameId に対局ID を入れる。対局ID の違うフレームを受けたら、エラー（CONDITION_MISMATCH）で対局を止める（9.7節）。

9.1 開始（State0 と READY）

先手                                          後手
  ── STATE_PROPOSE（State0, 先手の承認）────→   State0 と署名を検査
  ←────────────── STATE_ACCEPT（0, 後手の承認）──
  ←────────────── CONTROL READY（[state0Hash]）──   ここから、先手の初手の時間を観測する
  READY を受けた時点から、初手の計時を始める
  • 後手は、受けた State0 が 7.2節の値と完全に一致することと、署名が先手の一局用鍵で正しいことを確かめる。
  • 先手は、READY の state0Hash が自分の State0 のハッシュと一致することを確かめる。READY を2回受けても、時計を初期化し直さない。
  • 両方の開始署名がそろってから 30 秒以内にここまで済まなければ、対局を始めずに終える（結果のない記録になる）。

9.2 着手の提案（STATE_PROPOSE）

Frame   = [1, 4, requestId, gameId, payload]
payload = [State, signature]       ; signature は、指した側の一局用鍵による StateApproval への署名（bstr(64)）

手番の側は、指し手を決めたら、次の State（7.2節）を作り、その StateApproval に一局用鍵で署名して送る。

  • spentMs は、自分の手番が始まってから State を作る直前までの時間（自分の時計）である。
  • 残り時間は 9.4節の計算で決める。
  • 相手の承認（STATE_ACCEPT）が届くまで、次の手を提案してはならない。未承認の自分の手は、同時に1つだけである。
  • 5 秒たっても承認が届かなければ、同じバイト列（requestId も同じ）のフレームを送り直す。最初に送ってから 30 秒たっても届かなければ、接続が切れたものとして再接続へ移る（11章）。

受けた側は、次の順で確かめる。

  1. State の gameId が対局ID である。違えばエラー（CONDITION_MISMATCH）。
  2. ply が 0 なら、9.1節のとおりに扱う（State0 が期待の値と違う・署名が正しくないときは、エラー（INVALID_SIGNATURE））。ply が 1 以上なのに、State0 の承認と READY がまだ済んでいなければ、エラー（CONDITION_MISMATCH）。
  3. ply が、自分の知る最新の State 以下なら、再送として扱う。同じ State なら、保存してある自分の承認を STATE_ACCEPT で送り直す（盤・時計は動かさない）。同じ手数で違う State なら、エラー（STATE_CONFLICT）で止める。
  4. ply が最新の次（＋1）で、相手の手番であり、自分に未承認の手がない。外れればエラー（STATE_CONFLICT）。
  5. 署名が相手の一局用鍵で正しい。外れればエラー（INVALID_SIGNATURE）。
  6. previousStateHash が最新の State のハッシュであり、指し手の文字列が 7.3節の形である。外れればエラー（INVALID_MOVE）。
  7. 申告された spentMs が時間切れ（E ≥ R + B。9.4節）でない。時間切れならエラー（CLOCK_MISMATCH）。
  8. 指し手が最新の局面で合法手であり（9.6節）、sfen が、指した後の局面を 7.3節の形で書いたものと一致する。外れればエラー（INVALID_MOVE）。
  9. 残り時間（blackMainMs・whiteMainMs）が 9.4節の計算どおりである。外れればエラー（CLOCK_MISMATCH）。
  10. 申告された spentMs が、自分が測った時間と比べて短すぎない（9.4節の許容差）。外れればエラー（CLOCK_MISMATCH）。

すべて通れば、承認を保存してから STATE_ACCEPT を送り、盤に反映する。payload の形が合わない STATE_PROPOSE は、エラー（INVALID_MOVE）で止める。

手順 3 の「承認の送り直し」は、自分がすでに次の手を提案した後は、行わなくてよい。ストリームは順序を保つので、最初に送った承認は必ず相手に届く（届かないのは切れたときで、そのときは再接続の照合が補う）。

9.3 承認（STATE_ACCEPT）

Frame   = [1, 5, requestId, gameId, payload]
payload = [ply, stateHash, signature]    ; signature は、受けた側の一局用鍵による StateApproval への署名

提案した側は、ply と stateHash が未承認の自分の State と一致することと、署名が相手の一局用鍵で正しいことを確かめる。通れば、その State は双方が承認した状態になり、盤に反映する。

  • すでに承認済みの手に対する同じ承認（ply と stateHash が、双方が承認した State のものと一致する再送）は、無視する。自分に未承認の手があるときも同じである（提案の再送に相手が承認を送り直し、それが、こちらが次の手を提案した後に届くことがある）。
  • それ以外の承認（未承認の自分の手のものでも、承認済みの手のものでもない）は、エラー（STATE_CONFLICT）で止める。
  • payload の形が合わない STATE_ACCEPT は、エラー（INVALID_SIGNATURE）で止める。

双方が承認した State の列（State0 から最新まで）が、対局の正式な記録である。

9.4 時間の決まり

持ち時間は「基本の持ち時間（R）＋1手ごとの秒読み（B）」である。手番の開始時の基本の持ち時間の残りを R、秒読みを B、その手に使った時間を E とする（すべてミリ秒）。

  • 指せる条件：E < R + B。E ≥ R + B は時間切れで、その手は指せない（境界と同じ値は時間切れ）。
  • 指した後の残り：指した側の基本の持ち時間は max(R − E, 0)、相手の側は変わらない。これを State の blackMainMs・whiteMainMs に書く。

時間は、指した側が自分の時計で測って申告する。相手は、自分の時計で観測した時間と照らし合わせる。

測るもの始まり
自分の手番の時間（E）先手の初手は、READY を受けた時点。それ以外は、相手の手を確かめて STATE_ACCEPT を送った時点
相手の手番の観測自分の STATE_PROPOSE を最初に送った時点。後手が先手の初手を観測するときは、READY を送った時点。再接続の後に、未承認の自分の手を送り直したときは、送り直した時点から測り直す（相手の手番は、相手がその手を受け取って承認した時点から始まるため。11.5節）
  • 申告の検査：受けた手について、観測した時間 − spentMs > 10,000 ＋ その手番の間に切れていた時間 なら、エラー（CLOCK_MISMATCH）で止める。つまり、申告は観測より 10 秒まで短くてよい（通信の遅れの分）。
  • 自分の時間切れ：自分の手番で、未承認の手がなく、自分の時計で E ≥ R + B になったら、自分の負けを申告する（相手の勝ち・原因は時間切れの結果を提案する。10.2節）。
  • 相手の時間切れの主張：相手の手が届かないまま、観測した時間（切れていた時間を除く） > R + B + 10,000 になったら、時間切れによる自分の勝ちを提案してよい。同じ手数で1回だけ。
  • 回線が切れている間も、手番の側の時計は進む。
  • 時計は単調増加の時計で測る。スリープや時刻の変更で、測った時間の連続性を確かめられなくなった実装は、対局を中断する（ABORT、理由は CLOCK_DISCONTINUITY）。ShogiBoardQ は、単調増加の時計と OS の時刻の進みが 15 秒を超えて食い違ったら中断する。

9.5 制御メッセージ（CONTROL）

Frame   = [1, 6, requestId, gameId, payload]
payload = [Control, body, signature]
Control = ["SBQ-CONTROL", 1, gameId, connectionId, sequence, kind, bodyHash]     ; bodyHash = H(CBOR(body))

signature は、送る側の一局用鍵による CBOR(Control) への署名（bstr(64)）である。body は配列で、中身は kind ごとに決まる。

kind名前body意味
1READY[state0Hash]後手が、State0 を承認して対局を始められることを知らせる（9.1節）
2RESUME[latestPly, latestStateHash]再接続の後、双方が承認した最新の State を知らせる（11.3節）
3RESULT_PROPOSEFinalResult そのもの結果の提案・同意（10.2節）
4ABORT[latestStateHash, reasonCode]一方的に対局を離れる。結果は確定しない（10.5節）
5ERROR[errorCode, relatedPly]相手の入力を検査で断り、対局を止める（9.7節）
6RESULT_DECLINE[bodyHash]RESULT_PROPOSE に同意しない（断る提案の bodyHash）

reasonCode・errorCode は 12章の番号、relatedPly は関係する手数（0〜512）である。

番号（sequence）の規則：送る側は、接続ごと・向きごとに 1 から 1 ずつ増やす。再接続で新しい接続になったら 1 に戻す。受ける側は、次のように扱う。

  1. payload の形を確かめる（3 要素の配列、Control の形、kind が 1〜6、sequence が 1 以上、body が配列、bodyHash が body のハッシュと一致）。外れれば、どの接続のものでも、エラー（INVALID_SIGNATURE）で止める。
  2. Control の gameId・connectionId が今の対局・今の接続のものでなければ、黙って捨てる。
  3. sequence が、すでに受けた番号以下なら、再送として黙って捨てる。
  4. sequence が「最後に受けた番号＋1」でなければ、エラー（STATE_CONFLICT）で止める。
  5. 署名が相手の一局用鍵で正しいことを確かめる。外れればエラー（INVALID_SIGNATURE）。通れば、その番号を「最後に受けた番号」にする。

再接続の照合が済むまでの間に届いた RESUME 以外の制御メッセージは、上の検査をして番号を進めたうえで、中身を処理せずに捨てる。

1局で送受信する制御メッセージは、合わせて 4096 件までとする。超えたらエラー（LIMIT_EXCEEDED）で止める。

9.6 指し手の合法性

指し手は、本将棋の規則で合法でなければならない。互換実装は、少なくとも次を同じように判定しなければならない（判定が食い違うと、片方が INVALID_MOVE で対局を止める）。

  • 駒の動き、成り（敵陣に入る・敵陣の中で動く・敵陣から出る手で成れる。成れる駒だけ）
  • 行き所のない駒の禁止（1段目の歩・香、1〜2段目の桂は、不成で進めない・打てない）
  • 二歩の禁止、打ち歩詰めの禁止
  • 自分の玉に王手がかかったままにする手・自分の玉を王手にさらす手の禁止
  • 512 手を超える手の禁止（ply が 512 の State の次の手はない）

持将棋の宣言（入玉宣言）と「待った」はない。入玉は、双方の合意で引き分けにできる（10.2節）。

9.7 検査の失敗（ERROR）

対局中に相手の入力が検査に通らなかったら、CONTROL ERROR（[errorCode, relatedPly]）を送り、自分の側の対局を「エラー（結果未確定）」として終える。ERROR を受けた側も、対局を同じく結果未確定として終える。検査の失敗を、相手の負けとして記録してはならない。どちらの側も、それまでの記録（双方が承認した State まで）を証跡として保存する。

同じ手数に対して相手が2つの違う State に署名した証拠（2つの State と2つの署名）を得た実装は、それを保存しておくことが望ましい。

形の合わない payload（配列の長さ・型・範囲が違う）を受けたときも、同じく ERROR で止める（STATE_PROPOSE は INVALID_MOVE、STATE_ACCEPT・CONTROL・RESULT_SIGNATURE は INVALID_SIGNATURE、SYNC_REQUEST・SYNC_CHUNK は STATE_CONFLICT）。開始前の形の HELLO・START_AGREEMENT・START_SIGNATURE を開始後に受けたときは、CONDITION_MISMATCH で止める。外枠の合わないフレームは、ストリームを閉じる（6.2節）。

次のときは、何も送らずに終える。再接続の照合が済むまでの間（11章）に検査が失敗したとき、開始の期限（9.1節の 30 秒）が過ぎたとき、切断の上限（11.6節）を超えたとき、結果への署名を待つ時間（10.4節）が過ぎたとき。

対局を終えた実装は、ストリームを閉じる。相手がすでに終えているとき、こちらから送ったフレームやつなぎ直しには、応答がない。

10.1 結果と原因

outcome は 1＝先手の勝ち、2＝後手の勝ち、3＝引き分け、4＝合意による中断。表にない組み合わせの FinalResult は拒否する。

10.2 結果の提案と一致

結果は、CONTROL RESULT_PROPOSE（body は FinalResult）で提案する。双方が、同じ FinalResult の RESULT_PROPOSE を送り合った時点で、結果が一致したとする。同意する側は、受けた提案と同じ FinalResult を RESULT_PROPOSE で送り返す。同意しないときは RESULT_DECLINE を送り、対局を続ける。

FinalResult は、今の双方が承認した最新の State を指していなければならない。

FinalResult = ["SBQ-RESULT", 1, gameId, H(CBOR(最新の State)), transcriptHash, 最新の ply, outcome, cause]
  • 自分に未承認の手がある間は、結果を提案しない。
  • 手数が進んだら、それまでの提案と、答えを待っている申し出は無効になる。
  • 結果が一致した後は、別の結果の提案に同意しない（無視する）。
  • 結果が一致した後に届いた STATE_PROPOSE・STATE_ACCEPT は、無視する（承認しない・盤に反映しない）。FinalResult が指す手数より後の State を承認すると、証跡が 13.2節の検査に通らなくなる。
  • 自分の「合意による引き分け・中断」の申し出に答えが届くまでは、次の手を提案しないことが望ましい。申し出た側の着手と、相手の承諾が行き違うと、上の状況になる（その着手は、相手の承認のない手として、指した側の証跡の最後にだけ残る）。
  • 再接続の照合が済むまでの間（11章）は、相手の申し出に承諾して結果を一致させてはならない（承諾を相手へ送れない）。照合の後に相手が提案を送り直すので、そのときに答える。

RESULT_PROPOSE を受けた側は、次のように決める。

場合扱い
READY を交わす前（先手は READY を受ける前、後手は READY を送る前）に届いたRESULT_DECLINE（開始の手続きの途中の提案には同意しない）
形が合わない、または今の最新の State（ply・finalStateHash・transcriptHash）を指していないRESULT_DECLINE
自分がすでに提案した FinalResult と同じ一致
確定した手順から、棋譜で決まる終局（10.3節）にすでに達していて、提案がその結果（outcome・cause）と違う投了・時間切れ・合意による引き分けと中断（cause 1・3・6・8）は RESULT_DECLINE（利用者に尋ねない）。同意すると、署名した結果が棋譜と食い違い、13.2節の検証に通らない。詰みなどの判定の食い違いは、下の行のとおり
投了（cause 1）自分の勝ちで、かつ相手の手番なら、同じ提案を送り返して一致。そうでなければ RESULT_DECLINE
詰み・千日手・連続王手の千日手・512 手到達（cause 2・4・5・7）自分でも棋譜から判定する（10.3節）。終局でなければ RESULT_DECLINE。同じ結果なら、同じ提案を送って一致。終局だが結果が食い違うなら、エラー（CONDITION_MISMATCH）で止める（実装の不一致）
時間切れで、自分の勝ち（相手が自分の時間切れを申告した）相手の手番なら、同じ提案を送り返して一致。そうでなければ RESULT_DECLINE
時間切れで、相手の勝ち（相手がこちらの時間切れを主張した）自分の時計で確かめる。自分の手番が始まっていて（先手の初手は READY を受けた時点から）、未承認の手がなく、E ≥ R + B になっていれば、同じ提案を送り返して一致。そうでなければ RESULT_DECLINE。E は自分の手番が始まった時点から数え、それより前の時間を含めない
合意による引き分け・合意による中断（cause 6・8）利用者に尋ねる。承諾なら同じ提案を送り返して一致、断るなら RESULT_DECLINE。答える前に自分が指したら、断ったことにする

合意による引き分け・中断の申し出は、利用者の操作としては、同じ手数でそれぞれ1回までとする。ただし、受ける側は、同じ手数で同じ提案が繰り返し届いても、違反として扱ってはならない（その都度、上の表のとおりに扱う）。ShogiBoardQ は、再接続の後に提案を送り直し（11.5節）、1局の実時間の上限を超えた後は、断られるたびに合意による中断を提案し直す（10.5節）。

10.3 棋譜から決まる終局

手が1つ進む（双方が承認した State が増える）たびに、双方が次の順で判定し、終局なら、その結果を RESULT_PROPOSE で提案する。双方が同じ判定をすれば、同じ提案を送り合って一致する。

  1. 詰み：最新の局面（ply ≥ 1）で、手番の側に合法手が1つもなければ、手番の側の負け（cause 2）。王手がかかっていない場合も同じに扱う。
  2. 千日手：最新の局面と同じ局面（盤・持ち駒・手番が同じ。手数の欄は比べない）が、State0 からの列の中に、最新のものを含めて 4 回以上あるとき。
    • 最新の1つ前に同じ局面が現れた State の次から、最新の State までを調べる。この間に先手が指した手がすべて王手なら、先手の負け（後手の勝ち・cause 5）。そうでなく、後手が指した手がすべて王手なら、後手の負け（先手の勝ち・cause 5）。「王手」は、その手を指した後の局面で、相手の玉に王手がかかっていることである。
    • どちらでもなければ、引き分け（cause 4）。
  3. 512 手到達：最新の ply が 512 なら、引き分け（cause 7）。

10.4 結果への署名（RESULT_SIGNATURE）

Frame   = [1, 9, requestId, gameId, payload]
payload = [FinalResult, side, signature]    ; signature は、プレイヤー鍵による CBOR(FinalResult) への署名（bstr(64)）

結果が一致したら、それぞれが次の順で行う。

  1. 一致した結果（resultDigest）を保存する。以後、この対局で別の結果に署名してはならない。
  2. プレイヤー鍵で FinalResult に署名し、RESULT_SIGNATURE を送る。
  3. 相手の RESULT_SIGNATURE を待つ（30 秒）。

受けた側は、side が相手の側であること、署名が StartAgreement の相手の playerKey で正しいこと、FinalResult が一致した結果と同じであることを確かめる。外れればエラー（INVALID_SIGNATURE、結果が違えば STATE_CONFLICT）。side と署名の検査は、結果が一致する前でも行う。

同意を示す RESULT_PROPOSE は、必ず RESULT_SIGNATURE より先に送る。結果が一致する前に届いた RESULT_SIGNATURE は、検査に通っても捨てられ、後から使われない（その対局は「相手の確定なし」で終わる）。

  • 双方の署名がそろえば、「双方で確定」した記録になる。
  • 30 秒たっても相手の署名が届かない、または待っている間に回線が切れたら、自分の署名だけの記録として終える（「相手の確定なし」）。

10.5 対局をやめる（ABORT）

利用者が一方的に対局を離れるときは、CONTROL ABORT（[最新の State のハッシュ, reasonCode]）を送り、自分の側の対局を「中断（結果未確定）」として終える。reasonCode は、利用者の操作なら CANCELLED（12）を使う。ABORT を受けた側も、対局を結果未確定として終える。ABORT は合意による中断（cause 8）ではなく、相手の負けでもない。

ABORT は、再接続の照合が済むまでの間と、State0 の承認がそろう前には送らない（送らずに、自分の側の対局を終える）。

1局の実時間（両方の開始署名がそろった時点から数える）が 24 時間を超えたら、合意による中断を提案する。断られたら、提案し直す。さらに 120 秒たっても一致しなければ、ABORT（理由は GAME_TIME_LIMIT）で終える。ShogiBoardQ は、24 時間を超えた後は、未承認の手の送り直しと、時間切れの申告・主張を行わない。

11. 再接続

対局中にストリームが切れても、同じ対局へつなぎ直せる。つなぎ直した後は、双方の最新の状態を照らし合わせてから続ける。

11.1 つなぎ直す側と受ける側

  • つなぎ直すのは申込側（最初にストリームを開いた側）である。切れている間、5 秒おきに相手の PeerId へ接続し、/shogiboardq/game/1.0.0 のストリームを開く。宛先は、最初の接続で使えたもの・Identify で知ったものを使う。INVITE_TOKEN は送らない。
  • 申込側は、ストリームを開いたら、相手を待たずに直ちに再接続の HELLO（11.2節）を送る。招待側は、最初のフレームを受け取るまで、新しいストリームができたことに気づかない。最初のフレームの gameId は対局ID でなければならない（違えば、対局がエラーで止まる）。
  • 切れたと判断した側は、古いストリームを閉じる。閉じないと、相手は切れたことに気づかず、つなぎ直しが始まらない（申込側がつなぎ直すのは、自分のストリームが閉じたとき・自分が切れたと判断したときだけである）。
  • 招待側は、対局が始まってから終わるまで、対局の相手の PeerId からのストリームだけを受け付ける（ほかの相手のストリームと、INVITE_TOKEN で始まるストリームは受け付けない）。最初のフレームを 5 秒待つのは 6.3節と同じである。
  • 相手がつなぎ直してきたとき、古いストリームがまだ生きているように見えても、古いほうを閉じ、切れたものとして下の手順へ進む。照合が済んだ直後でも同じで、新しいストリームが届くたびに、新しい乱数で照合をやり直す（申込側の接続の試みは重なることがある）。
  • PeerId は対局の間、変えてはならない（3.2節）。アプリやノードを終了すると、同じ対局には戻れない。

「切れた」と判断するのは、ストリームが閉じた・リセットされたとき、または自分の STATE_PROPOSE に 30 秒承認が届かないとき（9.2節）である。開始前（両方の開始署名がそろう前、または READY が済む前）に切れたときは、つなぎ直さずに終える。結果が一致した後（10.4節の署名待ち）に切れたときも、つなぎ直さない。このとき、相手がまだ結果の一致に気づいていなければ（同意の RESULT_PROPOSE が届く前に切れた）、相手はつなぎ直そうとするが、応答はなく、相手の側は 11.6節の上限で終わる。

11.2 HELLO（再接続）

Frame   = [1, 1, requestId, gameId, payload]
payload = ["SBQ-RECONNECT", 1, side, connectionRandom]     ; side は自分の側（1＝先手、2＝後手）

新しいストリームができたら、双方が、新しい 32 バイトの乱数を入れた再接続の HELLO を送る。相手の HELLO を受けたら、side が相手の側であることと、乱数が自分のものと違うことを確かめ、新しい connectionId を計算する（7.5節。先手の乱数・後手の乱数の順）。制御メッセージの番号（sequence）は、双方とも 1 から始め直す。

開始前の HELLO と再接続の HELLO は、フレームの gameId（zero32 か対局ID か）と payload のラベルで見分ける。

再接続の HELLO が、再接続の間でないときに届いた・side が相手の側でない・乱数が自分のものと同じ、のどれかなら、ShogiBoardQ は黙って捨てる（照合は進まず、11.6節の上限で終わる）。

11.3 RESUME

相手の再接続の HELLO を受けたら、CONTROL RESUME（[latestPly, latestStateHash]）を送る。latestPly は、双方が承認した自分の最新の State の手数、latestStateHash はそのハッシュである。この CONTROL は新しい connectionId に対する一局用鍵の署名を持つので、相手が開始のときと同じ相手であることを確かめ直せる。

RESUME を確かめるまで、ほかのフレームを受け付けてはならない（着手・承認・結果の提案などは、黙って捨てる）。再接続の間に送ってよいのは、再接続の HELLO・CONTROL RESUME・SYNC_REQUEST・SYNC_CHUNK だけである。

RESUME は、1回の照合につき1回だけ送る。再接続の間でないとき（照合が済んだ後を含む）に届いた RESUME は、エラー（STATE_CONFLICT）で止める。求めていない SYNC_CHUNK も同じである。

相手の RESUME を受けたら、自分の最新の手数（myPly）と比べる。

場合扱い
相手の latestPly ＝ myPlyその手数の自分の State のハッシュが一致すれば、照合は終わり。違えばエラー（STATE_CONFLICT）
相手の latestPly ＜ myPlyその手数の自分の State のハッシュが一致することを確かめ、相手の SYNC_REQUEST を待つ
相手の latestPly ＞ myPly足りない分を SYNC_REQUEST で求める

11.4 SYNC_REQUEST と SYNC_CHUNK

SYNC_REQUEST: Frame = [1, 7, requestId, gameId, [fromPly, previousStateHash]]
SYNC_CHUNK:   Frame = [1, 8, requestId, gameId, [[[State, blackApproval, whiteApproval], ...], final]]
  • 古い側は、fromPly ＝ 自分の最新の手数＋1、previousStateHash ＝ 自分の最新の State のハッシュで求める。
  • 新しい側は、相手の RESUME を受けた後であること、fromPly が 1 以上で自分の最新の手数以下であること、previousStateHash が自分の fromPly − 1 手目の State のハッシュであることを確かめる。外れればエラー（STATE_CONFLICT）。通れば、fromPly から最新までの State を、双方の承認の署名（どちらも bstr(64)）とともに、1回に 64 件までの SYNC_CHUNK で順に返す。最後の塊は final ＝ 1、それ以外は 0。求められた範囲の外のものは送らない。
  • 古い側は、受けた State を1つずつ、手数が連続していること・双方の承認が正しいこと・9.2節の手順 6〜9（前状態ハッシュ・指し手の形・時間切れ・合法手・局面・残り時間の計算）で確かめてから取り込む。どれが外れても、エラー（STATE_CONFLICT）で止める。自分に未承認の手があり、同じ手数で違う State が届いたら、エラー（STATE_CONFLICT）で止める（片方の署名しかない別の手順へ巻き戻さない）。同じ State なら、未承認の手が承認されたものとして扱う。
  • 再接続で初めて知った相手の手については、自分の手番の計時を、取り込んだ時点から始める（失われた時刻を推測しない）。

11.5 照合の後

  • 相手の承認のない自分の手が残っていれば、同じバイト列の STATE_PROPOSE を送り直す。相手の手番の観測（9.4節）は、この送り直しの時点から測り直す。未承認だった手が SYNC で「承認済み」と分かったときは、測り直さない（最初に送った時点から測り、切れていた時間を差し引く）。
  • 結果を提案していたなら、RESULT_PROPOSE を送り直す。棋譜から決まる終局（10.3節）に達しているなら、照合の後に必ず提案する。ShogiBoardQ は、最後の手を SYNC で知った側からは提案しないので、最新だった側が提案を送り直さないと、対局が終わらない。
  • 切れていた時間（切れたと判断してから照合が終わるまで）を、その対局の切断時間の合計に足す。

11.6 切断の上限

上限長さ超えたとき
1回の切断で、照合が終わるまで120 秒「通信中断（結果未確定）」として終える
1局の切断時間の合計600 秒中断（理由は DISCONNECT_LIMIT）として終える

自分の回線の障害と、相手の意図的な切断は見分けられない。切断を、相手の負けとして扱ってはならない。

12. エラーの番号

REJECT（8.7節）の errorCode、CONTROL ERROR の errorCode、CONTROL ABORT の reasonCode は、同じ表の番号（1〜15）を使う。送る側は、表にない番号を送ってはならない。受けた側は、表にない番号を、理由の分からない拒否・中断として扱う（相手を断る理由にはしない）。

13. 対局記録（証跡）

対局が終わったら（結果が確定しなかったときも）、それぞれが、対局の記録を1つのファイルに保存する。これを証跡と呼ぶ。証跡は、ネットワークも相手も使わずに、だれでも検証できる。拡張子は .sbqmatch、大きさは 8 MiB 以下である。互換実装が書いた証跡は、ShogiBoardQ の「対局記録」と shogiboardq-cli verify-match で検証できなければならず、逆も同じである。

13.1 形

ファイルの中身は、次の値の決定的CBORのバイト列だけである（前後に何も付けない）。

            FinalResult または [],

13.2 検証の手順

検証する側は、次を順に確かめる。それぞれの結果は別々に示す（「署名が正しい」「棋譜が規則に合う」「時間の計算が合う」を混ぜない）。署名の検証は、すべて 2.4節のとおりに行う（公開鍵の検査を含む）。

  1. 形：8 MiB 以下で、決定的CBORであり、13.1節の形である。Rules・NetworkPolicy が v1 の値で、TimeControl が 7.1節の範囲にある。
  2. 条件：Rules・TimeControl・NetworkPolicy のハッシュが、StartAgreement の中の 3 つのハッシュと一致する。
  3. 開始署名：2 つの開始署名が、StartAgreement の blackPlayerKey・whitePlayerKey でそれぞれ正しい。gameId = H(CBOR(StartAgreement)) を計算する。
  4. State の列：先頭から順に、次を確かめる。
    • State の gameId が対局ID で、ply が列の中の位置（0, 1, 2, …）と一致する。
    • 長さ 0 でない承認の署名が、対応する側の一局用鍵（blackSessionKey・whiteSessionKey）で正しい。どちらの承認もない State は認めない。
    • State0 が 7.2節の値と一致する。それ以降は、前の State から 9.2節の手順 6〜9（前状態ハッシュ・指し手の形・時間切れ・合法手・局面・残り時間の計算）のとおりに作られている。
    • 片方の承認しかない State は、列の最後にだけ置ける。
  5. 双方が承認した手順：両方の承認がそろった State（列の先頭からの連続した部分）を「双方が承認した手順」とする。これが空でなければ、10.3節の判定を行い、棋譜から終局が決まるかを求める。
  6. 結果：FinalResult があれば、次を確かめる。
    • gameId が対局ID で、ply・finalStateHash が双方が承認した手順の最後の State を指し、transcriptHash が、双方が承認した手順から計算した値と一致する。
    • 長さ 0 でない結果への署名が、対応する側のプレイヤー鍵で正しい。
    • 棋譜から終局が決まるなら、FinalResult の outcome・cause がそれと一致する。棋譜から終局が決まらないなら、FinalResult の cause が、棋譜から決まる原因（詰み・千日手・連続王手の千日手・512 手到達）でない。

13.3 記録の区分

検証の結果から、記録を次の 3 つに分ける。上から順に当てはめる。

区分条件示せること
双方で確定手順 2〜4 に通り、FinalResult があって最後の State を指し、両方のプレイヤー鍵の署名が正しい双方が同じ結果に同意した
棋譜から決まる結果手順 2〜4 に通り、双方が承認した手順が、棋譜から決まる終局（10.3節）で終わっている双方が確かめた手順から、結果が決まる
結果未確定上のどちらでもないここまでの手順だけ（勝ち負けは示せない）

どの区分でも、証跡が示せないことがある。実際に考えた時間（消費時間は自己申告である）、人間が指したこと、対局した日時は、証跡からは確かめられない。検証の結果を出す実装は、そのことを一緒に示すことが望ましい。

15.1 試験の入力

ShogiBoardQ のリポジトリの protocol/testvectors/ に、実装どうしで同じ結果になることを確かめるための入力がある。互換実装は、これらを自分の試験で読むことが望ましい。# で始まる行と空行は読み飛ばす。

15.2 確かめる順序

互換実装を作るときは、下の層から順に確かめるとよい。

  1. 決定的CBORとハッシュ：15.1節の入力と、付録 A の値が一致する。
  2. 証跡の検証：ShogiBoardQ が保存した .sbqmatch を読み、13.2節の検証がすべて通る（署名の検証と、指し手・局面・時間の計算が合っていることの確認になる）。
  3. 招待文字列：ShogiBoardQ が作った招待文字列を読めて、自分が作った招待文字列を ShogiBoardQ の「招待文字列を確かめる」で読める。
  4. 接続と交渉：ネットワークを sbq-local-1 にして、同じ PC の ShogiBoardQ と、招待する側・される側の両方で条件確認画面まで進める。
  5. 対局：先手・後手の両方で、投了・詰み・時間切れ・合意による引き分けまで指し、双方の証跡が「双方で確定」になる。自分の書いた証跡を shogiboardq-cli verify-match --input-path <ファイル> で検証し、valid が true、category が mutually_signed になる。
  6. 再接続：対局中にストリームを切り、つなぎ直して続けられる（自分が申込側のとき・招待側のとき、未承認の手があるとき・ないとき）。
  7. 断ること：不正な署名・合法でない手・時間の計算の合わない State・番号の飛んだ CONTROL などを送り、相手が勝ち負けを付けずに止めることを確かめる。自分の実装も、同じ入力を同じように断る。

ShogiBoardQ は、同じ PC でいくつも起動すると、開いた順に別のプレイヤーになる（2つ目は「2人目」）。互換実装との試験は、同じ PC の中で行える。
