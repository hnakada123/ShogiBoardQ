# GUI 描画処理の再監査と高速化（2026-10-12）

「GUI 描画処理に関するコードで高速化できる箇所はあるか」という依頼で、`board-input-performance-2026-10-11.md` の項目1〜30の後に残っていた箇所を監査し、優先度の高いものから順に修正した。盤（ShogiView）本体は既存の項目でほぼ出し切られており、残っていた大物は駒画像のキャッシュの溢れだった。ほかは周辺のウィジェットの「1手ごとの作り直し」と「隠れている間も更新する」型が中心だった。

計測は Linux（Arch）、Qt 6.12.0、Release ビルド、`QT_QPA_PLATFORM=offscreen` で `QWidget::render` を使う単体ベンチ（静的ライブラリ `libshogiboardq_static.a` と qrc のオブジェクトにリンク）で行った。

## 1. 2倍表示で大きなマスだと駒画像のキャッシュが溢れ、毎回 SVG から描き直していた

### 問題点

- `PiecePainter` は駒種ごとに「元の SVG 画像」（`QIcon::pixmap`、Qt の SVG アイコンエンジンが預ける）と「影付きの描画済み画像」の2枚を `QPixmapCache` に預ける。Qt の既定の上限は 10MB。
- 2倍表示でマスが 110〜150px になると、16〜28駒種で上限を超える。溢れると覚えておいた鍵が無効になり、駒を描くたびに SVG の解析と9回重ねの影の描画をやり直す。`PiecePainter::image` の輪郭の覚え（画像の鍵で引く）も取り直しになる。
- 既存の記録の2倍表示の計測はマス 50〜60px で、この条件の外だった。

| 条件 | 全面描画 | 1マスの描き直し |
|---|---|---|
| 平手 16駒種・2倍・マス125px | 9.8ms | 0.04ms |
| 平手 16駒種・2倍・マス150px | 63ms | 0.05ms |
| 成駒あり 28駒種・2倍・マス110px | 64ms | 1.4ms |
| 成駒あり 28駒種・2倍・マス150px | 138ms | 2.2ms |

1倍では 150px まで溢れない。

### 改善内容

- `ApplicationRendering::reservePixmapCacheForPieces` を加え、`QApplication` の生成直後に `QPixmapCache` の上限を 64MB に広げる（既に広い値は縮めない）。2倍・150px・28駒種で約28MB、読み筋ウィンドウなど別の大きさの盤の分と Fusion の部品の分を合わせても足りる。使った分だけ確保されるので、小さな盤では増えない。
- `tst_application_rendering` に確認を足した。

### 効果（単体ベンチ、上限 64MB）

| 条件 | 全面描画 | 1マスの描き直し |
|---|---|---|
| 成駒あり 28駒種・2倍・マス110px | 64ms → 9.4ms | 1.4ms → 0.035ms |
| 成駒あり 28駒種・2倍・マス150px | 138ms → 14.9ms | 2.2ms → 0.047ms |

## 2. 定跡ドックが裏のタブにある間も、1手ごとに表を2回丸ごと作り直していた

### 問題点

- 更新を止めるガードが `isVisible()` だった。タブにまとめたドックは裏に回っても Qt では表示中のままなので（項目18・31）、一度でも定跡を表示すると、その後は裏にあっても毎手更新していた。
- `JosekiWindowWiring::updateJosekiWindow` は `setHumanCanPlay` と `setCurrentSfen` を続けて呼び、どちらも無条件に表を作り直していた。人間対エンジンでは手番が替わるたびに前者も変わるので、1回の呼び出しで2回の作り直しになる。棋譜をたどるときは `boardSyncRequired` と `josekiUpdateRequired` の両方から届き、同じ局面で2回更新していた。
- 作り直し1回は、表をいったん空にしてから行ごとに `QPushButton` を2〜3個作って `setStyleSheet` し（これが最も重い）、状態表示（ラベルの `setStyleSheet`、案内の表示・非表示）を2回更新し、行ごとに同じ SFEN を解析し直していた。定跡に無い局面でも状態表示は毎回走る。
- 定跡ドックだけ `LayoutBoundaryWidget` と `OpaqueBackground::keep` が無く、局面のラベルの `setText` からの配置の計算が `MainWindow` まで伝わり、表の描き直しがドックのタイトルまで広がっていた。

### 改善内容

- `JosekiWindowWiring::attachDock` でドックの `visibilityChanged` を受け、前面に出ている間だけ更新する。裏に回っている間に進んだ局面は、前面に戻ったときに反映する（`onDockVisibilityChanged(true)`）。
- `JosekiWindow::setCurrentSfen` は、表に出している局面と同じで、人間が指せるかも変わらなければ作り直さない（`m_displayedSfen`）。Wiring 側の `setHumanCanPlay` は外し、表示を作り直すたびに provider で判定する。
- `updateJosekiDisplay` は表を空にせず、行数を合わせて中身を入れ替える。行のボタンは列ごとに文字と接続先が決まっているので使い回す（`ensureRowButton`）。状態表示は最後に1回、ラベルのスタイルシートは変わったときだけ付ける。次の手の局面は、解析済みの局面を写して1手進める。
- 定跡ドックにも `LayoutBoundaryWidget` と `OpaqueBackground::keep` を適用した。
- `tst_josekiwindow` に、同じ局面では行とボタンを作り直さないことの確認を足した。

### 効果（単体ベンチ、定跡手10手の局面）

| 操作 | 1回 |
|---|---|
| 同じ局面の設定 | 0.1µs（作り直さない） |
| 定跡10手の局面どうしの切り替え（ボタンを使い回す） | 1.7ms |
| 定跡の無い局面との往復（ボタンを作り直す） | 6.1ms |

変更前は1手ごとに作り直しが2回で、裏のタブにある間も止まらなかった。

## 3. 手番交代のたびに時計の緊急度がリセットされ、スタイルの付け直しが余分に走っていた

### 問題点

- 1手の流れは、時計の `applyByoyomiAndResetConsideration` が `timeUpdated` を出して新手番側の警告色（秒読み・残り10秒）を付けた直後に、`updateTurnDisplay` → `updateTurnStatus` → `ShogiView::setActiveSide` が緊急度を Normal に戻していた。
- 警告色は次に秒表示が変わるまで最大1秒消え、そこでまた付け直す。秒読み1秒でエンジンが1秒以内に返すと、警告色は出ないままになる。項目33で「必要な分」とされていた手番交代の `setStyleSheet` に、余分な2回が混ざっていた。

### 改善内容

- `MainWindowServiceRegistry::updateTurnStatus` の `setActiveSide` を外した。手番側の表示は直後に `TurnStateSyncService` が呼ぶ `ShogiView::updateTurnIndicator` が行い、側が同じなら緊急度を保つ。着手の直後から警告色が出るようになる（見た目の変更。本来の意図どおり）。

## 4. 分岐ツリーの現在手の強調が、1手ごとに手数に比例した付け替えをしていた

### 問題点

- `BranchTreeManager::highlightPathTo` は、前回強調した辺をすべて戻してから、開始局面まで辿って全辺を付け直していた。本譜 n 手目なら 2n 回のペン変更と重なり順の変更になる。
- Qt は `setPen` のたびに辺の輪郭を計算し直し、BSP から出し入れする。dirty な矩形が50を超えるとビュー全体の描き直しになる。項目6でノードの追加は差分になったが、強調は O(手数) のままだった。

### 改善内容

- 新しい経路と前回の経路を開始局面の側から比べ、違う部分の辺だけを戻す・付ける。続けて指すときは1本で済む。最終的なペンと重なり順は同じなので、見た目は変わらない。

## 5. 評価値グラフは、マウスを動かすたびに全面を描き直し、1手ごとにも全点を作り直していた

### 問題点

- `hoverAt` は、ホバー対象の点が前回と同じでも、吹き出しの `setText`・`adjustSize` と `updatePresentation`（表示領域全体の update）を行っていた。
- 対局中は棋譜欄の行追加で `setRecordLength` の長さが伸びるため、点は変わっていないのに `refreshData` で両系列を `replace` していた。50ms 後の `setEngineXName` も同じ名前で無条件に `updatePresentation` していた。

### 改善内容

- 同じ点の上にいる間は吹き出しを動かすだけにする。
- `refreshData` は、点が変わった（`appendScore`・`clearAll`・`removeLast`・`trimToPly`）か、点を収める縦の表示範囲が変わったときだけ系列を作り直す。エンジン名は変わったときだけ表示を更新する。
- `tst_evaluationchart` の「記録が伸びたときは作り直す」の期待を、「横の範囲は広げるが系列は作り直さない」に改めた。

## 6. CSA通信対局で1手ごとに盤を全面 update() していた

- `CsaMoveProgressHandler`（相手の着手・自分の着手）と `CsaGameWiring::onMoveMade` の計3か所。盤・駒台の変化は `ShogiBoard` の通知で変わった所だけ描き直され、ハイライトと手番表示も部分更新なので、項目13でサブ盤から外したものと同じ重複だった。3か所とも外した。

## 7. 棋譜欄の列幅合わせが1手ごとに全行を測り直していた

### 問題点

- `RecordPane::onKifuRowsInserted` の `resizeColumnToContents(0)` は全行の `sizeHint` を取る。項目6で大きさは覚えているが、鍵を作るための `initStyleOption` と書体の解決は毎行走る。単体ベンチでは行数に比例した（100行 0.09ms、200行 0.17ms、400行 0.34ms）。

### 改善内容

- 末尾に足した行だけ測り、今の列幅に収まるなら測り直さない。列幅は全行の最大なので結果は同じ。先頭からの追加（作り直し）は従来どおり全行を測る。
- `tst_ui_display_consistency` に、行を足すたびに全行を測り直した場合と同じ幅になることの確認を足した。

## 8. そのほかの修正

- **候補手の矢印**: 矢印が変わったとき、前の矢印と新しい矢印が掛かる範囲だけを描き直す（`ShogiViewHighlighting::arrowsPaintRect`）。盤全体の描き直しは1倍で約0.5ms、2倍で約3ms。
- **局面編集**: `PositionEditController::applyEditMove` の全面 `update()` を外した（盤・駒台・駒箱の変化は通知で部分更新される）。
- **棋譜解析結果の表**: 1行足すたびに全列・全行を測り直していたのを、足した・変わった行だけ測って `qMax` で広げるようにした（`AnalysisResultsPresenter::reflowNow`）。リセット・書体の変更は全行を測る。
- **数値列の表示**: `NumericRightAlignCommaDelegate` が描くたびに作っていた `QLocale` をメンバにした。
- **日本語書体の生成**: `ApplicationFonts::japaneseFont` の結果を入力の書体ごとに覚える（1回 2.6µs → 比較だけ。`resolveMask` も比べる）。表のモデルが `FontRole` のたびに呼んでいた。書体の設定が変わると捨てる。
- **ShogiView の `resizeEvent`**: `relayoutTurnLabels` を3回呼んでいたのを1回にした。
- **対局情報欄の編集中の表示**: フォーカスの移動のたびに同じスタイルシートを付け直していたのを、変わったときだけにした。
- **詰将棋対局の判定表示**: 不要な同期描画（`repaint()`）を外した。
- **デバッグ用の文字列**: リリースでも組み立てていた3か所（分岐候補の一覧、ナビゲーションの結果の要約2か所）を、ログを出すときだけにした。

## 9. 残した項目（理由）

- **検討の経過時間ラベルの毎秒の配置計算**: 固定幅にすると縦の配置が1px 変わるおそれがあり、効果も毎秒1回で小さいので見送った。
- **外観ダイアログのプレビューの3回描画**: 0ms タイマーでまとめると、プレビューの画像を同期的に読むテストと合わないので見送った。利用者の操作時だけの処理。
- **`setActiveSide` の直後の `updateTurnIndicator`（棋譜欄の行クリックなど）**: 2回目はガードで軽く、終局後の警告色の扱いが変わるおそれがあるので見送った。
- **「表示」ボタン列の文字の配置の覚え、メニューウィンドウの全ボタン走査、`ElideLabel` の描画ごとの `QTextLayout`、持駒の枚数バッジの文字合わせ（84µs）、時計の文字合わせの毎秒のミス（46µs）、`minimumSizeHint` の段名の測り直し（16µs）**: 1回が小さいか、見た目を保つ確認の手間に見合わない。
- **`relayoutTurnLabels` の `raise()` による描き直しの予約**: 最後尾でない部品を `raise()` すると Qt は自分と親のその範囲の描き直しを予約する（実験で確認）。手番交代では枠の描き直しと重なるので、今は実害が無い。

## 10. 検証

- 単体テスト 131 件（CTest、GUI 機能テストと MCP を除く）がすべて通った。
- GUI 機能テスト（`tests/gui/run.py`、Xvfb、92シナリオ）: 定跡の2シナリオは、テストが定跡ウィンドウの親を直接ドックとみなしていたため失敗した。入れ物を挟んだ構成に合わせてドックを名前（`JosekiWindowDock`）で探すように改め、通った。`sfenCollection` の1件は、30msごとの監視タイマーがダイアログを操作する前に結果を確かめていたための失敗で、変更前（2026-10-12 21:58 の実行）では偶然通っていた。処理されるまで待つ（`QTRY_VERIFY_WITH_TIMEOUT`）ように改め、3回続けて通った。
