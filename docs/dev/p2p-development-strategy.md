# P2P対局のリポジトリ構成と開発方針

作成日: 2026-11-10

改訂: 2026-11-10（実装仕様の第2版・第3版に合わせた。第3版でブロックチェーンとウォレットを使わない構成になったため、関連する記述を削り、検査と配布の安全対策を加えた。第4版に合わせ、通信プロセスから届く宛先の確認、検査の追加、ビルドの使用期限を加えた）、2026-11-11（実験版の開発を終えて通常版へ取り込んだ。11.3節）、2026-11-14（実験版から正式な機能にした。11.4節）

状態: 開発計画。本書の作成・改訂は文書化のみで、アプリ識別子の変更、CI の整理、機能実装、公開を含まない。実験版リポジトリで確認できた現状は 11.1節に記録する。

関連文書: [P2P対局の実装仕様](p2p-game-spec.md)

## 1. 基本方針

ShogiBoardQの基準コミットから、別リポジトリ・別アプリとしてP2P実験版を開発する。通常版の配布へ実験中のP2P通信、新規依存ライブラリを組み込まず、独立した環境で検証する。

実験版を将来そのまま通常版へマージすることは前提にしない。検証結果と保守負担を見て、通常版への限定的な組込み、外部の連携アプリ、独立アプリとしての継続のいずれかを選ぶ。

分離する対象は次の三つである。

| 対象 | 目的 | 分離だけでは保証しないこと |
|---|---|---|
| リポジトリ・開発権限 | 通常版への混入を避け、変更・依存関係・レビューを独立管理する | 実験プログラムを起動したPCの安全性 |
| アプリ・配布・CI | 通常版の設定、配布物、署名資格情報、公開権限を守る | 不正な通信を受けても侵害されないこと |
| 実行プロセス・OS権限 | 侵害を想定し、読めるデータや実行できる操作を制限する | アプリ全体の無欠陥、対局の完全な公平性 |

別ブランチや別worktreeは変更管理には使えるが、リポジトリの資格情報や実行時の権限を自動的に分離するものではない。非公開リポジトリにするだけでも、同じ問題は解決しない。

## 2. 最初は2リポジトリで始める

| リポジトリ | 役割 | 管理するもの |
|---|---|---|
| `ShogiBoardQ` | 通常版 | 既存機能、一般的な不具合修正、安定版の配布 |
| `ShogiBoardQ-P2P`（仮称） | 実験版 | 対局UI、P2P通信、プロトコル、試験環境 |

実験版はGitHubのFork、またはGit履歴を引き継ぐ独立した新規リポジトリとして用意する。作成方式は所有者と公開範囲に合わせて選ぶ。名称・公開範囲・作成元のコミットは、作成時に確定する。

コードを単純にコピーして由来を失わせず、基準コミット、取得元、取り込んだ修正を追跡できるようにする。既存のライセンスと著作権表示も引き継ぐ。

初期構成の例は次のとおり。これは作成予定の構成であり、現在存在するディレクトリの一覧ではない。

```text
ShogiBoardQ-P2P/
  src/                  # ShogiBoardQ由来のUI・将棋処理と実験版の追加
  peer/                 # 制限された権限で動かすP2P通信
  protocol/             # スキーマ・版管理・共通テストベクトル
  tests/                # 結合試験、異常入力、接続・復旧試験
  docs/                 # 仕様、脅威モデル、試験結果、運用手順
  .github/workflows/    # 実験版専用のCI
```

通信とUIを最初から別々のリポジトリにすると、仕様変更のたびに版を合わせる必要がある。まず実験版の中で役割を分け、プロトコルが安定して他のアプリからも利用する段階で、必要な部品だけ独立リポジトリへ切り出す。

## 3. 基準コミットと変更の流れ

### 3.1 作成時に記録すること

- 通常版の取得元URLと完全なコミットSHA。
- その時点のビルド・関連テストの結果と、既知の不具合。
- サブモジュールが指すコミットと依存ライブラリの版。
- 実験版の名称、所有者、公開範囲、最初の対応OS。
- 通常版へ反映する一般的な修正と、実験版固有の変更の区分。

基準は追跡可能なコミットに固定し、「常に通常版の最新コードを自動取得する」構成にしない。

### 3.2 同期のルール

通常版をupstreamとして参照し、実験版でのpush先は実験版リポジトリに限定する。自動化には通常版へ書き込む権限を与えない。

| 変更の流れ | 扱い |
|---|---|
| 通常版 → 実験版 | セキュリティ修正・一般的なバグ修正を優先して取り込み、実験版の試験を実行 |
| 実験版 → 通常版 | 通常版でも再現する修正だけを、小さな独立したPRとして提出 |
| 実験版のP2P機能 → 通常版 | 統合判断の対象。自動マージや一括同期は行わない |
| 通常版の配布設定 → 実験版 | コピー後に見直す。通常版の公開先や資格情報を引き継がない |

通常版との乖離を記録し、少なくとも実験版のリリース前には未取込みの修正を確認する。長期に分岐を維持する場合、通常版の更新を追う工数も保守計画に含める。

### 3.3 文書の管理元

実験版リポジトリの作成後は、P2P仕様、脅威モデル、試験結果を実験版側で更新する。通常版にある文書は案内リンクへ切り替え、二つの場所で同じ仕様を独立して更新しない。

既存の `docs/dev/` のリンクは削除せず、移転先を案内する短い文書として残す。移転先URLは実際のリポジトリ作成後に設定する。

## 4. アプリと配布経路を分離する

実験版を通常版と同時にインストールでき、通常版のデータを意図せず上書きしない構成にする。

| 項目 | 分離方針 |
|---|---|
| 表示名・実行ファイル | 実験版であることが分かる別名 |
| アプリ識別子 | Qtのアプリ名、macOS bundle ID、Windowsの識別子、Linuxのdesktop情報を分離 |
| 保存先 | 設定・データ・キャッシュ・ログ・自動保存先を分離 |
| 設定移行 | 通常版の設定や登録エンジンを自動的に読み込まない。必要なら明示的な取込み機能を設計 |
| インストーラ | 通常版を上書き・アンインストールしない |
| 配布先 | 実験版リポジトリのReleasesと専用アーティファクト |
| 更新処理 | 更新機能を設ける場合も、通常版と実験版の配布先を混在させない |
| 通信プロセス | 実験版の配布物の中の決まった場所に置き、通常版と共有しない。P2P を使わない間は起動しない |
| ローカルの待受 | 自動化 API のソケットなど、アプリ名によらない固定の場所を使う待受を分ける |
| ネットワーク | 検証用のネットワーク名で始め、公開用のネットワークと招待が混ざらないようにする。実験版のビルドが参加するネットワーク名を限定する |
| OS の鍵の保管庫 | プレイヤー鍵を置く項目の名前を実験版専用にし、通常版やほかのアプリの項目を読まない |

現在のアプリ名は [main.cpp](../../src/app/main.cpp)、保存先は [AppPaths](../../src/services/apppaths.h)、設定ファイルは [SettingsCommon](../../src/services/settingscommon.cpp)で決まる。実験版ではこれらを含めて確認する。名前や保存先を分けることは上書き事故の防止であり、ファイルへのアクセスを禁止するサンドボックスの代用にはならない。

既存CSA・MCP・自動化APIも実験版へ継承されるため、P2P試験に不要な待受や自動化機能は起動しない。実験版の起動オプション・環境変数・連携機能を棚卸しし、意図しない入口を残さない。

## 5. CI・資格情報・公開権限

通常版の[リリースワークフロー](../../.github/workflows/release.yml)には、署名資格情報の参照とリリース公開の処理がある。実験版では最初のpushで意図せず動かないよう、作成先のActionsを停止した状態で準備し、コピーした公開ワークフローを無効化・整理してから、実験版用CIだけを有効にする。

### 5.1 初期CI

- ビルド、単体試験、静的解析、依存関係の点検を実行する。
- 既定のトークン権限は読み取りのみとし、成果物の公開権限は通常の試験ジョブに渡さない。
- 模擬ピアを使い、公開ネットワークを通常CIの必須条件にしない。
- 外部Actionと依存関係を追跡可能な版に固定し、更新は差分をレビューする。
- 信頼していないPRのコードを、署名鍵や公開の資格情報のあるジョブで実行しない。

トークンの最小権限、外部Actionの固定、信頼していないコードと資格情報の分離は、GitHubの推奨にも沿う。[GitHub Actionsのセキュリティ資料](https://docs.github.com/en/actions/reference/security/secure-use)

P2P の追加にあわせて、次の検査を CI に加える。

| 検査 | 内容 |
|---|---|
| 依存の点検 | Rust のツールチェーンと Cargo.lock を固定し、既知の脆弱性とライセンスを点検する（cargo-audit、cargo-deny）。追加する C・C++ のライブラリ（libsodium、QtKeychain）も版を固定する。libp2p は使う機能だけを有効にして依存の数を抑え、依存の追加と更新では、増えるクレートの一覧を差分で確かめる |
| 静的解析 | 既存の clang-tidy・cppcheck に加え、リポジトリのコード走査（code scanning）を有効にする。Rust は clippy を通し、自前のコードで安全でないコード（unsafe）と、異常終了を起こしうる書き方（unwrap、検査なしの添字と算術）を禁止する |
| サニタイザ | 既存の `ENABLE_SANITIZERS`（アドレス・未定義動作）で P2P の単体試験を回す |
| ファジング | 外部由来のデータを読む部分（決定的CBOR、IPC の JSON、証跡ファイル、鍵ファイル、招待文字列、表示名の判定）を、C++ は libFuzzer、Rust は cargo-fuzz で回す。通常 CI では短時間、長時間の実行は別のジョブにする。見つけた入力は回帰試験の入力として残す |
| 実装どうしの一致 | 決定的CBOR・フレームの外枠・networkId は、通信プロセス（Rust）と対局・UI側（C++）で同じ入力に同じ結果を返すことを、共通の入力の一覧で確かめる（第4版までは、全員に届く募集と表示名の判定も対象だった。公開募集は実装仕様の第5版でやめた） |
| 秘密の検出 | リポジトリの走査と push 時の保護を有効にする |

配布物を作る段階（D5）では、次を加える。

- 配布物に含めた依存の一覧（SBOM）を出力する。
- どのコミットとワークフローから作った配布物かを示す来歴の証明（GitHub の artifact attestation）を付ける。
- 通信プロセスの実行ファイルにも、アプリ本体と同じ署名を付ける。
- ビルド時にネットワークから取得したコードを、版の固定と検査なしに配布物へ入れない。

### 5.2 共有しないもの

通常版の公開用トークン、署名秘密鍵、開発PCのSSH鍵・エージェント、本番の資格情報を実験用CIへ渡さない。署名が必要な配布段階では専用ジョブと必要最小限の資格情報を用意し、実験用テストジョブから分離する。

Gitの履歴を引き継ぐことと、GitHubのSecretsを移すことは別である。リポジトリを分けても、組織のSecrets、runner group、GitHub Appの権限、クラウドの認証条件が新リポジトリを含む設定になっていないか確認する。

runnerや作業ディレクトリを通常版と共有しない。外部コードを実行する試験は使い捨て環境とし、資格情報や成果物が次の試験へ残らないようにする。

テスト用のプレイヤー鍵は試験のたびに作る。開発者が普段使うプレイヤー鍵や、協力ノードの識別鍵を、リポジトリ、テストの入力ファイル、CI のログに置かない。

## 6. 実行時の権限分離

P2P通信を処理するプロセスは、侵害される可能性を前提に設計する。別プロセスでも通常のユーザー権限をそのまま与えると、ユーザーのファイルや他のプロセスへアクセスできる場合がある。OSのアクセス制御とサンドボックスで制限する。[Chromiumのサンドボックス設計](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md)

### 6.1 処理と権限の分担

| 部分 | 許可する処理 | 与えない権限 |
|---|---|---|
| P2P通信プロセス | 接続、招待、サイズ制限付きのメッセージ送受信 | ファイルの読み書き、任意プログラム起動、プレイヤー鍵、一局用鍵 |
| 対局・UI側 | 合法手・状態・署名の検証、プレイヤー鍵と一局用鍵による署名、表示、証跡と利用者が指定した棋譜の保存 | 相手や通信プロセスから受けた命令の無条件実行 |

通信プロセスが侵害されても、署名や保存を指示できないIPCにする。対局側は通信プロセスの出力も信頼せず、サイズ、型、署名、現在状態に対応した操作かを再検証する。

IPCに任意コマンド、任意ファイルパスの実行口を設けない。起動済みの正しいプロセスと要求IDを照合し、取消済み・別対局・古い世代の応答を拒否する。

プレイヤー鍵と一局用鍵は対局・UI側が保持し、通信プロセスへ渡さない（実装仕様5.1節）。インターネットから届く入力を解釈するプロセスに署名の権限を置かないためである。この決定で、通信プロセスの侵害でできることは通信の妨害・盗み見と不正な入力の送り込みに限られ、対局記録の偽造はできなくなる。代わりに、対局・UI側が署名の演算と外部由来のデータの検証を受け持つ。その読み取り部を小さく保ち、ファジングの対象にする。

通信プロセスにはネットワークの権限が要る。侵害されると、署名や保存はできなくても、利用者の PC から LAN 内の機器や loopback のサービスへ接続を試せる。宛先の規則（実装仕様4章）は通信プロセス自身のコードで守るので、侵害されたプロセスには効かない。OS の側でどこまで止められるかを 6.2節で確かめる。

第2版にあったチェーン読み取りとウォレット連携のプロセスは、第3版でなくなった。補助プロセスは通信の1つだけである。外部ウォレットへ意図しない署名を求められる経路は、構成からなくなった。

### 6.2 OSごとの検証

ファイルの読書き、子プロセス起動、他プロセスへの干渉、ローカルサービスへの接続、引き継ぐ環境変数とハンドルを、OSごとに許可表として定義する。具体的なサンドボックス方式は接続実証段階で選び、拒否されることを試験する。

方式の候補は次のとおり。候補であって決定ではない。OS やカーネルの版、配布形式（署名の要否）で使える範囲が変わるので、対応する最低の版を決めて確かめる。

| OS | 候補 |
|---|---|
| Linux | seccomp-bpf（システムコールの制限）、Landlock（ファイルとネットワークの制限）、名前空間、新しい権限を得ない設定（no_new_privs） |
| Windows | AppContainer または制限付きトークンとジョブオブジェクト、プロセスの緩和ポリシー（子プロセス生成の禁止など） |
| macOS | App Sandbox、Hardened Runtime |

通信プロセスが、親（対局・UI側）の終了で確実に終了すること、コアダンプを残さないこと、配布物の中の決まった場所から起動され差し替えられないことも、OSごとに確かめる（実装仕様10.4節）。

次も D2 で OS ごとに確かめ、結果を記録する。

| 確かめること | 理由 |
|---|---|
| 侵害された通信プロセスに見立てたプログラムから、loopback・私設アドレス・ローカルのソケットとパイプへ接続できるか | 宛先の制限を OS の側で掛けられるかは、OS と方式で異なる。掛けられない OS では、残る危険として利用者に説明する |
| 選んだ方式で、Qt の QProcess から通信プロセスを起動できるか | 起動の時点で権限を決める方式（Windows の AppContainer など）は、起動時に属性の指定が要る。QProcess で指定できなければ、起動だけを行う小さな部品を挟む。その部品も権限表と試験の対象にする |
| 待受を始めたときに、OS のファイアウォールが利用者に許可を求めるか | 求める OS では、利用者への案内が要る。許可されなくても、外向きの接続と中継で対局できることを確かめる |
| 名前解決に、ファイルやローカルのサービスへの接続が要るか | 許可表の「読み取りなし」の例外を、必要な最小の範囲に決める |

プレイヤー鍵を置く OS の鍵の保管庫も、OS とデスクトップ環境ごとに使えるかを確かめる（実装仕様5.2節）。使えない環境では、暗号化したファイルへ切り替わることを確かめる。保管庫の項目が、ほかの PC やクラウドへ同期されない設定で保存されることも確かめる。

サンドボックスの起動に失敗したとき、制限なしで黙って継続しない。公開試験を許可するOSは、実際に制限を確認できたものに限定する。未対応OSでは外部ネットワーク試験を停止するか、明示した隔離環境に限定する。

### 6.3 開発中の隔離環境

実インターネットとの最初の接続試験は、専用の仮想環境で行う。ホストのホームディレクトリ、SSHエージェント、共有フォルダ等を不用意に渡さない。

隔離環境を使うことも、アプリ側の権限制限を省く理由にはしない。

## 7. 実装仕様への反映状況

[実装仕様](p2p-game-spec.md)は、本書が改訂対象に挙げていた箇所を第2版で反映し、第3版でブロックチェーンとウォレットを使わない構成に変えた。開発場所と権限分離については、引き続き本書の方針を優先する。

| 対象 | 内容 | 反映先（実装仕様） |
|---|---|---|
| 全体構成・技術選定 | 通信を別プロセスに分け、信頼境界を表にした。補助プロセスは通信の1つだけ | 2.1節・2.2節 |
| 鍵管理 | プレイヤー鍵と一局用鍵を対局・UI側に置き、侵害時の影響を表にした。プレイヤー鍵の保管方法を定義した | 5.1節・5.2節 |
| 組込み先 | 派生した実験版への追加として書いた | 10章 |
| IPC | 通信プロセスの窓口、権限表、起動失敗時の挙動を定義した | 10.4節・10.5節 |
| 段階導入 | 各段階に本書のD段階の前提を対応させた | 13章 |

## 9. レビュー・脆弱性対応・保守

通信パーサ、IPC、暗号処理、鍵の保管、CI、配布設定を重点レビュー対象にする。担当範囲はCODEOWNERS等で明示できるが、ファイルを置くだけでレビューを強制できると考えず、実際のブランチ保護設定と合わせて確認する。

既存の[SECURITY.md](../../SECURITY.md)を基に、実験版の対応バージョン、対象機能、報告先を定める。信頼しない入力の一覧に、P2P のピアからの受信、招待文字列、他人から受け取った証跡ファイルを加える。通信プロセスの権限の制限を越えられる欠陥も、報告の対象と明記する。フォーク元の報告先URLをそのまま残さず、作成したリポジトリで利用できる非公開の受付経路を確認する。GitHubにはリポジトリ単位のPrivate vulnerability reportingがある。[GitHub公式資料](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)

脆弱性発見時は、再現確認、影響範囲の特定、必要な機能停止、修正、修正版の配布、公開情報の更新までを手順に含める。通常版にも影響する共通コードの問題は、両リポジトリで追跡する。

P2P のネットワークには、中央から機能を止める仕組みがない。問題が見つかったときに取れる手段は、修正版の配布、プロトコルの版を上げて古い版との接続を断つこと、協力ノード（ブートストラップ・中継）での古い版の拒否や停止、告知に限られる。招待による直接の接続は、協力ノードを止めても残る。この前提で、配布した版を識別できるようにし、版ごとの対応状況を告知する場所を決めておく。

止める仕組みの代わりに、実験版のビルドには使用期限を入れる（実装仕様3.1節）。期限を過ぎたビルドは、限定試験用と公開用のネットワークへ参加しない。利用者が更新しなくても、欠陥の直っていない版がネットワークに残る期間に上限ができる。期限は、修正版を出せる間隔より短くしない。期限内に次の版を出せなければ、利用者は P2P 対局を使えなくなる。実験をやめるときは、次の版を出さなければ、期限とともにネットワークが止まる。

協力ノードを運用する場合は、接続元の IP を含むログの項目と保存期間、識別鍵の保管、停止時の告知を運用手順に含める。

実験版を止める場合も、配布済みバイナリの扱い、協力ノードの停止、サポート終了の告知を決める。利用者の手元にある対局記録とプレイヤー鍵は、配布を止めても残る。

## 10. 通常版への統合を判断する条件

通常版への追加は、独立した設計・変更としてレビューする。実験版全体のマージを完了条件にしない。

- P2Pを使用しない通常版利用者に、新たな待受や補助プロセスの起動が発生しない。
- 通信・署名の権限境界と異常系が試験されている。
- 依存ライブラリの更新、脆弱性対応、協力ノード運用を継続できる。
- 設定・棋譜・既存対局・配布への影響を説明でき、回帰試験が通る。
- 不具合発見時の機能停止、修正版の配布、互換性の扱いが決まっている。
- 利便性に対して保守と安全性確保の負担が妥当である。

統合する場合も、まず小さな連携窓口と必要なUIから検討する。独立アプリとしての継続が適切なら、通常版へ機能を取り込まずに維持する。

| 表記 | 画面・ガイド・ホームページから「実験版」を外した。画面のネットワークの呼び名を「ローカル（同じPC・同じLAN）」「インターネット」にした（networkName の `sbq-local-1`・`sbq-limited-1` は変えていない） |
| 使用期限 | 9章のビルドの使用期限（180日。インターネットのネットワークだけ）は残した |
| プロトコル | これより後は、互換性のない変更ではプロトコルの版を上げる（互換仕様書 1.5節） |
| CI | `ci.yml` の主のビルド（Release・Debug）は既定（P2P対局あり）でビルドする。静的解析・サニタイザ・カバレッジ・macOS・Windows のジョブは、今までと同じ範囲のまま `-DENABLE_P2P_PLAY=OFF` を付けた |

D4（限定ネットワーク試験）へ進む条件と、11.2節の「残り」の項目（実回線での試験、ファジング、cargo-audit・cargo-deny、サニタイザでの P2P の試験の常時実行）は、満たしていないままである。Windows・macOS の配布用スクリプトの変更は、Linux の PC で書いたもので、その OS では動かしていない。
