# P2P・ブロックチェーン対局のリポジトリ構成と開発方針

作成日: 2026-11-10

状態: 開発計画。本書の作成作業は文書化のみで、リポジトリの作成・移行、機能実装、公開を含まない。

関連文書: [P2P・ブロックチェーン対局の実装仕様](p2p-blockchain-game-spec.md)

## 1. 基本方針

ShogiBoardQの基準コミットから、別リポジトリ・別アプリとしてP2P実験版を開発する。通常版の配布へ実験中のP2P通信、ウォレット連携、新規依存ライブラリを組み込まず、独立した環境で検証する。

実験版を将来そのまま通常版へマージすることは前提にしない。検証結果と保守負担を見て、通常版への限定的な組込み、外部の連携アプリ、独立アプリとしての継続のいずれかを選ぶ。

分離する対象は次の三つである。

| 対象 | 目的 | 分離だけでは保証しないこと |
|---|---|---|
| リポジトリ・開発権限 | 通常版への混入を避け、変更・依存関係・レビューを独立管理する | 実験プログラムを起動したPCの安全性 |
| アプリ・配布・CI | 通常版の設定、配布物、署名資格情報、公開権限を守る | 不正な通信を受けても侵害されないこと |
| 実行プロセス・OS権限 | 侵害を想定し、読めるデータや実行できる操作を制限する | アプリ全体の無欠陥、対局の完全な公平性 |

別ブランチや別worktreeは変更管理には使えるが、リポジトリの資格情報や実行時の権限を自動的に分離するものではない。非公開リポジトリにするだけでも、同じ問題は解決しない。

## 2. 最初は2リポジトリで始める

| リポジトリ | 役割 | 管理するもの |
|---|---|---|
| `ShogiBoardQ` | 通常版 | 既存機能、一般的な不具合修正、安定版の配布 |
| `ShogiBoardQ-P2P`（仮称） | 実験版 | 対局UI、P2P通信、ウォレット連携、コントラクト、プロトコル、試験環境 |

実験版はGitHubのFork、またはGit履歴を引き継ぐ独立した新規リポジトリとして用意する。作成方式は所有者と公開範囲に合わせて選ぶ。名称・公開範囲・作成元のコミットは、作成時に確定する。

コードを単純にコピーして由来を失わせず、基準コミット、取得元、取り込んだ修正を追跡できるようにする。既存のライセンスと著作権表示も引き継ぐ。

初期構成の例は次のとおり。これは作成予定の構成であり、現在存在するディレクトリの一覧ではない。

```text
ShogiBoardQ-P2P/
  src/                  # ShogiBoardQ由来のUI・将棋処理と実験版の追加
  peer/                 # 制限された権限で動かすP2P通信
  wallet-bridge/        # 利用者が承認したウォレット操作
  contracts/            # 結果レジストリとコントラクト試験
  protocol/             # スキーマ・版管理・共通テストベクトル
  tests/                # 結合試験、異常入力、接続・復旧試験
  docs/                 # 仕様、脅威モデル、試験結果、運用手順
  .github/workflows/    # 実験版専用のCI
```

通信、UI、コントラクトを最初から別々のリポジトリにすると、仕様変更のたびに版を合わせる必要がある。まず実験版の中で役割を分け、プロトコルが安定して他のアプリからも利用する段階で、必要な部品だけ独立リポジトリへ切り出す。

## 3. 基準コミットと変更の流れ

### 3.1 作成時に記録すること

- 通常版の取得元URLと完全なコミットSHA。
- その時点のビルド・関連テストの結果と、既知の不具合。
- サブモジュールが指すコミットと依存ライブラリの版。
- 実験版の名称、所有者、公開範囲、最初の対応OS。
- 通常版へ反映する一般的な修正と、実験版固有の変更の区分。

基準は追跡可能なコミットに固定し、「常に通常版の最新コードを自動取得する」構成にしない。

### 3.2 同期のルール

通常版をupstreamとして参照し、実験版でのpush先は実験版リポジトリに限定する。自動化には通常版へ書き込む権限を与えない。

| 変更の流れ | 扱い |
|---|---|
| 通常版 → 実験版 | セキュリティ修正・一般的なバグ修正を優先して取り込み、実験版の試験を実行 |
| 実験版 → 通常版 | 通常版でも再現する修正だけを、小さな独立したPRとして提出 |
| 実験版のP2P機能 → 通常版 | 統合判断の対象。自動マージや一括同期は行わない |
| 通常版の配布設定 → 実験版 | コピー後に見直す。通常版の公開先や資格情報を引き継がない |

通常版との乖離を記録し、少なくとも実験版のリリース前には未取込みの修正を確認する。長期に分岐を維持する場合、通常版の更新を追う工数も保守計画に含める。

### 3.3 文書の管理元

実験版リポジトリの作成後は、P2P仕様、脅威モデル、試験結果を実験版側で更新する。通常版にある文書は案内リンクへ切り替え、二つの場所で同じ仕様を独立して更新しない。

既存の `docs/dev/` のリンクは削除せず、移転先を案内する短い文書として残す。移転先URLは実際のリポジトリ作成後に設定する。

## 4. アプリと配布経路を分離する

実験版を通常版と同時にインストールでき、通常版のデータを意図せず上書きしない構成にする。

| 項目 | 分離方針 |
|---|---|
| 表示名・実行ファイル | 実験版であることが分かる別名 |
| アプリ識別子 | Qtのアプリ名、macOS bundle ID、Windowsの識別子、Linuxのdesktop情報を分離 |
| 保存先 | 設定・データ・キャッシュ・ログ・自動保存先を分離 |
| 設定移行 | 通常版の設定や登録エンジンを自動的に読み込まない。必要なら明示的な取込み機能を設計 |
| インストーラ | 通常版を上書き・アンインストールしない |
| 配布先 | 実験版リポジトリのReleasesと専用アーティファクト |
| 更新処理 | 更新機能を設ける場合も、通常版と実験版の配布先を混在させない |
| チェーン設定 | ローカルEVM・テストネットから開始し、本番の登録先・鍵・資格情報と分離 |

現在のアプリ名は [main.cpp](../../src/app/main.cpp)、保存先は [AppPaths](../../src/services/apppaths.h)、設定ファイルは [SettingsCommon](../../src/services/settingscommon.cpp)で決まる。実験版ではこれらを含めて確認する。名前や保存先を分けることは上書き事故の防止であり、ファイルへのアクセスを禁止するサンドボックスの代用にはならない。

既存CSA・MCP・自動化APIも実験版へ継承されるため、P2P試験に不要な待受や自動化機能は起動しない。実験版の起動オプション・環境変数・連携機能を棚卸しし、意図しない入口を残さない。

## 5. CI・資格情報・公開権限

通常版の[リリースワークフロー](../../.github/workflows/release.yml)には、署名資格情報の参照とリリース公開の処理がある。実験版では最初のpushで意図せず動かないよう、作成先のActionsを停止した状態で準備し、コピーした公開ワークフローを無効化・整理してから、実験版用CIだけを有効にする。

### 5.1 初期CI

- ビルド、単体試験、静的解析、依存関係の点検を実行する。
- 既定のトークン権限は読み取りのみとし、成果物の公開権限は通常の試験ジョブに渡さない。
- ローカルEVMと模擬ピアを使い、公開ネットワークや実ウォレットを通常CIの必須条件にしない。
- 外部Actionと依存関係を追跡可能な版に固定し、更新は差分をレビューする。
- 信頼していないPRのコードを、署名鍵やデプロイ資格情報のあるジョブで実行しない。

トークンの最小権限、外部Actionの固定、信頼していないコードと資格情報の分離は、GitHubの推奨にも沿う。[GitHub Actionsのセキュリティ資料](https://docs.github.com/en/actions/reference/security/secure-use)

### 5.2 共有しないもの

通常版の公開用トークン、署名秘密鍵、デプロイ用ウォレット、開発PCのSSH鍵・エージェント、本番の資格情報を実験用CIへ渡さない。署名が必要な配布段階では専用ジョブと必要最小限の資格情報を用意し、実験用テストジョブから分離する。

Gitの履歴を引き継ぐことと、GitHubのSecretsを移すことは別である。リポジトリを分けても、組織のSecrets、runner group、GitHub Appの権限、クラウドの認証条件が新リポジトリを含む設定になっていないか確認する。

runnerや作業ディレクトリを通常版と共有しない。外部コードを実行する試験は使い捨て環境とし、資格情報や成果物が次の試験へ残らないようにする。

## 6. 実行時の権限分離

P2P通信を処理するプロセスは、侵害される可能性を前提に設計する。別プロセスでも通常のユーザー権限をそのまま与えると、ユーザーのファイルや他のプロセスへアクセスできる場合がある。OSのアクセス制御とサンドボックスで制限する。[Chromiumのサンドボックス設計](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md)

### 6.1 処理と権限の分担

| 部分 | 許可する処理 | 与えない権限 |
|---|---|---|
| P2P通信プロセス | 接続、募集、サイズ制限付きのメッセージ送受信、必要な一時データ | 通常版の設定・棋譜へのアクセス、任意プログラム起動、ウォレット操作 |
| 対局・UI側 | 合法手・状態の検証、表示、利用者が指定した棋譜の保存 | 相手から受けた命令の無条件実行 |
| ウォレット連携側 | 利用者が承認した一件の署名・送信を外部ウォレットへ依頼 | P2P相手が指定した任意の署名・送金、ウォレット秘密鍵の取込み |

通信プロセスが侵害されても、ウォレットへ任意の要求を出せないIPCにする。P2P側とウォレット側に共通の操作用capabilityを渡さない。対局側は通信プロセスの出力も信頼せず、サイズ、型、署名、現在状態に対応した操作かを再検証する。

IPCに任意コマンド、任意ファイルパス、任意JSON-RPCの実行口を設けない。起動済みの正しいプロセスと要求IDを照合し、取消済み・別対局・古い世代の応答を拒否する。

一局用鍵をどこに保持するかも改訂対象とする。仮に通信プロセスへ一局用鍵を置く場合、その侵害で当該対局の通信証跡を偽造され得る範囲を明記する。一局用鍵に最終結果のウォレット署名や資産移動の権限を与えない。

### 6.2 OSごとの検証

ファイルの読書き、子プロセス起動、他プロセスへの干渉、ローカルサービスへの接続、引き継ぐ環境変数とハンドルを、OSごとに許可表として定義する。具体的なサンドボックス方式は接続実証段階で選び、拒否されることを試験する。

サンドボックスの起動に失敗したとき、制限なしで黙って継続しない。公開試験を許可するOSは、実際に制限を確認できたものに限定する。未対応OSでは外部ネットワーク試験を停止するか、明示した隔離環境に限定する。

### 6.3 開発中の隔離環境

実インターネットとの最初の接続試験は、専用の仮想環境とテスト用ウォレットで行う。通常利用しているウォレットのシードや秘密鍵を移さず、ホストのホームディレクトリ、SSHエージェント、共有フォルダ等を不用意に渡さない。

隔離環境を使うことも、アプリ側の権限制限を省く理由にはしない。

## 7. 既存の実装仕様で改訂する箇所

現在の[実装仕様](p2p-blockchain-game-spec.md)は機能・通信・署名・結果記録の初期案として利用する。開発場所と権限分離については、本書の方針を優先する。

| 対象 | 改訂内容 |
|---|---|
| 2章の全体構成・技術選定 | P2P通信とウォレット連携のプロセス・権限を分ける |
| 5章の鍵管理 | 一局用鍵の保持主体と侵害時の影響を決める |
| 10章のウォレット接続 | loopback bridgeの起動主体、承認元、capabilityの受渡しを限定する |
| 12章の組込み先 | 通常版への追加ではなく、派生した実験版への追加として扱う |
| 12章のIPC | 通信・署名・RPC操作の窓口を分け、許可する呼出し元を固定する |
| 15章の段階導入 | 権限制限と配布分離の確認を、外部ネットワーク試験の前提へ追加する |

ファイルを別リポジトリへ移すだけで、この改訂を完了したことにはしない。少なくともプロセス図、権限表、IPCスキーマ、起動失敗時の挙動を更新してから機能実装へ進む。

## 8. 開発段階と次へ進む条件

| 段階 | 作業 | 次へ進む条件 |
|---|---|---|
| D0 基準の確定 | 元コミット、所有者、公開範囲、名前、保守対象を決定 | 出発点と通常版との関係を記録済み |
| D1 開発・配布の分離 | 実験版リポジトリ、識別子、保存先、CIを整備 | 通常版のデータや公開権限を使用しないことを確認 |
| D2 境界の設計と試作 | 権限表、IPC、サンドボックス、プロセス起動を試作 | 禁止操作が拒否され、制限に失敗した場合に停止する |
| D3 ローカルの機能試験 | 模擬ピア、合法手、時計、署名、ローカルEVMを実装 | 正常対局と異常入力・切断・再送の試験が成立 |
| D4 限定ネットワーク試験 | 隔離環境、既知の参加者、テストネットで対局 | 接続・復旧・記録の失敗を安全に扱い、秘密情報が漏れないことを確認 |
| D5 実験版の配布 | 対応OS、公開手順、脆弱性窓口、更新手順を整備 | 実験版の利用条件と既知の制約を説明でき、修正版を配布できる |
| D6 継続形態の判断 | 保守負担と検証結果をレビュー | 独立継続・外部連携・通常版への限定統合の方針を決定 |

D2では接続用の最小プログラムやIPCの試作を認めるが、不特定の相手との公開対局へは進まない。実装仕様のP0〜P5は機能開発の区分であり、本書のD0〜D6は開発環境と公開範囲の区分である。両方の条件を満たす必要がある。

主要な試験対象は、不正署名、過大・壊れた入力、順序の逆転、重複、連続接続、書込み失敗、再接続、プロセス異常終了、ウォレット要求の偽装、RPC停止・虚偽応答である。正常対局が一度できたことだけを、公開試験へ進む根拠にしない。

本番チェーンへのデプロイはテストネットでの実証とは別に判断する。コントラクトのレビュー、ビルド再現性、デプロイ先の検証、費用と運用責任を確認する。

## 9. レビュー・脆弱性対応・保守

通信パーサ、IPC、暗号処理、ウォレット連携、コントラクト、CI、配布設定を重点レビュー対象にする。担当範囲はCODEOWNERS等で明示できるが、ファイルを置くだけでレビューを強制できると考えず、実際のブランチ保護設定と合わせて確認する。

既存の[SECURITY.md](../../SECURITY.md)を基に、実験版の対応バージョン、対象機能、報告先を定める。フォーク元の報告先URLをそのまま残さず、作成したリポジトリで利用できる非公開の受付経路を確認する。GitHubにはリポジトリ単位のPrivate vulnerability reportingがある。[GitHub公式資料](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository)

脆弱性発見時は、再現確認、影響範囲の特定、必要な機能停止、修正、修正版の配布、公開情報の更新までを手順に含める。通常版にも影響する共通コードの問題は、両リポジトリで追跡する。

実験版を止める場合も、配布済みバイナリの扱い、協力ノードの停止、サポート終了の告知を決める。公開チェーンに登録した情報がリポジトリ削除によって消えるとは扱わない。

## 10. 通常版への統合を判断する条件

通常版への追加は、独立した設計・変更としてレビューする。実験版全体のマージを完了条件にしない。

- P2Pを使用しない通常版利用者に、新たな待受やウォレット操作が発生しない。
- 通信・署名の権限境界と異常系が試験されている。
- 依存ライブラリの更新、脆弱性対応、協力ノード運用を継続できる。
- 設定・棋譜・既存対局・配布への影響を説明でき、回帰試験が通る。
- 不具合発見時の機能停止、修正版の配布、互換性の扱いが決まっている。
- 利便性に対して保守と安全性確保の負担が妥当である。

統合する場合も、まず小さな連携窓口と必要なUIから検討する。独立アプリとしての継続が適切なら、通常版へ機能を取り込まずに維持する。

## 11. 最初に行う作業

1. ShogiBoardQの基準コミットと、実験版の名称・所有者・公開範囲を決める。
2. 通常版の公開ワークフローを動かさずに、履歴を引き継ぐ実験用リポジトリを用意する。
3. アプリ識別子、保存先、配布先、CI権限を分離する。
4. 実装仕様のプロセス・鍵・IPC設計を、本書の権限分離に合わせて更新する。
5. サンドボックスと最小通信プログラムを試作し、禁止操作が拒否されることを確認する。
6. ローカルの対局・結果記録を実装し、段階条件を満たしてから外部ネットワーク試験へ進む。

各段階の記録では、文書作成、環境構築、機能実装、動作検証を区別する。既存アプリのビルドコマンドが正常終了しただけで、未実装のP2P機能を検証したとは報告しない。
